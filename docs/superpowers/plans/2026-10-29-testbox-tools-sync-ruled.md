# The test box's tool sync, as built: departures from the plan's sketch

- **D-7553 (2026-10-30)** — `testbox-tools-sync-departures`: TB6 of `docs/superpowers/plans/2026-10-29-test-box.md` (D-7408) is built with five departures from the plan's sketch, none of which changes what the box verifies or installs. (1) The service's side is two files, not one: `agent/src/testbox/tools.ts` (L1) holds every decision the plan names (the sync state, the backoff on `CCRC_TESTBOX_PRISTINE_RETRY`, the no-op, the sets kept for live runs, the takeover, the rebuild after a node change), and `agent/src/testbox/toolsync.ts` (L4) is its driver, which writes `specs/tools`, starts `ccrc-testbox-tools.service` through the system manager and reads the unit's report; an L1 file cannot act. (2) `service.ts` keeps its one-line budget: the `tools.sync` line in `FRAME_HANDLERS` reaches the driver by a literal dynamic `import('./toolsync.js')` (the import census follows it), and the driver is attached to the service by the entry point. The status answer a connection is sent carries the sync's state through `toolsync.ts#statusOf`, the service's own answer with the sync's reason put first, which is where `status.ts#degradedReasons` puts it. The box's measured versions fill the status through the service's existing `tools` dependency. (3) The takeover is D-7426's, not a departure from it (D-7559, the coordinator's ruling: queued runs wait for the new service and are never dropped). It closes admissions through the `admitting` dependency the entry point hands the service, false once a sync has replaced the release (the run limit the status answer reports stays the configured one, so every answer during the takeover reads as the frame family's); it then waits for the service's runs to end, hands every run still queued (those queued during the takeover included) to the next service, and exits 0. The hand-over is a file per queued run under `<root>/handover/`, its `run.submit` as the service queued it (read from the service's own queue, so a refused duplicate never replaces it), named in queue order; the run's empty log directory is removed so the next service takes the id afresh. The next service, after its own start, queues those runs in that order, each with no connection, so a later takeover hands each over again while it waits, and removes the files; a file that does not read as a `run.submit` is dropped. So queued runs wait for the new service, as D-7426 rules; their summaries land in `results/<id>` like any run whose link dropped, for the wrapper's reconnect (TB8). The service's timer work and the sync are separate: the timer does not wait for a retried sync (`main.ts#timerWork`), and the rebuild tick a node change makes runs after the timer's tick in progress, never beside it (`toolsync.ts#serviceTick`). The service reads `<tools>/current/chrome` when each prepare starts, not once at its start, since a sync prunes the Chrome no kept set names. (4) In step 6 the new tool set and the verified release tree, with its `server/` production dependencies, are both made complete before `<tools>/current` and then `<tools>/release/installed` are each switched in one rename, so a failure in any step, `npm ci` included, leaves both names as they were (spec §2.10: a failed sync leaves `current` and the installed release on the previous set). `<tools>/current` is a link to a set directory under `<tools>/sets/`, since a rename cannot replace a non-empty directory; a set holds `node` and `chrome` (the verifier's PATH, D-7424, and `CCRC_CHROME`) and `bin/` with `node`, `npm` and `npx`, the directory first on every run's and install's PATH. That entry is the set's own `bin/`, never the link: the entry point hands `spec.ts` a `toolsBin` setting that resolves `<tools>/current` to its set on each read (`toolsync.ts#bin`), so each spec names the set current when it is built, and a sync during a run changes nothing under it (spec §2.10), node, npm and npx included; without the setting `spec.ts` falls back to `<tools>/current/bin`. The sets kept are the previous set and the `K` records, which name the set each live run's own spec and the pristine install's spec start their `PATH` at, read before every unit run (D-7559); TB7's bootstrap lays out its first set the same way. The release is staged under `<tools>` through `_upd_resolve`'s `UPD_STAGE_PARENT` (the seam Step 0 allows, one line of `ccd/ccrc` edited and a row in `ccrc-update-fetch.test.ts`), so the tools script composes no TMPDIR. (5) The node and Chrome download hosts are fixed in the root script, so the service user can choose versions but not where root downloads from; the tests reach fixture servers for those two names through root's fixture `~/.curlrc` (`connect-to` and a fixture CA), and a containment row proves the redirect before any other row runs. The script names no `TB_FIXTURE_` variable and no test box setting.
