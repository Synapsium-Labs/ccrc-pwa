# Build 7 — fleet coordination, PR I: the server core

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A program becomes a live, observable, coordinated thing *server-side*: `~/.ccrc/coord.db` holds runs, work items and mail; a session can POST mail to another session and have it land — idle-timed, verified, replayed until acked — inside that session's own input box; a coordinator can open a run, dispatch a wave under enforced caps, and close it with a done-claim the server **re-measures** rather than believes.

**Architecture:** One new `server/src/coord/` directory (opener, store, prhistory reader, git-ref reader, fingerprint, envelope), one new watcher lane (`MAIL_SWEEP_MS`, `void`-dispatched, never awaited), six new routes, one widened `HookState`, one additive `FleetMsg` frame and two additive `NotifyEvent` kinds. Storage is `node:sqlite`'s `DatabaseSync` — synchronous, zero native deps, `user_version` as the schema key, migrations that **refuse to start** rather than start empty. **Zero new ccd verbs**: every fleet mutation rides `CCD_ARGV` entries that are already minted, already granted and already in `ccd caps`.

**Tech Stack:** TypeScript ESM (Node ≥22.13, Fastify), `node:sqlite` (built-in, experimental), vitest. **No new dependencies in any package.json** — only `engines` fields.

**Spec:** `docs/superpowers/specs/2026-08-07-build7-fleet-coordination-design.md` (approved 2026-08-08; the three **Operator rulings** at `spec:294-302` are binding).

**Scope:** PR I of two. **PR J is not yours** — the coordinator skill, its four-homes install lane, the `/runs` screen, the mail feed, the session mail strip and every renderer. Where PR I lands a wire type or a store slot that PR J will render, this plan says so and stops at the seam.

**Branch:** one PR, `feat/build7-core`, cut from `docs/build7-spec` (which carries the approved spec and is itself cut from `main` at `00ec0a1`). The orchestrator merges and deploys.

**Baseline for every anchor:** `00ec0a1` (current `main`), which `docs/build7-spec` has not moved code from — the two commits on it are spec documents. Every `file:line` below was re-derived by `grep`/`read` against this tree while writing the plan. **An anchor here is a snapshot at plan-writing time, not a live index**: trust the shipped source's own comments once execution starts moving lines.

### D-1 (blocking) — "dispatches wave N+1 **fresh** into the same workspace" is not reachable with zero new ccd verbs

`spec:214-216` describes the coordinator dispatching a *fresh* session into a held workspace at each wave boundary, and `spec:97-101` forbids any new ccd verb. Those two cannot both hold. Measured: `cmd_ensure` (`ccd/ccd:6851-6858`) picks `mode=resume` whenever `$REG/<id>.started` is `1`, and `cmd_ws_add` sets `started 1` at creation (`ccd/ccd:1115`). The only thing that would make `ensure` spawn `new` is clearing that field — a registry **write**, which the agent's whitelist forbids the server outright (`agent/src/whitelist.ts:78-80`: writes are `.cc-clips` and nothing else). `CCD_ARGV.start(w, p, wd)` is not a substitute: it derives the id as `<wrapper>-<project>` (`ccd/ccd:105`), so pointing it at a workspace workdir would seize the project's **main-checkout** session id, not the workspace's.

**Adaptation (orchestrator-amended):** dispatch for wave N ≥ 2 is `CCD_ARGV.ensure(id)` — the pane comes back with the harness resuming its own transcript — **followed by a `/clear` injected through `sendPrompt`'s full proof discipline** inside the same KeyedQueue slot (the exact move ccd itself makes with `/compact` from `_auto_compact_check`, upgraded from blind send-keys to the verified path). `/clear` discards the resumed context and rotates the harness uuid (`_sync_uuid` refreshes the registry copy within one supervise tick, so mail attribution re-arms itself); the wave brief is then delivered as **mail**, through the delivery lane, into a genuinely fresh context. Freshness is thereby mechanical again; only brief *quality* stays discipline (`docs/superpowers/programs/TEMPLATE.md:22-36`). The dispatch route performs all three steps and records them on the run row (`resumed: 1`, `clearedAt`); a `/clear` whose send is refused (dialog open, draft present) leaves the run in `dispatched` with the refusal recorded, retried by the coordinator like any failed step. The named ccd change (a `--fresh` flag on `ensure`, or `ws-dispatch`) is **still recorded and not invented** — it remains the cleaner eventual path.

**Amended (found in Task 2 review):** this deviation names `clearedAt` on the run row and `RunSummary.clearedAt`'s docstring (Task 3) calls it "the proof the second step ran" — but no task below ever adds the column. Task 2's v1 DDL as drafted stops at `resumed`; `CoordStore.hydrateRun` was then written to hardcode `clearedAt: null` for every run, which is indistinguishable on the wire from D-1's own refusal case (a `/clear` whose send was refused). Fixed in Task 2 directly rather than deferred to a Task 9 migration that was never scheduled: `runs.clearedAt INTEGER` lands in the v1 DDL now — `coord.db` exists on no box yet (`README.md` still says "No database"), so amending v1 before it has ever been observed costs nothing, versus a migration 2 landing mid-PR against a schema no deploy has ever seen. `hydrateRun` reads the real column. Nothing writes it yet — Task 9's dispatch route is still what performs the `/clear` and is still what will call the setter — so every run's `clearedAt` stays honestly `null` until then, exactly as before, but now because nothing has cleared anything rather than because the column doesn't exist.

### D-2 (blocking) — `no-handoff-commit` cannot mean "the commit touches the ledger"

`spec:127-132` wants the coordinator to re-measure `{branchTip, prNumber, prPhase, handoffCommit}`. Three of the four are reachable. The fourth is not, and the reason is structural: `EXEC_COMMANDS` is the closed set `['tmux','ccd']` (`agent/src/whitelist.ts:134`), so the server can never run `git`; and `FleetIO` (`server/src/io.ts:11-24`) reads bytes, so a commit object — a zlib-deflated loose object, or a slice of a packfile — is not readable in any useful sense. **Nothing server-side can tell whether a commit edits `docs/superpowers/programs/<slug>.md`.**

**Adaptation:** `no-handoff-commit` is redefined, in writing, as a **correspondence** check, not a content check: the claim is rejected when `handoffCommit` is absent, is not 40 hex, or is not equal to the `branchTip` the same claim carries. So the worker cannot report a handoff that is not the branch's own tip, and cannot report a tip the branch does not have (`stale-tip` covers that half). Whether the tip commit is a *real* handoff stays exactly where `spec:246-252` already puts it — "briefs are written prose reviewed like code" — i.e. the coordinator's ordinary review of the commit. The route's own docstring says this so nobody later reads the token as a stronger guarantee than it is.

### D-3 (additive, forced by the spec's own requirements) — two tables beyond the six §3 names

`spec:106-117` names six tables. Two of its own sentences need more:

- *"Every transition records who caused it"* (`spec:126`) is a history, not a column. → `run_events`.
- *"Every rejection is itself recorded (a rejected message is a fact about the fleet)"* (`spec:147-148`). A rejected ingress has **no** `mail` row by construction — it may carry an unknown recipient, a stale uuid or a forged sender, and writing it into `mail` would put unattributable rows in the table the delivery lane walks. → `mail_rejections`.

Both are additive and are named in the schema's own comment as the spec's requirements rather than as embellishment.

### D-4 (accepted hazard, stated) — `deploy/ccrc.service` sources no `EnvironmentFile`, and the live server is in remote mode anyway

`deploy/ccrc.service:1-13` has no `EnvironmentFile=` line, while `deploy/deploy.sh:101` ships `deploy/ccrc.env` to `~/.ccrc/ccrc.env` and `deploy.sh:103` copies the repo's unit file over the installed one on **every** server deploy. Yet the live server answers `{"mode":"remote"}`, which requires `CCRC_FLEET`, `CCRC_AGENT_URL` and `CCRC_AGENT_TOKEN` to be reaching it from somewhere this repo does not show — most likely a hand-made drop-in under `~/.config/systemd/user/ccrc.service.d/` on `server-box`.

**Adaptation: this PR does not touch `ccrc.service`, and the mail token is therefore NOT an env var.** Adding `EnvironmentFile=` to a unit whose live environment we cannot read risks flipping a production server to `CCRC_FLEET=local` (the value `ccrc.env.example:12` ships) on the next deploy. The token is read from a **file on the server box** — `~/.ccrc/mail.token`, path configurable via `CCRC_MAIL_TOKEN_PATH` — which `deploy.sh` can ship with no unit-file change at all. `config.ts` stays a pure env→config function; the file read happens at the composition root beside `notifyLog.load()`. The unit-file gap is real and is left as a finding for the operator, not silently patched by an agent that cannot see the box.

### D-5 (correction to the task framing) — run close **releases**, it does not archive

The spec's mapping table is explicit that "a coordinator that archives autonomously runs *through* [the merged-archive] gate, not around it" (`spec:89-95` and the Build 2.5 lifecycle at `spec:214-217`, "releases on final merge"). `FleetWatcher.archiveMerged` (`server/src/watch.ts:795-855`) already archives a merged, unheld workspace on a level-triggered sweep, and it skips a held one. So the honest close is `CCD_ARGV.wsRelease(id)` on the final wave and `CCD_ARGV.wsHold(id, 'program:<slug> wave:N+1/M')` on every other one — the existing sweep does the archiving on its own clock, with its own `archiveSafety` gate.

`CCD_ARGV.wsArchive` is used on **one** path only: an explicit abandon (`state: 'failed'`, `archive: true`), mirroring `POST /api/sessions/:id/archive` (`server/src/server.ts:599-614`) including its `verbSupported` 501.

### D-6 (measurement, carried) — the node floor number must be verified, not remembered

`node:sqlite` shipped in Node 22.5.0 behind `--experimental-sqlite` and stopped needing the flag in a later 22.x. This plan writes `>=22.13.0` into `engines` **and pins it with a test that actually imports `node:sqlite` and asserts `DatabaseSync` exists on the running interpreter** (`.github/workflows/ci.yml:31,72`). Measured live while writing this plan: `node v24.14.1` on the fleet host imports it clean; the spec records `v22.22.3` proven on `server-box` (`spec:36-38`).

**Amended after Task 1's implementation review:** the sentence this replaces overstated what the import assertion catches. It is absolute — no `package.json` read, fails on any interpreter below the real flag boundary no matter what `engines.node` says — but it only *fires* when the interpreter CI actually resolves for `node-version: '22'` happens to sit below that boundary. `setup-node` resolves the latest 22.x release, which sits well above any candidate boundary, so the assertion staying green is evidence the interpreter that ran the suite could do it — it is not independent confirmation that `22.13.0` specifically is Node's real number. That confirmation still doesn't exist anywhere in this plan or its tests; the Self-review's unverified-items list already says so (item (b), below) and this amendment stops D-6 from implying otherwise. **The test is a floor-crossing detector, not a historical-accuracy check on the constant `22.13.0`; the number in `engines` is still what moves if assertion 3 ever goes red.**

### D-8 (correction, found in Task 2 review) — two of the five v1 enum columns have no we-do-not-know member, and Task 3 as drafted below never gives them one

`schema.ts`'s header comment claimed, verbatim, that "every enum column has a designated we-do-not-know member on the READ side" — the Global Constraint quoted above ("every enum has a designated we-do-not-know member") — for all five enum columns the v1 DDL declares. ### D-9 (correction, found in Task 3 review) — `RUN_TRANSITIONS` had no edge into `closing` from where Task 9 actually closes a run

`RUN_TRANSITIONS` as landed only reached `closing` via `merging`, but no writer in this PR ever advances a run to `awaiting-review` or `merging` — Task 9's dispatch route advances only to `dispatched`, and its close route immediately does `advance(id, 'closing')` next. Every close in the build would have 409'd with `bad-transition` the first time it ran; the shipped `coord-store.test.ts` never exercised this because its only transition test stops at `working`.

**Adaptation:** `dispatched` and `working` both gain a direct edge to `closing`. `awaiting-review`/`merging` stay in the table and in `RUN_TRANSITIONS` unchanged — PR J's `POST /api/runs/:id/advance` is what reaches them; PR I never does.

### D-10 (bug, found in Task 3 review) — `dueDeliveries` only ever encoded the `queued` arm; replay-until-ack (spec:174-177) was unreachable

The shipped query was `WHERE state = 'queued' AND nextAttemptAt <= ?`. `markDelivered` moves a row's `state` to `'delivered'`, and nothing in the file ever moves it back — so once a delivery was injected, an unacked recipient could never be re-selected. `deliveredAt`/`ingestedAt` were already in the return shape with no arm that could ever produce a non-null value for them, which was the tell.

**Adaptation:** `dueDeliveries` gains a second parameter, `replayMs`, and a second WHERE arm: `OR (state = 'delivered' AND COALESCE(ingestedAt, deliveredAt) + replayMs <= now)`. `replayMs` is NOT a store-owned constant — `MAIL_REPLAY_MS` stays in `watch.ts` (Task 8) and the caller passes it in, the same way `capsUsage`/`markDispatched` take `now` from the caller rather than reading the clock internally. **Task 8's implementer**: `store.dueDeliveries(now)` in this plan's Step 6 body must become `store.dueDeliveries(now, MAIL_REPLAY_MS)` — a one-line adaptation the shape-authoritative-not-text-authoritative rule already covers, called out here so it is not a surprise. `schema.ts`'s v1 DDL also gains `mail_deliveries_replay(state, deliveredAt)`, the index this arm needs the way `mail_deliveries_due` already covers the `queued` arm — landed in v1 directly rather than a migration 2, on the same reasoning D-1's `clearedAt` amendment already gives (`coord.db` has been observed on no box yet).

### D-11 (bug, found in Task 3 review) — `reconstruct` accepted `registry.held` and never read it; the plan's own Step-4 rule 2 was dropped

Step 4's second rule is explicit: "The last wave in `reconstruct` takes its state from the hold, not from a guess: a held workspace whose ledger shows wave N of M with no handoff commit is `working`." The shipped body derived state purely from `handoffCommit !== null ? 'done' : 'working'` — `held` was typed, accepted, and never read. The shipped reconstruction drill fixture happens to be held, so it could not have told the two cases apart.

**Adaptation:** the last wave in the ledger, when it has no handoff commit, is `working` while `registry.held !== null` and `failed` when the hold is also gone — a released workspace backing a wave with no handoff commit has nothing live to call `working`, and `spec:82-85`'s "nothing is invented" applies to the state column too. Every earlier wave keeps the original `handoffCommit !== null ? 'done' : …` formula (the ledger is append-only, so this only ever matters for the last wave).

### D-12 (bug, found in Task 3 review) — `reconstruct`'s `claimedBy = NULL` rows permanently disarmed `openRun`'s one-coordinator refusal for that program

`openRun`'s guard read `SELECT claimedBy FROM runs WHERE program = ? ORDER BY id LIMIT 1` — the absolute first row. `reconstruct` inserts every rebuilt run with `claimedBy` bound to `NULL` (it has no way to know who will resume the program), so after any disaster rebuild the lowest-id row for that program carried `NULL` forever and the guard's `existing?.claimedBy != null` was false for every subsequent caller — a second coordinator was silently let in.

**Adaptation:** the guard query gains `AND claimedBy IS NOT NULL`, so it finds the first row a real `openRun` actually claimed rather than the first row full stop. A reconstructed-but-not-yet-resumed program is claimable by the first coordinator that calls `openRun` on it, and refuses every one after — the intended behaviour, now reachable.

### D-13 (bug, found in Task 3 review) — `capsUsage().running` counted `planned` runs, wedging the concurrency cap on a botched dispatch

`SELECT count(*) FROM runs WHERE state NOT IN ('done','failed')` counts `planned` — a run with no session, no workspace and no worker, exactly the state Task 9's `ambiguous-dispatch` refusal deliberately leaves a run in. Three botched dispatches, or a coordinator that pre-opens several waves before dispatching wave 1, would pin `running` at the default `maxConcurrentWorkers = 3` against zero live workers, with no route in this PR that can un-wedge it.

**Adaptation:** `running`'s predicate gains `dispatchedAt IS NOT NULL` — the one column only `markDispatched` ever sets, so it names the runs that actually hold a session rather than every non-terminal state.

### D-14 (bug, found in Task 4 review) — `readPrHistory`'s null-read arm could refuse a file that appeared mid-check

The shipped reader did `io.readFile` → (null) → `io.readdir`, and refused whenever the listing named the file — indistinguishable from a file that is genuinely unreadable. But ccd's one append chokepoint (`ccd/ccd:849-859`) fires on a `prnumber` replacement, which lands exactly at a merge, and a run close is exactly what happens at a merge too: a `.prhistory` created in the gap between the read and the listing — by the watcher's 120s sweep or a PR-sheet `GET`, neither serialised against the close — named itself in the listing with nothing behind the first read, and was reported `unreadable` about a file that was present, readable and correct. The module's own docstring cited `registry.ts`'s `HOLD_UNREADABLE` mechanism as its model and even flagged the gap as "a WS round trip wide" in remote mode, but `registry.ts` closes that gap with a **second listing** confirming an ambiguous read (`registry.ts:158-176`); this reader took the first listing alone and skipped the confirming look — the mirror image of the bug `registry.ts`'s comment says it exists to prevent.

**Adaptation:** on the null-read arm, a listing naming the file gets a **second read**, not a second listing — a read is the only op that can produce the actual entries, and refusal is reserved for a file that is still unreadable on that second attempt. Pinned by `coord-prhistory.test.ts`'s stub-`FleetIO` race case (the listing's own callback writes the file, modelling "something else just created it"), which fails against the pre-fix ordering.

### D-15 (correction, found in Task 4 review) — the MALFORMED rung's docstring credited ccd with a ladder ccd does not implement, and the divergence was unrecorded

The docstring said "THE THREE-ANSWER LADDER IS ccd'S OWN (`ccd/ccd:2018-2035`)" and gave MALFORMED as "the lines that parse, in order." Read against the cited lines, ccd's own comment says the opposite by name — "MALFORMED -> `[]`, raw file untouched on disk" (`ccd/ccd:2020-2022`) — and its implementation matches: a list comprehension over every line inside one `try` (`ccd/ccd:2046`), one bad line raises, the `except ValueError` (`ccd/ccd:2060-2061`) discards the whole `rows` down to `[]`. This repo's own `ccd-prhistory.test.ts:105` pins that whole-file behaviour on the ccd side. The plan's own prose at Task 4 (above the Step-3 code block) already said "malformed is `[]` with the raw file untouched," agreeing with ccd; only the code block — followed correctly, per the shape-authoritative rule — implements per-line salvage instead, and nothing recorded that the two had come apart.

Kept as a deliberate divergence rather than reverted to match ccd: ccd's writer only ever appends with `O_APPEND`, so the one line ever at genuine risk of tearing is the LAST one (the scout's own caveat, `coord-prhistory.test.ts:29-31`), and discarding a good record because a later one tore is a worse failure than the one ccd is guarding against. The cost — this reader and ccd's own `ws-archive` fold can disagree about a workspace's PR lineage on a ledger whose bad line isn't the tail — is accepted and now stated in the reader's own docstring, along with the second-order divergence review finding 2 named: ccd performs no shape validation at all, so a line that parses as JSON but fails this reader's `pr`/`branch`/`phase`/`recordedAt` type guards is dropped here the same as an unparseable one, with nothing on `PrHistoryRead` distinguishing a genuinely empty ledger from one that had a line rejected. That gap is left unsignalled for now rather than given a new arm on the return type: the one prospective consumer of such a signal is the run-close route, which Task 9 has not yet built in this tree, and shaping the signal ahead of its actual error contract would be a guess.

**Adaptation:** `prhistory.ts`'s docstring is rewritten to name only ABSENT and UNREADABLE as ccd's own rungs, states the MALFORMED divergence and both its costs explicitly (mixed-file disagreement with ccd; unsignalled shape-rejection), and this Task 4 section above is left as-is with this entry as its correction — the shape-authoritative code block was followed as drafted; the comment above it is what gets corrected, here rather than by re-editing history.

### D-16 (test-coverage, found in Task 4 review) — the `listing === null` refusal arm and the four shape-reject predicates had no test, and Task 11's mutation table credited coverage it didn't have

Every case in the originally-shipped `coord-prhistory.test.ts` ran against a registry directory that existed and was readable, so `io.readdir` never returned `null` anywhere in the suite — the arm production actually takes in remote mode (`README.md:445`: `readdir` is an agent round trip there). Task 11's mutation table (`readPrHistory`: unreadable → `{ok:true, entries:[]}`) named exactly one prhistory mutant, for the `includes` arm alone; mutating the null-check independently (`listing !== null && listing.includes(name)`) reproduced all four then-committed test results byte-for-byte. Separately, the four shape guards (line 50-52 of the original) were pinned only in the accept direction — the suite's one negative case is a torn tail that never reaches them (`JSON.parse` throws first) — so deleting all four guards was also a silent survivor.

**Adaptation:** `coord-prhistory.test.ts` gains three cases — a registry directory that does not exist, a registry directory `chmod 000`'d (both exercising `listing === null` with no root dependency), and a two-line ledger of valid-JSON-wrong-shape records (`{"pr":"577",...}` / `{}`) pinning the reject side of the shape guards. All three were confirmed to kill their respective mutants (measured, isolated copies, sha256-verified restore between) and are added to the mutation table below alongside the existing `includes`-arm and second-read (D-14) rows.

### D-17 (bug, found in Task 5 review) — `verifyDone` re-measured a branch column `markDispatched` freezes once, dead before any `worker_done` could exist

`DoneRun.branch`, as originally typed, read field-for-field like the `runs` row it is built from — but `runs.branch` is written exactly once, by `markDispatched` at dispatch time (`store.ts:138-142`), and `FleetWatcher.sweepNames` (`watch.ts:545-610`) renames the workspace's registry branch autonomously, on the ordinary path, strictly before the first push (`cmd_ws_rename`'s one hard refusal is `has-upstream` — a branch that has been pushed is never renamed) — i.e. before any `worker_done` this claim could be. Every ordinary wave-1 close was measuring a branch ref git had already deleted, with no repair route for `runs.branch` anywhere in this PR: a permanent `tip-unmeasurable`, retried forever.

**Adaptation:** `verifyDone` resolves the branch to re-measure from the LIVE registry (`readRegistry`, keyed on `sessionId`) — the same read `sweepNames`/`sweepPr` already do — and falls back to `run.branch` only when the registry no longer carries a row for that session at all (retired, purged). `DoneRun`'s docstring is rewritten to say so explicitly, so a future reader does not mistake the field for "the run's branch" rather than "the run's branch, if the registry has forgotten it." Pinned by `coord-fingerprint.test.ts`'s "measures the RENAMED branch the registry names, not the born branch frozen on the run row" case, and the fallback case beside it.

### D-18 (bug, found in Task 5 review) — `prPhase`/`prNumber` were typed but never runtime-validated, so a malformed claim could read as agreement

`DoneClaim`'s own docstring says every field is UNTRUSTED input off an HTTP body, and `branchTip`/`handoffCommit` were validated against the `SHA` regex — but `prPhase` and `prNumber` were trusted to be a `PrPhase` and a `number|null` on the strength of a TypeScript annotation alone; no route in this PR, or its plan, names a parse step between the JSON body and this claim. ### D-19 (bug, found in Task 5 review) — a readable-but-non-SHA loose ref fell through to a STALE `packed-refs` entry, which is not how git resolves

The shipped `readBranchTip` read the loose ref, and only fell through to `packed-refs` when `SHA.test` on its trimmed content failed — folding "loose ref absent" and "loose ref present but not a SHA" (the shape a symref holds) into the same fallthrough. Git does not work this way: a loose ref, once written, SHADOWS the packed entry entirely, and `packed-refs` can hold a stale tip for the same branch after `git pack-refs`. The docstring even said the opposite ("A `.git` this process cannot read, and a symref, are both null here"), while the code fell through for the symref case. On a workspace branch packed at an OLD tip and later moved by a real commit, a torn write, an `EISDIR`, or a `git symbolic-ref` would resolve to the OLD tip from `packed-refs` instead of `null` — and a stale `worker_done` naming OLD would settle the run.

**Adaptation:** a readable loose ref now returns immediately — `SHA.test(v) ? v : null` — never falling through to `packed-refs` whether or not it parses as a SHA. Pinned by "never falls through a PRESENT loose ref to a stale packed-refs entry," a fixture with loose=symref, packed=OTHER, that fails against the pre-fix fallthrough and passes against the fix.

### D-20 (bug, found in Task 5 review) — the project guard's character class admitted `.` and `..`, a one-level escape above `projectsRoot`

**Adaptation:** the guard gains an explicit `|| project === '.' || project === '..'`, matching the branch guard's own explicit `..` exclusion one line above. ### D-24 (bug, found in the same later Task 2 review) — the 0-byte "never start empty" guard could be tripped by its own process's aborted first migration, turning one transient, already-remedied failure into a permanent refusal over a message asserting data loss that never happened

`openCoordDb`'s guard against adopting a truncated file as a fresh database (rule 2) ran a real check — `existsSync(dbPath) && statSync(dbPath).size === 0` — but the file it was checking could be one THIS OPEN ATTEMPT created: `new DatabaseSync(path)` creates the file eagerly, at 0 bytes, before any migration writes a byte, and the migration loop's own `catch` block only ever `db.close()`s and throws — nothing removed the 0-byte artifact a first-boot migration failure (disk-full, EIO, a SIGKILL in the window, or any later bad migration) left behind. **Adaptation:** `openCoordDb` records `existedBefore = existsSync(dbPath)` before `new DatabaseSync` runs, and the migration-failure `catch` block removes the file, best-effort, when `shouldRemoveMigrationFailureArtifact(existedBefore, sizeAfterRollback)` says so — true only when `!existedBefore && sizeAfterRollback === 0`, i.e. an empty file this call's own aborted attempt created and never got a row into. A mutant dropping the `!existedBefore` half of that function would therefore pass every `openCoordDb`-level test in the suite; pinned directly against the function instead, the same treatment `describeMigrationProgress`'s otherwise-unreachable branch already gets. A new `coord-db.test.ts` case forces `MIGRATIONS[0]` to invalid SQL against a path with no pre-existing file, confirms the resulting `CoordDbUnmigratable` leaves no file at all (measured directly, not inferred from a second call succeeding), and confirms a second `openCoordDb` call — cause now fixed — migrates clean instead of hitting the guard.

## Global Constraints (from the spec, verbatim where quoted)

- **The storage rules, and they are deliberately NOT the cache rules.** "`user_version` pragma **is** the schema version. Migrations are forward-only, idempotent, run at open, in a transaction — and a DB that cannot migrate **refuses to start loudly** (rejection-collapses-to-empty is the cache rule; here it would erase a program's history)." "Columns are additive-only; nullable means 'an older build lacked it'; every enum has a designated we-do-not-know member." "An older build meeting a newer schema ignores unknown columns and never treats a higher `user_version` as fatal downward — it may only refuse to *migrate*, never to *read*." "The markdown ledger stays the disaster-recovery ground truth… a test proves the reconstruction path for a representative program." "`engines` fields land in all three package.jsons and CI's node version is asserted against them."
  The code comment on `openCoordDb` must **name** `server/src/fleetstate.ts:47-55` ("the READ is the version negotiation") and `pwa/src/lib/offline.ts:11-16` (v1-forever) and say why neither transfers — otherwise a reviewer will cite them against this file, which is exactly what `spec:66-69` anticipates.
- **"No new ccd verbs in this build."** "`ws-hold` is the claim/veto, `ws-add`/`start` are dispatch, `pr-open`/`pr-state` are the PR lane, `ws-archive` the close. Every one is already granted and gated." If a task finds this impossible, it records a deviation — it does not invent a verb. (Two already exist: **D-1** and **D-5**.)
- **Identity is attribution, not authentication.** "On the fleet host, identity is attribution, not authentication. All sessions share one UNIX user… The spec never pretends otherwise." The box token "authenticates *the box*, which is the honest unit; per-session identity rides as attribution: `{fromId, fromUuid}`, verified server-side against the registry (`fromUuid === $REG/<id>.uuid` read via FleetIO, the hookstate gate's exact shape) — **freshness, not forgery-proofness, and the spec says so**."
- **`/api/notify` adopts the box token in this build** (operator ruling 1, `spec:150-155`): "`notify.sh` gains the token read from `~/.cc-secrets/ccrc-mail.token`; the server accepts the old shape for one deploy generation (absent token → accepted, logged as legacy) so the hook cannot go dark mid-rollout, then the tolerance is removed."
- **Rejection codes are typed and total** — "`unknown-sender`, `stale-uuid`, `unknown-recipient`, `unknown-run`, `oversize`, `bad-kind`, `unauthenticated`, plus the done-authority set (§3). Every rejection is itself recorded."
- **Delivery.** "`MAIL_SWEEP_MS = 10_000`, never awaited… session alive; hookstate fresh and `state ∈ {done, idle}`-equivalent; no dialog/ask pending; quiet ≥ 60s; per-session mail cooldown; a fleet `mail-disabled` marker file as kill-switch (read via FleetIO). Only then does it inject through **`sendPrompt`'s full proof discipline** (echo verified, draft-present refused, dialog-open refused) inside the session's KeyedQueue slot." "**Busy sessions are backed off, not stacked.**" "`attempts` capped with exponential spacing, and a delivery that keeps failing parks as `rejected('undeliverable')` with its mail intact." "Until acked, the delivery replays — **verbatim, never re-rendered** — on later sweeps after cooldown."
- **Nothing in this build teaches `sendPrompt` to retry.** Its two-Enter budget and `submitEnter`'s one-Enter doctrine (`server/src/inject/send.ts:456-460`) are load-bearing: "A human tap does: they looked at the pane first." The escalation for a stuck box is the human.
- **Caps and pause.** "`maxConcurrentWorkers` (running runs), `maxSessionsPerDay` (dispatches per rolling 24h) — rows in `coordinator_state`… **Pause is a file**: `$REG/coordinator-paused` on the fleet host, operator-owned (`touch`/`rm`), read via FleetIO before any dispatch… no verb, no route, no way for the coordinator to unpause itself."
- **The wire is additive.** "A `{type:'runs'}` frame on `/ws/fleet` (additive; old clients drop it)… REST `GET /api/runs` for cold start". // The Node floor stops being prose here. `node:sqlite` is a built-in whose
```ts
// availability is version-sensitive — it shipped behind `--experimental-sqlite`
// and stopped needing the flag in a later 22.x — and `server/src/coord/db.ts`

// degrade, it fails to boot.
//
// THREE assertions, and the third is the one that matters: the first two pin
// the DECLARATION (all three packages agree, and they say a number), the third
// pins the FACT (this interpreter can actually do it). If they ever disagree,
// the declaration is what moves — see the plan's deviation D-6. Do not "fix" a
// red third assertion by lowering `engines`.
import { describe, it, expect } from 'vitest';
import { readFileSync } from 'node:fs';
import path from 'node:path';
import { fileURLToPath } from 'node:url';

const root = path.resolve(path.dirname(fileURLToPath(import.meta.url)), '../..');
const PACKAGES = ['server', 'agent', 'pwa'];

const enginesOf = (pkg: string): string | undefined => {
  const j = JSON.parse(readFileSync(path.join(root, pkg, 'package.json'), 'utf8')) as
    { engines?: { node?: string } };
  return j.engines?.node;
};

 *  moment someone writes `^22 || >=24` this parser must fail loudly rather than
 *  silently accept a floor it did not understand. */
const floorOf = (range: string): [number, number, number] => {
  const m = /^>=(\d+)\.(\d+)\.(\d+)$/.exec(range.trim());
  expect(m, `engines.node must be a single '>=x.y.z' range, got ${JSON.stringify(range)}`).not.toBeNull();
  return [Number(m![1]), Number(m![2]), Number(m![3])];
};

describe('the node floor', () => {
  it('is declared in all three package.jsons, identically', () => {
    const ranges = PACKAGES.map((p) => [p, enginesOf(p)] as const);
    for (const [p, r] of ranges) expect(r, `${p}/package.json has no engines.node`).toBeTruthy();
    expect(new Set(ranges.map(([, r]) => r)).size,
      `the three packages declare different floors: ${JSON.stringify(ranges)}`).toBe(1);
  });

  it('is satisfied by the interpreter running this suite', () => {
    const [maj, min, pat] = floorOf(enginesOf('server')!);
    const [rMaj, rMin, rPat] = process.version.slice(1).split('.').map(Number) as [number, number, number];
    const ok = rMaj > maj || (rMaj === maj && (rMin > min || (rMin === min && rPat >= pat)));
    expect(ok, `running ${process.version}, floor is ${enginesOf('server')}`).toBe(true);
  });

    const { DatabaseSync } = await import('node:sqlite');

    db.exec('CREATE TABLE probe (a INTEGER)');
    db.prepare('INSERT INTO probe VALUES (?)').run(1);
    expect((db.prepare('SELECT count(*) AS c FROM probe').get() as { c: number }).c).toBe(1);

});
```

```ts
/**
 * The v1 DDL, and the ONLY place a migration is written.
 *
 * COLUMNS ARE ADDITIVE-ONLY (spec:77). A column is never repurposed and never
 * dropped; nullable means "an older build lacked it". Every enum column has a
 * designated we-do-not-know member on the READ side (`shared/api.ts`'s
 * `RunState`/`WorkItemState`/`MailKind` each carry one), so a token written by
 * a newer build lands somewhere honest instead of being switched on and
 * rendered as nothing — `PrPhase`'s `'unchecked'` is the precedent
 * (`server/src/registry.ts:133-140`).
 *
 * `run_events` and `mail_rejections` are NOT in spec:106-117's six-table list.
 * They are forced by two of the spec's own sentences: "Every transition records
 * who caused it" (spec:126) is a history, not a column; and "Every rejection is
 * itself recorded" (spec:147) has nowhere to go — a rejected ingress has no
 * `mail` row by construction, since it may carry an unknown recipient or a
 * stale uuid, and writing it into `mail` would put unattributable rows in the
 * table the delivery lane walks. See the plan's deviation D-3.
 *
 * `runs.claimedBy` implements spec:291-292's multi-coordinator non-goal: one
 * coordinator per program, and a second one refuses rather than arbitrating.
 */
export const MIGRATIONS: readonly string[] = [
  // ── 1: user_version 0 -> 1 ────────────────────────────────────────────────
  `
  CREATE TABLE programs (
    slug       TEXT PRIMARY KEY,
    title      TEXT NOT NULL,
    createdAt  INTEGER NOT NULL,
    state      TEXT NOT NULL              -- active|paused|done|abandoned
  );

  CREATE TABLE runs (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    program       TEXT NOT NULL REFERENCES programs(slug),
    wave          INTEGER NOT NULL,
    waveOf        INTEGER,
    project       TEXT NOT NULL,
    sessionId     TEXT,                   -- null until dispatch mints the workspace
    workspace     TEXT,
    branch        TEXT,
    state         TEXT NOT NULL,          -- see RUN_TRANSITIONS
    claimedBy     TEXT,                   -- the one coordinator; a second refuses
    resumed       INTEGER NOT NULL DEFAULT 0,   -- deviation D-1: wave N>=2 resumes
    openedAt      INTEGER NOT NULL,
    dispatchedAt  INTEGER,
    closedAt      INTEGER,
    handoffCommit TEXT,
    prLineage     TEXT                    -- JSON, folded from .prhistory at close
  );
  CREATE INDEX runs_by_state   ON runs(state);
  CREATE INDEX runs_by_program ON runs(program, wave);

  CREATE TABLE run_events (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    runId     INTEGER NOT NULL REFERENCES runs(id),
    at        INTEGER NOT NULL,
    fromState TEXT NOT NULL,
    toState   TEXT NOT NULL,
    causedBy  TEXT NOT NULL,              -- 'coordinator' | 'operator' | <session id>
    detail    TEXT
  );
  CREATE INDEX run_events_by_run ON run_events(runId, at);

  CREATE TABLE work_items (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    runId           INTEGER NOT NULL REFERENCES runs(id),
    title           TEXT NOT NULL,
    state           TEXT NOT NULL,        -- pending|claimed|done|failed|abandoned
    claimedBy       TEXT,                 -- a session id
    blockedBy       TEXT NOT NULL DEFAULT '[]',  -- JSON array of work_item ids
    doneFingerprint TEXT                  -- JSON, as reported then re-measured
  );
  CREATE INDEX work_items_by_run ON work_items(runId);

  CREATE TABLE mail (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    at        INTEGER NOT NULL,
    fromId    TEXT NOT NULL,
    fromUuid  TEXT NOT NULL,
    toId      TEXT NOT NULL,              -- 'coordinator' | a session id
    runId     INTEGER REFERENCES runs(id),
    kind      TEXT NOT NULL,              -- finding|question|answer|status|artifact
    subject   TEXT NOT NULL,
    body      TEXT NOT NULL,              -- <= MAIL_BODY_MAX_BYTES
    artifacts TEXT NOT NULL DEFAULT '[]'  -- JSON array of PATHS, never payloads
  );

  CREATE TABLE mail_deliveries (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    mailId        INTEGER NOT NULL REFERENCES mail(id),
    toId          TEXT NOT NULL,          -- the resolved SESSION id
    state         TEXT NOT NULL,          -- queued|delivered|acked|rejected
    attempts      INTEGER NOT NULL DEFAULT 0,
    nextAttemptAt INTEGER NOT NULL DEFAULT 0,
    -- The rendered envelope, stored at QUEUE time. spec:174-177 requires a
    -- replay to be verbatim and never re-rendered; a render deferred to each
```

```ts
/**
 * Open the coordination database, migrating it forward if needed, or refuse to
 * start.
 *
 * THE HOUSE CACHE RULES DO NOT APPLY HERE, and this paragraph is why — because
 * without it a reviewer will cite them, correctly, against this file:
 *
 *  - `fleetstate.ts:47-55` says "the READ is the version negotiation", and that
 *    a cache which cannot be revived is treated as ABSENT. `offline.ts:11-16`
 *    stays at v1 forever for the same reason. Both govern artefacts whose loss
 *    is FREE: the degraded-mode snapshot is re-assembled live, the offline
 *    snapshot is replaced by the next frame.
 *  - This is the first artefact in ccrc whose loss is NOT free. Collapsing an
 *    unreadable database to "empty" would answer "that program never happened"
 *    — the exact shape of `ccd`'s SIXTEENTH FORGERY, a manifest that lies
 *    pristine (`ccd/ccd:2018-2035`).
 *  - And the reason those files could not do better is absent here: they had
 *    NOWHERE to put a version key. This file has `PRAGMA user_version`, which
 *    IS the key, so the negotiation is a real one and does not have to be
 *    smuggled into the read.
 *
 * The four rules, from spec:70-81:
 *   1. Forward-only, idempotent, at open, EACH IN A TRANSACTION.
 *   2. Cannot migrate -> refuse to start LOUDLY. Never start empty.
 *   3. A HIGHER user_version is not fatal: a rollback (`~/ccrc-backups/`, and
 *      `shared/api.ts:566-575` on why rollback is a real scenario) must be able
 *      to READ. It may only refuse to MIGRATE. `user_version` is never written
 *      downward, and unknown columns are ignored because every read names its
 *      columns explicitly — `SELECT *` is banned in this directory.
 *   4. The markdown ledger stays the disaster-recovery ground truth
 *      (`docs/superpowers/programs/<slug>.md` + the registry + `.prhistory`);
 *      `coord-store.test.ts`'s reconstruction drill proves the path.
 */
export function openCoordDb(dbPath: string): DatabaseSync {
  // `~/.ccrc` is not created by the deploy except incidentally (`deploy.sh:34`
  // runs `mkdir -p ~/.ccrc` only inside `ship_env`), so every writer makes its
  // own parent — `fleetstate.ts:40`, `push.ts:50`, `notifylog.ts:85`.
  mkdirSync(path.dirname(dbPath), { recursive: true });
  const db = new DatabaseSync(dbPath);
  // WAL first: a reader must never be blocked by the sweep's write, and the
  // journal mode is a property of the FILE, so it survives every later open.
  db.exec('PRAGMA journal_mode = WAL');
  db.exec('PRAGMA foreign_keys = ON');
  db.exec('PRAGMA busy_timeout = 5000');

  const current = (db.prepare('PRAGMA user_version').get() as { user_version: number }).user_version;
  if (current > COORD_SCHEMA_VERSION) {
    // Rule 3. Loud, because it is worth knowing; not fatal, because refusing
    // here would make a rollback unable to read the history it rolled back to.
    console.warn(
      `ccrc-server: coord.db is at schema ${current}, this build knows ${COORD_SCHEMA_VERSION} — ` +
      'reading it as-is and migrating nothing (a rollback may only refuse to migrate, never to read)',
    );
    return db;
  }

  for (let v = current; v < COORD_SCHEMA_VERSION; v++) {
    try {
      tx(db, () => {
        db.exec(MIGRATIONS[v]!);
        // Inside the same transaction as the DDL it describes: SQLite's DDL is
        // transactional, so a crash between the two would otherwise leave a
        // migrated schema claiming to be unmigrated and re-run it on next boot.
        db.exec(`PRAGMA user_version = ${v + 1}`);
      });
    } catch (err) {
      db.close();
      throw new CoordDbUnmigratable(
        `ccrc-server: ${dbPath} is at schema ${v} and migration ${v + 1} failed: ` +
        `${err instanceof Error ? err.message : String(err)}. REFUSING TO START. ` +
        'Nothing was changed (the migration ran in a transaction). Restore from ~/ccrc-backups/ ' +
        'or move the file aside — starting empty would erase a program\'s history.',
      );
    }
  }
  return db;
}

/**
 * Every write in a transaction (spec:60). `BEGIN IMMEDIATE`, not the default
 * DEFERRED: under WAL a deferred transaction takes its write lock at the first
 * write, so a busy database fails in the MIDDLE of a multi-statement unit
 * instead of at its start.
 *
 * SYNCHRONOUS by construction — `DatabaseSync` has no async surface — and that
 * is a property worth naming rather than apologising for: a whole transaction
 * runs without yielding the event loop, so no route, sweep or socket can
 * interleave inside one. `fn` must therefore never await, and nothing in this
 * directory does.
 */
export function tx<T>(db: DatabaseSync, fn: () => T): T {
  db.exec('BEGIN IMMEDIATE');
  try {
    const out = fn();
    db.exec('COMMIT');
    return out;
  } catch (err) {
    // A rollback that itself throws must not replace the real error: the caller
    // needs to know what failed, not that the recovery also did.
    try { db.exec('ROLLBACK'); } catch { /* the transaction is already gone */ }
    throw err;
  }
}
```

```ts
  openRun(input: {
    program: string; title: string; project: string;
    wave: number; waveOf: number | null; claimedBy: string;
  }): OpenRunResult {
    return tx(this.db, () => {
      const existing = this.db.prepare(
        'SELECT claimedBy FROM runs WHERE program = ? ORDER BY id LIMIT 1',
      ).get(input.program) as { claimedBy: string | null } | undefined;
      // spec:291-292: multi-coordinator arbitration is a NON-GOAL. A second
      // coordinator is refused, in words, rather than silently allowed to
      // interleave dispatches with the first one's.
      if (existing?.claimedBy != null && existing.claimedBy !== input.claimedBy) {
        return { refused: 'claimed-by-another' as const, by: existing.claimedBy };
      }
      const now = Date.now();
      this.db.prepare(
        'INSERT INTO programs (slug, title, createdAt, state) VALUES (?, ?, ?, ?) ' +
        'ON CONFLICT(slug) DO UPDATE SET title = excluded.title',
      ).run(input.program, input.title, now, 'active');
      const res = this.db.prepare(
        'INSERT INTO runs (program, wave, waveOf, project, state, claimedBy, openedAt) ' +
        'VALUES (?, ?, ?, ?, ?, ?, ?)',
      ).run(input.program, input.wave, input.waveOf, input.project, 'planned', input.claimedBy, now);
      return { id: Number(res.lastInsertRowid), program: input.program, state: 'planned' as const };
    });

   * The ONLY way a run's state changes, and the only place `run_events` is
   * written — one call, so "every transition records who caused it"
   * (spec:126) is a property of the code rather than of everyone remembering.
   *

   * kind of claim this repo has already had to retract elsewhere.

  advance(runId: number, to: RunState, causedBy: string, detail?: string): AdvanceResult {
    return tx(this.db, () => {
      const row = this.db.prepare('SELECT state FROM runs WHERE id = ?').get(runId) as
        { state: string } | undefined;
      if (!row) return { ok: false as const, error: 'unknown-run' as const };
      const from = isRunState(row.state) ? row.state : 'unknown';
      if (!(RUN_TRANSITIONS[from] as readonly string[]).includes(to)) {
        return { ok: false as const, error: 'bad-transition' as const, from, to };
      }
      const now = Date.now();
      this.db.prepare('UPDATE runs SET state = ?, closedAt = CASE WHEN ? IN (\'done\',\'failed\') THEN ? ELSE closedAt END WHERE id = ?')
        .run(to, to, now, runId);
      this.db.prepare(
        'INSERT INTO run_events (runId, at, fromState, toState, causedBy, detail) VALUES (?, ?, ?, ?, ?, ?)',
      ).run(runId, now, from, to, causedBy, detail ?? null);
      return { ok: true as const, from, to };
    });
```

**Files:**

- Create: `server/test/coord-prhistory.test.ts`

**Interfaces:**
- Consumes: `FleetIO.readFile` (`server/src/io.ts:12`), `FleetIO.readdir`, `cfg.registryDir` (`config.ts:34`).
- Produces: `readPrHistory(io, registryDir, id): Promise<PrHistoryRead>`.

**The three-answer ladder's outer two rungs are not optional here, and they are `ccd`'s own** (`ccd/ccd:2013-2035`): absent is `[]` *measured*; **present-but-unreadable is a REFUSAL**, because a `chmod 000` ledger answering `[]` says "this workspace retired no PRs" in a record that authorises a close. `FleetIO.readFile` collapses every error to `null` (`io.ts:41-43`), so present-vs-absent is distinguished the way `registry.ts` already does it: the registry **directory listing** names the file whether or not its bytes can be fetched (`server/src/registry.ts:26-46`, the `HOLD_UNREADABLE` dance) — and, unlike `registry.ts`, an ambiguous null read gets confirmed with a **second read**, not a second listing, because a read is the only op that can produce this function's actual answer (D-14).

**The middle rung — MALFORMED — is NOT ccd's, and this is a deliberate divergence, corrected here after Task 4 review (D-15).** ccd's own handling is whole-file: one line `json.loads` cannot parse discards the ENTIRE ledger down to `[]`, raw file untouched (`ccd/ccd:2020-2022,2046,2060-2061`; pinned on the ccd side by `ccd-prhistory.test.ts:105`). This reader instead salvages every line it can parse **and** validate, in order, dropping only the lines it can't — because ccd's writer only ever appends with `O_APPEND`, so the one line ever at risk of tearing is the LAST one, and a torn tail is one lost record, not grounds to discard every record before it. Accepted cost: on a ledger whose bad line isn't the tail, this reader and ccd's own `ws-archive` fold can disagree about a workspace's lineage; and because ccd does no shape validation at all, a line that parses as JSON but fails this reader's own `pr`/`branch`/`phase`/`recordedAt` guards is dropped the same as an unparseable one, unsignalled on `PrHistoryRead` (left that way deliberately — the one prospective consumer, Task 9's close route, does not exist in this tree yet). Both are stated in the shipped docstring, not left implicit.

```ts
import path from 'node:path';
import type { FleetIO } from '../io.js';
import type { PrLineageEntry } from './store.js';

export type PrHistoryRead =
  | { ok: true; entries: PrLineageEntry[] }
  | { ok: false; error: 'unreadable' };

/**
 * `$REG/<id>.prhistory` — the FIRST server-side reader of this file. It is
 * appended by ccd at exactly one chokepoint, the `prnumber` replacement inside
 * `_pr_py` (`ccd/ccd:849-859`), which is the only line in ccd that ever
 * replaces a persisted `prnumber` and therefore the only place PR lineage can
 * be recorded at all.
 *
 * THE THREE-ANSWER LADDER IS ccd'S OWN (`ccd/ccd:2018-2035`), and it is
 * load-bearing rather than defensive:
 *   - ABSENT      -> `[]`, and it is a MEASURED answer: this workspace has
 *                    retired no PR.
 *   - MALFORMED   -> the lines that parse, in order; a torn tail is one lost
 *                    record. The file on disk is never touched.
 *   - UNREADABLE  -> REFUSAL. A `chmod 000` ledger answering `[]` would put
 *                    "this workspace retired no PRs" into the record that
 *                    closes a run — the SIXTEENTH FORGERY's exact shape.
 *
 * `FleetIO.readFile` maps every error to `null` (`io.ts:41-43`), so present and
 * unreadable are indistinguishable from the read alone. The registry DIRECTORY
 * listing is what separates them — it names `<id>.prhistory` whether or not its
 * bytes can be fetched — which is the same mechanism `registry.ts:26-46` uses
 * for `HOLD_UNREADABLE`. In remote mode both are agent round trips; two is the
 * price of the distinction, and it is paid once per run close, never per sweep.
 */
export async function readPrHistory(
  io: FleetIO, registryDir: string, id: string,
): Promise<PrHistoryRead> {
  const name = `${id}.prhistory`;
  const raw = await io.readFile(path.join(registryDir, name));
  if (raw === null) {
    const listing = await io.readdir(registryDir);
    // A listing we could not take either: refuse. Absence is only absence when
    // something actually looked.
    if (listing === null || listing.includes(name)) return { ok: false, error: 'unreadable' };
    return { ok: true, entries: [] };
  }
  const entries: PrLineageEntry[] = [];
  for (const line of raw.split('\n')) {
    if (line.trim() === '') continue;
    try {
      const o = JSON.parse(line) as Record<string, unknown>;
      if (typeof o['pr'] !== 'number' || !Number.isInteger(o['pr'])) continue;
      if (typeof o['branch'] !== 'string' || typeof o['phase'] !== 'string') continue;
      if (typeof o['recordedAt'] !== 'number') continue;
      entries.push({ pr: o['pr'], branch: o['branch'], phase: o['phase'], recordedAt: o['recordedAt'] });
    } catch { /* a torn or hand-edited line is one lost record, never a lost history */ }
  }
  return { ok: true, entries };
}
```

Create `server/src/coord/gitref.ts`:

```ts
import path from 'node:path';
import type { FleetIO } from '../io.js';

const SHA = /^[0-9a-f]{40}$/;
/** git's own rules, narrowed hard. No leading `-`, no `..` anywhere, no
 *  control characters, no absolute path — every one of which is a way to make
 *  the `path.join` below name a file outside the ref tree. This is a PATH
 *  guard, not a git validity check: `_ws_branch_valid` on the box owns that
 *  rule, and the server does not re-implement it (the standing ruling from the
 *  branch-naming build — two implementations of one rule drift). */
const BRANCH_OK = /^[A-Za-z0-9][A-Za-z0-9._\-\/]*$/;

/**
 * The commit a branch points at, read from git's own ref files through
 * `FleetIO` — because the server can NEVER run git. `EXEC_COMMANDS` is the
 * closed set `['tmux','ccd']` (`agent/src/whitelist.ts:134`) and widening it is
 * a three-edit, two-package, boot-audited change made deliberately or not at
 * all. The projects root IS readable (`whitelist.ts:82-88`), so the ref files
 * are.
 *
 * A WORKSPACE'S BRANCH LIVES IN THE MAIN REPO'S REF STORE, not in the worktree:
 * linked worktrees share `refs/` and keep only `HEAD` and their own
 * per-worktree refs under `.git/worktrees/<name>/`. So this reads
 * `<projectsRoot>/<project>/.git/refs/heads/<branch>`, then `packed-refs` —
 * loose first, which is the order git resolves in, and the reason the "prefers
 * the loose ref" case is pinned.
 *
 * `null` means UNMEASURABLE and callers must treat it as a refusal, never as a
 * mismatch and never as a pass: not knowing is not `[]` (`ccd/ccd:2018-2035`).
 * A `.git` this process cannot read, and a symref, are both null here — the
 * last deliberately, since resolving one is a second hop this does not need for
 * the one case it serves (a workspace branch).
 */
export async function readBranchTip(
  io: FleetIO, projectsRoot: string, project: string, branch: string,
): Promise<string | null> {
  if (!BRANCH_OK.test(branch) || branch.includes('..')) return null;
  if (!/^[A-Za-z0-9._-]+$/.test(project)) return null;
  const gitDir = path.join(projectsRoot, project, '.git');

  const loose = await io.readFile(path.join(gitDir, 'refs', 'heads', ...branch.split('/')));
  if (loose !== null) {
    const v = loose.trim();
    if (SHA.test(v)) return v;
  }
  const packed = await io.readFile(path.join(gitDir, 'packed-refs'));
  if (packed === null) return null;
  for (const line of packed.split('\n')) {
    if (line.startsWith('#') || line.startsWith('^')) continue;
    if (line.length < 42 || line[40] !== ' ') continue;
    if (line.slice(41).trim() !== `refs/heads/${branch}`) continue;
    const sha = line.slice(0, 40);
    if (SHA.test(sha)) return sha;
  }
  return null;
}
```

Create `server/src/coord/fingerprint.ts`:

```ts
import { CCD_ARGV, verbSupported } from '../ccdargv.js';
import { isFullLine, parsePrLines, phaseFor } from '../prstate.js';
import { readBranchTip } from './gitref.js';
import type { CcrcConfig } from '../config.js';
import type { FleetState } from '../fleetstate.js';
import type { FleetIO } from '../io.js';
import type { Deps } from '../server.js';
import type { MailRejectCode, PrPhase } from '../../../shared/api.js';

const SHA = /^[0-9a-f]{40}$/;

/** What a `worker_done` claims (mail kind `status`, subject `wave-done` —
 *  spec:127-129). Every field is UNTRUSTED input off an HTTP body. */
export interface DoneClaim {
  branchTip: string;
  prNumber: number | null;
  prPhase: PrPhase;
  handoffCommit: string;
}

export type DoneVerdict =
  | { ok: true; measured: { branchTip: string; prNumber: number | null; prPhase: PrPhase } }
  | { ok: false; code: Extract<MailRejectCode,
      'stale-tip' | 'tip-unmeasurable' | 'pr-regressed' | 'pr-unmeasurable' | 'no-handoff-commit'>;
      detail: string };

/**
 * A PR phase that has gone BACKWARDS since the worker looked. Forward motion is
 * not a mismatch: a PR that merged after the worker reported it open is the run
 * succeeding, not a stale claim.
 *
 * `unchecked`/`unknown` are neither — they are FAILED READS (`shared/api.ts`'s
 * `PrReason` docstring makes that split explicit) and get their own code, so a
 * GitHub outage can never read as "the PR regressed" or, worse, as agreement.
 */
function prVerdict(claimed: PrPhase, measured: PrPhase): 'ok' | 'regressed' | 'unmeasurable' {
  if (measured === 'unknown' || measured === 'unchecked') return 'unmeasurable';
  if (measured === 'closed' && claimed !== 'closed') return 'regressed';
  if (claimed === 'merged' && measured !== 'merged') return 'regressed';
  if ((claimed === 'open' || claimed === 'draft') &&
      (measured === 'none' || measured === 'no-commits')) return 'regressed';
  return 'ok';
}

/**
 * Re-measure a done claim. THE RUN IS NOT TOUCHED HERE — this answers, and the
 * route decides; a verifier that also advanced would be a verifier nobody can
 * call twice.
 *
 * WHAT IS RE-MEASURED, AND WHAT IS NOT (deviation D-2, stated here because this
 * is where a future reader will look for the guarantee):
 *  - `branchTip` — measured, from git's own ref files (`gitref.ts`).
 *  - `prNumber`/`prPhase` — measured, through `ccd pr-state --session`, the
 *    same verb and the same parser the PR lane already uses. Never `gh`: there
 *    is no `gh` key in the agent's whitelist and there must not be one
 *    (`agent/src/whitelist.ts:296-303`).
 *  - `handoffCommit` — CORRESPONDENCE ONLY. The server cannot read a commit
 *    object (no git, and `FleetIO` reads bytes), so it cannot tell whether the
 *    commit edits `docs/superpowers/programs/<slug>.md`. What it CAN prove is
 *    that the worker's own two facts agree and that the tip is real. Whether
 *    the commit is a real handoff is the coordinator's ordinary review of the
 *    diff — spec:246-252, "briefs are written prose reviewed like code". Do
 *    not let a later reader mistake this token for the stronger claim.
 */
export async function verifyDone(
  deps: { io: FleetIO; cfg: CcrcConfig; runCcd: Deps['runCcd']; fleetState?: FleetState },
  run: { sessionId: string; project: string; branch: string },
  claim: DoneClaim,
): Promise<DoneVerdict> {
  // Cheapest first, and it is also the one that needs no I/O: a claim whose own
  // two facts disagree is rejected before the fleet is touched at all.
  if (!SHA.test(claim.handoffCommit) || !SHA.test(claim.branchTip) ||
      claim.handoffCommit !== claim.branchTip) {
    return { ok: false, code: 'no-handoff-commit',
      detail: 'handoffCommit must be the 40-hex sha this same claim reports as branchTip' };
  }

  const tip = await readBranchTip(deps.io, deps.cfg.projectsRoot, run.project, run.branch);
  if (tip === null) {
    return { ok: false, code: 'tip-unmeasurable',
      detail: `no readable ref for ${run.branch} under ${run.project}` };
  }
  if (tip !== claim.branchTip) {
    return { ok: false, code: 'stale-tip',
      detail: `${run.branch} is at ${tip}, the claim says ${claim.branchTip}` };
  }

  const argv = CCD_ARGV.prStateSession(run.sessionId);
  if (!verbSupported(deps.fleetState, argv)) {
    return { ok: false, code: 'pr-unmeasurable', detail: 'the fleet host cannot answer pr-state' };
  }
  const res = await deps.runCcd(argv);
  if (!res.ok) return { ok: false, code: 'pr-unmeasurable', detail: res.stderr.trim() };
  const line = parsePrLines(res.stdout).find(isFullLine);
  if (!line) return { ok: false, code: 'pr-unmeasurable', detail: 'pr-state answered no full line' };
  const measured = phaseFor(line);

  const verdict = prVerdict(claim.prPhase, measured.phase);
  if (verdict === 'unmeasurable') {
    return { ok: false, code: 'pr-unmeasurable', detail: `pr-state answered ${measured.phase}` };
  }
  if (verdict === 'regressed') {
    return { ok: false, code: 'pr-regressed',
      detail: `the claim says ${claim.prPhase}, the PR is ${measured.phase}` };
  }
  if (claim.prNumber !== null && measured.number !== null && claim.prNumber !== measured.number) {
    return { ok: false, code: 'pr-regressed',
      detail: `the claim names PR #${claim.prNumber}, the branch is bound to #${measured.number}` };
  }
  return { ok: true, measured: { branchTip: tip, prNumber: measured.number, prPhase: measured.phase } };
}
```

> **On the `runCcd` parameter type:** take `Deps['runCcd']`, never a bare `(argv: string[]) => …`. The `CcdArgv` brand (`ccdargv.ts:27`) is the one mechanism that makes "every ccd argv is built in ccdargv.ts" enforceable rather than text-scanned, and a widened parameter type here would quietly undo it for this module.

```ts
import { readFileSync } from 'node:fs';
import { timingSafeEqual } from 'node:crypto';

/** The header every box->server POST carries. Lowercase because Fastify
 *  normalises incoming header names, and a mixed-case constant here would read
 *  as if the case mattered. */
export const MAIL_TOKEN_HEADER = 'x-ccrc-mail-token';

/**
 * The box token, off this box's own disk.
 *
 * WHY A FILE AND NOT AN ENV VAR (plan deviation D-4). `deploy/ccrc.service` has
 * no `EnvironmentFile=` line and `deploy.sh:103` copies it over the installed
 * unit on every server deploy, so an env-var token would either be inert or
 * would require editing a unit whose live environment this repo cannot see —
 * and `ccrc.env.example` ships `CCRC_FLEET=local`, which is not what the live
 * server is running. A file needs no unit change at all.
 *
 * `readFileSync`, at the composition root, deliberately: this is local-box
 * housekeeping and never crosses `FleetIO` — the same stance `fleetstate.ts`
 * takes for the degraded-mode cache. `~/.cc-secrets/` on the FLEET host is not
 * even readable through the agent (`agent/src/whitelist.ts:82-88` lists
 * `.cc-sessions`, `.cc-limits`, `.cc-clips`, `.claude*` and the projects root —
 * `.cc-secrets` is on none of them), which is the structural reason the two
 * boxes each hold their own copy of the same secret rather than one reading the
 * other's.
 */
export function readMailToken(tokenPath: string): string | null {
  try {
    const v = readFileSync(tokenPath, 'utf8').trim();
    return v === '' ? null : v;
  } catch {
    return null;   // absent is a configuration state, not an error
  }
}

/**
 * `'ok' | 'legacy' | 'bad'`.
 *
 * `'legacy'` is the operator ruling's one-deploy-generation tolerance
 * (spec:150-155): a fleet host still running yesterday's `notify.sh` presents
 * NO token, and the hook must not go dark between the server deploy and the
 * agent deploy. A caller that presents a token and gets it WRONG has no such
 * excuse and is refused.
 *
 * REMOVE THE TOLERANCE ONE DEPLOY AFTER THIS SHIPS. It is not a permanent
 * accommodation: while it stands, the ingress is still open to anything on the
 * tailnet, which is the hole this whole task exists to close. The README's
 * coordination section names the deploy that removes it.
 *
 * `timingSafeEqual` needs equal lengths, so the length check comes first and
 * leaks only the length — which a caller can measure anyway by sending one.
 */
export function checkMailToken(expected: string | null, presented: unknown): 'ok' | 'legacy' | 'bad' {
  if (expected === null) return 'ok';                 // unconfigured: nothing to check against
  if (presented === undefined || presented === null || presented === '') return 'legacy';
  if (typeof presented !== 'string') return 'bad';
  const a = Buffer.from(presented, 'utf8');
  const b = Buffer.from(expected, 'utf8');
  if (a.length !== b.length) return 'bad';
  return timingSafeEqual(a, b) ? 'ok' : 'bad';
}
```

Mail's version is the same two lines with a typed code on each: no registry row for `fromId` → `unknown-sender`; `fromUuid !== $REG/<id>.uuid` (including the registry having no uuid at all) → `stale-uuid`. **And the docstring must repeat the spec's own honesty**: this is freshness, not forgery-proofness. Every session on the box can read every `.uuid` file and could present a neighbour's pair. What it catches is a **stale** sender — a session that was `/clear`ed or compacted since it read its own uuid, which `_sync_uuid` rotates every 5 s (`ccd/ccd:6425-6437`) — and an honest mistake. That is the bar, and the spec says so at `spec:26-30`.

```ts
import type { MailKind } from '../../../shared/api.js';

export interface EnvelopeInput {
  id: number; fromId: string; toId: string;
  runId: number | null; program: string | null; wave: number | null; waveOf: number | null;
  kind: MailKind; subject: string; body: string; artifacts: readonly string[];
}

/** A fence long enough that the body cannot close it. Markdown's own rule: a
 *  fenced block ends only on a fence AT LEAST as long as the opener, so one
 *  backtick more than the longest run inside is always safe. Three is the floor
 *  because a shorter fence is not a fence. */
function fenceFor(text: string): string {
  let longest = 0;
  for (const m of text.matchAll(/`+/g)) longest = Math.max(longest, m[0].length);
  return '`'.repeat(Math.max(3, longest + 1));
}

/**
 * The text that gets typed into the recipient's input box.
 *
 * SELF-DESCRIBING BY REQUIREMENT (spec:173-177): the receiving agent must be
 * able to act on this with no tooling — it can see who sent it, which run it
 * belongs to, what the artifacts are, and exactly how to acknowledge it. There
 * is no client, no library and no MCP server on the other end; there is a
 * language model reading its own terminal.
 *
 * RENDERED ONCE, AT QUEUE TIME, AND STORED (`mail_deliveries.envelope`). A
 * replay is byte-identical because it is the same string, not because this
 * function is deterministic — which it is today and might not be after the next
 * edit. spec:176-177 says "verbatim, never re-rendered", and storing the bytes
 * is the only way to make that a property of the system rather than of
 * everyone's care.
 *
 * COST, stated because it is real: `sendPrompt` types one `tmux send-keys` per
 * line plus an `M-Enter` between lines (`inject/send.ts:300-305`), each an
 * agent round trip in remote mode. An 8KB body of short lines is a few hundred
 * round trips inside one KeyedQueue slot. That blocks ONLY this session — the
 * lane is `void`-dispatched and per-session — and it is the price of a message
 * an agent can read. Do not "optimise" it by shortening the body: the cap is
 * the spec's, the header is what makes it actionable.
 */
export function renderEnvelope(m: EnvelopeInput): string {
  const lines: string[] = [
    `id: ${m.id}`,
    `from: ${m.fromId}`,
    `to: ${m.toId}`,
  ];
  if (m.runId !== null) {
    const wave = m.wave === null ? '' : ` wave ${m.wave}${m.waveOf === null ? '' : `/${m.waveOf}`}`;
    lines.push(`run: ${m.runId}${m.program === null ? '' : ` (program:${m.program}${wave})`}`);
  }
  lines.push(`kind: ${m.kind}`, `subject: ${m.subject}`);
  if (m.artifacts.length > 0) {
    lines.push('artifacts:');
    for (const p of m.artifacts) lines.push(`  ${p}`);
  }
  lines.push(
    `ack: POST /api/mail/${m.id}/ack with header x-ccrc-mail-token (the value in`,
    '  ~/.cc-secrets/ccrc-mail.token) and body {"fromId":"<your ccd id>","fromUuid":"<your uuid>"}.',
    '  Until you ack, this message will be delivered to you again.',
    '--',
  );
  const head = lines.join('\n');
  const fence = fenceFor(`${head}\n${m.body}`);
  return `${fence}ccrc-mail\n${head}\n${m.body}\n${fence}`;
}
```
