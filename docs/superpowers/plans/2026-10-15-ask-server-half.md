## The bug

The operator reports that only the **first** question of a multi-question AskUserQuestion can be answered from the PWA, and that free-text ("Type something.") answers do not work at all. The diagnosis found eight causes. This branch fixes the server's share of them. The sheet's share follows #346.

| # | Cause | Half |
|---|---|---|
| 1 | `EnvelopeSheet` wires `questions[0]` only, and the frozen hook envelope wins the display for the whole tool call, so once the pane moves to Q2 every row is disabled. | sheet |
| 2 | The final "Review your answers" screen (Submit answers / Cancel) is unmodelled. | sheet |
| 3 | The sheet's question-to-pane correspondence compares labels only, so a Yes/No Q2 answers under Q1's title. | sheet |
| 4 | multiSelect is never answerable. `answerAsk` sends digits and then Enter, which on 2.1.280 and later **toggles** the cursor row instead of committing, and still returns `ok:true`. | server (Task 4) and sheet |
| 5 | The "answer in your own words" box picks "Chat about this", which declines the whole ask, and then sends the text as a new prompt. | sheet |
| 6 | A tap on "Type something." makes `answerDialog` walk onto the **empty** input and press Enter, which rejects the **whole** AskUserQuestion. | server (Task 1) |
| 7 | No server route can type into the free-text row: `sendPrompt` refuses `dialog-open` while a menu is up. | server (Task 3) |
| 8 | `Tmux.sendLiteral` passes the text with no `--`, so tmux parses a leading `-` as flags, and `sendPrompt` ignores the failure. | server (Task 2) |

## The measured protocol (Claude Code 2.1.300)

**How it was measured.** On 2026-10-15 Claude Code 2.1.300 (`--safe-mode --model haiku`) ran in a throwaway local tmux server with its own `-L` socket. The window was 220x50, as the fleet runs, and every screen was read with `capture-pane -p`, as `Tmux.capture` reads. The probe finished by killing that server. An earlier probe the same day ran at 220x50 and 100x40, and checked the core sequence on 2.1.291, which renders the same. Each screen below is a fixture under `server/test/fixtures/panes/`, scrubbed of its work-dir path, and its parser reading is pinned in `server/test/dialog.test.ts`, describe "2.1.300 AskUserQuestion (recorded)". Answers were read back from each session's own transcript (`toolUseResult.answers`). **The fleet's Claude Code version was not measured.**

### Which screen is up

- **Several questions, or any multiSelect:** a tab row `←  ☐ H1  ☐ H2 …  ✔ Submit  →` sits above the question, and the footer reads `Tab/Arrow keys to navigate`. **One single-select question:** no tab row and no review screen, and the footer reads `↑/↓ to navigate` (`cc300-ask-1q-open.txt`). The active tab is marked by colour only, so a plain capture cannot see it. The question line is what identifies the live question: `parseDialog`'s `title` is the question on every question screen (`cc300-ask-q1-of-2.txt`, `-q2-of-2-single`, `-same-labels-q1`, `-same-labels-q2`, `-4q-100col`, `-1q-open`).
- **Markdown is not rendered.** Backticks and asterisks reach the screen and the title verbatim, so the title equals the envelope's question text (`cc300-ask-markdown-question.txt`).
- **A question longer than one row wraps under a `│ ` bar on every row.** The title is its **last** row, with the bar kept: `│ must land before any writer that relies on it?` (`cc300-ask-wrapped-question.txt`). A suffix match against the envelope's question works only after the `│ ` is stripped.
- **Two questions with the same labels** (Yes/No twice) differ only by their title, and so by their dialog id (`cc300-ask-same-labels-q1.txt`, `-q2.txt`).
- The rows after a single-select question's `n` options: `n+1. Type something.`, then a rule, then `n+2. Chat about this`. A **ticked** tab (`☒`) means the question has an answer, not that it was committed. For multiSelect it flips as soon as one box is ticked.

### Single-select free text

- **A Down walk onto the empty row focuses it:** the cursor sits on `n+1`, the label is still `Type something.`, and the footer gains `ctrl+g to edit in Vim` (`cc300-ask-freetext-walk-2-focused.txt`). The digit `n+1` focuses it the same way (`cc300-ask-wrapped-question-focused.txt`). Up and Down never select or submit.
- **The hint outlives the row.** After a walk *through* the free-text row, the hint stays on the row below: on `Chat about this` (`cc300-ask-1q-walk-through-to-chat.txt`), and on a multiSelect `Next` row (`cc300-ask-multiselect-next-focused.txt`). Enter on `Chat about this` after such a walk gave Chat's own outcome (a rejection with the "wants to clarify" message), not the empty-row cancel. **So the hint proves nothing alone.** Focus is the conjunction: cursor on the row, AND label still the placeholder, AND the hint.
- **Typing** (`send-keys -l -- <text>`) replaces the row's label with the text. The **dialog id changes**, because it hashes the labels. The title stays (`cc300-ask-freetext-walk-3-typed.txt`).
- **A leading `-` needs `--`.** Without it, local tmux 3.7c answers `unknown flag -x` with exit 1. With it, `- only in staging, sampled 10%` was typed, and in a second ask `- oolong, no sugar` came back verbatim in `toolUseResult.answers`.
- **Stepping off keeps the text.** Up moves the cursor off the row, the text stays and the hint goes. Down comes back onto the held row, and the hint returns. The id stays the typed one throughout (`cc300-ask-freetext-walk-4-stepped-off.txt`, `-walk-5-back-on-held.txt`). A row that holds text replaces the placeholder, so no `Type something.` row is left on screen (`cc300-ask-freetext-held.txt`).
- **Enter on a held row submits the text** as the answer and moves on (`cc300-ask-review-same-labels.txt` lists it).
- **A 1000-character, single-line answer arrives intact.** It was sent as one `send-keys -l` call and painted as 5 rows at 220 columns, with the question still on screen in the 50-row capture. `parseDialog` reads the first row (212 characters) as the row's `label` and the other four as its `description`, and `label + ' ' + description` is exactly the 1000-character text (`cc300-ask-freetext-1000.txt`). After Submit, the transcript held both 1000-character answers and a 600-character one byte for byte. This sets D-5047's cap at 1000.
- **Hazard, earlier probe (2.1.300 and 2.1.291):** Enter on the **empty** row rejects the whole call (`User declined to answer questions`; `toolUseResult` is `User rejected tool use`) and discards questions already answered. Esc does the same.

### The review screen

- The body runs from `Review your answers` to `Ready to submit your answers?`, followed by `1. Submit answers` / `2. Cancel`, with no footer. The title is the tab row. A `⚠ You have not answered all questions` line appears when a question was skipped (`cc300-ask-review-same-labels.txt`, `-skipped`, `-1q-multiselect`, `-multiselect`, `-4q-100col`). `1` or Enter submits.
- **Cancel rejects the whole call.** Down then Enter on Cancel produced `User declined to answer questions`, with `is_error` set and `toolUseResult` `User rejected tool use`. Every answer was discarded, as with Esc and the empty-row Enter. The cursor on Cancel keeps the dialog id (`cc300-ask-review-cancel-focused.txt`, `-review-cancelled.txt`).
- **A review taller than `header()`'s 20-row climb** loses its title and its heading. With four questions, three of them answered with 600 to 1000 characters, there are 25 rows between the tab row and `Ready to submit`. The title becomes an answer row and the body loses `Review your answers`, but the body still **ends** with `Ready to submit your answers?` (`cc300-ask-review-4q-long.txt`).

### multiSelect

- **Layout:** rows `k. [ ] Label`, then `n+1. [ ] Type something` (no period), then an unnumbered `Next` row (`Submit` on the last question), a rule, and `n+2. Chat about this` (`cc300-ask-multiselect-next-open.txt`, `-submit-open.txt`).
- **The digit `k` toggles box `k` and the cursor does not move** (`cc300-ask-multiselect-digit1.txt`, `-digit1-3.txt`). Answers come back comma-joined in **tick order**: `Logging, Tracing` and `Saw, Drill`.
- **A digit with the cursor on the free-text row is TYPED:** `4. [✔] 2` (`cc300-ask-multiselect-digit-typed-on-freetext.txt`). That ticks the row and changes the id. BSpace restored the placeholder screen byte for byte.
- **Tab commits from an option row with no hint,** moving to the next question or the review (`cc300-ask-multiselect-row3.txt`, then `-submit-open.txt`). **Tab on the `Next` row after a walk through the free-text row is swallowed:** the screen was byte-identical after it, in two separate asks (`cc300-ask-multiselect-next-focused.txt`, `-walk-to-next.txt`). **Enter on `Next` commits** (`cc300-ask-multiselect-next-enter.txt`). Tab on an untouched question skips it (earlier probe). A revisit keeps the ticks and resets the cursor to row 1.
- **Recorded for Task 4** (the same way, the same day; `cc300-ask-multiselect-tools-*`, `-sizes-*`, `cc300-ask-review-tick-order.txt`): **a digit on a ticked box unticks it**, the cursor staying put (`-tools-digit1-2`, then `-tools-untick1`). **A revisit repaints the screen Tab left**, byte for byte, ticks kept and the cursor on row 1 (`-tools-revisit`). **The tick order survives a revisit:** Saw and Drill ticked, Tab, Left, then `2` (unticking Saw) and `1` (ticking Hammer), Tab, `2` on the next question, Tab: the review and the transcript read `Drill, Hammer` and `Large`. The earlier probe's `cc300-ask-multiselect-freetext-ticked.txt` is digit `n+1` ticking the EMPTY free-text box with the cursor on row 1 (no hint).
- **`parseDialog` before D-5048:** `parsed:false`, `options: []`, the question as `title`, and one id however the boxes are ticked or the cursor moves. `paneOptionRows` reported a `checkbox` flag but no tick state, the `Next`/`Submit` row was not a row, and with the cursor on `Next` no row was `selected`. Task 4 keeps all of that and adds `OptionRow.checked` and `Dialog.multi`.
- **`answerAsk` on 2.1.300:** `3` then Enter left rows 1 and 3 both ticked and committed nothing (earlier probe; the 2.1.280 fixtures `cc280-multiselect-seq-*` agree).
- **`answerDialog` on a multiSelect dialog** (a scratch probe on `cc300-ask-multiselect-next-open.txt`, not committed): `optionIndex` 1 sends a bare Enter, which toggles row 1, and returns `{ok:true}`. `optionIndex` 3 sends Down, Down, then refuses `walk-failed`, because an unparsed dialog's `selectedIndex` is always 1. See §Pending a number.

### Facts the sheet half needs (recorded here, built there)

- The live question's title matches the envelope's question by suffix only once a leading `│ ` is stripped. Markdown is literal.
- Detect the review screen by the body's **last** line (`Ready to submit your answers?`) and the two row labels, never by its first line.
- Cancel declines **every** question, so its copy must say so.
- An empty "Type something." row is never a tap target. Own words go through `POST /api/sessions/:id/dialog/text`.
- A typed row's dialog id changes **while the text call is still in flight**, so the input's state is keyed to the call, not to `dialog.id`.
- `isDialogText` (`shared/api.ts`) is the route's own text rule, so the sheet can disable Send on exactly what the route would refuse `bad-text`. After `echo-failed` the text may be left in the row. The same text, sent again under the dialog id the stream then shows, submits it without typing.
- A multiSelect question arrives as `parsed:false` with `Dialog.multi`: its options with `checked`, the free-text row, the commit row's label and the cursor. The stream re-sends an unparsed dialog whenever its screen repaints under the same id (`sessionws.ts`'s `nextDialogFrame`), so ticks made in the terminal reach the sheet. `POST /api/sessions/:id/dialog/multi` takes the WHOLE set of boxes to leave ticked, never a toggle, so a sheet showing stale ticks still sends the right answer. `isDialogMultiIndexes` (`shared/api.ts`) is the route's own set rule. The set's order is the order new boxes are ticked, which is the order the answer lists them, after any box already ticked.

### Task 2: `--` before literal text, and a dropped line is never silent (D-5046) (done)

**Routing:** band 2, with a band-1 tail: the argv pin updates are mechanical. **Files:** modified `server/src/exec.ts` (`sendLiteral`), `server/src/inject/send.ts` (`sendPrompt`'s type loop, and `type-failed` in `SendResult`), `README.md` (the `/prompt` sentence), `server/test/exec.test.ts`, `send.test.ts`, `routes.test.ts`, `deliverability-parity.test.ts`, `mail-sweep.test.ts`, `ccd-tmux-anchor.test.ts`, and a comment in `ccd-win-size.test.ts`.

**Re-measured first** (tmux 3.7c, a throwaway `-L` server running `cat` in its pane, killed afterwards). Without `--`: `-x probe`, `- item`, `---`, `-- x` and `--foo` exit 1 and type nothing; a lone `--` exits **0 and types nothing**, because the parser takes it as the end of the flags; a lone `-` types. So the `--` is the only thing that saves a bare `--` line, since no return check can see that drop.
