# The delegation spool's first write of an hour, raced, and the race rows' skip count: ruled

- **D-7448 (2026-10-29)** — the delegation spool append's node gate in `ccd/session-hook.sh` (`_hook_spool_append`) probes the bucket's path as `( ! -e "$f" || -f "$f" )`, absence first. Before, it probed `( -f "$f" || ! -e "$f" )`: a hook that probed `-f` while the bucket did not exist yet, and `! -e` after a racing hook had created it, refused the append and wrote no line.
- **D-7449 (2026-10-29)** — the stub tmux in `server/test/delegation-spool.test.ts` (`tmuxStub`) runs `trap '' TERM` just before its reply, so the hook's 2 s bound can no longer split the reply from its `answered` record. A split answer was read as an identity skip, and its run was replayed into a second line.
- **D-7450 (2026-10-29)** — the race rows' lost-append control runs beside one honest skip every time: the slow lookup. It no longer requires all 32 lookups answered before it takes a line out, so a lookup that load times out on its own cannot turn its premise red.

**D-7448.** Two merge-group runs went red in `server/test/delegation-spool.test.ts`. One was the small-cap race row (12 hooks, 12 lookups answered, 12 parses, 1 line missing). The other was the slow-lookup race row (32 hooks, 31 lookups answered, 2 lines missing, 1 skip). Each run had every line whole and valid, so nothing interleaved. The test's verdict, "lost append, not an identity skip", was right.

Measured in a fixture on Ubuntu 24.04 (bash 5.2.21, jq 1.7.1, the CI runner's versions). Twelve hooks append at once to a fresh owner directory each round, under CPU load. About one round in 300 to 600 lost one line. A breadcrumb on every `return 1` of the append named the node gate in each lost line. Every lost hook had answered its lookup, parsed with jq status 0, built a line of the right length and passed the generation re-read. So the gate itself refused it.

The race is inside the one `[[ ]]`. Each operand is its own `stat`. The bucket of the current hour makes one move only, absent to regular file. Prune removes buckets of earlier hours, and nothing else deletes one. So with absence probed first, the gate sees either "absent" or "regular file" and passes both. The old order could see "not a regular file" and then "not absent" for one bucket. The `fresh` test just above it can race the same way, but harmlessly: two first writers both prune, as the block's own PRUNE note says.

The new row in `delegation-spool.test.ts`, "a bucket created by a racing hook between the gate's probes...", reads the gate line from the shipped hook. It runs that line in a spinning checker while a background writer creates each fresh path, and over 300 transitions no evaluation may refuse. Its control runs the same harness with the two probes swapped back. That control must be caught, and it stops at the first refusal. The old order refused about one transition in six, on Linux and on macOS. Before the fix, the row was red on the control: the swapped order was then the new one, and it never refused.

Not changed here: the same idiom guards the history spool's append (`_hs_p`), the join file's rotation target (`jp`) and the history scope marker. Each of those has far less write concurrency than the delegation spool, whose bucket every tool call of a session appends to. They are left for their own change.

**D-7449.** A 100-run check of that fix under load turned up a different red row: "a single run whose pane lookup outlasts its bound is replayed". It failed `exactly one line` with two lines. The stub tmux replied first and wrote its `answered` record second. Under load the hook's `timeout 2` killed the stub between those two steps. The hook already had its pane name and wrote the line, but no record landed. `run` read that as an identity skip and replayed the run, and the replay wrote a second line. The race rows count skips the same way, so there a split answer raised the skip count, and that could excuse a real lost line.

Recording first would be wrong too. A stub killed after its record and before its reply would count an answer the hook never got, and a real lost append would hide behind it. So the stub ignores SIGTERM from just before its reply until it exits. The bound has no `-k`, so `timeout` then waits for the stub. A stub killed before the reply has no reply and no record, and one past that point finishes both. The race rows' slow lookup (`exec sleep 3`) runs before the trap, so the bound still kills it.

The new row "an answer the 2 s bound cuts between the reply and its record..." uses the stub's new `between` seam to put a 3 s sleep after the reply. Without the trap the run was replayed four times and wrote five lines (red). With the trap it writes one line and one record (green).

**D-7450.** The same 100-run check turned up one more red under load: the control "with every lookup answered, a line taken out of the bucket is a lost append" failed `every lookup answered` at 31 of 32. Its premise was that no lookup times out, and shard load can time one out on its own. That is an honest skip, but the row went red before it reached the verdict it exists for. With the slow lookup forced (`instrumentRace(true)`), the old row is red every time at that premise.

The control now forces the slow lookup in every run, so it always runs beside at least one skip. Its premise is that every missing line is a recorded skip, and that holds however many lookups the load adds. It then takes one more line out of the bucket and `assertLanded` must throw "lost append, not an identity skip". A skip is a run that wrote no line, so the lines missing are always at least the skips recorded, and the removed line is one more than any skip can explain. The row keeps what it guarded (the skip count cannot excuse a line that went missing) and adds that it holds next to a real skip.
