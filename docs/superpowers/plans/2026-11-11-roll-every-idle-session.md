# Roll every idle session, and show each session's Claude Code build

## Goal

The operator's ruling of 2026-11-10 reverses the 2026-10-29 rule "always auto-roll all coordinators when they go idle, but never auto-roll any non-coordinators" (D-7443, D-7453): every idle session rolls to the newest Claude Code build as soon as possible, and the console tracks each session's build against the build the roll targets.

## What was read first

- The coordinators-only rule lived in the server, not in ccd. `ccd hibernate --roll` (D-7458) never read the role. The rule was `rollTargetVerdict` (`server/src/coord/rollTarget.ts`), and `rollPass` (`server/src/rollLane.ts`) skipped the whole pass unless the Settings row read `coordinators`.
- The rule was a config switch: `CLAUDE_ROLL_TARGETS` (`shared/claudeVersion.ts`) was `coordinators | off`, with `coordinators` as the default. The `roll_settings` row (migration 34) is seeded `coordinators` at `updatedAt` 0, and every operator write stamps its own time.
- The roll's "behind" test read only the ccrc release: the pane started before `~/.ccrc/installed`. No server code knew a target Claude Code build. Spec §6.2's node file (`~/.ccrc/claude.json`) has a parser but no writer. Each `FleetSession.version` is measured from Claude Code's own live file. Nothing in `pwa/src` showed it (`session/buildAndSpend.ts` notes this).
- Safety the roll already had, all kept: the idle gate (hibernation's ladder at a 90-minute quiet window), one roll a pass (`ROLL_PER_PASS`), the wake budget and its memory gate (D-8122), ccd's re-measure at the act (busy, draft, attached, turn marker, `.no-roll`), the hold-off after a refusal (D-7552), and `$REG/hibernate-disabled`.

## Deviations found

- **D-8276 (2026-11-11)** — every idle session rolls (the 2026-10-29 coordinators-only rule is reversed), a session on an older Claude Code build than the fleet's newest is behind, and the console shows each session's build against that newest build

## Design

- **The switch stays and its default changes.** `CLAUDE_ROLL_TARGETS` is now `all | coordinators | off`, and the default is `all`. `rollTargetVerdict('all', role)` takes every role without reading it. `coordinators` keeps the 10-29 rule as a choice. `.no-roll` opts a session out under every value, and `.no-hibernate` still does not.
- **The seed reads as the default.** A `roll_settings` row whose `updatedAt` is still 0 was written by the migration, not by an operator. `CoordStore.rollSettings` reports it as `seeded`, and `rollTargetsOf` reads a seeded row as the default (`all`). No migration was added. An older build reading the same row still sees `coordinators`, so a rollback falls back to the 10-29 rule and never to rolling nothing. A write over the seed always stamps, so an operator who picks `Coordinators only` keeps it. A row an operator already wrote stays as written.
- **Behind on the build, and what a restart reaches.** Installed is not running (binary-lifecycle spec §2.2, measured): the launcher picks a lane's own recorded build before the highest installed one, so a restart keeps a session on its lane's build until that lane's updater writes a newer one. That spec found seven sessions held on one stuck lane's build. Nothing in ccrc pins a build or sets the launcher's override. So `shared/claudeVersion.ts` has two readings, both measured from the running sessions, which the roll lane and the console share. `fleetClaudeLatest` is the newest well-formed build any awake session runs, and the console tracks every session against it. `laneClaudeLatest` is the newest build an awake session on the same lane (`wrapper`) runs. That build is on disk and is what the lane's launcher picks, so it is what a restart there reaches. `claudeBuildOf` places one row: `current`, `behind`, `asleep` (hibernated) or `unmeasured`. A `behind` row carries `reach`, the newer build its lane runs, or null when its lane runs nothing newer. `claudeBuildCounts` gives the fleet's totals, including how many of those behind are `reachable`. `autoRollVerdict` treats a session as behind on the release (as before) OR behind with a reach. A session behind only another lane's build is never rolled for it, because the restart would cost memory (spec §2.3: about 0.79 GiB net per recycle, and pane OOM kills cluster after restarts) and reach nothing.
- **No roll loop.** `RollSweepMemory.builtFor` records the reach at each roll. A session that is still behind that reach after its restart is not rolled for it again, because another restart would not reach it either. A newer reach asks again. The entry is pruned with its row. The memory lives in the server process, so a server restart (each `ccrc update`) forgets it. That costs at most one more roll per server start, and only for a session whose restart missed a build its own lane already runs. A roll that reaches its lane's build leaves the session with no reach, so nothing asks again.
- **Console.** The card stays a glance. A session on the newest build shows nothing there. A session behind shows one marker, `cc .296 behind` (the patch alone when major and minor match, otherwise the whole build), with the full pair and what happens next in `title`. The title promises a roll only when the session's lane reaches a newer build. Otherwise it says a restart would keep the session on its build and the roll does not restart it for the build. It is the last entry of `MARKER_ORDER`, so any louder marker keeps the card's one slot. It reuses `.sess-unmeasured`'s quiet ink, so there is no new colour pair. The header is the superset: a session on the newest build gets a `Claude Code 2.1.302` fact, and a session behind gets the marker in full. The row reads the newest build from the fleet store (`useFleetStore`), so no prop is threaded. Settings › Automation › Roll idle sessions offers `Every idle session`, `Coordinators only` and `Off`. Under the group it counts the sessions behind against the newest build, says what the setting does about the ones a roll can move, and says the rest stay until their lane's own updater installs a newer build.
- **Widths.** The marker is one short mono word group in the card's existing marker cell, which already fits at every width. The Settings line is a wrapping note. `browser/build-behind.browser.test.ts` measures the card at 390, 1280 and 1920 in both skins and both themes. `browser/roll-idle-card.browser.test.ts` measures the card at the same widths with its third choice and its line.
