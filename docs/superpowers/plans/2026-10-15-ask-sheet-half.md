## The bug

The operator reports that from the PWA only the **first** question of a multi-question AskUserQuestion can be answered, and that wherever a box lets you enter your own text "that doesn't work properly at all". It is equally broken on phone and desktop.

The diagnosis (2026-10-15, re-verified, with corrections that override its first plan where they conflict) found these causes. The server's share is fixed by #417. This branch fixes the rest.

| # | Cause | Fixed by |
|---|---|---|
| 1 | `EnvelopeSheet` renders and wires `questions[0]` only, and the hook envelope wins the display for the whole tool call (it is written whole once and cleared only on PostToolUse). Once the pane moves to question 2 every row is disabled and the other questions render as read-only divs under "answer these in the terminal". | Task 2 (D-5089) |
| 2 | The final "Review your answers" screen (`1. Submit answers` / `2. Cancel`) is not modelled, so even a sheet that followed the pane could not finish a multi-question or multiSelect ask. | Task 2 (D-5089) |

## What the server half provides (#417, on `main`)

- **`POST /api/sessions/:id/dialog/text {dialogId, optionIndex, text}`** (D-5047; client `api.answerDialogText`, `pwa/src/lib/api.ts:1051`). Walks to the free-text row, proves focus (same title, cursor on the row, still the placeholder, footer `to edit in` hint), types after `--`, proves the echo, then Enter. Refusals are `DialogTextRefuseCode` (`shared/api.ts:9920`): `bad-text` (400) and `not-alive`, `stale-dialog`, `not-free-text`, `focus-failed`, `echo-failed` (409). `isDialogText` (`:9902`) is the route's own text rule and `DIALOG_TEXT_MAX` (`:9893`) is 1000. **A retry with the same text, under the id the stream then shows, onto a row already holding exactly that text, types nothing and submits it.**
- **`POST /api/sessions/:id/dialog/multi {dialogId, optionIndexes[]}`** (D-5048; client `api.answerDialogMulti`, `:1058`). The WHOLE set of boxes to leave ticked, never a toggle. It sends a digit only for each differing box (unticks first, in screen order, then ticks in the order asked), proves the ticks, Tabs, and proves the screen moved on. Refusals are `DialogMultiRefuseCode` (`shared/api.ts:9960`); `isDialogMultiIndexes` (`:9937`) is the set rule (non-empty, distinct, 1 to 9).
- **`answerDialog`** (`POST /dialog`) now refuses `free-text-row` and `unparsed-dialog` beside `stale-dialog`, `walk-failed` and `not-alive` (`DialogRefuseCode`, `shared/api.ts:9882`). The sheet's `answer()` still handles every 409 alike (Task 5).
- **`Dialog.multi`** (`DialogMulti`, `shared/api.ts:4035`) on a multiSelect question, which stays `parsed:false`: its options with `checked`, the free-text row, the commit row's word (`Next`, or `Submit` on the last question) and the cursor (an index, `'commit'`, or null). Its id names the question, not its ticks. The stream re-sends an unparsed dialog whenever its screen repaints under the same id (`nextDialogFrame`, `server/src/sessionws.ts:943`), so ticks made in the terminal reach the sheet. A **parsed** dialog is re-sent only on a new id or an enrichment upgrade, so its `selectedIndex` can be stale.
- **`shared/ask-menu.ts`** (L0): `FREE_TEXT_PLACEHOLDER_RE`, `CHAT_ABOUT_ROW_RE`, `EDIT_HINT_RE`, `COMMIT_ROW_RE`, each with one home pinned by `server/test/single-definition.test.ts`.
- **45 recorded Claude Code 2.1.300 screens**, `server/test/fixtures/panes/cc300-ask-*.txt` (36 from the server half's Task 0, 9 from its Task 4), each reading pinned in `server/test/dialog.test.ts`. The measured facts this half needs are the server plan's §"Facts the sheet half needs": the live question's title matches its envelope text by suffix once a leading `│ ` is stripped, and markdown is literal; the review screen is told by its body's LAST line, `Ready to submit your answers?`; Cancel declines every question; an empty `Type something.` row is never a tap target; a typed row's id changes while the call is in flight; after `echo-failed` the same text resubmits.
- **Operator checks still open from #417:** the fleet's Claude Code version, and that the `ctrl+g to edit in …` hint renders on the fleet at all (it needs an external editor to resolve in the session's environment; without it every text answer refuses `focus-failed`). The sheet's `focus-failed` copy says to answer in the terminal if it repeats.

### Task 1: `askLive`, which question the pane is painting, and the review screen (D-5089)

**Routing:** band 3 (it decides which question a keystroke answers): native, the orchestrator reviewing. The readings JSON is band 1 and may be handed off. **Files:** create `pwa/src/session/askLive.ts`, `pwa/test/ask-live-question.test.ts`, `pwa/test/ask-panes.json`, `pwa/test/askPanes.ts`. Modify `shared/ask-menu.ts` (the review rules), `pwa/src/session/EnvelopeSheet.tsx` (it imports `questionCorresponds` from `askLive.ts` instead of defining it; behaviour unchanged in this task), `server/test/dialog.test.ts` (the readings case), `server/test/single-definition.test.ts` (the review rules' home).

**The module** (pure: imports `shared/api` types and `shared/ask-menu` only, no React):
- `questionCorresponds(q, dialog)`, `prefixMatches` and `norm`, moved verbatim from `EnvelopeSheet.tsx:54-77` with their comments.
- `titleMatches(question, title)`: strip a leading `│ ` (and surrounding space) from the pane title, `norm` both, and require a non-empty title that the question ends with. Markdown is literal on screen, so no unescaping.
- `liveQuestion(ask, dialog): number | null`. The candidates are the questions with options that correspond by labels (`questionCorresponds`). **Exactly one candidate wins on its own**, title or no title. Two or more are a tie, broken only by `titleMatches`: exactly one survivor wins, otherwise null. No candidate is null. (The verified correction: a title rule made mandatory would turn a question 1 that answers today into "can't be matched" whenever Claude Code renders the text differently; question texts are unique per the tool's schema, so a tie can always be broken.) A one-question envelope therefore keeps today's rule exactly. A `multiSelect` question is not a candidate in this task (Task 4 lifts that for `Dialog.multi`).
- `namedQuestion(ask, dialog): number | null`: the one question whose text `titleMatches` the dialog's title, else null. It names an unparsed question (a multiSelect one) that labels cannot reach.
- `isAskReview(dialog)`: parsed, exactly two options reading `Submit answers` and `Cancel` (`REVIEW_SUBMIT_ROW_RE`, `REVIEW_CANCEL_ROW_RE`), and the body, `trimEnd`ed, ending in `Ready to submit your answers?` (`REVIEW_READY_RE = /ready to submit your answers\?$/i`).
