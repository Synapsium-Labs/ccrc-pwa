# Coordinator-first routing — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Every task is one PR, cut from current `origin/main`, and follows superpowers:test-driven-development: the red test first, seen failing for the reason named; then the change; then green; then the task's mutation table RUN, never read. Steps use checkbox (`- [ ]`) syntax. Tasks 11 and 16 are not PRs: Task 11 is a verification on a throwaway rig, Task 16 an operator act that no session runs. Workers do not edit this file's §Deviations found: a further departure is named by slug in the task's report, and the coordinator allocates its number.

**Spec:** `docs/superpowers/specs/2026-10-17-coordinator-first-routing-design.md` (the measurements, the rulings, the design and the invariants). This plan does not restate the design's reasoning; read the spec section named in each task first.

**Branch of this file:** `docs/coordinator-first`, cut from `origin/main` `b6ce2eb8`. Each task's branch is its own (`fix/…` or `feat/…`), cut from `origin/main` at dispatch.

**Status:** rev 0 (2026-10-17), for adversarial review. Task 0 is done in the commit that adds this file.

**Operator rulings this plan builds on** (2026-10-17; the spec's §3 has them verbatim):
- only dispatched workspaces route to a coordinator; every session the operator creates is a coordinator (Tasks 8, 9);
- while a coordinator holds a child's question or prompt, the child shows a quiet "with coordinator" state and leaves Needs-you (Task 6);
- a daily digest of what coordinators decided in the operator's name, correctable by mail (Task 15);
- 180 s, late answer wins (Tasks 3, 5, 13);
- children's permission prompts are resolved by the coordinator: allowed, or denied when harmful (Tasks 10 to 16).

**Coordinator calls this plan builds on:** the first-sighting race (Task 4); late answer wins with `declined` (Task 3); one single-select question per call, agent first (Task 1), and the lane widened to the operator's own answer route (Task 7); the deadline and the ready-to-run command in the parent's mail (Task 5); the empty push body (Task 2).

**Citations** are to `origin/main` `b6ce2eb8`, written `≈:` and always with a function or constant name. Every path below was checked to exist there, except the files a task says it creates. **[B]** marks a reading of an installed Claude Code 2.1.302 binary (read-only `strings`).

**Depends on is structural.** Task 4 edits the hold path Task 3 changes and asserts `declined`; Task 6 reads Task 5's `notifyAt`; Task 13 reads Task 6's field for approvals, Task 10's classifier and Task 12's verbs; Task 15 reads Task 13's table.

**Lanes, in this repository's terms.** AGENT-FIRST is `ccrc rollout`'s default order (the fleet box, then the server box). A skill reaches a home only through `ccrc update`'s install spine (`_inst_skills`), never through a server-only deploy; doctor's `skills` check measures it. A fleet box ahead of its server is safe for Tasks 1, 8 and 14: the server reads nothing new from them until its own half ships, and its half reads `ccd caps` first.

**Self-gating (Task 12).** Task 12 changes what an existing event does (a PermissionRequest that today prints nothing may now print a decision), and is safe only behind a server that writes rulings through Task 13's guard. No rollout form can hold that for every mover (the PWA's one-tap and the update control plane's `auto` dispatcher move fleet nodes first, `deploy.sh` and a hand-run `ccrc update` follow no order, a server can be rolled back). So it uses the working-state plan's mechanism (D-5232, its Task 9b), unchanged:
- the server advertises capability words in `/health`'s `caps` (`SERVER_CAPS`, one home in `shared/api.ts`); Task 13 adds `coord-approvals-v1`, and is cut after Tasks 6, 10 and 12, so no server advertises it without the guard, the hold and the verbs;
- the fleet box records the words of the server it talks to in `~/.ccrc/server-caps` every minute, and the hook waits only while that file is whole, at most 180 s old, and lists `coord-approvals-v1`; otherwise it does exactly what it does today;
- on top of the word, the hook waits only while the server-written `$REG/<id>.approval-wait` exists (spec §6.6: only on a verified Claude Code version) and `$REG/approvals-live` exists (Task 16), and never while `$REG/approvals-disabled` exists.

So any mover in any order is safe, and a server rolled back below the word turns the wait off within one sync period. **If working-state Task 9b has not merged when Task 12 is cut, Task 12 waits for it**; it does not ship its own copy of the mechanism.

A server-lane task changes nothing on the fleet box.

## Global constraints

`CLAUDE.md` is the authority. This is its working subset for this plan.

- **Public repository.** Fixtures use neutral names: session ids `lane-a-project-a` and `project-a-quiet-basin` (child), `project-a-calm-mesa` (parent), wrappers `lane-a`/`lane-b`, agent ids such as `a0000000000000001`. No hostnames, accounts, project names, absolute home or scratch paths, emails, or anything read from a transcript. Guard-corpus commands are written for the corpus, never copied from a fleet transcript.
- **Hook payload fixtures copy a committed real shape.** A PreToolUse payload copies the key set of the PreToolUse events in `server/test/fixtures/delegation/2.1.280/agent-plain.json` (main: `session_id`, `transcript_path`, `cwd`, `prompt_id`, `permission_mode`, `effort`, `hook_event_name`, `tool_name`, `tool_input`, `tool_use_id`; a subagent's adds `agent_id`, `agent_type`). **No committed capture has a PermissionRequest yet.** Until Task 11 commits one (`server/test/fixtures/delegation/2.1.302/permission-main.json` and, if reproduced, `permission-subagent.json`, in the existing capture format), a PermissionRequest fixture is the PreToolUse key set with `tool_use_id` removed and `permission_suggestions` added, marked DERIVED with its source ([B]: the PermissionRequest input schema is the common base plus `tool_name`, `tool_input`, `permission_suggestions`, `mcp_server`, and has no `tool_use_id`). Every such fixture is replaced by the captured shape in the PR after Task 11.
- **Commands.** From inside the package, in the foreground, tool timeout at least 600000 ms, one suite process at a time: `./node_modules/.bin/vitest run --maxWorkers=2 test/<file>.test.ts`. Never bare `npx vitest`, never the full server suite. Typecheck with `./node_modules/.bin/tsc --noEmit -p .` in `server/` and `pwa/`. Every task also runs `single-definition`, `deviation-refs` (after `git fetch -q origin main`), `dtbd` and `topology-clean`, and `routes` when it touches a route.
- **Fixture HOMEs only.** Every `ccd` and hook test runs under `makeCcdHarness` (`server/test/ccdWsHelpers.ts`) with stubbed `tmux`, `systemctl` and `journalctl`. Nothing in a test touches the live `$HOME`, tmux, `~/.cc-sessions`, `~/.cc-limits` or a `claude-session@*` unit.
- **The hook.** New marker and decision logic goes in the hook's tail, below `ccd/session-hook.sh:2900` (`marker-logic-in-the-tail`, D-3615); the PermissionRequest arm (≈:2920) only sets a flag the tail reads. The role card (Task 8) is a card emitter beside `_hook_hold_card` (≈:804), where every card lives. New hook tests go in new files with the harness copied from `server/test/session-hook-turnmark.test.ts`. The PostToolUse budget (p95 of 20 runs under 150 ms) holds; the PermissionRequest wait is not on that path.
- **`ccd/ccd` carries a generated marker** (`# ccrc:generated 1 sha256=…`, `shared/mark.mjs`). Re-stamp it after every edit and verify it independently; keep the executable mode.
- **Mutation discipline.** Every guard ships with a test that goes RED when the guard is deleted and when it is made wrong. Apply each mutant to the uncommitted change, run the named suite alone, record the red line in the PR, restore the file and compare it byte for byte.
- **Wire discipline.** New fields are additive and read through one reader each; absent means the old behaviour; `reviveFleetSession` computes each one. No new `SessionBucket` or `SessionLifecycle` member. `FLEET_PROTO` stays 1. A new refusal code joins its union and its map in `shared/api.ts`, never spelled at a call site.
- **Single definition.** Registered in `server/test/single-definition.test.ts`: `ASK_GRACE_MS` (already one home; Task 5 re-pins its value); `AskState`'s map with `declined` (Task 3); `answerableAsk` (Task 7); `askPushBody` (Task 2); `APPROVAL_STATE_MAP`, `APPROVAL_HOOK_WAIT_S`, `APPROVAL_HOOK_VERSIONS` and the approval file grammar (Tasks 12, 13); `approvalClass` and its class map (Task 10); `SESSION_ROLE_MAP` (Task 8); `DIGEST_HOUR_UTC` (Task 15). The hook's bash spellings (the forbidden match, the wait bound, the rule-file grammar) are documented second copies, each held equal to the TypeScript one by a test that iterates over it.
- **SAFETY.** No session runs an operator act. Task 16 names, in its approval request, the SAFETY rule it is taken under: "NEVER touch tmux, `~/.cc-sessions`, `~/.cc-limits`, or `claude-session@*.service` directly" (the arm marker lives in `~/.cc-sessions`, so only the operator places it, by hand). No task adds a writer for `approvals-live` or `approvals-disabled`.
- **Branches and commits.** One PR per task. Never push from a worker; the coordinator lands through the merge queue. End commit messages with the attribution trailer the run's system prompt gives.
- **Deviation ledger.** D-5289 to D-5302 are issued and defined once, in §Deviations found. No tracked file carries a concrete placeholder of the `D-TBD-<slug>` form (`dtbd.test.ts`).

### Issued 2026-10-17 and defined here

- **D-5289** — `asks-late-answer-wins` (Task 3): a lapse at the deadline still fires the operator's push, but the row stays answerable by its parent until the operator acts: `takeAskForAnswer` and `heldAskFor` take `held` or `released`, under the `askAt` instance guard, and a late parent answer replaces the operator's notification under the same tag. It departs from the lane spec's rule that a lapse ends the parent's turn, because 3 of 37 measured child asks lost a parent answer that came 16 s to 4.5 min after the lapse. An older server reads `declined` as `unknown`.
- **D-5290** — `asks-first-sighting-hold` (Task 4): the amendment branch, where an actionless dialog gains its envelope, tries the parent hold with the same checks as the first sighting; and the first actionless raise is deferred up to two ticks while hookstate is not yet `waiting`. Approvals are never deferred. It closes the race in which 6 of 37 measured child asks reached the operator without a hold.
- **D-5291** — `one-question-per-ask` (Task 1): worker clause 5 and reviewer clause 9 tell a child to ask one single-select question per AskUserQuestion call and to split independent decisions, so its parent can rule each. Shipped agent first; clause counts unchanged.
- **D-5292** — `no-variable-rm-in-subagent-scripts` (Task 1): worker clause 5 and reviewer clause 9 tell a child never to delete through a variable in a subagent's shell script, using a literal path under its scratch directory or leaving temp directories to the reaper. The shape accounts for 18 of 27 measured human-allowed child permission prompts.
- **D-5293** — `ask-hold-follows-the-answer-route` (Task 7): the parent hold's eligibility is no longer its own predicate but `answerableAsk`, the one rule `askActions` and `answerAsk`'s refusal both read, and the parent's answer route accepts the operator route's body shape.
