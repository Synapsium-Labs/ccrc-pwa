# Accounts connect A24: the Codex lane's add arm

**Goal:** plan Task A24 of `2026-10-18-accounts-connect.md` (spec §7.2, §9 row 5, §11, G2, G20; D-5519, N4). A ChatGPT lane stops being a hand edit of the roster. `ccrc account add --provider openai` makes it, `remove` deletes its sign-in folder, and Sign in again keeps the old sign-in until the new one has passed its check. No screen changes: A25 is the sheet.

**Before this change:** `add --provider openai` refused `external-provider-use-declare`, so a Codex lane was a roster edit with two ports and a folder chosen by hand. `remove` kept `exec.authDir`, so a re-added id could inherit the old sign-in (G20). An attempt on a Codex lane ran `ccrc codex login <id>` over the lane's own folder, which answers `already-signed-in` for a present credential, so Sign in again did nothing on a lane whose token was still there.

**Change:**
- `ccd/ccrc`:
  - `_acct_codex_pick`, under the placement lock: `codex-runtime-absent`, naming `ccgpt-runtime build`, unless `ccgpt-runtime python` resolves; two ports from `CCRC_ACCOUNT_CODEX_PORT_BASE` (14100) that no roster row names and nothing answers on, `no-free-port` otherwise; a folder `.local/share/ccrc/codex/<id>-<rand6>`.
  - `_acct_add` hands those to `check-add` and runs `ccrc models <id> init codex` after the lane state. `--credential` refuses `credential-not-managed` before it is read.
  - `_acct_install_codex`, reached by `set --method openai-login --attempt <a>`: the check, the library's `install`, and a first sign-in's `ccrc models refresh`. Each status of the probe's `--check` answers a code of its own.
  - `ccrc codex login <id> --scratch`, an attempt's: the sign-in goes to `~/.ccrc/auth-scratch/<id>/codex`, once the library has read the lane's own file (`--over`). Exit 5 is a file no sign-in can land on.
  - `remove` deletes the lane's `exec.authDir`, unless `--keep-codex-auth` or `--keep-credential`, and only on `auth-dir-fate`'s `delete`. `--delete-codex-auth` is accepted beside them, as the agent's builder spells it, and the two opposite flags refuse `bad-argument`. It also measures whether the folder held a sign-in, for `atProvider`.
- `ccd/ccrc-models-probe`: `--check`, an exit status that says how far the run got. Every other caller still reads 1 for any failure.
- `deploy/account-op.mjs`: `check-add` takes `--proxy-port`, `--litellm-port` and `--auth-dir`, refuses `authdir-occupied`, and its closing `rosterAdmits` judges the codex row; `addedEntry` assembles it. `removed` takes `--codex-sign-in none`, and answers no `atProvider` row for it. `auth-dir-fate` judges a lane's folder after the `drop`: `delete`, `outside` or `named`.
- `shared/roster.ts`, `shared/providers.ts`: the `exec.authDir` sentences no longer say ccrc never reads or destroys what is there.
- `ccd/ccgpt-auth.py`: `install --from <dir> --auth-dir <dir> --lane <id>` (`install_signin`), through `_commit_signin`, which is `sign_in_device`'s step 5 moved out whole. `signin --over <dir>` reads that folder before any request, and exit 5 on either verb is a lane's file the library will not write over, and nothing else (`LaneFileUnreadable`, `LaneFileForeign`).
- `ccd/ccd-account-auth`: an attempt's Codex sign-in runs `--scratch` and then `_auth_install openai-login`; exit 5 ends it on `lane-credential-refused`.
- `ccd/ccd`: `cmd_caps` prints `account-codex-v1`.
- `README.md` documents the verb, the install and the removal, in "Connecting an account" and the Codex section. `ccrc --help` names `set --method openai-login`, `add --provider openai` and `--keep-codex-auth`.

**Tests:**

Its last group runs the check on the real fetch arm with no fixture seam: `probeRuntime`'s interpreter records the credential folder and bearer the check used, and refuses every socket. Every refusal the check can answer has a case there. Two more groups pin what a review measured: a folder another lane reaches, in each spelling, nested and through a link, end to end and at `auth-dir-fate`; and a lane file no sign-in can land on, which publishes no code and sends no request. The last review's two have cases too: a folder holding only a crash checkpoint keeps the provider row, and a folder or lock that fails blames no lane file, at the install and after an approved code.
- Extended: `server/test/codex-auth-cli.test.ts` (`install`, `signin --over`), `server/test/ccdCapTokens.ts`, `server/test/models-probe.test.ts` (`--check`, each status beside the exit 1 of a run without it).
- Changed: `server/test/ccrc-account.test.ts`. The refusal row that pinned `external-provider-use-declare` now pins `codex-runtime-absent`, the same input's answer on that fixture, and the two removal cases that kept the OAuth pass `--keep-codex-auth`. Both follow from the plan's ruling that the folder goes by default; no assertion was dropped.

## Decisions

- **D-8016 (2026-11-04)** — `codex-add-as-built` (accounts plan Task A24; spec §7.2, §9 row 5, §11; D-5519, N4): the as-built decisions of A24, and where it departs from the plan's wording.
  1. **`ccrc models litellm <id>` moves from `add` to the first sign-in.** Spec §7.2 step 3 runs it in `add`. Measured, it refuses there: `never-probed`, because it renders from the lane's model catalogue, and only a signed-in lane can fetch one. So `add` runs `models <id> init codex` alone, and `_acct_install_codex` runs `ccrc models refresh <id>` once the credential is in, when `litellm.yaml` is absent. Without it the `check` of §7.2 step 7 would stop at `litellm-unrendered` until the hourly refresh. A refresh that fails refuses nothing: the credential is in, the hourly refresh renders it, and `check` names it until then. A lane that has its config is not refreshed, so Sign in again restarts no tier (§9 row 5).
  2. **The check of a scratch sign-in is the lane's model catalogue, fetched on that credential.** It is the model probe's own fetch, a real answer from the backend. The fetch is told the scratch folder and writes into scratch, so a refusal changes nothing of the lane's, its catalogue included. Only the code reaches the status file, so the refusal says how far the check got, read from the probe's `--check` exit status: 3, nothing was sent and the credential is why, is `no-credential`; 4, a request went and got no usable answer, is `token-unverified`; 5, the provider answered with a body the normaliser refused, is `codex-answer-unreadable`; anything else, the check did not finish, is `codex-check-unrun`. No runtime is `codex-runtime-absent`, read before the probe runs, because its remedy is the code. Only `token-unverified` blames the provider, and it says "did not accept or did not answer", because a rejected credential and an unreachable backend are not separated, so no `key-rejected` is claimed. An answer the normaliser refuses is not installed: a redirect to a sign-in page can also end in a 200, so it proves nothing of the credential. `--check` is a flag and not a change to the probe's exits because every other caller, and the suite, read any failure as 1.
  3. **The move is the auth library's.** The plan's Files list has no `ccd/ccgpt-auth.py`, but it predates the codex-bridge spec's §2.6, and the library is now the one writer of `auth.json`. A bash copy would be a second writer that holds neither the library's lock nor its checkpoint. `install_signin` holds its own offline checks too (present, unexpired, not barred, 0600 or tighter, this user's), since it is a verb of its own. Under `set --method openai-login` the check runs first and answers an absent, expired or barred sign-in itself (2), so what reaches these gates is a mode or owner failure, or a sign-in that changed after the check. They refuse with `login-failed` at exit 4, which the verb answers as `no-credential`. It adds no refusal word, because the bridge's error table holds every word of the library and this one never reaches a tier.
  4. **Every attempt on a Codex lane signs in to scratch, a first sign-in too.** The plan names Sign in again. The helper never reads the authDir, so it cannot tell the two apart, and it need not: one path, and a device flow that always runs. `ccrc codex login <id>` with no attempt stays as it was.
  5. **`remove`'s default is delete** (spec §11 step 4, Q11; the plan's mutant "remove keeps the authDir by default"). The route sends no field today and deletes, which is the UI's default. `--keep-codex-auth` is the CLI's, and `--keep-credential` implies it, because a Codex lane's credential is that folder. A25's unticked line needs a way to say keep: it adds a `keepCodexAuth` field to `shared/account-argv.ts` and takes `deleteCodexAuth` on the route. That is agent-side, so that PR is agent-first.
  6. **The guard is the path, not who made the folder.** Nothing on the box records who made one, so a hand-written row under `.local/share/ccrc/codex/`, the path the README's example and the roster's remedies give, is deleted by default as an added lane's is, with `operator-steps` empty. Every Codex lane older than this verb is hand-written, so this applies to them until A25's sheet line shows it, and the CLI's `--keep-codex-auth` keeps one. The default itself is Q11's. Two folders stay whatever was asked: one outside that home, and one another lane's row still names, which the roster does not refuse. Each is reported in `kept` and named in `operator-steps`. The README and the `shared/roster.ts` remedies say this, and no longer say that ccrc never reads or destroys what is in the folder. Item 14 says how the second is told.
  7. **`account-codex-v1` is in `ccd caps` and not yet in `ACCOUNT_CAPS`.** N4 lists it for A24. As with `account-auth-v1` (D-7849 (1)), the word joins `ACCOUNT_CAPS` with the screen that uses it, A25, so `connect.caps` does not offer a sheet that does not exist.
  8. **The usage timer waits.** `_inst_codex_usage` is the one converger of `ccrc-codex-usage@<id>.timer`, and it needs the install spine. `add` does not enable it, and says so in `operator-steps`. The next `ccrc install` or `ccrc update` does.
  9. **`external-provider-use-declare` is retired.** `openai` was the one provider `add` could not generate, so the refusal has no input left. `declare --provider openai` is unchanged.
  10. **The growth check.** `ccd/ccrc` grows past the 40-line limit, measured +109 net code lines, so this PR adds the waiver `server/test/growth-waivers/D-8016-ccd-ccrc.json`.
  11. **Deploying this restarts each `litellm`-mode Codex tier once.** A tier's `.started` record hashes the placed auth library, so a new library reads as stale and `_inst_codex_tiers` restarts it, as for any change to that file. In-flight turns fail once and retry.
  12. **`atProvider` names a sign-in only where the folder may hold one.** `remove` asks the library before the delete, and a folder it reads `absent` with nothing at its checkpoint path answers `--codex-sign-in none`, so `removed` lists no row: the lane `add` leaves, and the same lane after a cancelled first sign-in. `read` looks at `auth.json` alone, so a crash between a checkpoint's fsync and its rename on a first sign-in reads `absent` beside a whole sign-in, and only a settle under the lock would promote it. Anything at that path keeps the row, for the reason `incomplete` does: that record may hold a refresh token. A library that cannot answer, or names no checkpoint path, keeps it too. A folder somebody deleted by hand reads `absent` as well, since nothing records that a sign-in ever existed.
  13. **An attempt now needs the Codex runtime.** `ccrc codex login` still does not, but the check runs on it, so an attempt on a box without one ends `codex-runtime-absent` after the operator approved the device code. Only a hand-written lane can meet this, since `add` refuses without a runtime. Refusing at `auth-start`, before the device flow, is left for A25, which owns the sheet that would show it.
  14. **A folder another lane reaches stays, however the row spells it.** The roster admits several spellings of one folder (`codex//<x>`, `<x>/.`), so a string compare missed them and deleted a folder another lane still named. `deploy/account-op.mjs`'s `auth-dir-fate` resolves both paths, and compares them through their symlinks too, since that is where a credential is. It answers `named` for the same folder, one inside it and one around it. The folder's own last component is not followed, because `rm` removes a link there and not what it points at. A folder is deleted only on `delete`: an op that fails, or answers nothing or a word it does not know, keeps it and says so in `operator-steps`, since a delete cannot be taken back. The op is node and not jq because a symlink has to be resolved, and it takes the home check too, so `<home>/.` is `outside` and `<home>/link/x` that leaves the home is `outside`.
  15. **The first ChatGPT lane on a box takes `ccgpt-runtime build`.** `_inst_codex_runtime` builds nothing until the roster names a codex lane, and `add` will not write that row without a runtime. So `add` is not the whole of the first lane, and the refusal and the README name the step that breaks the loop: `ccgpt-runtime build`, which reads no roster. Building at `ccrc install` on a box with no codex lane was rejected: it would put minutes of pip and a LiteLLM environment on every box, for a lane most never have, and the install suite pins that the builder is not run there. A25 owns what the sheet does here, since a sheet has no shell.
  16. **A lane's file no sign-in can land on refuses before the code.** An attempt signs in to scratch, so the library's `_refuse_signin` would first meet the lane's file at the install, after the operator approved a code. `signin --over <lane folder>` reads it first, with no lock and nothing written, and the attempt ends `lane-credential-refused` with no request sent and no code published. The install reads it again, and a file that went bad during the flow gets the same code, not `credential-write`. Both are exit 5, which only `--scratch` and the library's `install` can return, so `ccrc`'s 0/1/2 table holds for every other caller, as `ccrc-models-probe --check` keeps its statuses to itself. A crash checkpoint beside a bad lane file is not settled by this read, so that double fault refuses where the commit might have healed it. **Exit 5 is that reading and nothing else.** `Unreadable` also answers a folder or a lock `held` could not make, on any folder, and a checkpoint that cannot be read, none of which says anything of the lane's file, so the two readings raise subclasses of their own, `LaneFileUnreadable` and `LaneFileForeign`, and `main` keys on those. A lane folder or lock that fails at the install is exit 1, `credential-write`. A scratch folder or lock that fails, or a bad file in scratch, is exit 1, an ordinary failed sign-in, and `ccrc codex login --scratch` says the lane's folder is as it was, not that the lane is signed out. So `--over` exits 5 only before any request, and "no code was asked for" holds wherever it is said. The install reads the lane's file before the lock, because a checkpoint's settle under the lock would refuse the same file as a plain `Unreadable`; a file that goes bad between that read and the lock is `credential-write`, whose line still names it.
