# Console speed — Implementation Plan

> **For agentic workers:** one PR per task. The six tasks build in files that overlap only where §Landing order says; it also says which steps wait for another task, or another plan's task, to merge. To execute a task, REQUIRED SUB-SKILL: superpowers:subagent-driven-development, with superpowers:test-driven-development for every red-first step. Steps use checkbox (`- [ ]`) syntax. Workers do not edit this file's §Deviations found. A departure is named by slug in the task's report; the coordinator gives it a number. A worker never allocates.

**Goal:** The console stops feeling stuck. The watcher's tick does far less work and sends the fleet frame as soon as the list is assembled; per-request routes serve what the last tick measured, with an age; the app notices a dead socket within about 30 s, puts a time limit on reads, keeps each screen's last view while it reloads, and loads the big screens only when opened. After a release it reloads at the next move between screens, never in the first seconds back; on a cold start the Waiting on you page and an opened item draw the list last saved on the device, marked as not current, with acting blocked until live data lands. Then a measurement pass reads the new timers.

**Architecture:** On the server, the watcher (L4) decides per row whether to read it (a pure L1 decider), reads tmux once per tick through `exec.ts`'s `Tmux` (L3, the one server file that names tmux), and publishes what it measured through getters stamped with the listing time. Routes (L4) read those getters under the one freshness bound that already exists (`FLEET_ROWS_MAX_AGE_MS`, `lifecycle.ts:149`) and fall back to today's reads. In the app, `ReconnectingSocket` gains a watchdog armed by a server heartbeat frame, `request` gains a GET time limit, and one in-memory module keeps the last answer per query.

**Tech Stack:** TypeScript (ESM), Fastify, `node:sqlite` (`CoordStore`, synchronous), the agent link (`ws`), React and Zustand in `pwa/`, vitest (jsdom and the Chrome browser config).

**Spec:** `docs/superpowers/specs/2026-11-04-console-speed-design.md` (D1 to D16 agreed; D15 and D16 are the operator's rulings on items 33 and 34). Investigation reports of 2026-11-04 (app, server, agent link), summarised in the spec's §1. Main measured at `1d5b09e01`.

## Review Focus

1. **A stopped row that comes back to life.** A cold row whose session restarts must be read in full on the first tick its session appears in the tmux listing, never 30 s later. Expected: hot on that tick, its record fresh, its status live. Pinned in S1 (`registry-row-temperature.test.ts` "a cold row named live by the listing is hot", and `tick-cold-rows.test.ts` "a restart is seen on the next tick").
2. **A dropped tmux listing that folds to "dead".** A listing that fails, times out or prints a line that does not parse must not read as every session gone. Expected: that tick asks each row the old way (`sessionVerdict`, `panePid`) and logs once; no row goes from live to dead because the listing failed. Pinned in S1 (`exec-pane-listing.test.ts`, `tick-pane-listing.test.ts` "a failed listing falls back per row").
3. **A stale cached record after a swap or a rotation.** A swap rewrites `.uuid` and `.wrapper`; a rotation moves the transcript. Expected: the swapped row is hot (live) or its key changes (mtimes), so its record is fresh on the next tick; `row:<id>` fires; an open chat re-resolves and sends `rotated` exactly as today. Pinned in S1 (`registry-row-cache.test.ts` "a rewrite in place changes the key") and S2 (`sessionws-watcher-facts.test.ts` "a swap re-resolves within one row event").
4. **A watchdog flapping on a slow but live link.** A tick that takes 20 s, or a quiet fleet that sends no fleet frame for an hour, must not close the socket. Expected: the beat comes from a per-socket timer independent of the tick, the watchdog arms only after the first beat, and any message resets it. Pinned in S2 (`ws-beat.test.ts`) and C1 (`ws-watchdog.test.ts`).
5. **A timeout aborting a slow but valid read.** A read the server legitimately bounds above 20 s must not be cut off, and a POST must never time out by default. Expected: the default applies to GETs only, the reads with longer server bounds pass their own limit, and a timeout is a distinct `ApiTimeout`, never a generic failure. Pinned in C1 (`api-timeout.test.ts`).
6. **A reload that still lands in the first seconds back.** A phone returns, the update check finds a release, and the new worker takes over a few seconds later. Expected: the activation alone never reloads; a move inside 15 s of a return, or on a hidden page, holds; only the block screen and a failed lazy chunk reload at once. Pinned in C3 (`reload-gate.test.ts`, `reload-on-move.test.ts` "after an activation, navigate in the first 15 s back pushes as today").
7. **The old build stranded under the new worker.** While a reload is pending, the old build runs and its cached chunks are gone (the server answers a missing asset with `index.html`). Expected: a move loads the new path as a full page and is never drawn in the old build first, and a failed chunk while pending reloads at once. Pinned in C3 (`reload-on-move.test.ts` "after 15 s back, navigate to another screen calls go once", "vite:preloadError while pending reloads").
8. **An act sent from a saved copy.** Expected: no tick, dismiss or secret goes out until the live list lands, and `waiting` is never filled from the copy, so every reader that asks whether the page has heard the list answers as today. Pinned in C4 (`waiting-saved-copy.test.tsx` "clicking a disabled act sends nothing", `stores.test.ts` "a cold store hydrates waitingSaved and leaves waiting null").
