# Console speed — Implementation Plan

> **For agentic workers:** one PR per task. The four tasks build in parallel, in disjoint files; §Landing order says which two final steps wait for another task to merge. To execute a task, REQUIRED SUB-SKILL: superpowers:subagent-driven-development, with superpowers:test-driven-development for every red-first step. Steps use checkbox (`- [ ]`) syntax. Workers do not edit this file's §Deviations found. A departure is named by slug in the task's report; the coordinator gives it a number. A worker never allocates.

**Goal:** The console stops feeling stuck. The watcher's tick does far less work and sends the fleet frame as soon as the list is assembled; per-request routes serve what the last tick measured, with an age; the app notices a dead socket within about 30 s, puts a time limit on reads, keeps each screen's last view while it reloads, and loads the big screens only when opened. Then a measurement pass reads the new timers.

**Architecture:** On the server, the watcher (L4) decides per row whether to read it (a pure L1 decider), reads tmux once per tick through `exec.ts`'s `Tmux` (L3, the one server file that names tmux), and publishes what it measured through getters stamped with the listing time. Routes (L4) read those getters under the one freshness bound that already exists (`FLEET_ROWS_MAX_AGE_MS`, `lifecycle.ts:149`) and fall back to today's reads. In the app, `ReconnectingSocket` gains a watchdog armed by a server heartbeat frame, `request` gains a GET time limit, and one in-memory module keeps the last answer per query.

**Tech Stack:** TypeScript (ESM), Fastify, `node:sqlite` (`CoordStore`, synchronous), the agent link (`ws`), React and Zustand in `pwa/`, vitest (jsdom and the Chrome browser config).

**Spec:** `docs/superpowers/specs/2026-11-04-console-speed-design.md` (D1 to D14 agreed). Investigation reports of 2026-11-04 (app, server, agent link), summarised in the spec's §1. Main measured at `1d5b09e01`.

## Global Constraints

- The repository is public: no private names in code, fixtures, commits or PRs. Fixtures use `lane-a`, `project-a`, `sess-a`.
- Wire changes are additive only; `FLEET_PROTO` stays 1. A new field or frame is read through one reader, and its absence means today's behaviour.
- `shared/*.ts` imports nothing, not even `node:*`.
- Decide in L1, act in L4. The row-temperature decider, the pane-listing parser, the release window and the watchdog's next step are pure functions with their own tests.
- `coord.db` stays synchronous; no async wrapper over `CoordStore`.
- tmux is named only in `server/src/exec.ts` (and ccd). No new exec grant: the listing uses the granted `list-panes` prefix with literal tokens.
- Consolidate, don't duplicate: the freshness bound is `FLEET_ROWS_MAX_AGE_MS`; the run archive's one owner is the fleet store; query answers' one owner is `screenCache.ts`. A second mechanism needs a recorded reason in the PR.
- Characterization tests first when moving code: green on `main` against the old code; the move commit changes only imports; an intended behaviour change is a commit of its own.
- Every new guard ships with a test that goes red when the guard is deleted (the mutants listed per task), measured before and after and recorded in the PR.
- A file the growth check lists (`watch.ts`, `store.ts`, `server.ts` among them) grows only as far as the check allows; new logic goes in a new module with a one-line call site (run `GROWTH_CHECK=armed` before the first push).
- No `D-7987` to `D-7990` reference in shipped source until this plan is on `main`; the deviation-refs census reads main's ledger. Use the plan's task name in comments until then.
- The new client cache is memory only. It writes no `localStorage`, so `census-w7`'s storage owners are unchanged.
- Gates run through `ccrc test`, one at a time: `ccrc test --heavy -- ./node_modules/.bin/vitest run <file>` from inside the package for a suite, `ccrc test --light -- …` for a single small file. Never two heavy runs at once. Any PWA layout change (C1's lazy screens) runs the whole browser suite (`npm run test:browser`) through `ccrc test --heavy` and carries the `full-ci` label.
- Mail before every push and wave-done: a queued ruling can change a step.

## Review Focus

1. **A stopped row that comes back to life.** A cold row whose session restarts must be read in full on the first tick its session appears in the tmux listing, never 30 s later. Expected: hot on that tick, its record fresh, its status live. Pinned in S1 (`registry-row-temperature.test.ts` "a cold row named live by the listing is hot", and `tick-cold-rows.test.ts` "a restart is seen on the next tick").
2. **A dropped tmux listing that folds to "dead".** A listing that fails, times out or prints a line that does not parse must not read as every session gone. Expected: that tick asks each row the old way (`sessionVerdict`, `panePid`) and logs once; no row goes from live to dead because the listing failed. Pinned in S1 (`exec-pane-listing.test.ts`, `tick-pane-listing.test.ts` "a failed listing falls back per row").
3. **A stale cached record after a swap or a rotation.** A swap rewrites `.uuid` and `.wrapper`; a rotation moves the transcript. Expected: the swapped row is hot (live) or its key changes (mtimes), so its record is fresh on the next tick; `row:<id>` fires; an open chat re-resolves and sends `rotated` exactly as today. Pinned in S1 (`registry-row-cache.test.ts` "a rewrite in place changes the key") and S2 (`sessionws-watcher-facts.test.ts` "a swap re-resolves within one row event").
4. **A watchdog flapping on a slow but live link.** A tick that takes 20 s, or a quiet fleet that sends no fleet frame for an hour, must not close the socket. Expected: the beat comes from a per-socket timer independent of the tick, the watchdog arms only after the first beat, and any message resets it. Pinned in S2 (`ws-beat.test.ts`) and C1 (`ws-watchdog.test.ts`).
5. **A timeout aborting a slow but valid read.** A read the server legitimately bounds above 20 s must not be cut off, and a POST must never time out by default. Expected: the default applies to GETs only, the reads with longer server bounds pass their own limit, and a timeout is a distinct `ApiTimeout`, never a generic failure. Pinned in C1 (`api-timeout.test.ts`).

## Landing order

Rollout: the fleet box first, as always; the `readdir-mtimes` cap is inert until the agent carries it. The measurement pass (§After the fixes) starts once all four are live.
