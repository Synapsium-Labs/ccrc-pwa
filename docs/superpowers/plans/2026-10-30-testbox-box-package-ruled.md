# The test box's box package, as built: departures from the plan's sketch

- **D-7568 (2026-10-30)** — `testbox-box-package-departures`: TB7 of `docs/superpowers/plans/2026-10-29-test-box.md` (D-7409) is built on `origin/main` with these departures from the plan's sketch; none changes what the box isolates, verifies or installs, and the switch stays off. (1) **The prepare unit's main step.** No script in the tree ran a prepare (TB4's and TB5's tests give the fixture system manager a fixture prepare script), so the prepare unit's fixed `ExecStart` is a new `deploy/testbox/bin/prepare <spec file>`: TB3's `checkout` into `<run>/checkout`, then each install step the spec names (`N`/`W`/`J`), each with exactly the spec's environment, its last stderr line in `TESTBOX_FALLBACK`'s words (D-7501). The spec carries a build output's path (`X`) but not its build command, so the script refuses each output as `test box: build failed (<output>, exit 2)` and the run falls back to local; carrying the build argv in `specs/<k>` is a follow-up for `agent/src/testbox/spec.ts`, not this task. The script makes the spec's `TMPDIR` inside the unit's private `/tmp`; the runner, unchanged, does not, so a run unit's `TMPDIR` (default `/tmp/r`) is not there when the command starts, a follow-up for the runner before TB13's live suites. (2) **The installer's inputs.** The plan's invocation names no source for the distribution release the box must run (D-7423) or for the fleet host's push key (spec §2.1), so the installer takes `--distro <ID>-<VERSION_ID>` (compared with `/etc/os-release`) and `--push-key <public key file>` (one key line, its comment dropped). `--repos <row file>` may be given once per repository, each file one row named `<name>.json`, copied to `CCRC_TESTBOX_REPOS/<name>.json`; its `mirrorPath` and `fetchUrl` are read as the push user's forced command reads `mirrorPath` (one member of that name), and the service parses the whole row at its start. The installer refuses `~/` in `CCRC_TESTBOX_ROOT`, `CCRC_TESTBOX_REPOS` and `CCRC_TESTBOX_TOOLS_DIR` (root has no reader's home to resolve it against), a listen address or registry proxy that is not an IP literal (the firewall and `IPAddressAllow=` take addresses), and an egress name that is no row of spec §2.0's table; it unsets every `CCRC_TESTBOX_*` variable of its own environment before `_tb_load box`, so a value there (which box mode ignores anyway) cannot turn into the warning that refuses the run. (3) **The firewall.** Egress is one v4 and one v6 address set per row of spec §2.0's table, each matched with the sending unit's cgroup: the service and the tools unit add themselves to the cgroup sets `service_cg` and `tools_cg` with `NFTSet=` (systemd 254 and later), because a cgroup path in a rule must exist when the rule is loaded and the tools unit's does not; the tailnet client is matched by its cgroup path. Besides the table the file lets out the box's own infrastructure: loopback, replies, ICMP and ICMPv6 (neighbour discovery), the DHCP lease's renewal, DNS (53) and NTP (123), each by port. Inbound is ssh and the service port on the tailnet address only, enforced by the firewall: an sshd `ListenAddress` on that address would leave sshd unbound whenever it starts before the tailnet client. The file is loaded at boot by a drop-in for the distribution's `nftables.service`; a load empties the cgroup sets, so a re-run that reloads it restarts the service and refreshes the address sets. (4) **The egress resolver.** The installer writes the names, `<row><TAB><host>` per line, to `/etc/ccrc-testbox/egress` (beside the box file, under the directory `_tb_box_env_file` names): `CCRC_TESTBOX_EGRESS_ALLOW`'s three names, the registry upstream's host, the release base's host (through `_tb_release_base`, D-7457) and the OS mirror's host, or, with no mirror set, the hosts the box's apt sources name. `deploy/testbox/bin/egress`, the egress unit's `ExecStart`, replaces the sets in one nft transaction and keeps a row whose name did not resolve. A release host that redirects its downloads to another host (an asset host of a code forge) is not in the table; TB13 measures it. (5) **The slices.** The per-run slices are `ccrc-testbox-run-<k>.slice`, made by the system manager on use under the shipped `ccrc-testbox-run.slice`, and take the per-run caps from the prefix drop-in `ccrc-testbox-run-.slice.d/50-ccrc-testbox.conf`; the install slice takes the same caps from its own drop-in (spec §2.2 "the same caps"); `ccrc-testbox.slice` is their parent. (6) **The mirror.** Each row's mirror is `git init --bare --shared=0664` with `remote.origin` set and nothing fetched (the service's timer fetch fills it), the service's with group `ccrc-tb-git`, its `config` root's 0644, and its top directory 3775: group-writable for git's lock files and sticky, so no group member can replace the root-owned `config` there. (7) **Users and homes.** The service user's home is `/var/lib/<service user>` (its token file default is `~/`); the push user's home is `/var/lib/<push user>`, root's 0755, with `.ssh/authorized_keys` root's 0644; the run users and the install user have no home (`/nonexistent`: a run's HOME is its own `home/`). (8) **A re-run.** With the installed marker present and naming this tag and the box file's sha256, the installer changes nothing after its refusals. With the marker present otherwise, it runs phase 5 again and then reloads the firewall and the system manager, restarts the service, refreshes the address sets and records the tag and sha256. With no marker it runs every phase, and phase 2 keeps a `<tools>/release/<tag>` already there once it passes the root-only check.
