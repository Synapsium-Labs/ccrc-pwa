# The test box's box package, as built: departures from the plan's sketch

- **D-7568 (2026-10-30)** — `testbox-box-package-departures`: TB7 of `docs/superpowers/plans/2026-10-29-test-box.md` (D-7409) is built on `origin/main` with these departures from the plan's sketch; none changes what the box isolates, verifies or installs, and the switch stays off. (1) **The prepare unit's main step.** No script in the tree ran a prepare (TB4's and TB5's tests give the fixture system manager a fixture prepare script), so the prepare unit's fixed `ExecStart` is a new `deploy/testbox/bin/prepare <spec file>`: TB3's `checkout` into `<run>/checkout`, then each install step the spec names (`N`/`W`/`J`), each with exactly the spec's environment, its last stderr line in `TESTBOX_FALLBACK`'s words (D-7501). The spec carries a build output's path (`X`) but not its build command, so the script refuses each output as `test box: build failed (<output>, exit 2)` and the run falls back to local; carrying the build argv in `specs/<k>` is a follow-up for `agent/src/testbox/spec.ts`, not this task. The script makes the spec's `TMPDIR` inside the unit's private `/tmp`; the runner, unchanged, does not, so a run unit's `TMPDIR` (default `/tmp/r`) is not there when the command starts, a follow-up for the runner before TB13's live suites. (2) **The installer's inputs.** The plan's invocation names no source for the distribution release the box must run (D-7423) or for the fleet host's push key (spec §2.1), so the installer takes `--distro <ID>-<VERSION_ID>` (compared with `/etc/os-release`) and `--push-key <public key file>` (one key line, its comment dropped). `--repos <row file>` may be given once per repository, each file one row named `<name>.json`, copied to `CCRC_TESTBOX_REPOS/<name>.json`; its `mirrorPath` and `fetchUrl` are read as the push user's forced command reads `mirrorPath` (one member of that name), and the service parses the whole row at its start. The installer refuses `~/` in `CCRC_TESTBOX_ROOT`, `CCRC_TESTBOX_REPOS` and `CCRC_TESTBOX_TOOLS_DIR` (root has no reader's home to resolve it against), a listen address or registry proxy that is not an IP literal (the firewall and `IPAddressAllow=` take addresses), and an egress name that is no row of spec §2.0's table; it unsets every `CCRC_TESTBOX_*` variable of its own environment before `_tb_load box`, so a value there (which box mode ignores anyway) cannot turn into the warning that refuses the run. (3) **The firewall.** Egress is one v4 and one v6 address set per row of spec §2.0's table, each matched with the sending unit's cgroup. No rule names a cgroup path: nft resolves a path to an id once, when the file is loaded, so a path rule fails the whole load when its unit is not running yet (the load is at boot, before the tailnet client starts) and goes stale when its unit restarts. Each unit the firewall lets out instead adds its own cgroup to a cgroup set when it starts, with `NFTSet=` (systemd 254 and later): the service (`service_cg`) and the tools unit (`tools_cg`) in their own files, and the box's own tailnet client (`tailnet_cg`), resolver (`systemd-resolved`, `dns_cg`) and time client (`systemd-timesyncd`, `ntp_cg`) through drop-ins the installer writes, each with `After=nftables.service`; for the three that already run at the first install, the load step below adds their running cgroups to their sets. Besides the table the file lets out only the box's own infrastructure: loopback, replies, the ICMPv6 the kernel sends for neighbour and router discovery and multicast listening (no other ICMP or ICMPv6 leaves), the DHCP lease's renewal, DNS (53) from the resolver's cgroup only (every other process asks it on loopback) and NTP (123) from the time client's only. The file is pinned in the test line for line, a closed census. Inbound is ssh and the service port on the tailnet address only, enforced by the firewall: an sshd `ListenAddress` on that address would leave sshd unbound whenever it starts before the tailnet client. sshd so keeps binding every address, and a prepare or install unit shares the box's loopback, so the input chain's first rule drops ssh and the service port on loopback (where a local process reaching the tailnet address also comes in) before the chain accepts loopback; the service itself refuses to bind loopback or the wildcard. The file is loaded at boot by a drop-in for the distribution's `nftables.service`; the service, the tools unit and the egress unit `Requires=` that unit, so a failed load leaves none of them running without the firewall. A load adds to what the box holds: it declares the sets and the two chains, flushes the two chains and adds their rules, in one transaction, so a reload keeps every set's addresses and cgroups. The distribution's own start and reload of `nftables.service` run its file first, which on Debian and Ubuntu begins with `flush ruleset`: the table goes, and every set with it. A restart restarts the service, the tools unit and the egress unit through `Requires=`, but not the tailnet client, the resolver or the time client, and a reload restarts none of them, so `NFTSet=` alone would leave their sets empty. So the drop-in runs one load step, `deploy/testbox/bin/firewall`, as both `ExecStartPost=` and `ExecReload=`: it loads the file, adds the cgroup of each of the five units that runs at that moment (the tailnet client, the resolver, the time client, the service, the tools unit; one that is not running joins when it starts), and asks the egress unit, without waiting, to fill the address sets again. A reload and a restart therefore end where the install ended, closed until the egress unit has refilled the address sets. The installer copies the step to `/usr/local/sbin/ccrc-testbox-firewall`, on the root filesystem, because `nftables.service` starts early in boot, before a tools directory on another volume is mounted. Its last phase enables and starts `nftables.service` first (on a box where it was not running, that start flushes the ruleset and then runs the step), then runs the step itself, and only then starts the service, so no later start flushes the sets it filled. The flush also deletes netfilter rules other daemons added, the tailnet client's own chains among them; that client adds them again when it next starts, and the test box's own rules do not depend on them. (4) **The egress resolver.** The installer writes the names, `<row><TAB><host>` per line, to `/etc/ccrc-testbox/egress` (beside the box file, under the directory `_tb_box_env_file` names): `CCRC_TESTBOX_EGRESS_ALLOW`'s three names, the registry upstream's host, the release base's host (through `_tb_release_base`, D-7457) and the OS mirror's host, or, with no mirror set, the hosts the box's apt sources name. Each line is written once, so sources that name one host for a release, its updates and its backports give one line. `deploy/testbox/bin/egress`, the egress unit's `ExecStart`, replaces the sets in one nft transaction and keeps a row whose name did not resolve; a name resolves when it gives any address, one its row already holds included (a repeated name, or two names that share an address). A release host that redirects its downloads to another host (an asset host of a code forge) is not in the table; TB13 measures it. (5) **The slices.** The per-run slices are `ccrc-testbox-run-<k>.slice`, made by the system manager on use under the shipped `ccrc-testbox-run.slice`, and take the per-run caps from the prefix drop-in `ccrc-testbox-run-.slice.d/50-ccrc-testbox.conf`; the install slice takes the same caps from its own drop-in (spec §2.2 "the same caps"); `ccrc-testbox.slice` is their parent. (5a) **The release's agent/ dependencies.** The service runs `agent/dist/agent/src/testbox/main.js`, which imports `ws`, and a bare import there resolves from `agent/node_modules`, which the release tree does not carry. So the installer's phase 4 and the tool sync's release placement run `npm ci --omit=dev --ignore-scripts` in the release's `agent/` as well as in `server/` (the fleet installer does the same for the fleet agent); `--ignore-scripts` leaves `node-pty` unbuilt, and the test service reaches no import of it, which the test checks from `main.ts`'s import graph. (6) **The mirror.** Each row's mirror is `git init --bare --shared=0664` with `remote.origin` set and nothing fetched (the service's timer fetch fills it), the service's with group `ccrc-tb-git`, its `config` root's 0644, and its top directory 3775: group-writable for git's lock files and sticky, so no group member can replace the root-owned `config` there. (7) **Users and homes.** The service user's home is `/var/lib/<service user>` (its token file default is `~/`); the push user's home is `/var/lib/<push user>`, root's 0755, with `.ssh/authorized_keys` root's 0644; the run users and the install user have no home (`/nonexistent`: a run's HOME is its own `home/`). (8) **A re-run.** With the installed marker present and naming this tag and the box file's sha256, the installer changes nothing after its refusals. With the marker present otherwise, it runs phase 5 again and then reloads the firewall and the system manager, restarts the service, refreshes the address sets and records the tag and sha256. With no marker it runs every phase, and phase 2 keeps a `<tools>/release/<tag>` already there once it passes the root-only check. (9) **TB6's provenance census.** `agent/test/testbox-tools.test.ts` counted no line under `deploy/testbox/` that names a MANIFEST, but the plan has the installer's phase 1 check the staging tree's `MANIFEST`, so that census now names exactly that one line as its exception; the installer makes the check, and hashes the box file, through `ccd/ccrc`'s `_plat_sha256_check` and `_plat_sha256`, with no digest dispatch of its own. Its release host comes from the `KNOB` that `_tb_release_base` has just read in `file` mode, never from an expansion of `CCRC_RELEASE_BASE_URL`, which TB6's census of environment-mode reads holds.
