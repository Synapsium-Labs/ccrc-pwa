# A dispatch whose one child came back live is bound to it, ruled

- **D-7563 (2026-10-30)** — a dispatch whose one returned child is live is bound to it by the dead-dispatch pass.

**D-7563.** The dead-dispatch pass (`server/src/coord/abandonDeadDispatch.ts`, D-7319, capped by D-7502) kept a run with verdict `child-workspace` whenever a registry row's `.child` marker named it. Measured after that deploy: a run stood `planned` with a dispatch stamp about 64 hours old, and its child workspace carried the marker naming the run and had a live tmux pane. The `ws-add` had come back, but the run never bound its session. The coordinator card showed "spawn never completed" with no end, and the pass rightly kept the run every pass. The operator ruled AUTO-BIND: when a planned, dispatched run has exactly one child workspace whose marker names that run and whose pane is live, the server binds the run to that session itself.

| Requirement | How it is met |
|---|---|
| Bind through the store write a normal spawn completion uses, never a new mechanism | `bindReturnedChild` (`server/src/coord/dispatch.ts`, beside the fresh-spawn arm) calls `coord.setSession(runId, sessionId, null)`: the arm's own write, with the adopted arm's `null` birth, because the workspace may be an earlier attempt's. It lives in `dispatch.ts` so the binding's writers stay the files `BINDING_WRITER_FILES` names. No hold, advance or brief is written. The coordinator's next dispatch of the run resumes the bound workspace through the resume arm. |
| Exactly one child, its marker naming the run, its pane live | `deadDispatchVerdict` (L1, `server/src/coord/deadDispatch.ts`) answers `bind` only when exactly one row's marker names the run, that row is a measured workspace of the run's own project, the executor measured its pane `live` (`tmux.sessionVerdict`), and no run names its session yet (`runsNamingSession`). The executor asks tmux and the store only when exactly one row names the run. |
| Ambiguity never binds: today's behaviour is kept | Two children, a pane that is gone or that tmux could not measure, a session some run already names (or whose runs could not be read), a row of another project or one not measured, a row with a hold, a session this run's journal says was once unbound from it, and another row of the run's project that step 5 doubts (an unreadable marker, an unmeasured identity, or a cut-short `ws-add`'s shape: each could be a second child that no marker proves, so the one child is ambiguous): the verdict stays `child-workspace`, as before. The doubt is the same per-project check the `dead` answer runs (`projectDoubt`), and it is asked only of rows of the run's project, exactly as for `dead`. A hibernated child's pane reads `gone` (true of its pane), so it is never bound and its run is kept as before. A hold is read as the adopted arm reads it (`held === null` only): a run that never bound placed no hold, so a claim on the child, or a hold that could not be read, is someone else acting on it. A `session-unbound: <id>` event (`store.clearSession`, the resume arm's workspace-spent unbind, read through `unboundSessionOf` in `server/src/coord/runSpend.ts`) means the server already found that child spent for this run; clearing the session leaves the dispatch stamp, so without this the next pass would bind it back and the resume arm unbind it again, without end. A marker that names another run is not this run's child, so the verdict is the same as before (the run is abandoned when nothing else keeps it). |
| The one child bind gate | Before the re-measure and the write, the executor asks `childBindGate` (`server/src/coord/childBind.ts`), the gate every door that binds an existing workspace to a run goes through, for the session the verdict named, with the watcher's own `runCcd` and fleet state. Any answer but `ok` (`workspace-spent`, or `spent-unmeasured`) keeps the run, the gate's code in the pass's reason. The re-measure that follows must name the same session. |
| Same pass, its cap, its switch | The bind is a third answer of the same verdict in the same loop. It counts against `DISPATCH_ABANDON_PER_PASS` and comes after the switch, the cleanup pause, the bound, the marking-box check and a registry read whole, which all still run first. |
| Re-measured before the write | Inside the coordination serialiser, every fact is read again, the registry, the pane and the store included, and the re-measure must itself answer `bind`. Its facts are the ones bound. `bindReturnedChild` then re-reads the run and writes with no `await` between. It refuses when the run is not planned, already names a session, has another claimant, or carries another dispatch stamp. |
| Journaled with its own outcome word | After the write, `recordRunEvent(id, 'sweep', 'dispatch-bound:returned-child session=<id> started=<ms>')` (`DISPATCH_BIND_EVENT`, `shared/dispatch-abandon.ts`), and the pass's outcome reports the run under `bound`. Nothing is closed or mailed. |
| Idempotent | A bound run names a session, so `stalledDispatchRunIds` no longer returns it. A second pass does nothing. |
| The card clears | `nestFleet` draws the phantom "spawn never completed" only for a planned, stamped run whose session is not on the list. The bound run names the child, which is on the list, so the child's own row is drawn in its place. |

The pinned count of sites that decide a binding by hand stays 0. `server/test/hibernate-census.test.ts` gains two `tmux-verdict` rows, `abandonDeadDispatch.ts` and `deadDispatch.ts`, each `true-of-pane`: a hibernated child's pane is gone, so it never binds and its run is kept as before.

**Not in this change.** The coordinator is not mailed about the bind. The ruling asked for the bind, the journal and the card, and a mail would be a second notice beside the run's own trail. Whether to mail the coordinator so it re-dispatches the bound run is left for a ruling.
