# Flows wave 3a: where each programme is on its flow, read from the run machine

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the operator sees, on a flow's page, every programme that pins it and the block each one is on, derived from
the facts the run machine already reports.

**Architecture:** a pure L1 decider in `server/src/flows/position.ts` maps a programme's run facts onto its pinned flow's
protocol blocks. `flowsStore.ts` (L3) reads those facts; one session-gated door answers them; the PWA lists them. Nothing
is stored and nothing is sent: a position is re-derived on every read, so there is no second writer of anything.

**Tech Stack:** TypeScript, Fastify, `node:sqlite`, React, vitest.

**Spec:** `docs/superpowers/specs/2026-11-19-flows-design.md` §5 (protocol blocks are observations), §10 item 3. Builds
on `plans/2026-11-19-flows-w2.md` (branch `flows-w2`); this branch stacks on it.

## Global Constraints

- Imports point inward; decide in L1, act in L4. No new table, no new writer.
- The door is session-gated with no box token; it joins `FLOW_DOORS` and the route counts.
- Wire additive, absence permits.

## Decisions this plan makes

1. **Wave 3 splits.** Spec §10 item 3 is "the engine, shadow then live: positions, the outcome door, instruction and skill
   blocks". 3a ships positions as a derivation; 3b ships the outcome door and the engine's shadow; going live is the
   operator's arm after 3b's shadow has run. Deviation `D-10013`.
2. **A position is derived, not stored.** Every protocol step stands for a fact the run machine reports (spec §4 table),
   so reading the newest work run, and whether a review run is open, places a programme on a protocol block. A stored
   position would be a second copy of run state. The blocks before `open-wave` and the instruction blocks between protocol
   steps are not observable until 3b's outcome door; the answer says so instead of guessing.
3. **The mapping** (`flowPositionOf`): programme `done`/`abandoned` → `end`; no work run → none, "before the first
   wave"; an open review run, or the newest work run at `awaiting-review` → `review`; `planned` → `open-wave`;
   `dispatched`/`working`/`unknown` → the block the `dispatch` step leads to; `merging`/`closing` → `close-wave`; `done`
   → `end` when `wave >= waveOf`, else `close-wave`; `failed` → none, "the wave failed".

## Review Focus

- A flow whose `dispatch` step leads nowhere readable: the build position falls back to the `dispatch` block (Task 1).
- A programme with no runs at all: listed, with no block (Task 2).
