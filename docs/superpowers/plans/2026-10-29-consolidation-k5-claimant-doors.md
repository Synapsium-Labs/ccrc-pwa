## Review focus (the failure modes most likely to bite)

1. **A signing byte that moved.** Both paths call the same `questions.rule` with the same `ClaimantRule`; nothing in this plan should reach `approvalsign.ts`. Q3h's end-to-end row rules an `allow` through each path under the fixture key and a fixed clock and compares the ruling the hook fetches (`GET /api/approvals/:id/ruling`): record bytes and signature equal, and the verifier prints the same verdict. A difference here is a stop, not a re-point.
2. **A mailed command that broke.** The verbs, their argument grammar and their `--json` bodies are what the server mails (item 4). Renaming a verb, or requiring `kind` from the caller, breaks every brief already sitting in a coordinator's inbox. The client splices `kind`; the caller never sends it.
3. **The wrong fail direction.** Every unreadable, stale, torn, future or unlisted cap file must send the **old** door (which every server has until Q3l), never the family. After Q3l the direction inverts on purpose: no old door exists, so the client sends the family, except a fresh, well-formed file that lists words and omits `questions-v1`, which is refused locally with a named code (D-7328).
4. **A kind spliced over the caller's.** `splice_body_field` puts `"kind"` first; JSON's last-wins would let a caller's `kind` win anyway, but the textual "the caller has spoken" test must leave a body that names a top-level `"kind":` untouched, exactly as the `byId` fill does, so a contrary kind reaches the server. The server's answer is not one code: `rule` picks its body arm by the body's `kind` before attribution and the id/kind check, so a mailed body with a contrary kind is the other arm's `400 bad-request`, and only a body well formed for the contrary kind reaches `400 kind-mismatch`; `release` answers `400 kind-mismatch` (item 2). Each is a named difference row, with its after-value stated in Q3j.
5. **An id spelled two ways.** The family path is `ask-{id}` or `approval-{id}`; the id is still `SAFE_RE`-checked before it is substituted, and `parseQuestionId` refuses `ask-01`, `ask-+1` exactly as `parseCanonicalPositiveSafeInteger` refuses `01`. Q3h pins the bad-id rows through both paths.
6. **The child deny gone with the path.** The client verbs stay under `approvals` so the first-argument arm keeps denying a child's `ccrc-api approvals rule`; Q3k adds the path arm for the family's approval ids in both copies. A Q3k that edits one copy reds the guard corpus parity; a pattern that also matches `ask-<n>` would deny a worker answering its own children (worker clause 13), and a corpus row pins that it does not.
7. **A reader that is not the hook's.** `_api_server_cap` must be `_hook_server_cap`'s body byte for byte (only the name differs), generated, stamped, and red on drift. A hand-edited "improvement" in one copy is the duplicate the engine exists to stop.
8. **A cap read on every call.** Only the four claimant rows read the cap file; every other row's request is byte-identical to today's, with no extra file read (`census-w3/claimant.ts#capReaderCalls()`: one call of `_api_server_cap` in `ccrc-api`, on the line that tests `$family` before it). It is proved by that census, not by a FIFO at the path: the reader blocks on one (item 6), so such a row could only red through a vitest timeout (D-7339).
9. **A retirement that strands a client.** Q3l deletes doors a rolled-back fleet box's client would call. Its gates (two releases; fleet nodes measured at or above Q3j; stable carrying the family) and the agent-first release are the whole protection; the PR body states the rollback floor (§Rollback).
