# Chat reading at a desk — Implementation Plan

> **For agentic workers:** one PR per task, run through this repository's coordinator, worker and reviewer flow; a worker extracts its task by its `### Task` heading. The four tasks own disjoint files, and §Landing order says which task waits for which. To execute a task, REQUIRED SUB-SKILL: superpowers:subagent-driven-development, with superpowers:test-driven-development for every red-first step. Steps use checkbox (`- [ ]`) syntax. Workers do not edit this file's §Deviations found. A departure is named by slug in the task's report; the coordinator gives it a number. A worker never allocates.

**Goal:** At a desk the session chat uses the pane's width with prose held to a readable measure; the assistant's prose gains hue in four places only (action and informational lead-ins, status labels, named objects, the markers of an action list); and the names the chat uses (`#n`, `run N`, `item N`, repository document paths, commit SHAs) link to their objects.

**Architecture:** Width is two token values, one new length role and two chat rules. Recognising is one pure module, `pwa/src/lib/chatMarks.ts` (L1, imports nothing, so the parse worker can load it), read by one remark plugin in chat's two plugin lists; the plugin writes data attributes and marks that carry a kind and an id, never a URL. Resolving a mark to an address is a second pure module, `pwa/src/lib/chatRefs.ts` (L1), asked at render time with a context `SessionScreen` provides (L4). Colour is CSS in `prose.css` on those attributes, scoped away from the Docs reader and the recap, with existing palette pairs only.

**Tech Stack:** TypeScript (ESM), React 19, react-markdown, unified/remark, the parse worker, vitest (jsdom) and the Chrome browser config (`vitest.browser.config.ts`), `pwa/design/contrast-check.mjs`.

**Spec:** `docs/superpowers/specs/2026-11-06-chat-reading-design.md`, approved by the operator on 2026-11-06 ("Chat design - as recommended"): R1 to R14 agreed. Mockup: `docs/superpowers/specs/2026-11-06-chat-reading-mockup.html`. Main measured at `37c5e59c7`.

## Global Constraints

- The repository is public: no private names in code, fixtures, commits or PRs. Fixtures use `lane-a`, `project-a`, `sess-a`, repo slug `owner-a/repo-a`.
- Chat only. The Docs reader (`.doc-body`, the `docs` parse profile, `SHARED_COMPONENTS`) does not change in any task. The recap (`.compaction-body`) keeps today's colours.
- Width changes at 900 px and up only. Below 900 px the chat lays out exactly as today.
- Rings: `chatMarks.ts` and `remarkChatMarks.ts` import nothing outside their own pair (the parse worker loads both; `markdown-purity.test.ts` holds the closure). `chatRefs.ts` is L1: pure, no React, no store, no DOM. Decide in L1, act in L4: components only draw what `refHref` answers.
- Consolidate, don't duplicate: user-text links stay in `linkify` (`MessageBubble.tsx`); a document address is built only by `docHref`; an item path only by `itemPath`; a console path only by `routedHref`; the arrival at a row only by `useArrival`. A second mechanism needs a recorded reason in the PR.
- Every colour is an existing palette token, pairs as spec §3.1 lists them. `ui/src/styles/tokens.css`'s `[data-theme]` blocks are generated (`npm run themes`); no task edits them. The contrast gate (`node design/contrast-check.mjs` in `pwa/`) passes in all twelve palettes.
- A skin owns no colour: `skins.css` gains only a length.
- Characterization first when moving code: green on main against the old code; the move commit changes only imports; an intended behaviour change is a commit of its own.
- Every new guard ships with a test that goes red when the guard is deleted (the mutants listed per task), measured before and after and recorded in the PR; restore each mutant from a saved copy, sha checked, never `git checkout`.
- The markdown goldens (`pwa/test/golden/markdown/`) change only in Task M, only by the added data attributes, and every changed file is listed in M's PR. Never run the golden file with `-u`.
- Tasks start after this plan's PR merges, so `D-8059` to `D-8062` are on main's ledger before any shipped comment cites them.
- Gates run through `ccrc test`, one at a time: `ccrc test --heavy -- ./node_modules/.bin/vitest run <file>` from inside the package for a suite, `ccrc test --light -- …` for one small file. Never two heavy runs at once. A PWA layout change (Task W) runs the whole browser suite (`npm run test:browser`) through `ccrc test --heavy` and carries the `full-ci` label.
- Mail before every push and wave-done: a queued ruling can change a step.

## Review Focus

1. **Ordinary words read as names or statuses.** "run 2 times", "item 3 of the list", "C#1", "a red herring", "the value passed to the parser", `deadbeef`, `1234567`, a SHA inside a 41-character hex run. Expected: all stay plain ink, never a link or a label. Pinned in M (`chat-marks.test.ts` negative rows) and L (`chat-refs.test.ts` "a small id the console does not hold stays text").
2. **An unsafe address through the new in-app arm.** A Markdown link to `//host/x`, `/\host`, `/%2e%2e//host` or an unrouted `/api/x`. Expected: never navigated inside the app; it keeps today's external handling. Pinned in L (`lane-route.test.ts` `routedHref` cases, `chat-links.test.tsx` "an unrouted or protocol-relative path keeps the external arm").
3. **A session with no repository, no branch or an unknown project.** Expected: `#n` and a commit stay text (never a link to a guessed repo), a document path opens the project's default view when the branch is absent or outside the bare grammar, and with no project it stays text. Pinned in L (`chat-refs.test.ts`).
4. **The Docs reader and the recap drawn with the same Markdown.** Expected: no colour rule, no mark, no lead-in attribute reaches a `.doc-body` page; an opened recap shows today's colours. Pinned in M (`markdown-parse.test.ts` "the docs profile carries no chat mark") and C (`chat-colour.test.ts` scope case, `chat-colour.browser.test.ts` "the Docs reader keeps ink").
5. **A pane narrower than the cap, and wide code at 2560 in Instrument.** With the inspector rail open at 1600, or a 300-column code line in a full-pane Instrument column, the page must not scroll sideways. Expected: the column yields to the pane, code scrolls inside its own well. Pinned in W (`chat-width.browser.test.ts` "no horizontal page scroll").

**Interfaces:**
- Produces (`chatMarks.ts`, imports nothing):
  - `type MarkKind = 'pr' | 'run' | 'item' | 'doc' | 'commit'`; `interface Mark { readonly kind: MarkKind; readonly id: string; readonly text: string }` (`id`: the digits, the path or the SHA; `text`: as written, e.g. `run 1527`); `isMarkKind(s: string): s is MarkKind`.
  - `type StatusTone = 'ok' | 'merged' | 'wait' | 'fail'`; `STATUS_WORDS: Readonly<Record<StatusTone, readonly string[]>>` = ok: passed, green, accepted, approved, done; merged: merged, landed; wait: blocked, waiting, held, pending, stalled; fail: failed, red, refused, rejected, broken. `statusTone(word: string): StatusTone | null` (case-insensitive, whole word).
  - `STATUS_SUBJECTS = ['ci', 'checks', 'tests', 'suite', 'build', 'review']`; `STATUS_LINKERS = ['is', 'was', 'now']`.
  - `type LeadKind = 'action' | 'info'`; `ACTION_LEADS = ['what to do', 'to do', 'your call', 'decision needed', 'what i need from you', 'action']`; `leadKind(boldText: string): LeadKind | null` — `action` when the lower-cased, trimmed text starts with an entry followed by its end, a space, `(`, `.` or `:`; else `info` when it ends in `.` or `:`; else null.
  - `type MarkRun = { kind: 'text'; text: string } | { kind: 'mark'; mark: Mark } | { kind: 'status'; text: string; tone: StatusTone }`; `markRuns(text: string): readonly MarkRun[]` — the runs' texts joined are `text`; no two text runs adjacent; status runs only in position S3 (after a mark or a subject, with at most one linker between).
  - `wholeMark(text: string): Mark | null` — the mark when `text` is exactly one name and nothing else (R13).
  - `leadingStatus(text: string): { word: string; tone: StatusTone } | null` — S1, the cell text's first word.
  - `MARK_ATTR = { kind: 'data-mark-kind', id: 'data-mark-id', status: 'data-status', lead: 'data-lead', afterLead: 'data-after-lead' } as const`.
  - The grammar, in priority order, never overlapping: doc `docs/` then `[A-Za-z0-9._/-]*` ending `.md`, not preceded by a word character, `.`, `/` or `-`, not followed by a word character, `/` or `-`, and refused when it holds a `..` step; PR `#` and 1 to 6 digits, not preceded by a word character, not followed by one; run `run` or `review`, whitespace, digits, case-insensitive, word-bounded (kind `run`); item `item`, whitespace, digits (kind `item`); commit 7 to 40 lowercase hex with at least one digit and one letter, preceded by start, `@` or a non-word character other than `.`, `/`, `-`, and not followed by a word character. Which sections a document may sit in is not decided here: `docHref` decides it (Task L).
- Produces (`remarkChatMarks.ts`): `remarkChatMarks(): (tree: unknown) => void`, an explicit-stack walk like `remarkAlerts`, never descending into `inlineCode`, `code`, `link`, `linkReference`, `image`, `imageReference`, `definition` or `html`:
  - a text node becomes `markRuns`' runs: a mark is a node with `data.hName: 'span'`, `hProperties: { [MARK_ATTR.kind]: kind, [MARK_ATTR.id]: id }`; a status is `span` with `[MARK_ATTR.status]: tone`;
  - a `strong` whose whole text is a status word gets `[MARK_ATTR.status]` (S2); a `tableCell` whose first child is text starting with a status word has that word split into a status span (S1);
  - a root-level `paragraph`, or the first paragraph of an item of a root-level list, whose first child is `strong` with `leadKind(text) !== null`, gives that `strong` `[MARK_ATTR.lead]: kind`; a root-level `list` directly after a root-level paragraph with an `action` lead gets `[MARK_ATTR.afterLead]: 'action'`. Lead-ins inside a blockquote or callout are not marked.
- Produces (`markdown.tsx`): `CHAT_REMARK_PLUGINS = [remarkGfm, remarkAlerts, remarkChatMarks]`; `CHAT_COMPONENTS.span`: a span carrying `MARK_ATTR.kind` renders its children only (an unresolved mark is plain text, so marks alone change no golden); any other span renders as `<span>` with its props minus `node`. Task L replaces the first arm.
- Produces (`markdownParse.ts`): `PLUGINS_BY_PROFILE.chat = [remarkGfm, remarkAlerts, remarkChatMarks]`; `docs` keeps `[remarkGfm, remarkAlerts]`.

## Where the plan departs from the spec

- **`refHref` lives in `pwa/src/lib/chatRefs.ts`, not in `chatMarks.ts`** (spec §4.2 put both in one file). `chatMarks.ts` is loaded by the parse worker, whose import closure `markdown-purity.test.ts` holds free of React and of modules outside it; `refHref` needs `docHref`, `itemPath` and `routes.ts`, which would pull the Docs and ledger modules into the worker. The recogniser table stays one file; the resolver is the L1 module beside it. Legitimately different: another process (the worker) and its purity boundary.
- **The name grammar does not reuse `shared/ledgers.ts`'s `linkCandidates`.** That scanner finds addresses and paths in item text for an allow-list the server also refuses by (D27, D28); chat's grammar finds keyword names. The document path is the one overlap, and there the section list stays `docHref`'s alone. The reason is the one `pl10-linkruns-not-chat-markdown` records.
- **Lead-ins are marked at the top level only** (a root paragraph or an item of a root list). Spec §3.1 does not say where; inside a callout or quote the ground is a tint, and the gate measures these rules against `--bg-page` only.
- **The arrival effect is extracted to `useArrival.ts`**, so `/runs?run=` and `/accounts?lane=` share one mechanism rather than two copies.
- **The recap renders marks as links too.** It is the same renderer; spec §3.1 keeps its colours as today, which Task C's scope does.
