# ws-reap counts unpushed commits only against a live, fetched upstream (#126) — Implementation Plan

**Issue:** #126, "ws-reap strands a fully-merged workspace forever when its remote branch was deleted".

**Status:** one task, one PR. It changes rung C1 of `_ws_reap_eval` in `ccd/ccd` and adds tests to `server/test/ccd-ws-reap.test.ts`.

## The problem

Rung C1 of `_ws_reap_eval` refuses `unpushed-commits` when the branch is ahead of `@{upstream}`. It ran before C3's fetch and used whatever the local tracking ref held. GitHub deletes a merged head, and `git fetch` without `--prune` leaves its tracking ref where it was. A squash-merged workspace therefore kept a stale tracking ref at its pre-merge tip. C1 counted every commit on the branch as "not on the remote" and refused before the merge proof could run. Git itself reported zero commits unique to the branch. The workspace stayed un-reapable until something pruned the ref. Nothing about the commits changed in between, only the local ref. So the verdict depended on when someone last pruned, not on where the commits were.

## The fix

C1 moves to just after C3's fetch, so it counts against the ref the fetch just refreshed (D-5882). Before counting, it asks the upstream's remote whether the head still exists, with `git ls-remote --exit-code --heads <branch.<name>.remote> <branch.<name>.merge>`. C1 is skipped only when that probe answers "no such head" (exit 2). Then the ladder falls through to C4 and C5, the ancestry and merge provers. Any other result keeps the refusal: the head is live, the probe failed, or the probe timed out. A check that did not run is never evidence that the work is safe.

This change does not widen what a reap deletes. Skipping C1 only reaches the merge provers, and they refuse unmerged work on their own. The tests pin that. Because C1 now runs later, a workspace that is ahead of its upstream and also has no origin, or cannot be fetched, now refuses `no-remote` or `fetch-failed` first. Every path still ends in a refusal. The ccd stamp is regenerated with `ccrc restamp`.

## Tests

`server/test/ccd-ws-reap.test.ts`, describe "C1 reads only a tracking ref the remote still backs (D-5882)". `ready()` gains an optional list of commits, so the fixture can be built with six commits, as in the issue.

1. The issue's state: a squash merge, the head deleted on the remote, and the local tracking ref six commits behind after a plain fetch. The audit answers `reapable`, and the reap succeeds with proof `patch-id`. This is the acceptance test.
2. A live remote branch that is behind (one local commit that was never pushed) still refuses `unpushed-commits`, and the detail names `1 commit(s)`. This is the acceptance test's other half.
3. The test 1 fixture, but `ls-remote` fails (rc 128). It refuses `unpushed-commits` with `6 commit(s)`.
4. The same fixture, but the probe times out (rc 124). It refuses `unpushed-commits`.
5. The test 1 fixture plus one commit that was never merged. The audit is not `reapable`, so skipping C1 does not clear unmerged work.
6. A live head that holds every commit, with a local tracking ref three behind before any fetch. The audit is `reapable`, because C1 counts against the fetched ref.

Red first: against `origin/main`, tests 1 and 6 fail with `6 commit(s) are not on the remote` and `3 commit(s) are not on the remote`. Tests 2 to 5 pass on both trees. They are refusal guards, and mutants turn them red.
