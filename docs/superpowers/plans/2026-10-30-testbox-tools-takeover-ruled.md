# The test box's tool-sync takeover keeps the queue: the coordinator's ruling

- **D-7559 (2026-10-30)** — `testbox-tools-takeover-queue`: the coordinator ruled that D-7426 and spec §2.10 stand as written: during a tool-sync takeover, queued runs wait for the new service and are never dropped. A takeover that admits no run and loses the queue when the process exits is rejected; D-7553's third item is therefore not a departure from D-7426 but its build. The old service closes admissions (no waiting run starts; the run limit its status answers report stays the configured one, so every status answer and every hello during the takeover still reads as the frame family's), still accepts submissions, which queue behind the waiting ones, waits for the runs in progress to end, and writes every run still waiting, in queue order, to `<root>/handover/` before it exits 0. What is handed over is read from the service's own queue: each run's `run.submit` as the service queued it, so a refused duplicate submission never replaces it. The new service queues them at its start, in that order, as it queues any submission, so a run handed over and still waiting at a second takeover is handed over again. The sets a sync keeps (the tools unit's `K` records) are the ones the work in progress names: each live run's set is read from the `PATH` of its own spec (`specs/<k>`, matched by run id), the pristine install's from `specs/install` (kept until the next build replaces that spec), and a run whose spec is not written yet keeps the set it was first seen under. They are read again before every unit run, so a frame that waited for a sync keeps the sets of the runs that started meanwhile. A prepare's Chrome and its `PATH` come from one reading of `<tools>/current` (`toolsync.ts#currentSetDir`, once per turn of the event loop), so a switch between the two reads cannot give a run one set's node and another set's Chrome.
