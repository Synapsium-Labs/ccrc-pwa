# The fast pull-request path runs the whole-tree scanners: ruled

- **D-7455 (2026-10-29)** — the fast pull-request run (`.github/ci/fast-plan.mjs`) adds to its guard set every server test that the last full run RECORDED listing a source tree — `server/src`, `shared`, `pwa/src`, `agent/src` or `ccd` — when its file took at most `SCANNER_MAX_MS` (10 s) on that run, or has no measured duration. Before this, a whole-tree ratchet passed a pull request's run and failed only in the merge queue: `fleetio-contract.test.ts`'s plain `io.readdir(` ratchet walks `server/src` and reads every file as text, so vitest's import graph relates it to no change, and the guard rule (patterns, `TREE_READER`) did not name it. That ejection cost a queue slot and a re-run. A first cut found scanners statically, by source shape; review kept finding shapes it missed, so the coordinator ruled (2026-10-29) for runtime capture. How it works: in a full-suite run (the server shards when `tests == full`, the same runs that keep `times-<shard>`), `CCRC_TREE_SCANS_OUT` makes `server/vitest.select.config.ts` add `server/test/tree-scans.setup.mjs`, which wraps fs's directory listers (`readdirSync`, `readdir`, `opendirSync`, `opendir`, `globSync`, `glob` and the `fs/promises` `readdir`, `opendir`, `glob`) once per worker and records, per test file, each source root a listed path resolves at or under, never one in the temp tree where fixtures live (`.github/ci/tree-scanners.mjs`). `times-build` merges the shards' lines into `tree-scanners.json` and publishes it as the `tree-scanners` artifact beside `testtimes`; `fast-plan` fetches the newest trusted one with the same `main-artifact.mjs` lookup and hands it in as `--scanners`. The plan takes the UNION of the record and the static detector (`scansSourceTree`, kept, with no further shapes), so a shard whose scans were lost, or a listing the capture cannot see, drops no scanner the detector knows; with no readable artifact, the detector alone. The capture cannot see a listing made in a child process the test spawned, one through a mocked fs, or a listing of an ANCESTOR of the roots (the repository root or `server/`, listed recursively or globbed into them): it matches the listed path at or under a root, never above one, since recording every listing of the repository would record every test that lists it for any reason. The self-check in `server/test/ci-fast-plan.test.ts` runs every static positive fixture under the capture and requires it to be recorded (runtime is a superset of static); other rows require the plan to keep a static scanner the record left out (the union) and a missing artifact to fall back to static alone. Measured on the 350 server test files whose source or helper calls a lister and that took at most 10 s on the 2026-10-29 main run's `testtimes` (890 s of summed file time), each run alone: the capture recorded 122 scanners, every one of the 100 the static detector finds there plus 22 it missed (mostly `ccd` subdirectory walks, and four `single-definition` suites that list all five roots); the wrapper spent 124.5 ms in total over 19,897 lister calls in 343 files (about 6 µs a call, at most 14 ms in one file), 0.014% of the sample's time, and a 39-file A/B run twice (348 s and 433 s without, 362 s and 390 s with) is within run-to-run noise. The guard set is 173 files and 520 s of summed file time in 3 guard-only shards, against 156 files and 491 s (3 shards) for the static detector and 93 files and 401 s (2 shards) with no scanners. The other 188 lister-calling files are over the cap and cannot join the set; a heavy scanner stays queue-only because the plan runs files, not cases, and the step summary names each one that did not run. `PIN_MAP_CARRIED` stays out of the guard set even when it scans.
