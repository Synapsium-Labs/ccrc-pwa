# The pristine store's seams the plan left open: ruled

- **D-7543 (2026-10-30)** — `testbox-pristine-seams`: building TB5 of the test box plan (`docs/superpowers/plans/2026-10-29-test-box.md`, D-7407) on `origin/main` `efc2cd836` found that the plan's "one dispatch line" in `agent/src/testbox/service.ts` cannot carry the pristine store: no frame in `shared/testbox.ts` names pristine-install work (the six frame types are a run's four, `tools.sync` and `status`), and TB4's run manager hard-codes the status answer's `pristine` and `failedKeys` as empty, admits a `pristine` queue entry and then drops it, and writes the prepare's spec with no install step. Built instead: (1) `FRAME_HANDLERS` is unchanged; the store reaches the run manager through one optional dependency, `ServiceDeps.pristine` (the store's settings, the reader of a run's install inputs at its tree in the mirror, the node version and the platform), which `main.ts` gives and TB4's rows do not, so every TB4 row runs as before. With it, the prepare's spec names each package's install step (`runs.ts#installStep`), a due key is queued as a `pristine` entry and built in the install unit, the status answer lists the present and failed keys, and the timer queues due builds, applies a new node version and expires unused keys. (2) The install steps ride `specs/<k>` as `N` (package), `W` (directory) and `J` (argv word) records, and the install unit's spec, `specs/install`, holds the key, the inputs (path, then bytes in base64), the doomed keys and the `runner` records, so `install-pre`, `runner` and `install-post` read no config file and no test box variable. (3) A pristine install is root's, so the service user cannot delete one: a key past `CCRC_TESTBOX_PRISTINE_KEEP` leaves the store at once and is removed by the next install unit's privileged first step (`install-pre`, its `Z` records); until then no run clones it. (4) The store is in memory: at start the service adopts each `pristine/<key>` directory it finds as present and unnamed until a run names it, so a restart rebuilds nothing and an unnamed one expires unused. (5) The registry proxy fetches a packument from the upstream on every request (a new version must be seen) and keeps it only as the answer when the upstream cannot; a tarball is immutable and a cached one is served with no upstream call; packument tarball URLs are rewritten to the proxy's own address. (6) The proxy must bind a loopback address; `main.ts` refuses any other `CCRC_TESTBOX_REGISTRY_PROXY`.
