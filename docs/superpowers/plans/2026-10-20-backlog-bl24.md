# Backlog bl24: an ignored-set scan that loses under load is asked again

**Issue:** #128. **Size:** S. **Deploy class:** `ccd` only; no server, agent or PWA byte, no new verdict token, no wire change.

## Problem

`ws-audit` gave two different verdicts for one workspace in one state. Audited ten at a time, two large, healthy, fully merged workspaces came back `tree-unreadable`. Audited one after the other a few minutes later, with no writes in between, both came back `reapable`, and both were then reaped with `proof: contained`.

The ignored-set read in `_ws_reap_eval` (`_ws_collect_ignored`: one `git status --ignored`, then a bounded `find` inside each ignored directory) is the most expensive step of an audit. Under concurrent audits it failed or ran out of its budget, and either way the refusal said "could not read the ignored set". That is the wording of a tree that genuinely cannot be read. The bias also runs the wrong way: the bigger the worktree, the likelier the false refusal, so the workspaces most worth reclaiming were the ones reported as blocked. The detail named the path but not what went wrong, which is why the first sighting could not be diagnosed.

## Fix

1. `_ws_collect_ignored_settled` wraps `_ws_collect_ignored`. When the first read fails it asks once more, serialised on `$REG/.ignored-scan.lock` (`flock -w $REAP_IGNLOCK_WAIT`, 5 s). The wait is short, not the scan budget, because the `ws-audit` and `ws-reap` runner budgets were sized for one scan. The lock only lowers contention and is never a gate. Without `flock`, with a lock file that will not open, or after a wait that runs out, the retry still runs, unlocked. The retry is the same collector with every refusal intact, so it turns a failure into a pass only by reading the whole set. The lock fd is closed before the audit goes on. `_ws_reap_eval` is the only caller switched to it. The resume, gc and archive callers keep the single read, because they already refuse or record on their own terms.
2. Both expiry arms of `_ws_sensitive_inside` set `REAP_IGNTIMEOUT`: the `rc == 124` arm and the spent-budget arm. A scan that runs out of time is refused with a `scan-timeout:` detail that carries the remedy. It never says "could not read". The detail says "both times" only when both attempts ran out of time; when the first attempt failed another way, it says the retry ran out of time. `_ws_collect_ignored` resets its flag on every attempt, so the wrapper keeps the first attempt's flag in `_WS_IGNTIMEOUT_FIRST`.
3. A failed `git status --ignored` now records its exit status and the first line of its stderr in the detail. A read that exits 0 but warns records the warning.
4. The new lock is a dot-prefixed `$REG` artifact, so `_reg_purge`'s R-3 boundary paragraph names it as a sixth reachable alias (project `.ignored` + slug `scan`), and its cardinal goes from TWELVE to THIRTEEN. The alias is harmless: unlinking an advisory lock that is never a gate only lets two retries run at once. The census in `ccd-account-auth.test.ts` caught the omission in CI.

## Tests

`server/test/ccd-ws-audit.test.ts`, each case red at `origin/main`:

1. A read that fails once and then succeeds audits `reapable` with a token. The retry took the lock (`-w 5`) on `$REG/.ignored-scan.lock`, and no fd is left open afterwards.
2. A sensitive-set `find` that keeps timing out is refused with `scan-timeout`, the "did not finish within" wording and the remedy, never with "could not read". It ran exactly twice.
3. A spent budget (`REAP_SCAN_SECONDS=0`, the arm that never runs `find`) is refused as `scan-timeout` too.
4. A read that always fails is still `tree-unreadable` after two attempts, and names `exited 128` and git's message. A read that exits 0 with a warning names the warning.
5. A first read that fails with exit 128 and a retry that runs out of time is refused as `scan-timeout` "on the retry", never "both times".
6. A lock wait that runs out (`flock` returns 1) still retries, and the audit comes out `reapable`.

## Deviations and decisions

### Issued for this work and defined here

- **D-5884**: `ignored-scan-retry` (#128). `_ws_reap_eval` reads the ignored set through `_ws_collect_ignored_settled`, which retries one failed read under `$REG/.ignored-scan.lock`. A timeout that persists across both attempts is reported as `scan-timeout:` in the detail.
  - **Departs from the triage spec:** the timeout gets its own **detail**, not its own verdict. The verdict stays `tree-unreadable`. A new token would have to join `wsaudit.ts`'s sentence map, whose test requires it to equal ccd's tokens, and `archivedExpiry.ts`'s refusal classes, which an open PR holds. The refusal itself is the same either way: a tree ccd could not describe in time is still not reapable. Promoting `scan-timeout` to a verdict, for example so that reclamation retries it rather than treating it as terminal, is a separate change.
  - **Not done:** the `git status` read itself is still unbounded. A timeout on it would add refusals for slow trees that succeed today.
- **D-5885**: `ignored-read-says-why` (#128). A failed ignored-set `git status` puts its exit status and the first line of its stderr into `REAP_IGNREASON`, so the refusal names the cause as well as the path.
