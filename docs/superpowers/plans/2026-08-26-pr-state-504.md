# `pr-state` stops calling a query GitHub cannot answer Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `ccd pr-state` stops asking GitHub for 100 PRs' worth of `statusCheckRollup`
— a query GitHub answers with HTTP 504 on any repo with real PR history — and stops
filing GitHub's own 5xx under the same `reason:"error"` as an unexplained fault.

**Architecture:** Two independent defects, measured live on a fleet repo with several
thousand PRs of history, on
2026-08-26. One is the query's cost; the other is that the failure it produces is
unreadable. Each is fixed on its own, and neither depends on the other.

**Tech Stack:** bash (`ccd/ccd`), TypeScript ESM (server), vitest.

**Spec:** No standalone spec. The decision record is the live measurement below plus the
mail this fault produced: delivery 76 on run 8, `wave-advance-rejected` /
`pr-unmeasurable: pr-state answered no full line`.

## The measurement (2026-08-26, repeat-verified)

All rows below are one repo: a live fleet project with several thousand PRs of history.
The repo is not named here — this tree is bound for public release and its docs speak in
ROLES (`topology-clean.test.ts`'s "operator residue" class refuses the owner handle; the
real coordinates live in `deploy/reference-fleet.md`, gitignored). Every number is real
and every number is kept.

`gh pr list --repo <r> --state all --limit <N> --json <PR_JSON_FIELDS>`:

| variant | rc | wall | note |
|---|---|---|---|
| limit 100 (**what ccd sends today**) | 1 | 11.2s | `HTTP 504` from api.github.com/graphql. **3/3 attempts** — persistent, not a blip |
| limit 50 | 1 | 11.6s | `unexpected end of JSON input` — a TRUNCATED body, a different failure wearing the same `error` bucket |
| limit 30 | 0 | 7.4s | ok, but `PR_GH_TIMEOUT=12` leaves 4.6s of headroom |
| limit 20 | 0 | 3.6s | ok |
| limit 10 | 0 | 1.7s | ok |
| limit 100, `--state open` | 0 | 3.6s | ok |
| limit 100, **minus `statusCheckRollup`** | 0 | 0.89s | ok |
| limit 100, **`--head ws/swift-harbor`** | 0 | 0.78s | ok |

`gh` itself is healthy (`gh auth status` clean, scopes `gist read:org repo workflow`),
and PR #3291 for `ws/swift-harbor` is OPEN. The fault is entirely the query's cost.

**The load-bearing fact that makes the fix cheap:** ccd requests `statusCheckRollup`
for every row and **never reads it**. Its only consumer is the server, at
`server/src/prstate.ts:144` (`checksFor`), and `phaseFor` calls that on exactly ONE
row — `boundRow(line.rows, line.baseShort, line.branch)`. Ninety-nine rollups are
fetched, shipped and dropped on every call.

## Global Constraints

- `PR_GH_TIMEOUT=12` stays 12 unless a task argues otherwise: raising it to make a
  too-expensive query fit is treating the symptom.
- **One reader.** `_gh_pr_list` is deliberately the single gh reader for both verbs
  ("both readers get the same fields, the same 100-PR window and the same failure
  classification, which is the point of there being one reader", `ccd:1793-1796`).
  A task that splits it must say why in the code, not only here.
- Mutation-table discipline: every new arm ships with a measured red.
- Deviation numbers come from `POST /api/ledger/deviations`.
- **AGENT-FIRST**: this touches `ccd/`. Fleet host first, then server.

### Task 1: the classifier learns that 5xx is not "error"

**Files:** Modify `ccd/ccd` (`_gh_pr_list`, `:1804-1815`). Test: `server/test/ccd-pr-*.test.ts`
(find the suite that already drives `_gh_pr_list`'s classification; extend it).

Today's `case "$err"` has arms for `gh auth login`/`not logged in`/`HTTP 401`
(`unauthenticated`), `rate limit`/`HTTP 403` (`rate-limit`), `dial tcp`/`no such host`/
`proxyconnect` (`offline`), and a default of `error`. A GitHub-side `HTTP 504` and a
truncated `unexpected end of JSON input` both land in the default — so the one thing a
coordinator most needs to know (this will fail again identically vs. this was a fluke)
is exactly what the answer cannot say.

Add two arms **before** the default:
- `*"HTTP 500"*|*"HTTP 502"*|*"HTTP 503"*|*"HTTP 504"*)` → `reason:"unavailable"`
- `*"unexpected end of JSON input"*|*"unexpected EOF"*)` → `reason:"truncated"`

Keep `error` as the default: it is the honest name for a fault with no known shape.

`reason` is a string the server surfaces; check `server/src/prstate.ts` and
`shared/api.ts` for whether the reason vocabulary is typed. If it is, add both
values **once**, at the single definition (`single-definition.test.ts` fails the build
on a second copy), and let every runtime list derive.

- [ ] Step 1: write the failing test — a fixture whose stderr is `HTTP 504: …` expects
      `reason:"unavailable"`; one whose stderr is `unexpected end of JSON input` expects
      `reason:"truncated"`. Both assert they are NOT `error`.
- [ ] Step 2: run it — expect FAIL (both answer `error` today).
- [ ] Step 3: implement the two arms.
- [ ] Step 4: run green, plus every suite naming `_gh_pr_list` or `pr-state`.
- [ ] Step 5: delete each new arm in turn, record the failing count for each, restore.
- [ ] Step 6: commit — `fix(ccd): a 504 from GitHub is not an unexplained error`

### Task 2: the per-session query asks about the session's own branch

**Files:** Modify `ccd/ccd` (`cmd_pr_state`'s `--session` path, and its call into
`_gh_pr_list`). Test: the pr-state suites.

`_gh_pr_list` already takes an optional head-branch filter and already builds the flag
itself, safely, as a named second parameter — `pr-open` passes it "because it asks a
question about ONE branch". `pr-state --session` asks that same question and does not
pass it. Passing it takes the call from 11.2s-and-504 to **0.78s**.

**This was verified before the plan was written (2026-08-26) — do not re-derive it,
but DO re-check it if the code has moved.** Every consumer of the rows filters by
`headRefName == branch`, so a head-filtered result is a strict SUPERSET of what anything
reads:

| consumer | filter |
|---|---|
| `_pr_py` `bound()` (`ccd:1931`) | `headRefName == branch` |
| `_pr_py` `pick()` (`ccd:1950`) | rows filtered by `bound` |
| `_pr_py` `is_merged()` (`ccd:1938`) | conjoins `bound` |
| server `boundRow` (`prstate.ts:126`) | `headRefName === branch` |
| server `isMergedRow` (`prstate.ts:115`) | `headRefName === registryBranch` |

And `line.rows` has exactly ONE server-side consumer — `prstate.ts:158`,
`boundRow(line.rows, …)`. Nothing iterates rows for another branch.

The `branch-drift` arm (`ccd:4951`) was the specific risk, and it is not one: it is
decided from git's worktree record against the registry branch (`wthead != branch`) and
returns BEFORE any gh call, so it never reads PR rows at all.

If any of that has changed by the time you execute, STOP and report rather than
narrowing an answer the server depends on.

- [ ] Step 1: write the failing test — a fixture repo where the session's branch has a
      PR and a second branch also has one; assert the session path issues a
      head-filtered gh call (the harness's fake `gh` records argv) and still returns the
      correct phase. Assert the argv CONTAINS `--head <branch>`.
- [ ] Step 2: run — expect FAIL.
- [ ] Step 3: implement.
- [ ] Step 4: run green — all pr-state suites plus `pr-sweep.test.ts`.
- [ ] Step 5: remove the `--head` argument, record the red, restore.
- [ ] Step 6: commit — `fix(ccd): pr-state --session asks about one branch, not a hundred`

### Task 3: the project sweep stops shipping 99 rollups it drops

**Files:** Modify `ccd/ccd` (`_gh_pr_list` / `cmd_pr_state --project`).
Test: the pr-state project suites.

The wide window is genuinely needed for `--project` (it asks about every session's
branch at once), but `statusCheckRollup` is not: the server reads it off ONE row per
line. Drop `statusCheckRollup` from the wide call (0.89s, measured) and fetch the
rollup only for the rows that are actually bound.

**This splits the "one reader" property**, so the reasoning goes in the code at
`_gh_pr_list`, not only in this plan: the two verbs now share the same fields, the same
classification and the same window, and differ only in whether they ask for a per-row
rollup that one of them provably discards.

Design the second fetch so a failure of it CANNOT poison the first: a missing rollup
must degrade `checks` to null (which `checksFor` already returns for an absent
rollup — verify at `prstate.ts:145`), never turn a good phase into `unknown`.

- [ ] Step 1: write the failing test — assert the project call's argv does NOT contain
      `statusCheckRollup`, and that a bound row still carries checks.
- [ ] Step 2: run — expect FAIL.
- [ ] Step 3: implement.
- [ ] Step 4: run green, plus `pr-sweep.test.ts` and any PWA test asserting CI colour.
- [ ] Step 5: measure the red for both halves (argv, and the degrade-to-null path).
- [ ] Step 6: commit — `fix(ccd): fetch the check rollup for the row that is read`

## Deviations found

_(allocated from `POST /api/ledger/deviations` — D-628..D-636, floor 637; then
D-637..D-638 after CI, floor 639)_

- **D-628** — the plan document itself tripped `topology-clean.test.ts`'s "operator
  residue" class: it named the measured repo by its OWNER HANDLE in two places. This tree
  is bound for public release and its docs speak in ROLES; the real coordinates live in
  `deploy/reference-fleet.md`, gitignored. Caught by the suite, not by review. The branch
  was unpushed, so it was rewritten rather than patched — handle removed from the blob AND
  from the commit message, which a follow-up commit could not have reached.
- **D-629** — **the comment sizing the gh timeouts asserted the opposite of what ships.**
  It said `remote/runner.ts`'s `CCD_VERB_TIMEOUT_MS` had no `pr-state` key and the live
  bound was therefore the flat 90 s default. `'pr-state': 20_000` is the FIRST key in that
  map, and has been since 27946f31. Under 90 s, `12 + 6` was comfortable; under the 20 s
  that actually ships it left TWO SECONDS for `_pr_state_one` to loop every workspace of
  the project, each costing a dozen-odd `git` spawns plus a python3 start — and this branch
  is what added the second call. Resized to `8 + 5 = 13`, leaving 35 %.
  **`pr-timeout-budget.test.ts` now pins the relationship ACROSS THE TWO LANGUAGES** that
  own its halves, reading all three numbers from their real sources. Neither file can
  import the other's constant, which is exactly why a comment was holding it and exactly
  why the comment drifted.
- **D-630** — **the join fixture was positionally degenerate, so a positional join passed
  the whole suite.** The one rollup entry carried the number of the row that was also
  first in `rows`. In production the two windows are different SETS in different ORDER
  (rows: `--state all --limit 100`, newest first, merged included; rollups: `--state open
  --limit 100`), so a positional join attaches an open PR's rollup to an unrelated merged
  row — rendering another PR's checks, including its attacker-controllable `checkNames`,
  on any repo that takes fork PRs. The fixture now binds rows[1], supplies the rollups in
  the opposite order with a decoy that reads as a pass, and asserts the decoy landed on
  its OWN row too, because a swap is symmetric. Measured: a true positional join makes the
  bound row read `pass` instead of `fail`.
- **D-631** — "AFTER THE STAMP, NEVER BEFORE" shipped as a comment with no red behind it.
  Moving the stamp after the rollup block is legal and left every suite green. What it
  costs is the property the previous wave fixed: `prcheckedat` must describe when GitHub
  answered THE ROWS, because the compare-and-set ranks runs by it — so a sweep whose rows
  answered seconds earlier could overwrite a fresher `--session` answer. Now pinned by a
  rollup arm that sleeps, with a guard-the-guard asserting the sleep really happened.
  Measured: exactly one test red, and 97 others unaffected.
- **D-632** — **a failed rollup rendered as the affirmative claim "No checks configured".**
  `checks: null` is defined by `PrChecks` as *no checks are configured* and `PrKeycap`
  renders it in those words, under a fresh `checkedAt`. Once the rollup became its own gh
  call it could fail alone — a timeout, a 5xx, a join that would not run — leaving every
  row without the key, which `checksFor` reads as `null`. A red build therefore read as
  "no CI". **This branch created that failure path**, so it owns it: `PrChecks` gains
  `'unmeasured'`, ccd declares `checksUnmeasured` on the line when either failure route
  fires, and `phaseFor` reads it — the fact belongs to the LINE, because `checksFor` is
  handed one ROW and a row whose rollup never answered is byte-identical to a row GitHub
  said has no checks. Measured both ways: never-declare reds 2, always-declare reds 3
  (including the positive control that a MEASURED "no checks" still reads `null`).
- **D-633** — two existing assertions were changed deliberately, and they are the change:
  `ccd-pr-state.test.ts`'s failed-call and failed-join cases asserted `checks` was `null`.
  Both now assert `'unmeasured'`. The phase, number and absence of a `reason` are
  unchanged in both, which is the isolation those tests were written for and still prove.
- **D-634** — three tests hardcoded the timeout numbers, so resizing them (D-629) reddened
  assertions that were never about the value. They now READ the constant from ccd through
  a four-line helper, so the number lives once. A literal in a test that does not own a
  value re-pins it in a place nobody thinks to update.
- **D-635** — `single-definition.test.ts` caught the new budget test TWICE: first for
  joining the ccd script path itself instead of importing the one spelling, then for
  QUOTING that join in the comment explaining the first catch. The scan is textual and
  does not care whether a spelling is code. Recorded because the second catch is the
  funnier and more instructive one.
- **D-636** — the `--limit 50` "truncated body" row of the plan's measurement table did not
  reproduce on re-measurement: limit 50 now answers 504 as well, and limit 45 answers 0.
  The shape is real but intermittent, so its fixture string is the one measured on
  2026-08-26 rather than a fresh capture, and the arm also matches `unexpected EOF` —
  Go's other decoder message for the same condition — because a shape measured once is a
  shape whose exact spelling should not be the only thing a guard knows.

- **D-637** — widening `PrChecks` with `unmeasured` broke the build in a package the
  change never touched, and the break was the good half. `pwa/src/session/PrKeycap.tsx`
  holds `CHECK_GLYPH` as a `Record<Exclude<PrChecks, null>, string>`, which is exhaustive,
  so the new member was a compile error until somebody decided what it looks like — that
  is the mechanism working exactly as designed. What it caught in passing is the process
  gap: `npm run test` in `pwa/` does not run `tsc`, `npm run build` does, and the pwa
  suite had been run BEFORE the `shared/api.ts` edit rather than after. **Any change to
  `shared/` must re-run the pwa lane, and the pwa lane's typecheck is not its test
  script.** The glyph chosen is `?`, with no `[data-checks='unmeasured'] .pr-dot` colour
  rule beside the three that exist: those three override the phase colour with a checks
  VERDICT, and an unread rollup has none to override it with — an axis beside the state,
  not a takeover of it, which is `.sess-unmeasured`'s contract in `SessionLine`.
- **D-638** — the same widening also shipped a live regression the compiler could NOT
  catch, because the second site restated the union by hand instead of deriving it:
  `CHECKS` in `shared/api.ts` was the literal `['pass', 'fail', 'pending']`, and
  `revivePrState` throws `MalformedSnapshot('pr.checks')` on a token outside it. That
  refusal is not a degraded field — it discards the WHOLE snapshot. So once the server
  began writing `checks:'unmeasured'`, a state cache written by this build would have been
  rejected by this build on its next boot, cold-starting every phone. Fixed by deriving
  the list from a `Record<Exclude<PrChecks, null>, true>`, the `PR_REASONS` idiom already
  documented forty lines above it, which makes the next member a compile error at that
  line (measured: `../shared/api.ts(1470,7): error TS2741`). The test that goes red without
  the fix is a POSITIVE control — `offline.test.ts` had a thorough table of tokens this
  build must REJECT and nothing at all asking whether the ones it writes still pass.
