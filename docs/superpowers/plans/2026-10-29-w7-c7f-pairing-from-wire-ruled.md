# W7 C7f: the envelope pairing read from the wire, three departures, ruled

- **D-7363 (2026-10-29)** — C7f: the PWA tests take the wire's pairing from the server's rule (`pane/askPairing.ts#framePairing`) where no recorded table row holds the state

**D-7363.** The plan (`2026-10-27-consolidation-w7-pwa.md`, Task C7f) re-points C7a's pins and the sheet suites so their inputs carry the wire's `pairing`, read from C7q's recorded tables. Those tables are the server's corpus. The PWA's corpus is wider: the Claude Code 2.1.296 ask (`CC296_LONG`), fifteen recorded screens the server's corpus does not hold, and the DERIVED dialogs the sheet suites build. In `w7-transcript-pairing.test.ts`, 273 of the 540 copy states are in C7q's table and 267 are not. So `pwa/test/wirePairing.ts` reads a recorded table where one holds the state (`corpus.json` through `tablePairing`, `transcript-corpus.json` through `recordedPairing`). Everywhere else it applies the server's own rule, `framePairing`, imported from `server/src/pane/askPairing.ts`. It is a test-only import of the one pure module the stream pairs with, so no second copy of the rule exists. Where both sources hold a state they agree: 273 of 273. `served` (and `servedSocket` for the browser leg) attaches the pairing frame by frame as `sessionws.ts#paired` does. With `frameFirst`, an answer route's reply also arrives in the server's order: the stream's frame for `next` lands first, as C7q's sequence (e) records it. `.github/ci/reach.mjs#READS` lists `server/src/pane/` for the pwa and browser legs, so a change to the rule runs these suites. `ci-reach-census.test.ts` reads the import's extensionless specifier, so a single-file entry would not match it. No assertion changes. The PWA's own code imports none of this, because the sheets read the wire.

**D-7364.** `askLive.ts#pairingFor` accepts a structured question's pairing only when its `from` is the question's own. The plan names that rule. This departure adds one more condition: the pairing must fit the questions shown. That means one `corresponds` entry per question, with `shown` among them, and `live`, `named` and `placed` null or among them. A pairing from a skewed or older server could otherwise index past the questions. `askFrame` would then read an undefined question, or `MultiPick` an undefined copy. Failing closed shows the unpaired view (the terminal door), which is the same thing a missing pairing shows. On a server carrying C7q the pairing always fits, because the store holds the last frame's pairing beside that frame's envelope and dialog. So no screen changes there. The test `session-store-pairing.test.ts` has a row for it ("a pairing that does not fit the questions").

**D-7367.** D-7220 has `applyAnswered` clear the pairing with every dialog it writes. Read literally, that also covers a reply whose `next` is the screen the store already holds: the same dialog id. That happens when a tab move targets the tab already showing (`inject/send.ts`'s `to === at` arm answers `{ ok: true, next: dialog }`), or when a Submit lands on the review. For an unchanged screen the stream sends no frame (`sessionws.ts#nextDialogFrame` keeps the seen id). So the cleared pairing would never come back, and the sheet would be stuck on the unpaired view. A `next` with the held dialog's id therefore keeps the pairing. It is still the pairing the last frame carried for that very dialog, so "never an older frame's pairing beside a newer dialog" holds. Any other dialog the reply writes clears the pairing, as D-7220 rules. Rows (ix) and (x), and the mutation "keep the old pairing on `applyAnswered`", are unchanged. The row "a reply whose next is the screen the store holds keeps its pairing" pins this case.
