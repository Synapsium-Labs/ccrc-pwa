# The test box reads one config file, owned by root: ruled

- **D-7451 (2026-10-29)** — `testbox-box-config-file`: the test box plan (`docs/superpowers/plans/2026-10-29-test-box.md`, rev 1) said the box's installer reads "its `ccrc.env`" but never named the file, and ccrc's one settings reader cannot name it for the box. `_ccrc_knob` reads `BOX_ENV_FILE`, which `ccd/ccrc` sets to `$HOME/.ccrc/ccrc.env` when it is sourced (`ccd/ccrc#BOX_ENV_FILE`, measured on `origin/main` `d32509009`), and `_upd_release_base` reads `CCRC_RELEASE_BASE_URL` through it. On the box the root installer would have read root's home's file, the test service, running as its own user, that user's home's file, and the root tools unit root's file again for the release base, while the prepare, run, clean and install units read none. The box's units and its runs could then be built from different values. Ruled: the box has one config file, `/etc/ccrc-testbox/ccrc.env`, named once as `TB_BOX_ENV_FILE` in `ccd/testbox-knobs` and printed by `_tb_box_env_file`. It is owned by root, with mode 0640 and the service user's group, so the run users cannot read it. It holds no secret. The operator writes it before the first install, and the installer sets its group and mode and never writes a value into it. `_testbox_knobs box` binds `BOX_ENV_FILE` to that path for each `_ccrc_knob` call, in `file` mode, so neither the caller's home nor its environment is read. It refuses a file that is not a regular file, not owned by root, or writable by group or other. The four readers: the installer, as root, through `_testbox_knobs box`, which renders the unit drop-ins (slice limits, the proxy allow, the service's `User=`) and the users, directories and rule; the test service, as the service user, through `ccrc-test --testbox-knobs box` once at start; the tools unit, as root, which binds `BOX_ENV_FILE` to the path before `_upd_release_base`; and the prepare, run, clean and install units, which read no config file. The prepare, run, clean and install units carry no `EnvironmentFile=`, because one on a run unit would put the settings into a run environment that is built from empty plus the allowlist, and a unit property cannot be read from an environment file anyway; they take their values from the installer's drop-ins and the service's `specs/<k>`. A change to the file takes effect when the installer is re-run with the installed tag. The installer reloads and restarts only when the file's sha256 differs from the one its `installed` marker records. On the fleet host nothing changes: `_testbox_knobs host`, the wrapper and the agent op's `ccrc-test --testbox-knobs host` all run as the fleet user and read the same `~/.ccrc/ccrc.env`. TB7's `server/test/testbox-config-file.test.ts` holds that the four readers agree. It sets every box key in a fixture box file, other values in root's and the service user's fixture home files and in the environment, and checks that the drop-ins, the service's read, `specs/<k>` and the tools sync's release base all carry the box file's values, with one mutation per reader that reds it. A census fails on any `EnvironmentFile=` line under `deploy/testbox/`, and on any test box file that names `.ccrc/ccrc.env` or assigns `BOX_ENV_FILE` beyond the two bindings. TB1's `testbox-knobs.test.ts` holds the box-mode reads and refusals, and TB7 now waits for TB1.
