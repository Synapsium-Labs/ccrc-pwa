## Act F2 (Task 1I): the census's cost at G14's size

The fixture was built once, on fixture homes under the session temp root, and removed after the case:

- 1,454 subagent transcripts with metas, 276 of them carrying `toolUseId`;
- 182 parents: 181 at 8 subagents each and one at 6 (corrected in fix round 1, review 1749 A4);
- 64 candidate rows in every parent window, 11,648 stored;
- 34.7 MB allocated (21 MB apparent).

Five census runs over that one fixture:

| Figure | Value |
|---|---|
| Wall time | 193 to 226 ms; p50 201 ms, p95 226 ms |
| Decodes | 17,664 in every run |
| Peak RSS | about 352 MB, including the heap of the fixture's build in the same process |

The decode count is 276 × 64. The plan's "at most about 93,000" was 1,454 × 64, the bound if every unit searched. Only a unit whose meta names a `toolUseId` runs the Agent-tool search, and this fixture has no workflow (b) lookups. The p95 is far below the sweep timer's 2-minute interval, so no build question is raised. The census holds the writer's lock for that long.

Read these figures with their limits. The rows are a few hundred bytes, and a decode's cost grows with the body, up to `blobOverDecodeCap` (16 MiB) a decode. The runs are warm: the build and all five runs share one process, so the page cache and the statement cache are hot. The first run (226 ms) is the nearest to a cold verb. So the figure is a floor on body size, not a general p95. The census on an armed node measures the real one.

## Statements the build found that the ledger should hold

- **SA33, the untimed-only parent.** The plan's SA33 and the addendum's SA33 pin read a parent with no match and only an untimed candidate as `M` (`parent-untimed`). The addendum's parent table, row "a parent assistant row with `tool_name` and a NULL `ts_ms`", reads it as decided, and so `U` when the window is complete. The build follows the plan (worker clause 6). `M` widens the range and never narrows it.
- **SA23, what "writes nothing" measures.** A read-only open of the store creates SQLite's own reader sidecars (`-shm`, `-wal`) when they are absent, as every read verb's open does. SA23 compares the database file's sha256, mtime and `user_version`, and every other file under `~/.ccrc`, and names the sidecars and the shim's lock as its one exclusion. The addendum's SA23 row says "no file under the history directory".
- **A window read "to its end at the last tick"** counts as read past the window whenever that tick ran (addendum §3.3's own definition). A parent read to its end just before the window closed can therefore answer `U` while rows inside the window may still arrive. This affects the upper end only.
- **A holding whose first line changed under the same inode** reads as bound where no birth time is reported. The census opens no transcript file, so it cannot measure that change; §3.1 lists it as an unbound cause. Fix round 1 settles it as D-8163 (`history-w4-census-reads-no-transcript`): the census asks lib's one identity rule (`sameFileIdentity`, which ingest's `planFileRead` asks too) with no first-line sha, and the walk carries each holding's birth time from its own lstat, so another birth time reads `replaced`. What stays unmeasured is a holding rewritten in place under one inode and birth time with no shrink, or a first line changed where no birth time is reported. A row in an ingest retry or error state is labelled `unread` rather than `unreadable`, with the same range.
- **SA24's CONTROL** describes "two file rows, doubled memberships". That state is unreachable under `UNIQUE (dev, ino, source_key)`, so the mutant throws a UNIQUE-constraint error, and the case still reds.
- **SA32's CONTROL** says that with the row removed, the apply runs inside a session. The gate fails closed instead (`bad-args`), and the case reds on its row assertion.
- **The census reads bodies through `derive.mjs`' `blobReadStmts` and `bodyOf`**, not `store.mjs`' `unbrotli` as the plan says. `single-definition/late-census.test.ts` pins every blob `SELECT` to `blobReadStmts`, so `census.mjs` imports `./derive.mjs` (its `RINGS` row admits it).
- **`deploy/history-gate.mjs`' `GATE_CODE_FILES`** hashes `ccd/history/lib.mjs` but not the file lib now imports, `shared/workflow-ids.mjs`. The gate reads nothing that depends on `RUN_ID_RE`. `deploy/**` is outside W4-1's claims.
- **The armed scan walk lists every UUID-named session directory before its wanted-uuid filter**, and asks its stop per project and per subagent entry only. On a large tree that listing is unbudgeted. If it ever outgrows the run budget, the cut also stops main discovery of later projects at the same sorted point at every scan (D-8153 builds no rotation). Measure it on the first armed node.
- **Arming late ingests the whole gap at once.** The install record is written at the first W4 tick, armed or not (ruled keep). So a node armed long after its deploy ingests every subagent file changed since then on its first armed scans. The import dry run counts those as `post-install` but gives no bytes. The arming runbook (CP-72/73) should say so, and the operator reads that node's census `Q` first.
- **Hand-off to W4-2: raw lines and boundaries.** A raw (uuid-less) line is keyed by `rawRowKey(<parent uuid>, sha)`, so a subagent line byte-for-byte equal to one of its parent's shares the parent's entry. Subagent `boundaries` rows are already written by W4-1's ingest; derive's queue reads `agent_id = ''` only, so W4-2 inherits that backlog.
- **The census's policy is in L1 (fix round 1).** The holdings' cause, the search's cause order, the outcome after the candidates and the unbound-holding mapping are lib's `parentHoldingsCause`, `linkSearchCause`, `parentSearchOutcome` and `holdingUnboundCause`; `census.mjs` keeps its reads and joins.
- **The install-record withholding is D-8162** (`history-w4-census-withholds-without-install-record`, fix round 1).
- **A subagent row may reuse a message uuid its parent holds** (for example, a subagent started with the parent's context). `entries.uuid` is unique across the store, so the two would share one entry: the entry's first transcript keeps it, and a newer-ranked copy rewrites its structure. The coordinator measured one node read-only on 2026-11-10 (19 homes, 14,367 subagent files and their 585 parent sessions): no subagent row reuses a uuid of its parent's transcript or of a sibling's, and none of 488,265 raw lines repeats a parent line. No subagent of agentType `fork` existed there, so a context-inheriting one is unmeasured. A comment at `ENTRY_UPSERT` says so; the coordinator re-measures before each node is armed (review 1749 F6, no change in the ingest).
- **Waiting bytes are the inode row's (fix round 1, review 1749 F1).** The scan arm's count of a withheld file and the import dry run's forecast find the stored row by device and inode, the row `bindFile` resumes, and the dry run counts and sizes one physical file once.
