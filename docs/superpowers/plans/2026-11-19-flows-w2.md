# Flows wave 2: a programme pins its flow, and the brief is composed from it in shadow

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the operator names one published flow as the default for new programmes; a programme pins that flow's newest
version once, when its row is first written; and every work dispatch records, beside the brief it actually sent, the brief
the pinned flow would have composed.

**Architecture:** Flows stay in C5 Coordination. `shared/flows.ts` (L0) gains two pure functions: which block a dispatch's
brief comes from, and how its prompt renders. `server/src/flows/flowsStore.ts` stays the one writer of the flow tables and
gains the default and the pin lookup; the two `programs` inserters (`CoordStore.openRun`, `planStore.applyPlanChanges`)
take the pin from it. `dispatchRun` (L4) records one `run_events` row from a pure decider; it sends nothing new.

**Tech Stack:** TypeScript, Fastify, `node:sqlite` (`coord.db`), React (PWA), vitest.

**Spec:** `docs/superpowers/specs/2026-11-19-flows-design.md` (§4 Pin, §6, §7, §10 item 2). Builds on
`docs/superpowers/plans/2026-11-19-flows-w1.md` (branch `flows-w1`, PR #3082); this branch stacks on it.

## Decisions this plan makes (the builder as architect)

1. **The pin's moment is the programme row's first write**, not "the programme starts". Measured: no single start point
   exists; `programs` is first written by `POST /api/runs` (`CoordStore.openRun`) or by the plan put
   (`planStore.applyPlanChanges`), whichever comes first, each `ON CONFLICT(slug) DO NOTHING`. Both now write the pin in
   that same insert, so write-once falls out of the conflict clause. The brainstorm before either write has no row and no
   pin; that phase has no flow block that reads one until wave 3. `CoordStore.reconstruct` (legacy rebuild) pins nothing.
2. **Which flow a programme pins** is the operator's **default** (one setting), newest published version at the moment
   of the insert. No default means no pin (`NULL`), which reads as "today's method, as built in". Choosing a flow per
   programme waits for a start screen that names one (wave 3's engine needs it; not before).
3. **Names avoid the existing pins.** `programs` already has the spec pin (`specPath`, `setSpecPin`, `doneWhenBy='pin'`) and
   the landing line has `kind:'pin'`. The new columns are `flowId`, `flowVersion`; code says `flowPin`, never bare `pin`.
4. **The skill split moves out of this wave** (deviation `D-10011`). Spec §10 puts "split protocol from
   method in the three skills" here. Measured: of the worker's twenty clauses only 12 (graphify), 14 (routing) and parts of
   6 and 16 are method; the rest is fleet protocol. Removing the method half from the skills before a flow-composed brief is
   live removes it from every live session, and nothing in wave 2 sends a composed brief. The split ships with the brief
   going live, behind the wave 3 arm, characterization tests first, as the spec says.
5. **The shadow is a `run_events` row**, the pattern `dispatchRun` already uses (`skill-preflight:`), not a new lane or
   table: nothing is armed in this wave, so `lane-arm` has nothing to switch.
6. **Deleting a pinned flow is refused** (spec §7, wave 2), with `409 conflict`, reason `pinned by N programmes`.

## Review Focus

- A flow set as default and then deleted: the delete refuses when a programme pins it; otherwise the default clears in the
  same transaction and the next programme pins nothing (test in Task 2).
- A default flow with no published version: the default door refuses it (`409`); a programme never pins version `NULL` of
  a flow (test in Task 3).
- A second `POST /api/runs` for the same programme after the operator changed the default: the pin does not move (Task 2).
- A pinned version whose stored doc no longer parses: the shadow row says `unreadable`, never `no-flow` (Task 4).
- A prompt naming a variable the server cannot fill (`plan.path`, `wave.tasks`): the shadow lists it as missing rather
  than rendering an empty string (Task 1).

## Acceptance

1. With a default set, the first write of a programme's row pins the default flow's newest version, and nothing moves it.
2. With no default, programmes pin nothing and dispatch behaves exactly as before.
3. Every work dispatch records one `flow-brief:` event; no mail changes.
4. A pinned flow cannot be deleted; the default door refuses an unpublished flow.
5. Guards: censuses, `dtbd` (red only on this plan's `D-TBD` entries), rings, single-definition.

## Deviations found

- **D-10011:** spec §10 wave 2's skill split moves to the wave that sends the composed brief live
  (Decision 4).
- **D-10012:** the pin is written at the programme row's first write, not at a start event, because none
  exists (Decision 1).
