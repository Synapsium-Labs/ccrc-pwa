# Flows wave 3b: the outcome door, and the engine in shadow

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a programme's coordinator reports the outcome of an instruction or skill block of its pinned flow; the server
checks it against the flow, records it with the block the flow leads to and what the engine would do there, and sends
nothing.

**Architecture:** `server/src/flows/outcome.ts` (L1) decides; `flowsStore.recordFlowOutcome` (L3) is the one writer of a new
table; `server/src/flows/outcomeRoute.ts` (L4) is a box-token machine lane registered from `registerCoordRoutes`, in the
call record's order. The flow's page shows each programme's newest reported outcome.

**Tech Stack:** TypeScript, Fastify, `node:sqlite`, React, vitest.

**Spec:** `docs/superpowers/specs/2026-11-19-flows-design.md` §5 (the outcome door), §10 item 3. Builds on
`plans/2026-11-20-flows-w3a.md` (branch `flows-w3`); this branch (`flows-w3b`) stacks on it.

## Global Constraints

- Box token first, then attribution, then ownership (`claimsProgramme`); a refusal writes nothing.
- The door joins EXEMPT with its reason, the census's lane sources, the Overlord lanes census, the fastify allowlist and
  CLAUDE.md's box-token sentence.
- Migration **126** (written as 112; renumbered to 125 when the stack was rebased onto `main` on 2026-11-24, and to 126 the same day
  after the coordinator advisor took 123), re-measured before the push.
- SHADOW ONLY: no mail, no prompt, no run state.

## Decisions this plan makes

1. **The path is `POST /api/coord/programmes/:slug/flow-outcome`**, not the spec's `POST /api/flows/outcome`: the programme
   in the path is how the call record and the remaining-work doors check ownership, and those are the pattern this door
   copies. Deviation `D-10014`.
2. **Only the coordinator that holds the programme reports.** The spec says "the session answers"; a worker's outcome
   already reaches its coordinator as wave-done mail, and one reporter keeps the attribution rule the existing
   `claimsProgramme` check. A worker reporting directly can be widened later, with its own ownership rule.
3. **Only instruction and skill blocks take a reported outcome.** A protocol step is the run machine's to report (3a reads
   it); a gate is the server's to measure (wave 4).
4. **What the engine would do** is a word: `observe <step>`, `measure <gate>`, or `send <role> <block> bytes=<n>
   missing=<vars>`. Going live (actually sending) is the operator's arm after this shadow has run, and is not in 3b.
