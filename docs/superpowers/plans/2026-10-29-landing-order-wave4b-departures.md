# Landing order wave 4b: two departures from its plan, recorded

- **D-7514 (2026-10-29)** — `fresh-within-pinned` (wave 4c's review, F5): `freshWithin` and `FRESH_FUTURE_SKEW_S` are each defined once, in `shared/api.ts`, and `landingShown` only there, with D-7481's reason beside it. No radar reader holds `Date.parse(`, `FRESH_FUTURE_SKEW_S` or a freshness window times 1000 on a code line, and the PWA's two readers hold no `new Date(`. `server/test/single-definition/core-vocab.test.ts` pins it.
- **D-7515 (2026-10-29)** — `draft-is-open` (wave 4b's whole-branch review): a session's PR counts as open for the landing match when its phase is `open` or `draft`. Only a merged or closed PR keeps a number the radar no longer measures, and so matches nothing.

**D-7514.** Wave 4c's review (its F5) found that nothing pinned `freshWithin`'s one definition. The coordinator added the row to this wave's brief. Task 1 added the holders pin and the reader scan, and Task 2 added the positive checks that `assembleFleet` and the lane's re-age call `freshWithin(`. The final review found that the PWA ordered its landings with `new Date(…)`, which the scan did not see. The fix round made a landing's `at` a fixed-width UTC stamp (`isRadarStamp`, checked by `parseProbe` and `reviveSessionLanding`), so the PWA orders by string comparison. It also widened the scan to `* 1_000`, `* 1e3`, and `new Date(` in the two PWA readers. `watch.ts` keeps a pre-existing `new Date(…).toISOString()` in a log line, which formats a time and reads no freshness, so `new Date(` is not scanned on the server.

**D-7515.** The plan read the session's PR as open when `phase === 'open'` (Design, `sessionLandingsOf`; D-7484). The radar lists PRs with `gh pr list --state open`, which includes drafts, and binds and pairs them. The server's PR sweep reads a draft as `phase: 'draft'`. Under the plan's text, every draft-PR session matched nothing, and a fleet whose workers open draft PRs read "No predicted conflicts in N measured PRs" while those PRs went unmeasured. The plan's reason for the check is that a merged PR keeps its number. That reason excludes merged and closed PRs, not drafts. `server/test/radar-lane.test.ts` holds a draft that matches and a closed PR that does not.

The plan is not edited, because merged plans are append-only. This file is the record. The programme coordinator folds both into the ledger.
