# Landing order wave 4b: eleven departures from its plan and its rulings, recorded

- **D-7514 (2026-10-29)** — `fresh-within-pinned` (wave 4c's review, F5): `freshWithin` and `FRESH_FUTURE_SKEW_S` are each defined once, in `shared/api.ts`, and `landingShown` only there, with D-7481's reason beside it. No radar reader holds `Date.parse(`, `FRESH_FUTURE_SKEW_S` or a freshness window times 1000 on a code line, and the PWA's two readers hold no `new Date(`. `server/test/single-definition/core-vocab.test.ts` pins it.
- **D-7515 (2026-10-29)** — `draft-is-open` (wave 4b's whole-branch review): a session's PR counts as open for the landing match when its phase is `open` or `draft`. A PR whose phase is anything else and which still carries a number matches nothing: a merged or closed PR, whose number the radar no longer measures, and a PR the sweep is backing off on (`unknown` or `unchecked`), which fails closed while the sweep fails. A row with no PR number still matches by id and branch.
- **D-7516 (2026-10-30)** — `landing-keyed-by-project` (Task 3): the PWA keys each landing, line and pair by `FleetSession.project` as well as the PR number. Keyed by PR alone, a clean #12 of one project hid a conflicting #12 of another, which breaks D-7480. A pair is listed once, under its lower PR, within a project, and the sentence names the project when more than one project has a landing.
- **D-7517 (2026-10-30)** — `radar-stamp-only` (Task 1): a probe's `at` must be the radar's fixed-width UTC stamp, checked by `isRadarStamp`, defined once in `shared/api.ts`. `parseProbe` reads any other `at` as unreadable, not stale; `reviveSessionLanding` drops a landing without a stamp to absent; the PWA orders landings by string comparison. Every doc the shipped radar writes passes it (review 1225). The stamp's shape is checked, not its calendar, so an impossible date reads stale.
- **D-7518 (2026-10-30)** — `head-id-registry-or-null` (Task 1): a head `id` that is neither `null` nor a registry id makes the whole doc unreadable, where the plan said "a string or null". An empty id was the one fail-open path on a corrupt doc, and the radar never writes one.
- **D-7519 (2026-10-30)** — `not-paired-clause` (Task 3): the chip's sentence adds "N not paired" for measured landings outside `pairHeads`.
- **D-7520 (2026-10-30)** — `read-regular-cap` (Task 2): `readRegular` takes an optional byte cap, measured by `statMeasured` before the read and checked on the bytes after it, so `readRadarProbe` goes through the one regular-file reader rather than a copy of it.
- **D-7521 (2026-10-30)** — `sentence-without-now` (Task 3): `conflictChipSentence(summary)` takes no `now`, because the summary already holds only landings `landingOf` showed. `plain-words` owns `conflictWords.ts` only, because `ConflictChip.tsx` holds no sentence of its own (every word is in `conflictWords.ts`).
- **D-7522 (2026-10-30)** — `measured-distinct-prs` (Task 3): the chip's "measured" count is distinct (project, PR) landings, not sessions, so two sessions on one PR count once.
- **D-7523 (2026-10-30)** — `radar-pass-in-l3` (Task 2): `readRadarPass` in `lineageRead.ts` (L3) owns the per-project reads and their deadline, with a fifth read reason, `late`, where the plan put the fan-out and the deadline in the L4 lane and named four reasons. The lane schedules the pass and keeps the map; the deadline is a timer inside one adapter call, which is L3.
- **D-7526 (2026-10-30)** — `drop-stale-returns-input-when-clean` (fix round 1, R1): `dropStaleLandings` returns its input array when no landing in it is past the window, and when some are, a new array that shares every unchanged row and copies only the rows it strips. The ruling said "returns new session objects". The cold frame's `frameCache` is a WeakMap keyed on the array, so a new array on every connect would mask the whole fleet again each time. No caller mutates the array or a row (review 1226), and the test pins both the identity and that the watcher's last fleet is never mutated. It is numbered from a new block, because the run's block ended at D-7523.

**D-7514.** Wave 4c's review (its F5) found that nothing pinned `freshWithin`'s one definition. The coordinator added the row to this wave's brief. Task 1 added the holders pin and the reader scan, and Task 2 added the positive checks that `assembleFleet` and the lane's re-age call `freshWithin(`. The final review found that the PWA ordered its landings with `new Date(…)`, which the scan did not see. The fix round made a landing's `at` a fixed-width UTC stamp (`isRadarStamp`, checked by `parseProbe` and `reviveSessionLanding`), so the PWA orders by string comparison. It also widened the scan to `* 1_000`, `* 1e3`, and `new Date(` in the two PWA readers. `watch.ts` keeps a pre-existing `new Date(…).toISOString()` in a log line, which formats a time and reads no freshness, so `new Date(` is not scanned on the server.

**D-7515.** The plan read the session's PR as open when `phase === 'open'` (Design, `sessionLandingsOf`; D-7484). The radar lists PRs with `gh pr list --state open`, which includes drafts, and binds and pairs them. The server's PR sweep reads a draft as `phase: 'draft'`. Under the plan's text, every draft-PR session matched nothing, and a fleet whose workers open draft PRs read "No predicted conflicts in N measured PRs" while those PRs went unmeasured. The plan's reason for the check is that a merged PR keeps its number. That reason excludes merged and closed PRs, not drafts. A PR the sweep is backing off on reads `unknown` or `unchecked` and still carries its number, so it matches nothing too: its sessions' landings are absent while the sweep fails, which fails closed (review 1225, F2). `server/test/radar-lane.test.ts` holds a draft that matches and a closed PR that does not.

The plan is not edited, because merged plans are append-only. This file is the record. The programme coordinator folds all eleven into the ledger.
