# `ccd ws-gc --fast`: the candidate list without the sizing (#123) — Implementation Plan

**Issue:** #123, "`ccd ws-gc` is too slow to run interactively — exceeds 60s on a 45-workspace registry".

**Status:** one task, one PR. It adds a `--fast` flag to `cmd_ws_gc` and `_ws_gc_row` in `ccd/ccd`, adds tests to `server/test/ccd-ws-gc.test.ts`, gives the new function its row in `ccd/contexts.tsv` (C4), and updates the verb's row in `README.md`.

## The problem

A plain `ccd ws-gc` is the read-only "what can I clean up?" view. It measures every worktree with `du` (`_ws_gc_bytes`, once per row), and then the whole set once more for the total. On a registry of 45 workspaces, some of them several GB, it did not return within 60 s. Operators then fall back to hand-rolled `du` and `git status` sweeps. The verb also cannot be tested against a time bound.

The issue was not profiled on a live box, and this fix does not profile one either. The cost it removes is the one the issue names: every `du` the command makes.

## The fix

`ccd ws-gc --fast` (D-5886) prints the same rows as the full run and skips every `du`:

- `_ws_gc_row` sets the size to `-` (unmeasured) instead of calling `_ws_gc_bytes`. None of the rungs that decide a row's state reads the size, so the rows match the full run's rows.
- An archived row takes the `worktreeBytes` that its archive manifest (`$REG/<id>.archivemanifest`) recorded when `ws-archive` measured the tree. The new `_ws_gc_manifest_bytes` reads that value with `jq`. It reads the file in place, the way `_ws_gc_row`'s rungs test `$REG/<id>.archived`, keeping `_reg_get`'s guard (a regular file, never a symlink). It does not call `_reg_get`, because a call from C4 into C1 would be one more cross-context reference, and the `ccd/contexts.tsv` ratchet forbids a rise. The `_reg_get` census is unchanged. Anything other than a whole number reads as `-`, never as 0: no manifest, a manifest that is not JSON, `null`, a fraction, a symlink, or no `jq` on the box.
- The aggregate `du` is skipped as well. The footer says that `--fast` skipped sizing and claims no total.

`GC_FAST` is a `local` that `cmd_ws_gc` always sets, so an exported `GC_FAST` cannot turn a plain run fast.

`--fast` is a read and never combines with `--prune`, in either order (D-5887). A prune decides each row by its own checks, never by the size column. Refusing the pair keeps that true by construction: the flag cannot change what a prune removes. A repeated flag or an unknown argument beside `--fast` is a usage error. The usage string is now `ccd ws-gc [--prune | --fast]`. The ccd stamp is regenerated with `ccrc restamp`.

## Tests

`server/test/ccd-ws-gc.test.ts`, describe "ws-gc --fast".

1. The acceptance test. A 45-workspace fixture registry is built with plain git and registry files: 5 archived with a manifest, 30 tracked, 5 dirty, 5 orphans. `--fast` lists exactly the full run's rows (state, project, workspace, path), makes no `du` call (`_plat_bytes` is stubbed to log), and finishes under the stated bound of 20 s. Measured at about 1.7 s on a developer laptop.
2. An archived row shows its manifest's `worktreeBytes`, and a tracked row reads `-`. The full run measures the same tracked row (the control).
3. to 6. An archived row whose manifest holds `null`, is not JSON, holds a fraction, or is missing reads `-`, never 0.
7. The footer says sizing was skipped and claims no total.
8. and 9. `--fast --prune` and `--prune --fast` are refused, print no `pruning:` section, and remove nothing, even with a clean merged orphan present.
10. `--fast --purge`, `--fast --fast` and `--prune --prune` are usage errors.
11. `--fast` modifies nothing under the worktrees, registry or project roots.
12. `ccd ws-gc --fast` is reachable as a subcommand.
13. An exported `GC_FAST=1` leaves a plain run measuring.
14. An archived row whose manifest is a symlink reads `-`.

Red first: against `origin/main`, tests 1 to 12 and 14 fail, because `ccd ws-gc` refused `--fast` as a usage error (or, for 10, printed the old usage string). Test 13 passes on both trees. It is a guard, and mutant M8 turns it red. The other 75 tests in the file pass on both trees.

## Deviations and decisions

Issued 2026-10-20 to this fix, a block of two. D-5886 and D-5887 are defined here, once.

- **D-5886** — `ws-gc-fast`: `ccd ws-gc --fast` lists the full run's rows without any `du`. Archived rows take their archive manifest's `worktreeBytes`, and every other row reads unmeasured. The footer claims no total. Pinned by tests 1 to 7, 11 to 14.
- **D-5887** — `ws-gc-fast-read-only`: `--fast` never combines with `--prune`, in either order, so the flag cannot change what a prune removes. Pinned by tests 8 and 9.

## Follow-ups

- `--fast` still runs one `git status` per registered tree, because the dirty rung decides membership. If that read is also slow on very large trees, it needs its own measurement on a fixture before any change.
