# The coordination protocol stops depending on `curl` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A session can work a ccrc programme from a repo whose committed
`.claude/settings.json` denies `Bash(curl:*)` — because the protocol's client is a
closed-verb binary, not arbitrary HTTP.

**Architecture:** A self-contained `ccrc-api` on the fleet box, installed beside `ccd`,
carrying a CLOSED table of the seventeen routes the two skill corpora actually call. It
takes no host and no path from argv: the address comes from `~/.ccrc/agent.env`'s
`CCRC_SERVER_URL` and the route comes from the table. Both skill corpora are rewritten
onto it. `EXEC_COMMANDS` stays `['tmux','ccd']`, so nothing on the PWA→server→agent path
can reach it.

**Tech Stack:** bash (`ccd/ccrc-api`), vitest (`server/test/`), the two skill corpora.

**Spec:** No standalone spec. The decision record is the incident of 2026-08-26. A worker
on a fleet project whose committed `.claude/settings.json` denies `Bash(curl:*)` and
`Bash(wget:*)` could not read or ack mail — twelve permission denials in one wave — and
the coordinator on the same programme then halted itself on discovering that its OWN
calls had only ever succeeded because `resp=$(curl …)` slips past that matcher: the deny
rule was working on one session and being evaded by accident on the other. The project is
not named here; this tree is bound for public release and its docs speak in ROLES
(D-628's lesson, learned earlier the same day on a sibling plan). Operator ruling the
same day: ship the curl-free client.

## Why this is not an evasion of the deny rule, and what keeps it honest

A repo that denies `curl` and `wget` is denying **arbitrary outbound HTTP by the agent**.
`ccrc-api` is not that: it can reach exactly one host (this fleet's own server, from
config the agent does not supply) over exactly seventeen enumerated routes, with the box
token. It cannot fetch a URL. That property is the whole justification, so it is
**enforced and pinned**, not merely intended:

- No argument anywhere in the table is a URL, a host, or a path fragment. Task 5 pins it.
- There is **no passthrough verb.** No `ccrc-api get <path>`, no `--url`, no `--raw`.
  Adding one would make this curl with a different name, and would retroactively make
  every install of it an evasion.
- **No impersonation surface.** `mail ack` and `mail send` derive `fromId`/`fromUuid`
  themselves from tmux plus the registry — the same pair the skills derive by hand today —
  and there is deliberately no `--as <id>` flag. Identity on this fleet is attribution
  rather than authentication, so the client must not become the one place that makes
  forging it convenient.

If a future route is needed, it is a new row in the table and a new test — deliberately
more friction than an escape hatch.

## Global Constraints

- **`EXEC_COMMANDS` stays `['tmux','ccd']`.** `ccrc-api` must NOT be added to the exec
  whitelist. It is a session-side client; the PWA path has no business reaching it.
  Pin this (Task 5) — the temptation will be real once the binary exists.
- **NEVER print the token.** The client reads it and sends it; it must not echo it, log
  it, or put it in an error message. Pinned in Task 5.
- **The address is config, never a literal.** `CCRC_SERVER_URL` from `~/.ccrc/agent.env`,
  the same single source the corpora already name. Absent → a clear refusal, never a
  guessed host. (Guessing a host is exactly what a worker did on 2026-08-25.)
- **The token file is a DOCUMENT with a token in it, and the corpora already say so —
  but they state the wrong consequence.** Measured 2026-08-26 on the fleet host:
  `~/.cc-secrets/ccrc-mail.token` is 24 lines / 1453 bytes, 23 lines of `#` preamble above
  one 64-char value. Both `ccd/coordinator-skill/SKILL.md:113` and the installed home
  already teach the `grep -v` extraction ("EXTRACT, never `cat`"), so this is NOT an open
  corpus bug. What IS wrong is the sentence justifying it: it says `cat` makes "every call
  answer a bare 400 before any route logic runs". Neither observed failure looks like that.
  `TOKEN=$(cat …)` keeps the interior newlines, so curl refuses to send at all — **exit 43,
  no HTTP status whatsoever**, nothing for a caller's `$code` check to read. Strip the
  newlines and the header is legal but wrong, and the answer is **`401
  {"ok":false,"error":"unauthenticated","detail":"wrong box token"}`** — which reads as a
  rotated secret and sends the reader to the wrong box entirely. A caller told to expect
  400 will not recognise either one.
  Two things follow for this slice, and neither is "patch the comment on its own":
  1. `ccrc-api` reads the file itself with the extraction rule (first non-blank, non-`#`
     line — `coord/token.ts`'s `extractToken`, which `deploy/notify.sh` already matches),
     so no caller performs the dance and no caller can get it wrong. **Pinned in Task 5**,
     as a property, not an implementation detail.
  2. Tasks 3 and 4 rewrite that paragraph out of both corpora anyway. The corrected
     consequence goes in whatever replaces it — a fix landed as part of the slice that
     removes its subject, rather than an agent-first deploy of a comment.
  Standing lesson this cost, already in the operator's memory and re-earned here: **a
  skill loaded at session start goes stale across deploys.** The session copy driving this
  orchestrator still had the pre-2026-08-25 `cat` flow; the installed one did not. Re-read
  the installed `SKILL.md` before trusting a remembered protocol line.
- **`~/.local/bin` is NOT on the `claude-session@` unit PATH.** Measured 2026-08-26: the
  units run with systemd's default PATH, which is why a worker's own probe reported `ccd`
  and `ccrc` "not on PATH" while both are installed. So the corpora must invoke the client
  by a path that does not depend on PATH — `"$HOME/.local/bin/ccrc-api"` — or the unit's
  PATH must be fixed. **Prefer the explicit path**: it needs no unit-file change and
  therefore no restart of eighteen live sessions. Decide, and say which, in the ledger.
- **Self-contained.** `ccrc-api` may `source` nothing. The moment it does, it needs the
  shim treatment `ccrc` has (`deploy/deploy.sh:261-295` argues that at length) and a lone
  copy at `~/.local/bin` would be dead on every box. Task 5 pins it.
- Single definition: the route table is written ONCE. Any test, doc or skill listing that
  needs the route set derives it. `server/test/single-definition.test.ts` fails the build
  on a second copy.
- **AGENT-FIRST.** This touches `ccd/` AND both skill corpora. Fleet host first.
- Mutation-table discipline; deviation numbers from `POST /api/ledger/deviations`.

the one verb that clause forbids, and would do it in the name of convenience. A closed
table is only worth having if what it closes over is the set of routes the callers
actually call. **If a future need for it is real, it is an operator tool, not a row
here.** (D-688.)

### Task 1: the client, and its closed table

**Files:** Create `ccd/ccrc-api`. Test: `server/test/ccrc-api.test.ts`.

**The contract, chosen to simplify the corpora rather than mirror curl:**
- **stdout is the response body, verbatim.** Nothing else. The body IS the protocol —
  every refusal these routes send arrives as a 4xx JSON body.
- **stderr carries `http <code>`.** A caller that wants the status reads stderr; a caller
  that wants the body pipes stdout. This retires the `-w '\n%{http_code}'` +
  `${resp##*$'\n'}` dance the corpora repeat in six places.
- **Exit 0 whenever an HTTP response was received**, whatever its status — for the same
  reason the corpora say "never use `curl -f`". Non-zero ONLY when no response happened
  (DNS, refused, timeout), and then stdout still carries a synthetic JSON object
  (`{"ok":false,"error":"transport","detail":"…"}`) so a caller never has to parse
  two shapes.
- **Bodies come from `--json <file|->`,** not from a flag per field. The path is
  enumerated; the body was always the caller's. This keeps the client thin and the
  surface closed at the same time.

`ccrc-api whoami` prints this session's `{"id":…,"uuid":…}`, derived from tmux plus the
registry — the pair every skill currently derives by hand, and the one `mail ack`/`mail
send` use internally so it cannot be got wrong (D-41's two-sequences trap) and cannot be
forged.

Shape: `ccrc-api <group> <verb> [<id>] [--json <file|->] [--to <id>]`.
The table maps `<group> <verb>` → `(METHOD, path-template, needs-id?)`. Path templates
interpolate ONLY an id the table declares, and that id is validated against a
conservative pattern before interpolation — never pasted raw.

### Task 2: it ships

**Files:** Modify `deploy/deploy.sh`. Test: `server/test/deploy-*.test.ts`.

### Task 5: the guards that make the closed table a mechanism

**Files:** Create/extend `server/test/ccrc-api-closed.test.ts`.

Five standing tests, each with a measured red:

1. **The table covers what the corpora call.** Derive the route set from the corpora by
   the same grep used above, derive the client's table from `ccd/ccrc-api`, and assert
   the corpora's set is a SUBSET of the table's. A skill that starts calling an
   unreachable route goes red. (Subset, not equality: the table may lead the corpora.)
2. **No corpus calls curl any more.** Assert zero `curl ` occurrences in both corpora.
   This is the test that would have caught the original defect class.
3. **`ccrc-api` is not on the exec whitelist.** Assert `EXEC_COMMANDS` is exactly
   `['tmux','ccd']` and that no whitelist entry names `ccrc-api`.
4. **No passthrough, no impersonation, no token echo.** Assert the client's source
   contains no argument accepting a URL/host/path (`--url`, `--host`, `--path`, `--raw`),
   no `--as`/`--from-id`/`--from-uuid` override, and that the token variable is never
   passed to `echo`/`printf`/a log.
5. **Self-contained.** Assert `ccd/ccrc-api` contains no `source`/`.` of a sibling file —
   the property Task 2's install shape depends on, and whose loss is silent until a box
   runs the verb.

- [ ] Each: write, run red, implement/verify, run green, mutate, record.

## Deviations found

_(allocated from `POST /api/ledger/deviations` during execution)_

- **D-688** — the plan said eighteen routes and named `POST /api/coord/pause` as the
  eighteenth. Re-running the grep the plan itself mandates as Task 1's first step — the
  instruction exists because "the corpora move" — found it in **neither corpus, in any
  spelling**. It had been inferred from `routes.ts`, where the route is real, rather than
  measured from the callers, which is exactly the error the re-measure instruction was
  written to catch. The table ships **seventeen** rows.
  Excluding it is not a scope reduction, it is the safer answer on its own merits:
  D-282 leaves `coord/pause` and `runs/:id/abandon` deliberately UNGATED so a wedged run
  has a release valve the coordinator's own box token cannot lock, and coordinator clause
  4 forbids a session from ever raising or lowering that file itself. A session-side
  client carrying `coord pause` would hand every session the one verb that clause exists
  to deny. If the need is ever real it is an operator tool, not a row here.
  Two smaller findings from the same measurement, both for Task 5's standing test: the raw
  grep also emits `POST /api/mail/7/ack` (a worked example in
  `references/mail-envelope.md:25`, carrying a literal DELIVERY id) and the fragments
  `POST /api/mail/` / `GET /api/mail/` that the pattern clipped mid-sentence. The test
  must normalise a literal id segment to `:id` and drop a trailing-slash fragment, or it
  will demand three table rows that should not exist.

- **D-738** — the mail ENVELOPE is a third place the protocol is taught, and it is
  shipped by the SERVER at runtime. `renderEnvelope` (`server/src/coord/envelope.ts`)
  wrote `ack: POST /api/mail/<id>/ack with header x-ccrc-mail-token (the value in
  ~/.cc-secrets/ccrc-mail.token)`, and that text is injected into a recipient's pane on
  every delivery — so a session on a repo denying `Bash(curl:*)` was being handed
  instructions it could not follow, by the server, on every single mail. Rewriting the two
  corpora would have left it standing. Found only because `coordinator-skill.test.ts` pins
  `mail-envelope.md` byte-identical to `renderEnvelope`'s output, so editing the doc
  reddened a test that pointed at the source. The reference doc is not a copy of the
  protocol — it is a fixture of the server's own output, and that is what made this
  visible.
- **D-739** — Task 5's guard as the plan wrote it ("assert zero `curl ` occurrences in
  both corpora") contradicts Task 4 as the plan wrote it ("rewrite the paragraph to say
  the invariant in the new terms rather than deleting it — an invariant that loses its
  stated reason is how it gets re-broken"). Kept prose necessarily says the word. The
  guard implemented is therefore about INVOCATIONS: no fenced code block in either corpus
  may run curl, while prose may explain why the invariant exists. That is also the
  narrower, more accurate reading of what the deny rule itself forbids.
- **D-740** — the token-print guard was INERT as first written and passed its own
  mutation. It looked for `$token`/`$TOKEN`; `read_token`'s local is `$t`, so planting
  `echo "token=$t"` in the client left the suite green. It now DERIVES the variable
  names from the client's own assignments rather than guessing them, exempts
  `read_token`'s own `printf` (returning the value is how a bash function returns), and
  reds on both the local and the header spelling. Second instance this build of a guard
  that pinned a shape and measured nothing — the same class the operator's standing note
  records.
- **D-741** — three of Task 5's negative scans failed on the client's own docstring, which
  names every flag it deliberately does not have ("no `--url`, no `--host`, no `--path`,
  no `--raw`"). A whole-file scan reds on the sentence promising the property it is
  checking. The scans read comment-stripped source now. Recorded because the fix is not
  the interesting part: a negative textual guard over a file that DOCUMENTS its own
  negatives will always do this, and the next such guard should strip first by default.

- **D-791** — D-738 converted `renderEnvelope` and MISSED `renderMailNudge`, its sibling twelve
  lines below it in the same file. The nudge is the worse of the two to get wrong: `renderEnvelope`
  is stored once per mail, while the nudge is what the delivery lane TYPES INTO A PANE on every
  sweep, and its own docstring says why that matters — *"this line is the ONLY protocol text
  guaranteed CURRENT in the recipient's pane; a skill loaded into a session goes stale across
  deploys."* Measured consequence on the live fleet: a worker on a repo that denies `Bash(curl:*)`
  received the nudge every ten minutes for over an hour and refused every one, correctly, because
  raw HTTP was the only thing it taught. The nudge now names `ccrc-api` by explicit path and hands
  the reader no address and no token job at all — strictly more self-sufficient, since those two
  teachings became properties of one binary instead of instructions a stale reader must follow.
  **The lesson is the search, not the line:** D-738 was found by a test that pinned a doc against
  `renderEnvelope`'s output, so the search stopped at the function that test named. Nothing asked
  what else in that file spoke the protocol.
- **D-792** — a mail delivery blocked at a TRANSIENT gate never parks, never escalates, and never
  surfaces anywhere except an `unreadMail` integer. Measured: delivery 76 sat `delivered` with
  `attempts: 0` for eleven hours, re-selected as due on every sweep and refused each time at a gate
  that accrues no attempt — so it never approaches the replay ceiling that would park it. Every
  other surface reported health: `GET /api/peers` said the session was `deliverable: 'yes'` (the
  peers projection deliberately excludes the transient rungs), the run showed a tidy `unreadMail: 1`,
  and the session was `running` and idle. The console showed a healthy worker and a live run with no
  indication that its only wake-up call had been silently refused hundreds of times. Recorded, not
  fixed here: the fix is a visible rung for "refused at a transient gate, N times, since T", and it
  wants its own slice rather than riding a nudge rewrite.

- **D-842** — `POST /api/runs/:id/items` has always required item IDS, and until this slice
  NOTHING published them. `GET /api/runs` projects `RunItemTally` — `{done,total}` and nothing
  else; the dispatch response never carried them; `CoordStore.workItems` had the rows the whole
  time and no route asked. So a coordinator could DECLARE a ledger it could never SETTLE. Found
  the only way it could be: a live coordinator, unblocked at last, advanced its run, reached the
  settle call holding four titles and no ids, guessed `1`, and was refused `unknown-item`. It then
  stopped and reported rather than guessing again — which is the only reason the console tally was
  merely stuck rather than quietly wrong. Fixed by `GET /api/runs/:id/items`, exempt-but-
  authenticated like `GET /api/runs` (the coordinator reads it cookieless from the fleet host),
  plus the `runs items-list` client row and a line in both corpora. The pin that matters is the
  ROUND TRIP — read the ids, settle them, read again — because a shape assertion alone would not
  prove the ids it returns are the ids the settle route accepts.
  Worth noting what caught the rest: three separate standing guards refused the change until it
  was complete — the auth census (a new route must be classified), the corpus test (every
  coordinator-domain route must be NAMED in the skill), and the closed-table agreement. None of
  those are about this feature; all three are about not shipping half of one.
- **D-843** — the closed-table agreement test parsed the client's route keys with `[a-z.]+`, which
  silently DROPPED `runs.items-list` — the first verb in the table to contain a hyphen. The test
  went red comparing 17 keys against 18 rows, which is the guard working; had it been written to
  count its own array instead of reading the client, it would have passed. That is the second time
  in this build that reading the source rather than restating it is what caught a defect, and it is
  the same lesson the row-count assertion learned three commits earlier.
