## What was built

- `pwa/src/lib/screenCache.ts`: `SCREEN_CACHE_MAX = 64`, `peek`, `put`, `forget`, `clearScreenCache`, and the key
  builders `settingsKey(name)` (over a closed union of the eight Settings reads) and `digestKey(day)`. Memory only.
- The six hooks seed their first render with `reader(peek(key)?.raw)`, through each hook's own reader, and keep a good
  answer with `put(key, raw, Date.now())` after the reader accepts it. `settle` forgets the key.
- The provider seeds the auth status and the passkey list the same way, the list only under the same armed guard as a
  fresh read. `refreshAuth`, the re-read after an Add or a Revoke, forgets both keys. Push state is not kept.
- `DigestScreen` seeds its first render from `digestKey(day)` through `asDigestAnswer`, with state `ok`, and re-reads.
  A failed re-read keeps the shown digest beside the error, as it already did across a day change.

## Departures

- `setup-clears-screen-cache`: `pwa/test/setup.ts`'s shared `afterEach` calls `clearScreenCache()`, beside the
  highlight cache's `clearEveryLru()`. The file is outside the task's split. The coordinator ruled it in before the
  edit. Why: the cache is module state, and vitest keeps one module instance per test file. About 53 test files render
  a Settings hook, the provider, `FleetChrome` or the Digest, and per-file hooks would spread into files that other
  runs hold.
- `screen-cache-keeps-its-own-map`: `screenCache.ts` does not build on `createLru` (`pwa/src/lib/highlightCache.ts`),
  the one other bounded cache in the app. Its `get` makes the key newest, and it has no delete. The plan's `peek` moves
  nothing and its `forget` drops one key, so reusing it means editing `highlightCache.ts`, outside this task's split.
  The two are a primitive and an owner: `createLru` is the highlight worker's bounded LRU, and `screenCache` owns query
  answers. Folding the primitive under `screenCache` (add `peek` and `delete` to `Lru`) is a small later change, if the
  reviewer wants one mechanism.
- `a-dropped-view-forgets-its-key`: the collector, dispatch-abandon and test-box hooks drop their view on a
  not-available answer (and the collector also on `state-unmeasurable`). Each now forgets its key as well, so the next
  mount never draws a view the server said is gone, such as a Live radio from before a rollback. The plan names only
  `settle` as a forget.
- `a-correction-forgets-the-day`: a digest correction is a write, so it forgets the day's key before the re-read, as a
  hook's `settle` does.
- `gate-off-forgets-the-passkey-list`: a status read that says the gate is off forgets the kept passkey list.
- `auth-failure-replaces-the-kept-read`: a failed status read still draws `failed` (and the list `unasked`), as on
  main. `AuthRead` and `PasskeysRead` are unions with no "kept answer beside a failure" state, and adding one changes
  every card that reads them, outside this task's split. The six polls do keep their view beside a failure.
- `updates-seq-stays-zero-on-a-seed`: a seeded update view carries `seq` 0, so the halt banner's hold, which waits for a
  read issued after the operator's tap, never ends on a kept answer.
- `linear-kept-as-read`: `api.linearWorkspaces` already runs the list's reader, so the hook keeps the read list and
  draws it back through `readLinearWorkspaces`. `settings-last-view.test.tsx` pins that this reader reads its own answer
  whole.

## Mutants

Each was applied in place, its named case was run, and the file was restored from a saved copy with its sha checked.
All 18 were killed.

| # | Mutant | Case that went red |
|---|---|---|
| M1 | `put` without the bound | `screen-cache` "the 65th key drops the oldest" |
| M7 | `put` without moving the key | `screen-cache` "peek moves nothing, put moves the key to newest" |
| M2a to M2d | stall, updates, Linear and passkeys seed from `raw` without their reader | `settings-last-view` "a cached answer the reader refuses draws the pending state" |
| M2e | the Digest seeds from `raw` without `asDigestAnswer` | `digest-last-view` "a kept answer the reader refuses draws Loading" |
| M3a to M3d | stall, collector, dispatch-abandon and Linear `settle` do not forget | `settings-last-view` "a write's settle forgets the key" |
| M3e | `refreshAuth` does not forget | `settings-last-view` "a refresh of the auth pair after a write forgets both keys" |
| M3f | a digest correction does not forget | `digest-last-view` "a correction forgets the kept day" |
| M4 | the digest key ignores the day | `digest-last-view` "a different day draws nothing cached" |
| M5a to M5c | the collector, dispatch-abandon and test-box drops keep the key | `settings-last-view` "an answer that drops the view forgets the key too" |
| M6 | the test-box hook never keeps its answer | `settings-last-view` "a second visit draws the last updates, stall, collect, abandon, testbox and linear views" |

M2e and M4 survived the first round. The screen's own day filter hid a mis-keyed answer, and the refused answer carried
no `day`. Both cases were tightened, and both mutants were then killed.
