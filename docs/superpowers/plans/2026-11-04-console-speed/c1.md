## Departures

- **settings-provider-stays-eager** (accepted in 14945). `SettingsDataProvider` wraps the whole shell on every route
  (D-5504) and seven Settings section files import it. A lazy provider would hold the frame at start-up and defer
  nothing, so only `SettingsScreen` is lazy.
- **suspense-fallback-is-a-loading-line.** The plan names `ScreenFallback` as the Suspense fallback. That component is
  the boundary's error copy ("This screen could not be shown.", with "Back to the fleet"), so every first open of a
  lazy screen would flash an error. The fallback is a `role="status"` "Loading…" line in the existing placeholder copy
  style. A chunk that fails to load still throws into the boundary and draws `ScreenFallback`, as the plan's test asks.
- **docs-reads-keep-no-limit.** The five docs loaders (`projects`, `tree`, `file` and `refresh` through one helper,
  `raster` through its own call) pass `timeoutMs: null`. Their contract is never to reject for a
  server answer, and their slot vocabulary (`docs/failures.ts`) has no word for "slow": a timeout would reject, and
  `DocsScreen`'s index load has no catch, so the index would stay on "Loading" for good. The server bounds these reads
  (the ccd docs verbs at 15 to 20 s, after a read lane's wait of at most 10 s). A "slow" slot is the native docs
  reader programme's to add, if wanted.
- **read-limit-own-controller.** The plan's sketch is `AbortSignal.timeout` merged by `AbortSignal.any`, with a
  fallback for an engine without it. One `AbortController` carries both the caller's signal and the limit instead, and
  the call races the limit. It needs no fallback, and it rejects `ApiTimeout` even when a fetch ignores its signal.
  The limit's timer is not cleared on the answer, so a body still being read when it fires is aborted too; one already
  read is untouched.
- **beat-frame-consumed-by-socket.** `ReconnectingSocket` consumes `{type:'beat'}` and never hands it to a store's
  `onMessage`: it is the transport's frame. It still counts as a message for the silence bound.
- **nudge-acts-only-once-armed** (ruled in fix round 1, review 1464 F3; it replaces the first round's
  `nudge-measures-open-time-before-first-message`). The spec's §2.3 has `nudge()` replace any open socket whose last
  message is 30 s old. Today's server sends no beat and frames only on change, so that closed and reopened a quiet,
  healthy fleet or session socket on every return to the page. `nudge()` now replaces an open socket only once a beat
  has armed it (phase `armed`) and it has then been quiet for 30 s; before the first beat a return to the page never
  closes an open socket. A connecting socket is left to its 10 s connect limit. The spec sentence is corrected on the
  coordinator's ledger pull request.
- **lazy-screens-await-in-tests.** With the six screens lazy, a test that renders `<App />` on one of their routes and
  asserts in the same tick sees the loading line: the chunk resolves later (the session screen's, which pulls in
  xterm, often after many synchronous cases have finished). Measured before any fix: 44 cases red in 7 files, every
  one of that shape. Fixed without changing any assertion's meaning:
  - `app-detail-boundary.test.tsx` (in C1's list): `findBy` at each case.
  - `app.test.tsx` (7 cases) and `refined-phone.test.tsx` (5 cases): `findBy` at the failing sites.
  - `app-docs-boundary.test.tsx` (1 case): `findBy` at the site.
  - `skin-switch.test.tsx` (18 cases) and `inspector-hide.test.tsx` (10 cases): their cases and helpers are
    synchronous throughout (21 `openSession` calls in one file), so a `beforeAll` opens each lazy route the file uses
    once, through the real `React.lazy` path, and awaits it; every later render draws at once.
  - `browser/refusal-copy.browser.test.ts` (claimed under the ruling on 15029): one wait before its PR keycap click.
    At Refined 1920 px the eager inspector rail draws a PR keycap too, so `.keycap--pr` `.first()` met the
    inspector's before the lazy session screen had drawn, and "Archive now" never appeared (red 3 of 3 on the
    branch, green on main). The wait holds until the Suspense line is gone and `.shell-detail` holds a keycap.
  - `app-pane-reset-timing.test.tsx` (1 case): the same `beforeAll`, not an await. The case proves the pane reset
    runs before the arriving screen's mount effect in the same commit; awaiting a first chunk load would mount the
    screen in a later commit, after the reset by construction, and prove nothing.
- **browser-test-compares-reached-and-opened.** The plan asks for "the computed styles of the eager build". No eager
  build exists inside a browser run, so the test checks the two ways a lazy chunk could change styles: every entry
  button and heading's computed style is the same before and after the chunk (and its own sheet) loads, and a lazy
  screen draws the same whether reached by a navigation or opened as the first page. It waits out running CSS
  transitions before each snapshot.
- **ws-test-retry-opens.** `ws.test.ts` "treats a socket error like a drop" left its retry connecting for 60 s, which
  the new 10 s connect limit gives up and retries. The case now opens the retry, keeping what it pins: one retry, no
  duplicate from the trailing close.
- **api-test-get-carries-a-signal.** `api.test.ts` pinned `updates()` as a GET with no init at all. Every GET now
  carries its limit's signal, so the pin reads "only a signal": no method, header or body.

- **read-limit-in-its-own-module.** The plan puts the limit in `api.ts`. That file is one the growth check holds, and
  the limit grew it by 44 net code lines against a limit of 40, so `READ_TIMEOUT_MS`, `ApiTimeout`, `ReadOpts`,
  `LONG_READ_MS` and the limited fetch live in `pwa/src/lib/readLimit.ts`, called from the funnel in one line, as
  the plan's Global Constraints ask. `api.ts` re-exports every name, so the plan's interface is unchanged.
  `api.ts` now grows by 6.
- **lazy-screen-wrapper** (fix round 1, review 1464 F2; corrected in fix round 2, review 1473 F1 to F3). The plan
  names React's `lazy`. It keeps a rejected load for the life of the page, so the six screens use `lib/lazyScreen.ts`.
  A rejected load rejects with `ScreenLoadError`, and `ScreenFallback` answers that with "This screen could not be
  loaded." and a Reload button. The failure is forgotten only once React has seen it: the detail boundary's
  `componentDidCatch` calls `forget()` after drawing its fallback, so each reset asks the loader once more, never more
  (round 1 forgot it in the loader's own catch, and a load slower than a React turn to fail then retried without end:
  review 1473 F2). That second ask recovers on the next navigation only where the engine fetches a failed module
  again: Chromium remembers a failed module per URL and rejects with no request, so there Reload is the recovery
  (review 1473 F1; no cache-busting query, as ruled). Once a load has resolved, a newly mounted screen is the resolved
  component, with no Suspense on that path, so a preloaded first open draws in its first commit, with no loading
  line (review 1473 F3); a screen already mounted through the lazy path keeps its mount.
- **collect-lane-get-carries-a-signal.** `use-collect-lane-view.test.tsx` had the same "no init at all" pin for
  `collectLane()`; l.82 now reads "only a signal", under the leave above.

## The GETs whose server bound is above 20 s

Read from the server routes (`server/src/remote/runner.ts`'s `CCD_VERB_TIMEOUT_MS`, `CCD_TIMEOUT_MS` = 90 s and
`TMUX_TIMEOUT_MS` = 10 s; the agent link's `CLIENT_TIMEOUT_SLACK_MS` = 5 s; `update/inventory.ts`'s
`INVENTORY_BUDGET_MS`). Each takes its own limit, `LONG_READ_MS` in `api.ts`:

| Read | Server bound | Own limit |
|---|---|---|
| `workspaceAudit` (`GET /api/sessions/:id/workspace/audit`) | `knownId`'s registry read (15 s), then `ccd ws-audit`, the 90 s default, plus 5 s | 115 s (was 100 s) |
| `pr` (`GET /api/sessions/:id/pr`) | `knownId`'s registry read (15 s), then the slower of `ccd pr-state` (25 s, plus 5 s) and the route's task read beside it (`prTasks`: four sequential agent reads of up to 15 s each, five with its re-listing): 45 s on the pr-state path, 75 or 90 s if a slow agent still answers each task read near its bound | 50 s (was 35 s) |
| `paneHistory` (`GET /api/sessions/:id/pane/history`) | two tmux calls in sequence, 10 s each, with the 5 s slack on each call: 30 s | 35 s |
| `updates` (`GET /api/updates`) | on a cold start, two inventory sweeps of 10 s each | 30 s |
| the five docs loaders | ccd docs verbs 15 to 20 s, after a lane wait of up to 10 s | none (`docs-reads-keep-no-limit`) |

The `pr` limit stays at 50 s, as ruled in fix round 2 (review 1473 F4): the 75 to 90 s case needs an agent that is
slow and still answering (a wedged one drops the link within 30 to 45 s and rejects the reads at once), and a timeout
there is a fair "slow": the PR sheet keeps the fleet sweep's PR state and leaves the draft's title and body unfilled.
Every bound in this table is the remote fleet's. In local mode (`CCRC_FLEET=local`) the server's ccd and tmux calls
have no remote bound at all, and the client's limits are the only ones.

Fix round 1 (review 1464 F6) added the `knownId` headroom: both routes read the registry over the agent link (one
remote read, bounded at 15 s) before the ccd call, so their limits rose by 15 s. `paneHistory` is deliberately not
behind `knownId`. Each limit is pinned by a case in `api-timeout.test.ts` (F5).

These multi-read routes keep the 20 s default, and a 20 s `ApiTimeout` on them is a fair "slow": each remote read is
bounded at 15 s, several run in sequence with no overall cap, and only an agent that accepts requests and never
answers reaches 20 s (a down link rejects at once).

| Read | Server shape | Limit |
|---|---|---|
| `GET /api/projects` | several remote reads in sequence; the watcher serves it while fresh, `ProjectWalkCache` 30 s | 20 s |
| `GET /api/fleet` | several remote reads in sequence; S2 serves it from the watcher's last tick | 20 s |
| `GET /api/accounts` | several remote reads in sequence | 20 s |
| `GET /api/sessions/:id/commands` | `knownId`, then the pane's commands read | 20 s |

The one consequence worth a fix was the composer's: it cached any failed commands read as an empty list for its
whole life. Now a failed read stays unknown, is not asked again while that `/` command is typed, and is asked once
more when the next one starts (`composer-slash.test.tsx`). In local mode (`fleetMode` not remote) the server's ccd
and tmux calls are unbounded; the client's limits apply there too.

## Waits on

The watchdog arms only on a `beat` frame, which S2 adds to both sockets (spec §6 point 1). Until S2 lands, only the
connect limit acts: an open socket is never closed for silence, by the check or by a return to the page. C2's last step passes
`usePoll`'s signal through the `ReadOpts` added here; S2's app step calls `api.runsPage`.
