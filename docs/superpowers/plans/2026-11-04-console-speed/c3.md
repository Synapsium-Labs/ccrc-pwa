# Console speed, Task C3: reloading after a release

The task note for Task C3 of `docs/superpowers/plans/2026-11-04-console-speed.md`. The coordinator folds what the ledger
should learn from it into the plan. Spec: `docs/superpowers/specs/2026-11-04-console-speed-design.md` §2.5 and D15.

The operator's ruling on item 33: "Reload when you next move between screens, never in the first seconds back." The
coordinator set "the first seconds back" at 15 s (`RELOAD_QUIET_MS`).

## Step 0: measured on `origin/main` (`08e3b290a`)

- `pwa/package-lock.json` pins `vite-plugin-pwa` **2.0.0**. Its `dist/client/build/register.js`, read from this
  workspace's own `pwa/node_modules`, has this auto arm (`registerType: 'autoUpdate'`):

  ```js
  wb.addEventListener("activated", (event) => {
    if (event.isUpdate || event.isExternal) {
      if (onNeedReload)
        onNeedReload();
      else
        window.location.reload();
    }
  });
  ```

  Without `onNeedReload`, every activation of a new worker reloads the page. With it, the plugin calls it instead
  and reloads nothing itself.
- `requestUpdate`'s only caller is `pwa/src/stores/fleet.ts`, the `hello` arm (`if (blocked && !get().blocked)
  requestUpdate();`, line 654 at this commit).

  `lib/usePoll.ts`, `lib/ws.ts`, tests and its own note. It does not touch `main.tsx`, `swupdate.ts`, `router.ts` or
  `vite.config.ts`. PL10 (PR #2286) edits `lib/routes.ts`, which C3 only reads, through `matchRoute`.
- `main-bootstrap.test.tsx` and `stores.test.ts` "hello with min > FLEET_PROTO sets blocked and calls requestUpdate
  once" pass on the base. The `stores.test.ts` case stays green unchanged after the task.

- A typed draft: the composer keeps its text in component state (`Composer.tsx`, `useState('')`), not in storage, and

  route) therefore already unmounts the composer and drops that text today. The gate reloads only on such a move,

  holds until Retry or Discard, with no time bound. What the full load still loses that the in-page move kept, by the
  review's trace and not held: an "Archive all" loop the client drives, cut off part-way; an open sheet's typed fields
  on the desktop shortcut path; sidebar scroll; the instrument skin's phone tab.

## A failed lazy chunk, and C1

Since fix round 1 C3 has no failed-chunk arm (departure `no-chunk-failed-arm`). It adds no `vite:preloadError`
listener and never calls `preventDefault()`, so vite's preload helper rethrows the real error to its caller: C1's
`ScreenLoadError` and its screen fallback with a Reload door, the Docs reader's fallback, `ExportSheet`'s `no-start`.
That door is the immediate cure, by the person's own tap. While a reload is pending, a failed chunk waits for the next
move like any other moment. `reload-on-move.test.ts` "a failed lazy chunk never reloads" fires a synthetic cancelable
`vite:preloadError` and needs nothing of C1.

## Review focus, as amended

The plan's Review Focus 6 allowed a reload in the first seconds back for the block screen and for a failed lazy chunk.
After fix round 1 only the block screen reloads at once, and only while the block stands (`calm` lowers `urgent`
when the fleet store's `blocked` falls). Everything else waits for a move between screens, made at least 15 s after
the page came back, with no send unresolved, and the gate answers reload at most once per page.

## Departures, by slug

- **`hidden-page-holds-every-arm`.** The brief's rule "No reload while the page is hidden" is applied to every arm,
  not only to a move. The plan's `reloadStep` reloads on `urgent` (and, before fix round 1, `chunk-failed`) whatever
  the visibility. Here `activated` and `urgent` reload only when `visibleSince` is not null. An urgent reload (the block
  screen) held while hidden runs on the return: `visible` answers `reload` when both `pending` and `urgent` hold. A
  pending reload with no urgency still waits for a move. Pinned by `reload-gate.test.ts` "a hidden page holds every
  arm, and its return runs an urgent reload" and `reload-on-move.test.ts` "a hidden page never reloads" (mutants 9
  and 10).
- **`popstate-re-asks-navigate`.** `navigate` dispatches its own `popstate` after a push the gate allowed. The gate's
  `popstate` listener then asks the same move again, from the last path it saw to `location.pathname`, and gets the
  same answer at the same moment. If a view transition delays the push past the 15 s line, the listener reloads the
  already-pushed path in place, which also lands the new build on the new path. On a genuine Back or Forward that
  reloads, the router still draws the new path in this build until the page unloads (review 1476 F6, cosmetic). With
  the latch, no second reload follows either way.
- **`plan-mutant-4-case`.** The plan names "a return restarts the 15 s" for mutant 4 (`hidden` leaves
  `visibleSince`). As written, that case survived the mutant, because the return's `visible` step overwrites the
  time anyway. The case now also makes a move while hidden, two minutes after the load, which holds. Re-measured red.
- **`note-names-no-number-yet`.** This note names the task, not its deviation number: the number is defined by the
  plan revision on the coordinator's ledger pull request, which is not on `main` yet, and `deviation-refs.test.ts`
  refuses a tracked file that names a number above `main`'s ledger high-water. The coordinator's ledger fold adds it.
- **`once-per-page-latch`** (fix round 1, F1). `ReloadState` gains `reloading`. Once `reloadStep` has answered
  reload, every later event answers no for the rest of the page; the state still tracks visibility. The one stranding
  mode: a page whose reload never completes stays latched and falls back to in-page moves, the screen fallback's
  Reload and the block screen's Reload, which all still work. A page restored from the back-forward cache after a
  `go` load is no longer stranded (fix round 2, F1): see `bfcache-restore-is-back`.
- **`no-chunk-failed-arm`** (fix round 1, F2 and F3). The plan's `chunk-failed` event, its `vite:preloadError`
  listener and its `preventDefault()` are removed. Reason: the operator's "never in the first seconds back" (the arm
  had no quiet window), and C1's Reload door on the screen fallback, which is the immediate cure.
- **`held-by-unresolved-send`** (fix round 1, F4). The `move` event carries `held`; `swupdate.ts` asks a probe set by
  `setReloadHold`, which `main.tsx` registers with `anySendUnresolved` from the session store, added under the
  coordinator's leave in S2's file.
- **`block-lifts-calm`** (fix round 1, F5). A `calm` event clears `urgent`. `swupdate.ts` steps it before any event
  when the probe set by `setBlockProbe` (the fleet store's `blocked`, registered in `main.tsx`) answers false. The
  fleet store calls `requestUpdate` before it sets `blocked`, so the rising edge still steps `urgent`. `fleet.ts` is
  not edited.
- **`monotonic-quiet-window`** (fix round 1, F10). The default clock is `performance.now()`, not the plan's
  `Date.now()`, so a forward wall-clock step never shortens the 15 s.
- **`bfcache-restore-is-back`** (fix round 2, F1, ruled). A move reload uses `location.assign`, which adds a history
  entry, so Back can restore the old build from the back-forward cache with the latch set and nothing pending to
  hear. A `pageshow` with `persisted` (the page clock's `onPageRestored`) steps `restored`: the latch clears, the
  window restarts from that moment, `pending` stays, so the first move at least 15 s later reloads onto the new build,
  once, and the latch holds again after it.
- **`focus-counts-as-back`** (fix round 1, F11, ruled). Regaining window focus after the window was blurred for at
  least RELOAD_QUIET_MS restarts the window, when the page is visible. A page loaded without focus counts its blur from
  the load. The listeners are the page clock's (`onWindowFocus`, `onWindowBlur`).
- **`stopped-gate-never-reloads`** (fix round 1, F9). `stop()` clears `visibleSince`, so `reloadOnMove` on a stopped
  gate answers no. `startReloadGate` takes a partial set of acts, so a test can keep the real clock.
- **`bootstrap-resets-gate`.** The real `swupdate.ts` behind `main-bootstrap.test.tsx`'s mock outlives
  `vi.resetModules()`, so one case's latch carried into the next: "the gate is started at boot" called `go` and set
  it, after which the unsent-message case failed and the block-probe case passed vacuously. Each case now starts
  from `resetReloadGateForTests()`.
- **`inline-execution`.** The plan names subagent-driven development. The task is four small files and three test
  files, so it was built in the main thread, red first at every step.
