## 2. Open problems 2 and 3: no hashing kernel at all

**The sketch's `_ccd_hash_cmd`, measured.** Rev 8 put a new kernel function `_ccd_hash_cmd` beside `_plat_sha256_check` (inside the platform block) with a `K` row after it, and factored `_ccd_lib_load`'s tool selection into it. Applied on a scratch copy of `e664a6e11` and run, it turns **three** rows red, not two:

1. `macos-platform.test.ts` "is byte-identical in ccd and ccrc" (open problem 2);
2. `ccd-contexts.test.ts` "the K rows are pinned …" (open problem 3);
3. **unlisted:** `macos-platform.test.ts` "ccd/ccd's other exemption is the library loader's hashing-tool fallback, and nothing else (D-6913)". That row cuts exactly one function, `_ccd_lib_load`, plus the `__CCD_HASH_TOOLS` line out of the GNU-call sweep, and requires the cut to hold `hash=(_plat_sha256)` and exactly three `sha256sum` spellings. Factoring the selection out of the loader empties the cut. Put outside the platform block, the new function's `sha256sum` spellings would also hit the sweep itself.

Each alternative the problems name also costs a re-point or breaks a ratchet:
- inside the block with a `ccd/ccrc` copy: `ccrc` has no caller, so it would carry dead code, and rows 2 and 3 still red;
- outside the block as `K`: rows 2 and 3 red, and `K` means "a kernel every context uses", which a helper with two callers is not;
- as `C7` beside the loader: the front's call becomes a `C9 -> C7` edge, and the edge manifest may only shrink over each task;
- as `C9` beside the front: the loader's call becomes a `C7 -> C9` edge, the same.

**Decision (D-7126, D-7125).** No new hashing function. **`_ccd_lib_load` keeps its selection where it is, byte for byte, and publishes two facts it has already decided**, as two globals declared beside `__CCD_HASH_TOOLS`:

```bash
__CCD_LIB_SHA256=stamp-at-install
__CCD_REDACT_SHA256=stamp-at-install
__CCD_REDACT_CLI_SHA256=stamp-at-install
__CCD_LAYOUT=
__CCD_HASH_CMD=()
```

- In the source-checkout arm, just before its `eval "$src"`: `__CCD_LAYOUT=source`.
- After the digest check passes, just before the final `eval "$src"`: `__CCD_LAYOUT=installed` and `__CCD_HASH_CMD=("${hash[@]}")`.

Every refusal line, the selection block and the `hash=(_plat_sha256)` line keep their bytes. The front (C9) and `_docs_redact_cli` (C9) **read** the two globals. A read of a variable is not an edge in `ccdCallGraph`, which counts calls of defined function names, so there is no new edge, no `K` row, no platform-block byte and no `ccrc` copy.

**Why this is not a hidden edge.** The coupling is real. It is a data read, written once by C7 at source time and read by C9 at verb time, so it is pinned as a single-writer fact rather than left unseen. A new census function, `server/test/census-w5/redactors.ts#loaderGlobals()`, reports every assignment of `__CCD_LAYOUT` and `__CCD_HASH_CMD` by file and enclosing function. It imports `functionSpan` and `enclosingFunctions` from `./ccdHelpers.js`. `enclosingFunctions` is private in C5d's file today, so commit 5 adds `export` to it, a one-word, test-only change. It uses `heredocLines` from `redactors.ts` itself. **It scans every file the body evaluates**: `ccd/ccd` and every `ccd/lib/*.sh` (today only `ccd/lib/disk-retention.sh`). `_ccd_lib_load` evaluates the library inside its own function scope, right after it sets `__CCD_LAYOUT=installed` and `__CCD_HASH_CMD`. So a library line such as `__CCD_LAYOUT=source` would turn off the front's digest check and python's pin check (§3.3) in the installed layout, and a census of `ccd/ccd` alone would miss it. Its rows go in `ccd-lib-load.test.ts`: each global has exactly its declaration line at top level of `ccd/ccd` plus assignments inside `_ccd_lib_load`, and nothing in either file set assigns either. A second assignment anywhere reds it. The globals are not made `readonly`: the census covers the same risk, and a `readonly` line would itself be a declaration that the census must allow.

**What counts as an assignment.** A census that matched only `NAME=` would stay green on a shadowing `local`, so it would be a blind guard. `loaderGlobals()` reports, for each of the two names, every line in `ccd/ccd` and `ccd/lib/*.sh` (heredocs excluded, comments stripped) that holds any of these forms:
- a plain or appending assignment: `NAME=`, `NAME+=`, `NAME[…]=`;
- a declaration that names it, with or without a value: `declare`, `local`, `typeset`, `readonly`, `export` (any flags, any position in the name list);
- a builtin that writes it: `printf -v NAME`, `read … NAME` (any flags, the name anywhere in the list), `mapfile`/`readarray … NAME`, `unset NAME` (with or without `-v`);
- an `eval`, `source` or `.` line whose string names it, and an indirect write (`declare -n`/`local -n` whose target is the name, `${!…}` on the left of an assignment).

Any such line outside the declaration block and `_ccd_lib_load` reds the single-writer row. The FIXTURE row plants one line of each form in a fixture body, plus one `__CCD_LAYOUT=source` line in a fixture `lib/*.sh` file beside it, and requires the census to report all of them. So a form dropped from the matcher, or a census that stops reading the library, reds the fixture before it can blind the real row.

**One predicate, exactly.** `__CCD_LAYOUT` is read in exactly two functions, `_docs_redact_cli` and `_docs_front`, and both read it in exactly one spelling, `[[ $__CCD_LAYOUT == source ]]`: true is the source checkout, anything else (empty included) is the installed layout with both digests checked. A second census row, in the same file and over the same file set, reports every read of `__CCD_LAYOUT` (any `$__CCD_LAYOUT` or `${__CCD_LAYOUT…}`) by enclosing function and requires each read outside `_ccd_lib_load` to be that exact test, in one of those two functions. A front that tested `== installed` (so an empty value would reach the installed path with no digest check, a mutant no behaviour row can reach, because the loader never leaves the value empty) reds this row.

**One layout decision, not two.** The sketch made `_docs_redact_cli` fork "on the same test" as the loader, which means reading line 2 a second time. Here it reads `__CCD_LAYOUT`. **Where `$dir` comes from.** `_docs_redact_cli` derives it exactly as `_ccd_lib_load` does, from its own file's location and never from the environment or an argument: `local self="${BASH_SOURCE[0]}" dir=.`, then `[[ "$self" == */* ]] && dir="${self%/*}"`. It then makes `dir` absolute with one more line, `[[ "$dir" == /* ]] || dir="$PWD/$dir"`. It never resolves links, so the path python is given is the one the front checked (§3.3, item 2). The launcher starts the installed body by an absolute path, so this line matters only for a relative start such as `bash ccd/ccd` from a checkout. There, python, which runs later, gets an absolute CLI path and never reads the path against a different cwd. Row (commit 7): from the repository root, `bash ccd/ccd` with a docs verb gives python an absolute first argument (a python3 stub on PATH records its argv). The derivation is pinned by a census row in `ccd-lib-load.test.ts`: the body of `_docs_redact_cli` holds the line `[[ "$self" == */* ]] && dir="${self%/*}"` byte for byte, as `_ccd_lib_load` does, and its only other writes of `dir` are `dir=.` in its `local` line and the `$PWD` line. No `$CCD_*`, `$HOME` or positional-parameter read feeds `dir`. `source` means `$dir/../shared/redact-cli.mjs` and no digest check. **Any other value, the empty one included, is the installed layout**: `$dir/shared/redact-cli.mjs`, both digests checked, and on any doubt `redactor-mismatch`. That covers a broken install whose line 2 is stamped but whose redactor pins are still placeholders: the loader says `installed`, the pin reads `stamp-at-install`, no digest equals it, and the front answers `redactor-mismatch`.

**No link at either path.** `[ -f ]` follows links, and node, when it is given the CLI's path (the sketch's start), opens its main module by its real path and resolves `./redact.mjs` from there. So an installed `shared/redact-cli.mjs` that is a link to an identical CLI in another directory passes both digests (the CLI bytes match, and the real `shared/redact.mjs` beside the link is the one hashed), while node loads the other directory's `redact.mjs`, which was never hashed. Reproduced on scratch files under node v26.5.0 (a stub CLI that prints a value from `./redact.mjs`, linked into a directory whose own `redact.mjs` differs): `[ -f ]` passed on the link, and node printed the unchecked module's value. The front therefore refuses a link at either path, as `_ccd_lib_load` refuses a linked library (`lib-missing`): in the installed layout, `[[ -L $cli || -L $mjs || ! -f $cli || ! -r $cli || ! -f $mjs || ! -r $mjs ]]` answers `redactor-missing`, before any digest. A linked `shared/` directory needs no test of its own: the CLI and the hashed `redact.mjs` then resolve through the same directory, so node loads the file that was hashed. `redact.mjs` imports nothing (measured), so those two files are all node loads. The installer replaces a link on its next run (`converged()` uses `lstat`); until then the verb refuses rather than redact with unpinned rules. §3.3's read-once start closes this hole two more ways. Python opens both files with `O_NOFOLLOW` and refuses a link (§3.4), and node is given bytes, never a path. So the front's refusal is no longer the only guard. It stays so the installed layout has the library's one posture toward a link, and its row and mutant stay.

**The stripped-PATH case falls out of this.** `__CCD_HASH_CMD` is the loader's own choice: `_plat_sha256` when its tool is on PATH, otherwise the first of `__CCD_HASH_TOOLS`. So on a PATH without `sha256sum`/`shasum` the front hashes with the same absolute tool the loader did. An installed ccd with no hashing tool never reaches the front, because the loader refuses `lib-hash` at rc 125 first. A tool that exists but answers an empty digest gives `redactor-mismatch`, the only path to that answer that is not a differing digest, as in the sketch.

**Measured on the scratch copy** (the two globals, `_docs_redact_cli`, the front's whole probe and digest check, the two pin lines, one `contexts.tsv` row): `ccd-contexts.test.ts` 13/13, `macos-platform.test.ts` 121 passed and 3 skipped (the Linux-only rows), `ccd-lib-load.test.ts` 26/26, `growth-check.test.ts`, and `rings/mjs-node.test.ts`, all green. Both open problems are resolved with no guard re-pointed. The K list stays at its 29 names; `contexts-edges.tsv` stays at 539 lines.

### 3.1 The CLI's contract

**Its shape, for the `-e` start (§3.3).** The CLI runs at top level. It has no run-as-main guard and no `import.meta`, and its one import is spelled exactly `'./redact.mjs'`, in single quotes, once. The house pattern (`shared/mark.mjs`, `shared/hook-helpers.mjs`) compares `realpath(process.argv[1])` with `import.meta.url`. That breaks under `node --input-type=module -e`, where `argv[1]` is a label, so the CLI must not use it. `redact-cli.test.ts` pins all three from commit 2 (red there, green at commit 3), four commits before commit 7's `_redactor` enforces the spelling. The rows read the file's bytes: exactly one occurrence of the string `'./redact.mjs'` and one `import` statement, no `import.meta`, and no `process.argv[1]` read.

`node redact-cli.mjs --profile <name>`. Exactly two arguments, `--profile` and a name that `PROFILES` holds; `egress` (it needs caller shapes) and any other argv exit 2 with nothing on stdout. stdin is newline-delimited JSON strings. Each line is answered with `JSON.stringify(redact(profile, s))` and `\n`, written as soon as that line is read. A line that is not one JSON string exits 2 at once. End of input exits 0 when no partial line is left, else 2. The line scan starts from where the previous chunk ended, not from the buffer's start, so a 1 MiB request costs one pass. Lone surrogates survive the trip both ways (python's `json.dumps` writes `\udcxx`, and `JSON.stringify` writes it back the same way).

**Measured on a scratch CLI of this shape** (the authoring workstation, macOS, node v26, 20 runs, idle): node start to first answer median 30.6 ms, max 33.1 ms; a 1 MiB request after a warm start, median 11.1 ms, max 30.4 ms; `'fatal: https://u:tok@h/r \udcff'` came back as `'fatal: https://***@h/r \udcff'`; `--profile egress`, an unknown profile, no argv and a non-JSON line each exited 2 with empty stdout. **These numbers only show the shape works.** The fleet box's and the CI legs' Step 0 numbers decide the budget questions.

### 3.2 The helper's redactor seam

As the sketch has it (one node per verb, started lazily at the first `redact`; a per-verb cumulative budget; non-blocking chunked writes; sticky `RedactorFailed`; closed in `run()`'s `finally`; reset at `run()`'s entry; an `atexit` hook for units), with these exact decisions:

- **`RedactorFailed(Exception)`**: neither a `Fail`, an `OSError` nor a `ValueError`. Measured by listing every `except` clause in the helper: all but five name a class that `RedactorFailed` does not derive from (`Fail`, `DraftUnreadable`, `DraftTooMany`, `OSError` and its subclasses, `ValueError`, `UnicodeError`, `KeyError`, `TypeError`, `RecursionError`, `subprocess.TimeoutExpired` and the like). The five are `run()`'s two, `helper_failed_line`'s traceback `except Exception`, `elapsed_ms`'s `except Exception` (which never calls `redact`), and `trust_holder`'s `except BaseException: SYS.close(fd); raise` (which re-raises). So `RedactorFailed` reaches `run()` on every path. Step 0 re-lists them on the build's base.
- **`_redactor(self)`, the one start seam** (the sketch's, kept by name so its spawn-count rows and mutants stand as written). `redact` calls it only when `_rd_proc` is `None`, and it returns the started process, which `redact` stores in `_rd_proc`. It raises `RedactorFailed` when `redact_cli` or `redact_pins` is `None`. ### 3.3 The check-then-use window, closed (D-7127)

**The sketch's sentence is false, and this note replaces it.** The sketch says: "Python's `Popen` of node reads the file after the front's check; that window is the library's too, and is accepted the same way." The library has no such window. `_ccd_lib_load`'s header comment says the load reads the file once, hashes what it read and evaluates what it hashed, so no byte is checked and then swapped. The sketch's redactor has a long window. The front hashes both files, and python starts node lazily at the first `redact`, which can come seconds into the verb (the `docs-fetch` helper deadline is 45 s). Node then opens both files again. A `ccrc update` or `ccrc rollback` that renames `shared/` files during a running verb renames `redact.mjs` and the CLI one after the other, not as one atomic pair. So node could load a pair that was never checked against this body's pins, or a mixed pair (the old CLI with a new `redact.mjs`).

**Decision: python reads both files once, checks them, and gives node exactly the bytes it checked.** It is the library's read-once rule, applied at the point where node starts:

1. **The pins reach python on its argv.** `_docs_py` passes `"$(_docs_redact_cli pins)"` as python's second argument (§3). In the installed layout that is the body's two pins, the same ones the front checked. In the source checkout it is `-`, which means "nothing was installed, check nothing", as the loader's source arm skips its digest. `-` is printed only under `[[ $__CCD_LAYOUT == source ]]`, so §2's read-predicate census row covers it.
2. **`_redactor` reads `redact_cli` and `redact.mjs`** (the file of that name in `redact_cli`'s own directory, by the path it was given, never a resolved one) once each, through `_rd_read` (§3.4): no link, only a regular file, at most `REDACT_FILE_MAX` bytes, never blocking. When `redact_pins` is not `-`, it raises `RedactorFailed` unless `redact_pins == sha256(redact.mjs bytes) + ',' + sha256(CLI bytes)` (`hashlib`, hex). A placeholder pin never matches.
3. **Node gets those bytes and opens neither file.** The CLI's bytes must hold the specifier `'./redact.mjs'` exactly once, or `RedactorFailed` is raised. That one spelling is replaced by `'data:text/javascript;base64,<base64 of the redact.mjs bytes>'`, and the result is node's source: `['node', '--input-type=module', '-e', <source>, '--', redact_cli, '--profile', 'docs']`. `redact_cli` after `--` is a label in `process.argv[1]`, so the CLI's `process.argv.slice(2)` reads `--profile docs` exactly as when it runs from its path. `redact.mjs` imports nothing (measured, §2), so a `data:` module needs no resolver. No temporary file is written, which is the library comment's reason to avoid temp copies.
4. **A swap during the verb now fails closed.** A file changed after the front's check gives a digest mismatch in `_redactor`, so `RedactorFailed` is raised and the verb answers `helper-failed` / `redactor-failed`. It never gives node bytes that were not checked. The front's check stays: it answers the clearer `helper-unavailable` / `redactor-mismatch` before any work, which is the common case (an edited install).

**Measured on scratch files** (the authoring workstation, macOS, node v26.5.0, CPython 3, the real `shared/redact.mjs` at this note's base and a stub CLI of §3.1's shape, nothing under the repository): the `-e` start with the rewritten source answered `'fatal: https://u:tok@h/r \udcff'` as `'fatal: https://***@h/r \udcff'`, rc 0. Node start to answer, 10 runs: median 36.4 ms, maximum 53.0 ms, against 36.2 ms and 38.5 ms when the same CLI is given by path. The rewritten source is 35 716 bytes. With the CLI file removed and the same argv, node still ran, so it opens nothing at the label path. **These numbers only show the shape works**; Step 0 item 5 times this start, not a path start.

**The argv-size limit.** On Linux one argv string may hold at most 131 072 bytes (`MAX_ARG_STRLEN`). The rewritten source is about 36 KB. A larger `redact.mjs` that went over the limit would make `Popen` raise `OSError` (`E2BIG`), which `redact` turns into `RedactorFailed`, so the verb would fail closed. Row, in `redact-cli.test.ts`: the CLI's bytes plus the base64 of `redact.mjs` plus 64 stay under 98 304 bytes (three quarters of the limit), so growth is seen long before it fails a verb. The source also shows up in `ps` and `/proc/<pid>/cmdline`. It is the shipped redactor code, which holds no secret.

### 3.4 What node is started with: its environment, its files, its regex engine (D-7127)

**The trust posture.** PATH's `node` is trusted, as PATH's `python3` and the hashing tool already are (the library's stated trust surface). **The environment is not.** The helper already treats environment-borne hooks as hostile: `read_env` drops every `GIT_*` key before git runs, and `server/test/ccrc-versioned-audit.test.ts` deletes `NODE_OPTIONS` and `NODE_PRESERVE_SYMLINKS*` before it starts node. Node reads hooks from its environment that run code nobody checked. `NODE_OPTIONS=--require <file>`, or `--import data:text/javascript,…` with no file at all, can preload code into the redactor even when both digests pass, and a `module.register` loader hook could swap the `data:` import itself. A reviewer reproduced it on node v26.5.0 under `--input-type=module -e`: a preload that replaces `String.prototype.replace` brought `'https://u:tok@h/r'` back unmasked. The suites also set `NODE_OPTIONS` preloads widely (the `history-*` suites, `ccrc-doctor-codex`), so an inherited one is not hypothetical.

**Decision: node starts with an explicit environment.** It is `os.environ` minus `NODE_OPTIONS` and every other `NODE_*` key, the same shape as `read_env`'s `GIT_*` drop: `{k: v for k, v in os.environ.items() if not k.startswith(REDACT_ENV_DROP_PREFIX)}`, with `REDACT_ENV_DROP_PREFIX = 'NODE_'`. It is built at call time, inside `_redactor`, never at import, and passed as `Popen`'s `env=`. Nothing is added to it. PATH stays, because PATH's node is the trusted one.

Rows (commit 7, in `ccd-docs-helper-redactor.test.ts`):
- the python process runs with `NODE_OPTIONS='--import data:text/javascript,String.prototype.replace=function(){return String(this)}'` in its environment, and a verb that redacts still answers the masked line;
- its control: the same preload given to a node started with the inherited environment on the same CLI brings the line back unmasked. This shows the preload is potent, so the row above cannot pass for want of an effect;
- the counting subclass of the spawn-count row records the `env` it passes, which holds no `NODE_*` key and holds PATH.

Mutants (§6): the redactor `Popen` inherits `os.environ` (no `env=`), and the strip drops only `NODE_OPTIONS` rather than the whole prefix (the recorded-`env` row, with a planted `NODE_PATH`).

**`_rd_read(path)`, the one way python reads both files.** A plain `open(…, 'rb').read()` follows links. It blocks for ever on a FIFO swapped in after the front's `-f` check, and that read is outside the redactor budget, so python would hang until the runner kills ccd. It also has no size bound. Integrity would still hold, because the bytes are hashed, but python would not share the library's posture ("absent, a link, unreadable or not a regular file refuses"). So `_rd_read` opens with `os.open(path, os.O_RDONLY | os.O_NOFOLLOW | os.O_NONBLOCK | os.O_CLOEXEC)`, checks `stat.S_ISREG(os.fstat(fd).st_mode)`, reads at most `REDACT_FILE_MAX + 1` bytes and closes the fd in a `finally`. It refuses more than `REDACT_FILE_MAX` (98 304, the argv-size row's bound). Every failure, the `OSError` of a link or a missing file included, raises `RedactorFailed`. It calls `os.*` directly, never `SYS.*`, so no unit's `SYS` stub sees it, as `_redactor`'s own `Popen` avoids `self.spawn`. Its time counts toward `_rd_spent`, because it runs inside `_redactor`. One `os.read` of a regular file returns the whole file up to the limit. A short read would give bytes whose digest differs, or a module node cannot parse, so it fails closed either way. Rows (commit 7): a FIFO at the `redact.mjs` path raises `RedactorFailed` at once, inside the budget, with no node started. A `redact.mjs` of `REDACT_FILE_MAX + 1` bytes raises `RedactorFailed`. Both links raise it (§3.3's link row). Mutants: `_rd_read` drops `O_NOFOLLOW` (the link row) and drops `O_NONBLOCK` (the FIFO row, under the row's own timeout).

**Why the CLI never masks less than the python loop: the regex engines.** The guarantee rests on the corpus row (`H.redact == redactDocsText`), and `docs-parity` compares pattern strings, not engine semantics: python `re` with no flags against JS `gu`. For today's four rows the two engines agree, for these reasons:
- the classes are explicit ASCII classes;
- no pattern uses `\w`, `\s`, `\d`, `\b`, `$` or `.`;
- nothing folds case;
- a lone `\udcxx` surrogate is a code point that matches no class, in both engines;
- the replacement is group 1 plus a literal suffix, which both engines expand the same way.

A future rule that breaks one of these reasons would need its own argument, and the corpus alone would not show it. So commit 7, while the core python loop still exists (it goes in commit 10), adds a **differential row** in `ccd-docs-helper-redactor.test.ts`. Generated strings give the core loop's answer equal to the CLI's: non-ASCII letters, `\v`, `\r`, U+2028, lone `\udc80`-`\udcff`, astral characters, and near-miss `gh_` / `token` / userinfo shapes, built from a fixed seed so a red is reproducible. It is deleted with the loop in commit 10, and the corpus row stays.
