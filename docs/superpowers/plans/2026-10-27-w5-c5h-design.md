## 2. Open problems 2 and 3: no hashing kernel at all

**The sketch's `_ccd_hash_cmd`, measured.** Rev 8 put a new kernel function `_ccd_hash_cmd` beside `_plat_sha256_check` (inside the platform block) with a `K` row after it, and factored `_ccd_lib_load`'s tool selection into it. Applied on a scratch copy of `e664a6e11` and run, it turns **three** rows red, not two:

1. `macos-platform.test.ts` "is byte-identical in ccd and ccrc" (open problem 2);
2. `ccd-contexts.test.ts` "the K rows are pinned …" (open problem 3);
3. **unlisted:** `macos-platform.test.ts` "ccd/ccd's other exemption is the library loader's hashing-tool fallback, and nothing else (D-6913)". That row cuts exactly one function, `_ccd_lib_load`, plus the `__CCD_HASH_TOOLS` line out of the GNU-call sweep, and requires the cut to hold `hash=(_plat_sha256)` and exactly three `sha256sum` spellings. Factoring the selection out of the loader empties the cut. Put outside the platform block, the new function's `sha256sum` spellings would also hit the sweep itself.

Each alternative the problems name also costs a re-point or breaks a ratchet:
- inside the block with a `ccd/ccrc` copy: `ccrc` has no caller, so it would carry dead code, and rows 2 and 3 still red;
- outside the block as `K`: rows 2 and 3 red, and `K` means "a kernel every context uses", which a helper with two callers is not;
- as `C7` beside the loader: the front's call becomes a `C9 -> C7` edge, and the edge manifest may only shrink over each task;
- as `C9` beside the front: the loader's call becomes a `C7 -> C9` edge, the same.

**Decision (`slug c5h-no-hash-kernel`, `slug c5h-loader-publishes-layout`).** No new hashing function. **`_ccd_lib_load` keeps its selection where it is, byte for byte, and publishes two facts it has already decided**, as two globals declared beside `__CCD_HASH_TOOLS`:

```bash
__CCD_LIB_SHA256=stamp-at-install
__CCD_REDACT_SHA256=stamp-at-install
__CCD_REDACT_CLI_SHA256=stamp-at-install
__CCD_LAYOUT=
__CCD_HASH_CMD=()
```

- In the source-checkout arm, just before its `eval "$src"`: `__CCD_LAYOUT=source`.
- After the digest check passes, just before the final `eval "$src"`: `__CCD_LAYOUT=installed` and `__CCD_HASH_CMD=("${hash[@]}")`.

Every refusal line, the selection block and the `hash=(_plat_sha256)` line keep their bytes. The front (C9) and `_docs_redact_cli` (C9) **read** the two globals. A read of a variable is not an edge in `ccdCallGraph`, which counts calls of defined function names, so there is no new edge, no `K` row, no platform-block byte and no `ccrc` copy.

**Why this is not a hidden edge.** The coupling is real. It is a data read, written once by C7 at source time and read by C9 at verb time, so it is pinned as a single-writer fact rather than left unseen. A new census function, `server/test/census-w5/redactors.ts#loaderGlobals()`, built on C5d's `functionSpan`, reports every assignment of `__CCD_LAYOUT` and `__CCD_HASH_CMD` by enclosing function. Its rows go in `ccd-lib-load.test.ts`: each global has exactly its declaration line at top level plus assignments inside `_ccd_lib_load`, and nothing else assigns either. A second assignment anywhere reds it.

**One layout decision, not two.** The sketch made `_docs_redact_cli` fork "on the same test" as the loader, which means reading line 2 a second time. Here it reads `__CCD_LAYOUT`. `source` means `$dir/../shared/redact-cli.mjs` and no digest check. **Any other value, the empty one included, is the installed layout**: `$dir/shared/redact-cli.mjs`, both digests checked, and on any doubt `redactor-mismatch`. That covers a broken install whose line 2 is stamped but whose redactor pins are still placeholders: the loader says `installed`, the pin reads `stamp-at-install`, no digest equals it, and the front answers `redactor-mismatch`.

**The stripped-PATH case falls out of this.** `__CCD_HASH_CMD` is the loader's own choice: `_plat_sha256` when its tool is on PATH, otherwise the first of `__CCD_HASH_TOOLS`. So on a PATH without `sha256sum`/`shasum` the front hashes with the same absolute tool the loader did. An installed ccd with no hashing tool never reaches the front, because the loader refuses `lib-hash` at rc 125 first. A tool that exists but answers an empty digest gives `redactor-mismatch`, the only path to that answer that is not a differing digest, as in the sketch.

**Measured on the scratch copy** (the two globals, `_docs_redact_cli`, the front's whole probe and digest check, the two pin lines, one `contexts.tsv` row): `ccd-contexts.test.ts` 13/13, `macos-platform.test.ts` 121 passed and 3 skipped (the Linux-only rows), `ccd-lib-load.test.ts` 26/26, `growth-check.test.ts`, and `rings/mjs-node.test.ts`, all green. Both open problems are resolved with no guard re-pointed. The K list stays at its 29 names; `contexts-edges.tsv` stays at 539 lines.

### 3.1 The CLI's contract

`node redact-cli.mjs --profile <name>`. Exactly two arguments, `--profile` and a name that `PROFILES` holds; `egress` (it needs caller shapes) and any other argv exit 2 with nothing on stdout. stdin is newline-delimited JSON strings. Each line is answered with `JSON.stringify(redact(profile, s))` and `\n`, written as soon as that line is read. A line that is not one JSON string exits 2 at once. End of input exits 0 when no partial line is left, else 2. The line scan starts from where the previous chunk ended, not from the buffer's start, so a 1 MiB request costs one pass. Lone surrogates survive the trip both ways (python's `json.dumps` writes `\udcxx`, and `JSON.stringify` writes it back the same way).

**Measured on a scratch CLI of this shape** (the authoring workstation, macOS, node v26, 20 runs, idle): node start to first answer median 30.6 ms, max 33.1 ms; a 1 MiB request after a warm start, median 11.1 ms, max 30.4 ms; `'fatal: https://u:tok@h/r \udcff'` came back as `'fatal: https://***@h/r \udcff'`; `--profile egress`, an unknown profile, no argv and a non-JSON line each exited 2 with empty stdout. **These numbers only show the shape works.** The fleet box's and the CI legs' Step 0 numbers decide the budget questions.

### 3.2 The helper's redactor seam

As the sketch has it (one node per verb, started lazily at the first `redact`; a per-verb cumulative budget; non-blocking chunked writes; sticky `RedactorFailed`; closed in `run()`'s `finally`; reset at `run()`'s entry; an `atexit` hook for units), with these exact decisions:

- **`RedactorFailed(Exception)`**: neither a `Fail`, an `OSError` nor a `ValueError`. Measured by listing every `except` clause in the helper: all but five name a class that `RedactorFailed` does not derive from (`Fail`, `DraftUnreadable`, `DraftTooMany`, `OSError` and its subclasses, `ValueError`, `UnicodeError`, `KeyError`, `TypeError`, `RecursionError`, `subprocess.TimeoutExpired` and the like). The five are `run()`'s two, `helper_failed_line`'s traceback `except Exception`, `elapsed_ms`'s `except Exception` (which never calls `redact`), and `trust_holder`'s `except BaseException: SYS.close(fd); raise` (which re-raises). So `RedactorFailed` reaches `run()` on every path. Step 0 re-lists them on the build's base.
- **`redact(self, s)`**: sticky check; start node if none (`['node', self.redact_cli, '--profile', 'docs']`, stdin and stdout pipes, stderr `DEVNULL`, `close_fds=True`, `start_new_session=True`, stdin set non-blocking, the process added to `_REDACT_LIVE`); write `json.dumps(s) + '\n'` (ASCII) in `PIPE_CHUNK` pieces, each through `_rd_io`; read through `_rd_io` until the buffer ends in `\n`. EOF, or a second `\n` before the last byte, raises `RedactorFailed`. `json.loads` the UTF-8 line; a non-`str` raises `ValueError`. One `except (RedactorFailed, OSError, ValueError)` records the sticky failure, calls `close_redactor()` and re-raises as `RedactorFailed` (`UnicodeError` is a `ValueError`).
- **`_rd_io(fd, write, op)`**: `left = redact_budget_ms / 1000 - _rd_spent`; `left <= 0`, or a `select.select` that times out, raises `RedactorFailed`; otherwise `op()`. The elapsed time of the select **and** the op is added to `_rd_spent` in a `finally`. The spawn's own time is added the same way.
- **The clock** is `_REDACT_CLOCK` (`time.perf_counter`, bound once), never `time.monotonic` or `SYS.monotonic`. **Measured on CPython 3.12's library**: `selectors.py` reads no monotonic clock; `subprocess.py` binds `from time import monotonic as _time` and reads it only on its `wait(timeout=…)`, `communicate` and `_remaining_time` paths. The seam calls `Popen()`, `poll()`, `select.select`, `os.read`, `os.write`, `os.killpg`, `os.waitpid` and `time.sleep`, none of which reads it. Step 0 repeats this on the CPython versions of the CI image and the fleet box.
- **`close_redactor()`**: takes `_rd_proc` and sets it to `None`; closes stdin; polls up to `min(0.2 s, budget left)`; then `_redact_kill` (a `SIGKILL` to the group, a `poll()` loop of at most 200 ms, one `os.waitpid(pid, WNOHANG)`, closing stdout, and removal from `_REDACT_LIVE`). Each step is in its own `try … except BaseException: pass`. It never raises.
- **`helper_failed_line`**: `detail` starts as `'redactor-failed'`; when `exc` is not a `RedactorFailed`, `clip_utf8(redact(last), …)` replaces it inside `try … except BaseException: pass`.
- **`run(argv)`**: after the verb check, `SYS.reset_redactor()`, then `try: return _run_verb(verb, argv) finally: SYS.close_redactor()`. `_run_verb` is today's body from `t0 = None` on, byte for byte. Its docstring keeps `run()`'s contract sentence "It never raises", now held by the `finally`'s non-raising close.
- **`main()`**: `len(sys.argv) < 2` exits 2 with nothing written; otherwise `SYS.redact_cli = sys.argv[1]` and `run(sys.argv[2:])`. `run()`'s argv contract does not change, so none of the 17 inline `H.run(` sites changes.

**Measured, the whole of Step 5 applied on a scratch copy** (the seam above, `_docs_redact_cli`, `_docs_py`'s `set --`, `main()`, and the `prelude` line `H.Sys.redact_cli = <repository shared/redact-cli.mjs>`), run one file at a time on macOS: `ccd-docs-index.test.ts` 254 passed, **1 red: "main() writes once: rc 0 and exactly one line for a docs verb, rc 2 and nothing for anything else"**, the predicted argv re-point. **All seven `plantPython3(h.home, 'raises')` rows were green**, so the `perf_counter` clock and the `poll()`-loop close hold. `ccd-docs-tree.test.ts` 181, `ccd-docs-show.test.ts` 86 and `ccd-docs-fetch.test.ts` 31, all green through the real CLI. `docs-parity.test.ts` 54/54 (its corpus, idempotence and 1 MiB rows through the CLI). `docs-budget.test.ts` 19/19. ### 4.3 The installer (commit 6), with one fix the sketch missed

As the sketch's packaging bullet says (the library half is `shared/redact.mjs`, `shared/redact-cli.mjs` and `lib/disk-retention.sh`, renamed in that order, before the body; `moved` gains `'library'` once; `lib_moved` names what was renamed; exactly one placeholder of each pin or the install refuses, before anything moves; the module header gains its sentence), plus:

- **`slug c5h-stage-slots`, a real collision.** `ccd-entry-install.py#stage` names its staging file `.ccd.ccrc-stage.<pid>` in the directory it is given. Both `shared/` files stage into one directory, so the second `stage()` would unlink the first staged file, and the first `os.replace` would fail. Decision: `stage(directory, data, mode, slot='')`, the name `STAGE_PREFIX + pid + slot`. The library, body and launcher pass no slot, so their staging names are byte-identical. The `shared/` pair pass `'.1'` and `'.2'`. `STAGE_RE` becomes `^\.ccd\.ccrc-stage\.[0-9]+(?:\.[12])?$`, and `install` sweeps `shareddir` with it as it sweeps `libdir`. Measured: no test names the staging pattern.
