With the three in `failure_line` and `helper_failed_line`, 29 call sites reach `redact`. Measured by enclosing function and by what catches the result:
   - **Inside answers that succeed.** `docs-index`: `discover`'s and `find_owner`'s `repo-unreadable` and `git-failed` Fails (`os_head` 3 sites and `stderr_head` 3, `rev-parse`'s among them) are caught by `index_row`'s first `except Fail` and become a row (`index_failed_row` writes no head).    - **Inside failure answers.** Every other site: `list_committed`, `tree_head_of_m` (2), `_pin_git`, `show_failed`, `tracked_oid`, `verb_fetch`'s `fetch_detail` and `stderr_head`, and the same discovery and git calls when `docs-tree`, `docs-show` or `docs-fetch` reaches them outside `index_row`. **A head is redacted twice on the way out:** in `stderr_head`, and again in `failure_line` (`stderrHead` is re-redacted, and `detail` is re-redacted and then cut).
   - **Consequences for a CLI.** "Call node once per docs verb" cannot be a single pass over the finished answer: the cut would come first. Spawning node once per redacted string would start node inside successful `docs-index` and `docs-tree` answers, once per failing git call, under the 12 s helper deadline. And a CLI failure that is not a `Fail` would escape `index_row` (it catches only `Fail`) and turn the whole `docs-index` into `helper-failed`. **The design C5h takes:** the helper starts **one** node process lazily, at its first redaction, and sends each string to it as one JSON line and reads one JSON line back. So there is at most one spawn per docs verb, none when nothing is redacted, and every redaction still comes before its cut, with no call site changed. A redactor failure is sticky and fails closed: the verb answers `helper-failed` with the fixed detail `redactor-failed`, never an unredacted string and never a partial index. That is a behaviour change, named in its own commit (C5h, Step 5).
   - **`helper_failed_line` calls `redact` too.** `run()`'s two handlers both call it, and its docstring says it "cannot fail". So a redactor that raises must not be called again from it. C5h gives it the fixed detail for the redactor's own failure, and it catches any raise of `redact`.

10. **The log-line redactors (ARCH-67).** Two bash functions: `ccd/ccrc#_upd_redact` (three rules, all under `LC_ALL=C`: a scheme's userinfo by a regex loop, `:(/+)` then a run then `@`; the scheme-less userinfo run of D-6748; and `$HOME` to `~` at a path boundary) and `ccd/ccd-update-sync#redact` (two rules, in the caller's locale: a scheme's userinfo by ONE extglob pass of `${s//…}` over `://` then a run then `@`; and the home rule, whose code is byte-identical to `_upd_redact`'s, as `ccd-update-sync.test.ts`'s section-equality test pins). Measured on current main by running both functions, extracted from the two files, over one corpus (bash 5.2 on glibc under `C.UTF-8`, bash 5.2 on musl under `C.UTF-8` and `C`, bash 5.3 on macOS under `en_US.UTF-8`; `HOME=/home/u`), the outputs differ in four rules and agree in the fifth:
    - **R1, the scheme-less run (D-6748).** `redact` has no such rule. `user:s3cret@127.0.0.1:1/rel/x` → `redact` keeps it, `_upd_redact` gives `127.0.0.1:1/rel/x`; `"tok@h/r"` → kept, versus `"h/r"`.
    - **R2, a loop versus one pass.** `${s//…}` scans once and never re-reads text it has replaced, so a scheme followed by two or more `@`-ended runs keeps all but the first. `https://u:p@x@h/r` → `https://x@h/r`, versus `https://h/r`; `https://a@b@c@h/r` → `https://b@c@h/r`, versus `https://h/r`; a run that an earlier removal brings next to `:/`: `https://u@//v@h/r` → `https:////v@h/r`, versus `https:////h/r` (this row needs R3 too: the re-formed run follows four slashes).
    - **R3, `:/+` versus `://`.** `redact` needs exactly two slashes and a run with no `/` in it, so a scheme with one slash or with three or more keeps its userinfo (curl authenticates with both, D-6748's fix round 4). `http:/u:s3cret@h/r` → kept, versus `http:/h/r`; `https:///u:s3cret@h/r` → kept, versus `https:///h/r`; `file:///u@/home/u/x` → kept, versus `file:////home/u/x`. The same rule also reaches a `:/` in prose: `note:/x@y/z` → kept, versus `note:/y/z` (more masked, in a token that is not a URL; named so the reviewer sees it).
    - **R4, `LC_ALL=C` versus the caller's locale.** Under a UTF-8 locale `redact`'s `[:space:]` holds Unicode spaces, so one inside a run ends it before the `@`; `_upd_redact` reads bytes, where only ASCII whitespace ends a run. `https://a<U+2003>b@h/r` and `https://u<U+2003>:p@h/r` → kept, versus `https://h/r` (glibc, musl and macOS); `https://a<U+00A0>b@h/r` differs on macOS only (glibc and musl do not count U+00A0 as a space; both functions give `https://h/r` there). Under an ambient `C` locale no R4 row differs. An invalid byte in a password (`https://u:S3cr<0xFF>etTOKEN@h/r`) is masked by both in every locale measured: `redact`'s glob takes the byte into the run.
    - **R5, the home rule: no difference.** The code is the same bytes; the locale changes only whether `${seen: -1}` and `${post:0:1}` read a byte or a character, and every boundary character is ASCII, so the decision is the same. ## Review focus (the failure modes most likely to bite)

1. **A token set that moved.** C5e's harvests are scoped by family: the reap family is every helper call outside the `COLLECT` and `LOOSE` regions, the collector family every call inside them. A scanner that now reads the whole file, or a call moved across a region marker, changes a set; C5d's literal lists catch it. Reviewers diff each set at base and tip.
2. **A guard gone blind.** Five of the fifteen scanners stay green under a naive rename (§What the measurement found, item 3). Each must be re-pointed so its mutant still reds: a reap-family call added inside the swap slice or the lifecycle block (both lie outside the `COLLECT` and `LOOSE` regions, measured) must still red its "no reap-family call" row. The `WS-AUDIT-COLLECT` block lies inside the `COLLECT` region, so a reap-family call cannot be written there at all; its row is the containment fact instead, and its mutant moves the `COLLECT-BEGIN` marker. A re-point whose mutant cannot red, by construction, is itself a blind guard: reviewers ask of every re-pointed row what edit would red it.
3. **`return 1` lost.** `_ws_reap_leaf_ok` ends in `… || _reap_refuse …`, so its status is the helper's (the comment above `_reap_refuse` says so). `_ws_refuse` keeps `return 1`, and the comment moves with it.
4. **A token byte that changed.** C5f hands reap's fourteen facts to `_ws_reclaim_fingerprint` as `name=value` words in today's order. A reordered, renamed or added input changes every reap token: an audit taken before the deploy then reads `state-changed` once at the reap. The pin compares a literal token over fixed facts.
5. **A lock decline that changed.** C5g passes each verb's in-progress sentence verbatim; the flock-unavailable and lock-unopenable sentences are one text today and stay one. The decline answers at rc 0 with the document and the journal row, the locked function runs with the lock held, and the descriptor goes back on every path. `cmd_ws_restore`'s lock is not this wrapper (it dies on contention and holds the lock for the whole verb).
6. **A computed act no scanner can see.** Under C5g the act word reaches `_lc_refuse` and `_lc_emit` as `"$act"`. `ccd-refusal-v1.test.ts`'s "every call site names its token as a literal" counts only `_lc_refuse <literal-act>`, so a call with a computed act is invisible to it today. C5g extends the count to those calls and requires their tokens to be literal.
7. **Redaction after the cut.** C5h keeps every redaction before every `clip_utf8`. A node pass over the finished line would cut first.
8. **A fallback to a stale copy.** With no node or no CLI, the docs verb answers `helper-unavailable`; it never falls back to a python copy of the rules (spec §5.13).
9. **A node per string, or a raise that escapes.** C5h starts at most one redactor process per docs verb (the spawn-count rows), never through `self.spawn` (a unit's git stub must never see node's argv), and a redactor failure never escapes `run()`: `helper_failed_line` does not call the redactor again after its own failure, so the answer is still exactly one JSON line at rc 0.
10. **A `null` that now overwrites.** C5j's setter keeps three behaviours apart: a ready frame resets (any value, `null` included); a refresh writes only a non-null answer under the epoch it asked; local mode writes only a non-null answer.
