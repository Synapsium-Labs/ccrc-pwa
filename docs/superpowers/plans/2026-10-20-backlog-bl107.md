# Backlog item: halting predicate TS/SQL parity fixture (ARCH-16, #535)

**Issue:** GitHub #535 (ARCH-16 of the 2026-10-17 architecture audit). Size XS, test-only.

## The problem

Whether a node row HALTS update dispatch is decided in two spellings. The TS one, `isHaltingUpdate` in
`shared/update-move.ts`, is what the dispatcher, the PWA and the store's read-back `rowHalts` ask. The SQL one,
`haltingRowSql` in `server/src/coord/store.ts`, is embedded in the store's guards, because SQL cannot call TS.
D-3412 had to reconcile the two once: a `failed` row whose detail begins `PROVENANCE_DETAIL_PREFIX` is a verdict on
the release, not a fault of the node, and does not halt. `haltingRowSql` already derives its state list and its
prefix from the shared constants, but nothing ran the two over the same rows: the only check was indirect, through
`rekeyNode`'s heir guard in `update-store-nodes.test.ts`, over three states.

## The fix

- `server/test/halting-parity.test.ts` (new): every state `UPDATE_STATES` names plus one it cannot, crossed with
  twelve details (NULL, empty, ordinary failures, the bare prefix, a prefixed detail, case and position near
  misses), so 84 rows. They go into a minimal `nodes` table in a `node:sqlite` in-memory database, are filtered by
  `NOT haltingRowSql('nodes')` (the form every guard uses, so a NULL verdict reads as halting), and the result is
  asserted equal to `isHaltingUpdate` row for row. A short pin of the notion itself catches both spellings drifting
  together.
- `server/src/coord/store.ts`: `haltingRowSql` is exported (D-5890). Nothing else changes.
- `shared/update-move.ts`: the header comment names the new test as the parity check.

## The tests

Red first: on `origin/main` the parity case fails (`haltingRowSql` is not exported). Green after the export. The
mutation table is in the PR body: TS-only mutants of `isHaltingUpdate` turn the parity case red, and so does an
SQL-only mutant of `haltingRowSql`.

## Deviations and decisions

- **D-5890** — `halting-sql-exported` (#535): `haltingRowSql` is exported from `server/src/coord/store.ts` so the
  parity test runs the store's own SQL text, not a copy of it. A copy in the test would be a third spelling that
  nothing forces to agree with the store's. No production module imports it; the store's guards keep embedding it
  as before.
