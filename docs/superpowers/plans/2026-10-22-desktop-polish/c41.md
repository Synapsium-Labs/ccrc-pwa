# Task C41: a key across any number of rows is masked (D-8710)

The task note for desktop polish Task C41: what review 2326 found (F3, O1, O2), what was measured on `main` before
anything changed, the fix and why it fails closed, the tests and mutants, what other egresses do, C39's carries, and
what stays open. Every claim is labelled **measured** or **inferred**. Synthetic keys only: no real key, revoked or
not, was used anywhere.

## In short

- **F3 is real, and wider than reported.** On `main` the exact-bytes row join took a run that ends its row with the
  next row's leading run only, so a fingerprinted key drawn on three or more rows reached the drawer and pane history
  whole, under every row separator (**measured**). Through a real tmux 3.6 at 220 columns, a 500-character key a
  program drew on three rows arrived with no mark, under each of four program separators (**measured**). And the
  drawer held back only the last row's run of a chunk, so it sent the rows before it unjoined: even a two-row key
  showed its first row when a chunk ended after it, which a real tmux paint does (**measured**).
- **O1 is real.** A run the drawer masked tainted the next chunk's leading run for one chunk only, so a shape key
  longer than a drawer holds was drawn from the chunk after next: 2,713 of 12,000 characters, 10,713 of 20,000
  (**measured**). The same family: a long shape key's rows after any chunk cut were masked only while the 1 KiB
  context held its start (**measured**: a full row of a 1,599-character key at a third of all cuts).
- **O2 is real in the masker and unreachable through tmux.** A move down then CR (CUD+CR, IND+CR) between rows split
  every key the join and the shape walk could see (**measured**); tmux re-renders those moves as a cursor position
  before it forwards them (**measured**), so a drawer never receives them from tmux.
- **The fix** walks a key across every row it fills, holds every row a key could still run on from, reads what it sends
  with what it holds, keeps a taint for as long as its run, and walks a masked run's rows across a chunk boundary.
  After it: every case above shows no byte, one mark per row (**measured**). What stays open is named at the end.

## 4. The fix, and why it fails closed

All in `server/src/accounts/mask.ts` and `shapes.ts`; no `ccd`, tmux or PWA change, and the drawer draws nothing but
C39's mark.

- **One row break** (`shapes.ts#ROW_BREAK`): CR LF, LF, CR, or a LF, blanks and a CR that no LF follows (one row down,
  as CR LF). Every row reader builds on it: the shape walk's `ROW_END`, the wrap join, the carry test, the exact-bytes
  join, the drawer's row-tail hold. O2.
- **The exact-bytes join walks every row** (`SecretMasker#fingerprintSpans`): a run that ends its row, joined with each
  next row's leading run while the run before fills its row, as many rows as a key spans. The rows are read once (each
  break's leading run, whether it fills its row, a prefix sum of their lengths), and each held length is found by one
  binary search, so the pass stays linear. Bounded by the longest held length, by `KEY_ROWS_MAX` (128) rows, and only
  through rows of `WRAP_ROW_MIN` (12) units or more. F3.
- **The drawer holds every row a key could still run on from** (`chainBack`): a held run, at a chunk's end or ending its
  row, is held with the rows it continues, back until they hold the most a held key and its trims can. A run ending in
  blanks at the chunk's end is held as a row tail too, its row break being the next chunk's. What is sent before a
  hold is matched with the held text after it (`out`'s lookahead), and its carry is read at its own end.
- **A masked run goes on being masked** (`DrawerMask.out`, `SecretMasker.maskWithCarry`): a mask that reaches a text's
  end inside a run taints the next text's leading run, for as long as the run goes on, with one mark for the whole run;
  and a run the last text masked (a taint, a shape's carry) is walked on through every row it fills, by the shapes'
  own walk (`runOnRows`, now one function), so its rows never depend on the context still holding its start. A text
  that ends after a row break and the next row's indent carries. O1, and the long shape key.
- **Why fail-closed.** Every change adds a candidate, a hold or a mask; none removes one `main` made. The exact-bytes
  half still masks only what an HMAC matches, so a longer join shows no ordinary text as a key. The new bounds fail
  closed or name their residual: past `ROW_CHAIN_BYTES` a frame is cut with the too-large notice, as the run budget is;
  past `CHAIN_HELD_MAX` the drawer sends the earlier rows read with the held ones after them. A withheld run that never
  resolves is still never drawn (C36's fail-closed case is unchanged and passes).

**The security review of the commits** (automated, three findings, all taken): the drawer's hold had no bound by units,
so rows of one byte between long escapes could hold without limit (now `CHAIN_HELD_MAX`, twice what a drawer holds for
one run); the lookahead could cost a shape its carry, leaving its next row to the 1 KiB context (the carry is now read
at the sent text's own end, `carryAtText`); and a compact candidate id could let one view's candidate stand for the
other view's different text (row-join ids of three or more pieces now carry their view).

**Cost** (**measured**, 64 Ki units masked in rows mode, and through the drawer in 4 KiB chunks, held keys of 40 and 300
bytes, or one of 8,192; load 6 to 7):

| Text | `main` rows / drawer | After the fix rows / drawer |
|---|---|---|
| one-character rows | 24 to 29 / 28 to 31 ms | 29 to 30 / 32 to 34 ms |
| `seq`-like rows | 8 / 12 ms | 10 to 11 / 18 to 21 ms |
| prose | 1 / 1 ms | 1 / 2 to 3 ms |
| equal 12-unit lines, 300-byte key held | 5 / 7 ms | 36 / 42 ms |
| equal 16-unit lines, 8,192-byte key held | 4 / 5 ms | 5 / 11 ms |
| equal 64-unit lines, 8,192-byte key held | 2 / 3 ms | 8 / 33 ms |
| cursor-positioned rows of 20, 300-byte key held | 14 / 20 ms | 25 / 46 ms |

The worst rows are listings of equal lines whose width divides a held key's length: every line starts a candidate as
long as the key, which is exactly what a key wrapped at that width looks like, so only the HMAC can tell them apart.
Before `WRAP_ROW_MIN`, `KEY_ROWS_MAX` and `ROW_CHAIN_BYTES`, one-character rows cost 2.6 s and 38.8 s and the 16-unit
listing 177 ms and 256 ms (**measured**), which is why they exist.

- **`shape-walk-narrow-rows`** (not fixed, put to the coordinator): the shape half's walk goes on past a key's second
  row only while each row is as full as the shape's own, so a shape key a program wraps with rows narrower than its
  first (a prefix wider than the indent, 100/100/100 after `key: `) shows its third and later rows (**measured**, `main`
  and the fix). Widening the rule masks the first word of the indented row after nearly every wrapped key in Claude
  Code's tool output, whose last row reaches its row end over the TUI's blanks (**inferred** from `ROW_END`); D-5995
  already accepts this class for other causes.
- **`egress-no-row-join`** (not changed, put to the coordinator): §3's non-rows egresses.
- **`drawer-mark-terminal-wrap`** (C39's F2, not fixed): §8. A fix changes what the drawer shows beyond the mark, which
  the brief reserves to the coordinator.

## 10. What stays open

The line added to D-5995's accepted gaps in `2026-10-18-accounts-connect.md` names each: a quiet gap exactly at a row
break draws the rows before it, now on any number of rows (unchanged in kind); a key wrapped through a row of fewer
than 12 units, or across more than 128 rows (8,192 bytes at under 64 columns), is not joined; a frame past
`ROW_CHAIN_BYTES` is cut, and a drawer hold past `CHAIN_HELD_MAX` sends its earlier rows, so only a key that also reaches
rows not yet written can show; `shape-walk-narrow-rows`; and `egress-no-row-join`.
