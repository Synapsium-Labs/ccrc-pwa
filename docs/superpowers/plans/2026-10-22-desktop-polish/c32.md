# C32: a long run with no spaces pushes an item's text out of its card (D-8585)

The task note for the programme ledger (Task C32 of `docs/superpowers/plans/2026-10-22-desktop-polish.md`, D-8585). The
coordinator folds it into the ledger. This task starts from `main` at `972c36cb8`.

The brief: on a Waiting on you item page on desktop, a How step that held a long run with no spaces (path-like lists and ids
joined by slashes and commas) made the Why paragraph and every How step run past the card's right border, under the side
panel, and off the window's edge. Find the root cause in a browser at a desktop width, fix it in CSS so every text block on
the item page wraps inside its column, keep the mobile layout as it is, and add a browser test that is red without the fix.

Each claim below is labelled **measured** (seen in a real Chrome over the production build, or in a test run) or
**inferred** (read from the code, not run).

## In short

- **The cause (measured).** `.wi-card` is a grid with no `grid-template-columns`, so its children sit in one implicit `auto`
  column. An `auto` track is at least as wide as its widest child's min-content width. The How list (`.wi-card .wi-steps`)
  carried no `overflow-wrap`, so a step holding a long run could not break, and its min-content width was the whole run. At
  1280 px (Refined, an item holding a 340-character run) the card's border box was 596 px wide and stayed inside its column, but
  its one track measured **2588.58 px**, the How section's min-content width (2589 px); the other sections' min-content widths
  were 12 to 54 px. Every child of the card is laid out in that track, so the title, the Why text, the How steps and the
  history rows all ran about 2006 px past the card's right edge, under the side panel, and the card's `scrollWidth` was 2601
  against a `clientWidth` of 594.
- **The fix (measured).** Three declarations in `pwa/src/ledgers/ledgers.css`, the third from fix round 1:
  - `.wi-card` gets `grid-template-columns: minmax(0, 1fr)`, so the card's column is the card's width and no child's
    min-content can widen it. The side panel is a `.wi-card` too (`.wi-card.wi-act`), so it gets the same column.
  - `.wi-card .wi-steps` gets `overflow-wrap: anywhere`, so a How step wraps as the Why text (`.wi-text`), the title
    (`.wi-what`) and the history rows already did.
  - `.wi-act .wi-opt` gets `overflow-wrap: anywhere` (fix round 1, review 1938 F1), so a decision's option wraps whether it
    is recommended or not. Before, only the recommended option's own span (`.wi-opt-text`) wrapped; a plain option's words sit
    in the shared radio primitive's sentence span, which sets no wrap, and ran past the side panel. The shared primitive is
    unchanged.
- **The brief's inference, corrected (measured).** The brief inferred the card itself widened. The card's border box did not:
  it stayed in its `minmax(0, 1fr)` column of the detail grid (`.wi-detail`, `596px 336px` at 1280). What widened was the
  card's own inner track, and its content overflowed the card's box, visibly, since nothing clips it.

## The test

`pwa/browser/item-wrap.browser.test.ts`, in both skins:

- At 1280 and 1920, for an open decision (its recommended option and a plain one holding the run), a ticked item, and an
  open decision with no recommendation (every option holding the run): the card ends inside its column and left of the side
  panel; the band ends inside the item; no element inside the card, the side panel or the band ends past that box; none of
  them scrolls sideways; the page has no sideways scroll; and the detail pane (`.shell-detail`) has none either. On a desk
  the pane clips sideways (`overflow-x: hidden`), so a card's spill lands in the pane and the page's own sideways scroll
  stays 0 whatever the card does: the page's figure alone cannot fail there (review 1938 F2). On `main`'s stylesheet, with
  the pane assertion run first, it is red in all 12 desktop cases, the pane overflowing by 1090 to 1931 px (measured).
- At 1280: a probe paragraph with `white-space: nowrap`, holding the run, is added to the card. The title, the Why text, the
  How steps and the history must still end inside the card. This holds the card's column on its own. Once the steps wrap,
  the fixture's own text no longer needs the column.
- At 390, all three items: one column, every element inside its card, no sideways scroll.

## Departures (by slug)

- `card-box-stays-in-column`: the brief inferred the card widened past its column. Measured: its border box stayed in the
  column, and its inner `auto` track widened instead. The cure is the one the brief ruled: the card's column cannot be
  widened by one child's min-content, and a How step wraps.
- `phone-overflowed-too`: the same overflow was measured at 390 on `main` (both skins), in the one-column layout. The fix
  cures it there as well. The phone layout is otherwise unchanged: for text that fits, an `auto` track and `minmax(0, 1fr)`
  both size to the card's width (inferred from the grid sizing rules; the existing waiting and item-nav browser suites,
  which cover 360 and 390, pass).
- `probe-case-holds-the-column`: one case beyond the brief's test. It adds a probe child that cannot wrap, because the
  fixture alone does not hold the card's column once the How steps wrap (see the mutation table).
- `refusal-line-inferred`: the side panel's refusal line is not rendered with a long run in the browser test. Its wrap is
  inferred from its rule.

## Fix round 1 (review 1938)

- **F1 (fixed).** A long run in a decision option that is not the recommended one, or in any option of a decision with no
  recommendation, overflowed the side panel and, on a phone, the page. `.wi-act .wi-opt` now has `overflow-wrap: anywhere`;
  the shared radio primitive is unchanged. The fixture holds the run in a plain option of item 1 and in every option of a new
  item 3 with no recommendation, red without the rule (10 of 16) and green with it (measured). The checklist's option rows
  are corrected above.
- **F2 (fixed).** The desktop cases also assert that the detail pane has no sideways overflow, red on `main` in all 12 desktop
  cases (measured). The test's header comment says why the page's own figure cannot fail there.
- **F3 (fixed).** The run is 340 characters and the address 369, counted from the fixture; this note and the test's comments
  say so. The measurements above come from this fixture.
- **F4 (fixed).** The checklist says which rows hold no long run: the ticked item's status line and the empty note field.
- **F5 and F6** are carried with no change, on the coordinator's ruling. **F7** is the plan's existing entry form, left as it
  is.
