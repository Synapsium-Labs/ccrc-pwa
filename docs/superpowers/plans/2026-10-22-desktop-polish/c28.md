# C28: the sign-in pump confirms a macOS FIFO's end of file without select() (D-8345)

The task note for the programme ledger (Task C28 of `docs/superpowers/plans/2026-10-22-desktop-polish.md`, D-8345). The
coordinator folds it into the ledger. This task starts from `main` at `80d5823be`.

The brief: Task C27 (D-8344, PR #2689) found that D-2661's macOS red was its probe's reader. On Darwin a FIFO's end of
file is delivered once to whatever waits for it, and `select()` can then report a FIFO with no writer left as "not
readable", so bash 5.3's `read -t` waits in `select()`, consumes the EOF and answers 142. C27 inferred, without measuring
it, that the account sign-in helper's pump has the same defect. Root cause first; measure the pump on macOS; fix it so a
finished child's mint ends at once, while a descendant that still holds the write end (D-2736's case) still ends at the
backstop.

## In short

**Measured on macOS, the defect is real.** The helper's own spawn, pump and wait, driven against a mint that prints two lines,
sleeps a second and exits 0, ran to the pump's backstop and was stamped expired in **51 of 140** runs (all from run 43154928175), on both spawn arms. In
every one of them the mint had exited 0 and both lines had reached the pane, and the tick reads answered 0, 0 and then only
142 until the backstop: never 1. A mint that exits at once, or straight after its last line, never showed it (0 of 230).
That fits D-2661's first symptom, a 6 s `CCRC_AUTH_TIMEOUT` measured running 60 046 ms before D-2736's backstop existed:
with no backstop the loop never ends.

The fix: once a tick read has timed out and the child has exited, the pump makes one **drain read** with no `-t`, a
plain `read(2)` that checks the writer count instead of waiting in `select()`. It runs in its own shell under the
helper's deadline shim, bounded by the tick and by what is left before the backstop, so it can never hold the loop past
D-2736's backstop. It answers a line (rc 0), the end of the stream (rc 1), or "a writer is still there" (anything else),
which stays a timeout. The tick read is now a function of its own, `_auth_pump_read`, the seam the new tests drive.
Measured on macOS with the fix: 0 of 230 runs red under the same mints and loads, and a descendant holding the stream
still ended `expired` at the 10 s backstop in each of 5 runs.

## The defect, in the code (measured by reading, and on Linux through the seam)

`ccd/ccd-account-auth#_auth_pump` read fd 8, the child's output FIFO, with `_auth_read -r -t "$CCRC_AUTH_TICK" -u 8 line`.
It left the loop on rc 1 (EOF) or at D-2736's backstop, `CCRC_AUTH_TIMEOUT + CCRC_AUTH_PUMP_GRACE` (600 + 10 s by
default). Every rc above 128 looped. So if a `read -t` answers 142 for an EOF it consumed, every later `read -t` waits in
`select()` on a FIFO that `select()` will not call readable again, and the loop runs to the backstop, which sets
`AUTH_EXPIRED=1` and sends TERM to a child that has already exited. The method then ends `expired` (`_auth_end expired 1`)
whatever the mint did, even when it succeeded.

On Linux the new cases show that path through the seam (below): with the drain arm removed and a tick read that answers
142 at the end of the stream, a finished mint is stamped `expired=1` after the full 6 s backstop on both arms.

## The evidence on macOS

workflow on this task's branch, `c28-darwin-pump.yml`, ran `measure.sh`: it sources the helper (`CCRC_AUTH_NO_MAIN=1`) in
a fixture HOME, calls `_auth_open_pipes`, `_auth_spawn_pty_child bash -c "$MINT"`, `_auth_pump` and `wait` exactly as the

tick read's exit code, and counts a run red when it ends `expired` or forwards fewer than the two lines. Both were removed
before the wave-done.

The first run's mint exited within milliseconds of starting, before the pump was waiting in a timed read. C27's lost EOF
needs the last writer to close WHILE `read -t` waits in `select()`, which is what a real mint does: it prints, then the
operator or the network takes a moment, then it exits. A mint whose close follows its last write at once wakes the read
for that write and was green: inferred, from the "between" row, that the EOF is lost only when it arrives on a FIFO with
nothing left to read. Both spawn arms lose it, so the copier `cat` is not the cause; the FIFO and `read -t` are.

**Inferred, not measured:** the bash path that turns that EOF into 142, as C27 recorded it. The EOF arrives with the
child's SIGCHLD to the reading shell, and that coincidence may be what loses it.

| `ccd/ccd-account-auth#_auth_drain_read` | New. Exit 0 at a newline, 1 at the end of the stream; the shim's 124 (or any other code) means a writer is still there. The bytes come back in `AUTH_DRAINED`. ### Why the drain read reads `-u 8` and not its stdin (measured)

`_auth_timeout`'s pure-bash arm, used on a box with neither `timeout` nor `gtimeout`, runs its command as `"$@" &`, and
bash gives an asynchronous command /dev/null for stdin when the call carries the redirection. Measured, bash 5.3.9:
`f(){ "$@" & wait; }; f cat <&8` prints nothing, while a command reading `-u 8` gets the bytes. A drain read on stdin would
there read an instant end of file while a descendant still writes, and the pump would leave early. `7<&- 9<&-` keep the
code channel and the write end of `in.child` out of the drain's shell.

### Only while the child has exited, and what that costs on Linux

The drain arm needs the child gone because while the child lives a timeout is an ordinary quiet tick, and the timeout arm
exists for its partial line (the code prompt carries no newline). A Linux FIFO with no writer reports its end of file to
`read -t` as rc 1, so on Linux the arm runs only in D-2736's case, a descendant holding the stream after the child has gone:
there each loop is the timed read plus a drain read bounded by the tick, until the backstop, which ends the run as before.
(It can also run once in the moment a tick times out just as the child exits; the drain read then answers at once.)

## `_auth_forward_code`'s peek on fd 7

It cannot lose the code, and nothing here changes it. Measured on macOS (run 43154928175): a writer sending codes the way
`ccrc account auth-code` does (open the FIFO read-write, one `printf '%s\n'`, close) and a reader with the forward's shape
(`read -t 0 -u 7` peek, then `read -r -t 1 -u 7`) on a FIFO it holds open read-write: 200 of 200 codes whole bare and 200
of 200 under 2 x ncpu `yes`, no peek that then read nothing. Why it differs from fd 8 (inferred from the code and from
C27's measurement): `_auth_open_pipes` opens `in` read-write (`exec 7<>`), so fd 7 always has a writer, its own, and never
reaches end of file. Darwin's lost event is the end of file of a FIFO whose last writer has gone, and that never happens
on fd 7. A code is one short line written in one `write(2)`, so the timed read that follows a peek finds it whole. A peek
that missed a code would only delay it to the next tick: the bytes stay in the FIFO.

## Deviations

- **D-8345** (issued to this task): the pump's tick read on macOS, `read -t` on a FIFO whose end of file is one-shot.
  C27 inferred it; it is measured here (51 of 140 runs on macOS, run 43154928175), and fixed with a bounded drain read after a timed-out
  tick once the child has gone.
- `pump-takes-the-child` (by slug, not numbered): the brief named the fix's trigger as "once the child has exited", and
  `login` spawns its child without `_auth_spawn_pty_child`, so `AUTH_CHILD` is empty there. The pump now takes the
  child's pid as an optional argument and `login` passes its own. In fix round 1 the backstop TERMs that pid too (below).
- `login-backstop-kills-nothing`: closed in fix round 1 (review 1849, F2). For the same reason, D-2736's backstop TERMed
  an empty pid under `login`. The first round called that harmless, inferred and unmeasured; it held only where a
  `timeout` binary with `-k` had already killed the mint. On `_auth_timeout`'s pure-bash arm (no `timeout` or
  `gtimeout`: one TERM, no escalation, D-2764), a mint that ignores TERM kept the shim alive and `login`'s `wait` blocked
  until the mint chose to exit. Measured on Linux in the new case: hung to the driver's 20 s limit. It was there before
  D-8345 (the same line is at `80d5823be`). The backstop now TERMs the pump's own child, and the run ends `expired` at
  the backstop. Whether a real sign-in child ignores TERM was not measured.
- `pure-bash-arm-mint-stdin` (an observation, not changed, for a ruling): on `_auth_timeout`'s pure-bash arm the mint
  never gets the operator's code. Each spawn puts `<in.child` on the `_auth_timeout` call (the darwin arm, on the group
  around it), and the arm runs the command as `"$@" &`, which bash gives /dev/null for stdin, the same rule the drain
  read avoids with `-u 8`. Measured on Linux, bash 5.3, through the helper's own spawn, pump and wait with the code
  written to fd 9 and a mint that exits 0 only on that code: GNU arm rc 0, pure-bash arm rc 9 (it read nothing). So on a
  box with neither `timeout` nor `gtimeout`, a stock macOS box among them, no sign-in method can receive its code
  (inferred for macOS; its CI runners carry Homebrew `timeout`). Older than D-8345, outside this task's rulings, and the
  shim is one of three copies pinned byte for byte, so it is not changed here.
