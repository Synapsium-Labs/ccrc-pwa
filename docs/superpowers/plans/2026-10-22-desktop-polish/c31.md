# C31: release-main.test.ts's fixture steps fail on macOS with no output (D-8391)

The task note for the programme ledger (Task C31 of `docs/superpowers/plans/2026-10-22-desktop-polish.md`, D-8391). The
coordinator folds it into the ledger. This task starts from `main` at `2d4daf7e4`.

The brief: `release-main.test.ts` red on macOS in three branch dispatches, each time in the describe "release-main.sh:
compare — a build identical to the newest release HEAD contains cuts no release (W25 fix round 2)", each time with a
fixture step that exited non-zero and said nothing. A promotion to stable needs a green `full-suite`, which includes the
macOS shards. Root cause first, fix it where it is, and do not skip on Darwin, raise a timeout or add a retry.

## In short

- **The cause is in shipped code: `deploy/build-release.sh`. Fixed, and this is a release-path change.** The builder
  staged the tracked set with `git archive … | tar -x -C "$TOP"`. On macOS, `tar` is bsdtar, which can stop reading once
  it has read the archive's end marker, before `git archive` has written the rest of its last record. git then dies of
  SIGPIPE, `pipefail` fails the stage with status 141, and `set -e` ends the build. Bash reports no SIGPIPE, so nothing
  reaches stderr. GNU tar reads to the end of its input, so Linux never showed it.
- **The fix:** `git archive` writes `$STAGE/tracked.tar`, beside the tree and never inside it, and `tar -x -f` extracts
  that file. A file has no reader to outlive. What the tarball holds is unchanged, on both platforms.
- **The fixture now says how a step ended.** Every fixture step, and every assertion on a run, reports the pid, the
  status, the signal, any spawn error and the tails of stdout and stderr. The three original reds said `failed: ` and
  nothing else, because the fixture printed stderr alone.

## Finding the cause

### Diagnostics first (measured)

`told()` formats a finished child's pid, status, signal, spawn error and the last 2000 characters of each stream.
`spawnStep()` throws with it for every fixture step (git, the clones, `git init --bare`, the asset build, the tar
steps, the origin tag reads), and every `Result` carries it for its assertion's message (`exitsWith`, and `p.told` in
place of `p.stderr`). The helper's options are a literal, so `spawn-group-pin`'s timed-spawn census reads it as the
untimed spawn it is.

### A probe on macOS (measured)

A throwaway workflow on this branch (`c31-darwin-probe`, removed before the wave-done) ran the file on `macos-latest`
with two workers, with every signal sender logged and the release scripts traced:

- a `BASH_ENV` file that replaces bash's `kill` with a function logging every call that sends a signal (not `-0`),
  with its sender, and traces `release-main.sh` and `build-release.sh` to a file per pid (`BASH_XTRACEFD`);
- a `NODE_OPTIONS` preload logging `process.kill` and `ChildProcess#kill`, with a stack;
- `kill`, `pkill` and `killall` shims at the head of `PATH`.

Run 43209129054, at `f919ac379` (before the fix):

- **Alone, 25 runs: 21 green, 4 red.** Every red was a fixture step of the compare describe:
  - repeat 9 (W25-C12, a checksum mismatch) and repeat 18 (W25-C12, a failed download): `fixture asset build for
    v0.0.1 failed: pid …, status 141, signal none`, stdout `build-release.sh: building v0.0.1 …`, stderr empty. Each
    trace ends at `build-release.sh:130`, `git -C … archive --format=tar HEAD -- …` and `tar -x -C …`, followed straight
    away by the EXIT trap's `rm -rf "$STAGE"`;
  - repeat 6 (W25-C36) and repeat 19 (W25-C2): `prepare` exited 1 with `release-main.sh: build-release.sh failed — the
    local tag v0.0.2 was removed; nothing reached origin`, its nested `build-release.sh` having ended about 150 ms
    after it started with nothing on stderr. The probe's report did not print that nested trace, so its line is
    inferred from the matching symptoms;
  - each run logged one signal-sending call: vitest stopping its own worker. **No sender named any red's pid**, so
    nothing killed these steps.
- **The failing shard's 196 files, 2 runs (cancelled after them): `release-main.test.ts` green in both.** Both runs were
  red on `spawn-group-pin.test.ts` alone, which had counted this task's new fixture helper; fixed in `aa74afb2f`.

So the status is SIGPIPE's (128 + 13), the failing command is the archive pipe, and no process outside the build
signals anything. The stale-pid idea the timing first suggested (a neighbour file such as `ccd-prhistory.test.ts`
overlapped two of the reds) is refuted by the signal log.

### The mechanism (inferred, then reproduced on Linux)

That bsdtar stops reading after the end marker while git still writes the record's padding is inferred: from the
status, the line, GNU tar's reading to the end of its input, and the intermittency (git loses the race only when its
last write comes after tar has gone). It was reproduced deterministically on Linux with an extractor that stops early:
a `tar` stub that, reading a stream, takes one byte and exits 0, and a shipped 1 MB file, so git is still writing when
the reader goes. Before the fix the build exits **141 with empty stderr and `building v1.2.3 …` as its last stdout
line**, the macOS signature exactly; after it, green.

## The fix (measured)

`deploy/build-release.sh`, the staging step:

    git -C "$ROOT" archive --format=tar -o "$STAGE/tracked.tar" HEAD -- "${PATHSPEC[@]}"
    tar -x -f "$STAGE/tracked.tar" -C "$TOP"
    rm -f "$STAGE/tracked.tar"

The file sits in `$STAGE`, beside `$STAGE/tree`, so it never enters the MANIFEST or the tarball, and the EXIT trap
removes it with the rest of `$STAGE` if the extraction fails. The new case in `build-release.test.ts`, "the tracked set
reaches tar as a file, so an extractor that stops reading early cannot end the build (D-8391)", is red without the fix
on Linux and green with it. It also checks that the stub did the extraction and that the large file is in the tarball.

On Linux, `release-main.test.ts` and `build-release.test.ts` are green (114 and 68 tests), as are the suites that run or
read the builder: `ccrc-update-fetch`, `ccrc-install-versioned`, `ccrc-install-tree`, `update-watchdog-revert`,
`ccrc-uninstall`, `ccd-update-sync`, `release-artifact`, `release-stable`, `release-job-boundary`, `install-census`,
`compact-card-ship`, `license` and `ci-pipeline`. Two reds on this box are its own, not the change's:
`testbox-box-package`'s group-writable case is red on a clean `origin/main` too (this box's umask is 0002), and
`shellcheck-ratchet` was killed by the test slice's memory cap.

### Other pipes that end early (inferred, unchanged)

The release scripts' other pipes into an early-exiting reader are `git tag --points-at HEAD | grep -E … | head -n1`
(build-release.sh and three in release-main.sh) and `tar --version | grep -qi 'gnu tar'`. Each writer prints a few
bytes in a single write and is done before its reader can leave, so none of them can lose this race in practice. They
are left as they are.
