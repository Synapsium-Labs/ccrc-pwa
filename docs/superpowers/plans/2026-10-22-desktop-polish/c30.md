# C30: spawnSyncGroup hands an input to its child as a regular file (D-8381)

This is the task note for the programme ledger: Task C30 of `docs/superpowers/plans/2026-10-22-desktop-polish.md`,
D-8381. The coordinator folds it into the ledger. This task starts from `main` at `0c91b860a`.

The brief: `server/test/spawnGroup.ts`'s `spawnSyncGroup` must not hang on macOS when a caller passes an `input`. Fix it
once, in the helper, for every input, an empty one included. Keep the detached group, the timeout, the group kill and the
stray check as they are, and leave the callers unchanged. Measure first, and say whether a small or empty input can hang
too. Task C29 (D-8354, PR #2692) found the hang and fixed only its own file.

## In short

- **The cause (measured on macOS, through the helper itself).** A detached `spawnSync` given an `input` now and then
  delivers the input and never its end. The child waits in `read(2)` on its stdin socket and node waits in `kevent`
  until the timeout. `spawnSyncGroup` is detached by design (D-5894), so every caller that passes an `input` is exposed.
- **The fix.** When a caller passes an `input`, the helper writes it to a file in a directory of its own under the run's
  temp root. It opens the file for reading and removes the directory before the child starts. Then it passes the open
  descriptor as the child's stdin and keeps the caller's stdout and stderr settings. A regular file ends where it ends,
  and nothing is left on disk after a return, a timeout, a throw or the process being killed. Everything else in the
  helper is unchanged, and no caller changed.
- **The fix on macOS (measured).** 0 hangs in 30,000 runs of the fixed helper: 12,000 bare and 12,000 under a test
  shard's load with a 128 KB input, and 6,000 under load with an empty one. With the same inputs, the old route hung 2
  times in 18,000 runs at 128 KB.
- **Small and empty inputs.** No hang was seen at 4 KB (21,000 runs), 16 KB (3,000) or 0 B (21,000). That is weak
  evidence that they are safe, not proof. At the rate these probes measured for 128 KB, about 2 hangs would be expected
  in 21,000 runs, so a count of zero is not conclusive. The fix covers every size, so the question no longer decides
  anything.

Both hangs looked like C29's. `wc` sat in `read(2)` on fd 0, a unix socket shared with its `bash`. `bash` waited for

or Darwin never wakes the reader. The dumps cannot tell the two apart, and either way the input never ends.

## The fix

| Where | Change |
|---|---|
| `server/test/spawnGroup.ts#spawnSyncGroup` | Takes `input` out of the options. When it is set, `inputFile` writes it into a fresh directory (`INPUT_DIR_PREFIX`, under `os.tmpdir()`, which is the suite's TMPDIR), opens the file for reading and removes the directory. `withStdin` makes the descriptor the child's stdin and keeps the caller's other `stdio` entries. The descriptor is closed in a `finally` after `spawnSync` returns. The detached group, the timeout, `killGroup`, the grace wait, the stray check and `strays` are unchanged. |
| `server/test/proc-leak.test.ts` | Three new cases under "spawnSyncGroup: an input reaches the child from a regular file (D-8381)" (below). |

The directory is removed before the child starts, so the only remaining name is the descriptor. A timeout, a stray
throw, an exception in `spawnSync` or a SIGKILL of vitest leaves nothing in the temp root.

## What the new cases catch (measured, on Linux)

Each mutation was made on the work tree's `spawnGroup.ts` from a saved copy, then restored with `cp` and checked with
`cmp`. Linux cannot show the hang, so the cases pin the route (the child's stdin is a regular file and every byte
arrives), not the hang.

| Mutation | Result |
|---|---|
| The input goes back through `spawnSync`'s `input` | Red: `0 bytes: stdin is not a regular file` (all three cases) |
| The input's directory is never removed | Red: `expected '20000\nccrc-spawngroup-input-…' to be '20000'` |
| The directory is removed at process exit, not before the child starts | Red: same message (the child lists the temp root while it runs) |
| The caller's `stdio` is dropped for `['pipe','pipe']` | Red: `expected 'to-stderr\n' to be ''` |

## C29's local workaround

`session-hook-prune-deny.test.ts#childCpu` (C29) opens its own file and passes it as stdin. With this fix, the same call
could pass `input` and still get a file. So the workaround could now go: its own case, "a run reads its input from a
regular file", would stay green. It was not removed, as the brief ruled (claim 3952).

## Deviations

- **D-8381** (issued to this task), `spawnsyncgroup-input-from-a-file`: the brief's question of whether a small or empty
  input can hang has no firm answer. None hung in 21,000 runs at 4 KB or 21,000 at 0 B, but at the 128 KB rate measured
  here that count is not conclusive. The fix covers every size, so nothing depends on the answer.
- `c30-od-reread-on-darwin`: one of this task's own new cases first read `/dev/stdin` a second time, which macOS
  refuses after a reader has reached its end. Fixed in the case. The helper was not changed.
