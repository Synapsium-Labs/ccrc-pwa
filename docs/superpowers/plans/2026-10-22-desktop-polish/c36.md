# Task C36: the terminal view's stale and overlapping characters (D-8665)

Run 2235, wave 131. Base: `main` at 3499b905e. Every claim below is labelled **measured** (a run whose output is
quoted or summarised here) or **inferred** (read from code or documented behaviour, not run).

## What the operator saw

A desktop browser, a session open in terminal mode in the grid view. Lines drawn over earlier lines with two lines'
letters interleaved in one row, the same line drawn twice (once clean, once garbled), leftover characters in rows that
should be blank, stray characters at the right edge of the left pane, and list numbers drawn over other text. Two more
details turned out to be the key: tmux's status row ended in a cut-off `‹secret m`, and the date that belongs at the end
of that row sat alone on an extra row below it. The doubling also showed in a second pane of the same window, so the
fault was in the client's stream as a whole, not in one program's own redraw (**measured**, read off the screenshot).

## The hypothesis the brief gave, and what replaced it

The brief's lead was a cursor-relative redraw on a terminal whose width differs from the width the program believes
it has. Both widths were measured, and they agree:

| Side | Width | How it is decided | Label |
|---|---|---|---|
| The browser's xterm | 220 x 51 | `ATTACH` in `terminalFactory.ts`, from `PINNED_WINDOW_COLS` and `PINNED_WINDOW_ROWS + TMUX_STATUS_ROWS`; pinned once before the socket opens (`term.pin`), never fitted; the glass changes only the type size and the view | **inferred** (code) |
| The tmux client the server attaches | 220 x 51 | the drawer dials `?cols=220&rows=51`; `/ws/pty/:id` passes them to `attachPty` (local) or `ptyOpen` (remote), both `node-pty` with `name: 'xterm-256color'` | **inferred** (code) |
| The tmux window | 220 x 50 | `resizeWindow(id, 220, 50)` before every attach and on every close | **inferred** (code) |
| Grid and wrapped views alike | 220 x 51 | the view is a CSS choice over the same pinned grid (`consoleFit`, `chooseView`); no layout resizes the grid | **inferred** (code) |

So the width hypothesis does not hold for the drawer. What sits between tmux and the xterm is the server's drawer
masker (`DrawerMask`, `server/src/accounts/mask.ts`), which every drawer byte passes through (`server.ts`,
`/ws/pty/:id`'s `onData`).

## The cause

With fingerprint rows held (any box with a compatible lane), `DrawerMask` holds every open run at the end of a chunk
for 6 ms. When the hold expired and the run could still be a key, it drew a PROVISIONAL `SECRET_MASK`
(`‹secret masked›`, 15 columns) in the run's place, withheld the rest, and later erased the mask with `CUB 15` and
`ECH 15` before drawing the completed run (D-5995).

tmux's status row ends a chunk with the date, `16-Nov-26`, a 9-column run that ends in the last column of the last
row. The 15-column mask drawn there ran six columns past the right edge: the terminal wrapped onto a new row, which on
the last row scrolls the whole screen up one row. `CUB` cannot cross a row, so the erase and the date landed on the new
row. From then on the glass was one row off tmux's picture of it, and tmux's redraws (absolute and relative cursor
moves over the picture it thinks is there) produced every symptom in the screenshot: doubled lines, interleaved
letters, stale text in rows that should be blank.

## The reproduction

A scratch harness, kept out of the tree: a private tmux socket with the fleet's `ccd/tmux.conf`, a 220 x 50 window,
a pane program that redraws like Claude Code (each tick it moves the cursor up over a four-line live block, erases each
line, appends finished lines above, and rewrites the block), and a 220 x 51 `node-pty` `tmux attach` client, exactly as
the drawer attaches. Each chunk went to two headless xterms at 220 x 51 (`@xterm/headless` 6.0.0, the terminal the PWA
draws with): one raw, one through `DrawerMask` as `server.ts` wires it.

| Masker | Window | Provisional masks drawn | Rows of 51 that differ from the raw screen | Label |
|---|---|---|---|---|
| fingerprint rows held, before the fix | one pane | 1 | 51 | **measured** |
| fingerprint rows held, before the fix | two panes side by side | 2 | 51 | **measured** |
| shape-only (no fingerprint rows) | one pane | 0 | 0 | **measured** |
| fingerprint rows held, after the fix | one pane | 0 | 0, and the drawer's bytes equal the raw bytes | **measured** |
| fingerprint rows held, after the fix | two panes side by side | 0 | 0, and the drawer's bytes equal the raw bytes | **measured** |

The masked screen before the fix showed the status row ending `‹secret m` with `16-Nov-26` alone on the row below,
the same shape as the operator's screenshot (**measured**). In the two-pane window one mask also landed inside the
right pane's rows (a run split by tmux's move to the pane's next row), and its `ECH 15` blanked cells tmux still
counted as drawn (**measured**, in the stream).

## Why the fix draws nothing in the run's place

A mark of any width could be drawn safely only by knowing the cursor's column, which the masker does not track.
Measured on xterm (headless 6.0.0, 20 columns):

- a mark that reaches the right edge leaves the terminal's wrap pending, and `CUB n` from there lands one column short
  of where the mark began (**measured**: 18 `a`, a 2-cell mark, `CUB 2`, `CD` gives `aaaaaaaaaaaaaaaaaCD•`);
- a saved cursor (`ESC 7` before the mark, `ESC 8` after) does not keep a pending wrap either: the restore clamps the
  column, and the run's next character overwrites the last cell of the row above (**measured**).

So the fix keeps D-5995's fail-closed rule and drops only its drawing: a run that could still be a key is WITHHELD from
the moment its hold expires until it ends, and nothing is drawn in its place; the completed run is then drawn masked or
not, as one chunk would have been. What reaches the terminal is the stream's own bytes unless a secret is masked in it.
The change is in `DrawerMask` alone: `flush` no longer emits the mask, `resolve` and `settlePending` no longer lead with
`CUB`/`ECH`, and the now unused `lead` parameter, `MASK_COLUMNS` and `ERASE_MASK` are gone. No tmux window size, no
`ccd` and no PWA file changes.

What the reader sees differently (**inferred**, from the code paths): a withheld run is blank until it resolves, where
it used to show `‹secret masked›`. For tmux's own output that is the 12 ms row settle (two holds) or the next chunk. For
a key typed one key at a time, the echo stops after its first 19 bytes, as before, and the rest appears when the run
ends; before, the mask stood there instead. Nothing of a key is shown that was hidden before.

## Departures, by slug

- **`drawer-provisional-mark-dropped`** (D-8665): D-5995 item (3) says an expired hold's run "is drawn as a
  PROVISIONAL mask ... then the mask is erased (CUB, ECH)". It is now withheld with nothing drawn; the fail-closed rule
  and every accepted gap D-5995 lists are unchanged. D-5995 item (11) recorded that the erase was "drawn natively" and
  never rendered separately; this task rendered it.
- **`drawer-final-mask-columns`** (not fixed, reported): a key that is masked for good is still replaced by the
  15-column `SECRET_MASK`, so the row that held it is shorter on the glass than in tmux's picture. Measured through the
  same real-tmux harness with a fingerprinted 44-character key printed every 25th line: only the two rows holding the
  key differ from the raw screen, and nothing else moves (**measured**); tmux places each row it redraws itself
  (**inferred**). Only a secret shorter than 15 columns, masked at a row's end, could reach the right edge the way the
  provisional mask did (**inferred**). Making the final mask keep the columns it replaces is a separate change (it
  shows a key's length, which `SECRET_MASK` hides today), so it is left for a ruling. It is not the same one-line rule:
  the provisional mark was one `emit` in `DrawerMask.flush` and its erase, while the final mask is `spliceMasked`
  (`accounts/shapes.ts`), shared with every other egress, which replaces a whole span (escapes and row moves inside it
  included) by one `SECRET_MASK`; keeping its columns needs a drawer-only splice (**inferred**, from the code).
