## What turns from a link to text

Each is a fail-safe cost of a ruling above:

- F3: a flag inside a quoted body or value is no command's, so it is a candidate for every number: `gh pr comment 12 -R
  owner-b/repo-b --body "--repo=owner-c/repo-c" and #12`, the `'-R' owner-c/repo-c` body and `--body "see -R
  owner-c/repo-c" --repo owner-b/repo-b` (each pinned at owner-b by Task C20, from review 1766 F9) now give text. A flag of
  another program beside a command that names a number (`gh pr view 12 -R owner-b/repo-b; cp -R src/lib /x; #12`) gives text
  too, unless it names the same repository.
- F2: a path word in a `gh` message names its repository wherever it stands (`gh pr list, then the endpoint
  /repos/owner-b/repo-b/pulls; #12` gives text), as a `-R` flag does. A commit path read by its command now names its
  repository, so a bare SHA beside it is text (`gh api -XGET repos/owner-b/repo-b/commits/1234567abc and 1234567abc`).
- F4: `gh-pages`, `gh's`, `(gh)`, `gh:` and `gh` at the text's end hold a `gh` word, so another program's `-R` in such a
  message makes its bare names text (`Pushed gh-pages, then cp -R dist /x; #12`). Accepted by the brief.
- F8: `GH_REPO: ${{ github.repository }}` names a repository the chat cannot tell, so a bare name beside it is text, as the
  `=` form's `GH_REPO=$X` already was.

## Recorded

- **F6 (interpretation).** Any value the grammar refuses after a repository flag names an unknown repository, so another
  program's `-R` (`chmod -R 755 dir`, `sort -R x`, `ssh -R 8080:localhost:80 host`) in a `gh` message makes its bare names
  text. Unchanged, fails safe.
- **F7 (lookalikes).** An en or em dash, U+2212, a fullwidth `－R`, U+2010 or U+2011, a zero-width space inside `-R`, `--repo`
  or `gh`, and a fullwidth `ｇｈ` are not read. `gh` itself does not honour them. Unchanged.
- **F4's CJK shape.** A letter in any script directly before `gh` makes no `gh` word, as the ruling defines it, so
  `修复见gh pr view 12 -R owner-b/repo-b and #12` opens home, as on `main`. Pinned, with a letter outside the BMP read whole.

## Departures

- `unclaimed-joins-evidenced-numbers`: the ruling says an unclaimed repository is a candidate for every number in the
  message. It is added to every number the message gives a repository. A number given none goes to rule 3, where that
  repository already makes it text unless it is home; adding it there would let a lone unclaimed flag link a bare name to
  the flag's own word (`cp -R src/lib /x; gh pr list; #12` would open `src/lib`'s #12). A number takes at most two
  unclaimed repositories: two are enough to tell one repository from many, and the cost stays linear.
- `path-word-unclaimed-too`: an unclaimed `repos/o/r` path word joins the numbers as an unclaimed flag does ("the way `-R` is
  covered"), so `gh api --unknown-bool repos/owner-b/repo-b/pulls/12; gh pr view 12 -R owner-c/repo-c; #12` gives text. A path
  its command read is that command's.
- `lost-command-flags-are-claimed`: a repository flag that made its command lost (a value spelled as one, a run such as
  `-sR`, a glued `-Ro/r`) is that command's, since the command already gives its number to an unknown repository. So
  `gh pr merge 40 -s -R owner-b/repo-b; gh pr view 41 -R owner-c/repo-c; #41` still opens owner-c.
- `quoted-value-bounded-too`: the brief's bound names the unquoted scan; a quoted value ends at the next flag too, and is
  unreadable where its quote is not closed before it. Both readings name an unknown repository.
- `gh-word-is-a-command-in-any-case`: `GH pr view …`, `gh.exe pr view …` and `GH.EXE pr view …` are read as commands, so
  each opens the repository its flag attributes, the other answer the ruling allows.
- `census-extended`: the single-definition census pins the three new readers, so a second `gh` word or path reader cannot
  appear beside them unnoticed.
