# C7: the chat's rows are memoised, and markdown and highlighting are cached (D-6439)

The task note for the programme ledger (Task C7 of `docs/superpowers/plans/2026-10-22-desktop-polish.md`). The
coordinator folds it into the ledger; this file edits no ledger row.

## What changed

- `pwa/src/session/sameRow.ts` (L1, `import type` only). `sameTranscriptItem(a, b)` checks kind and key, then every
  own field by `Object.is`. Two fields are read off the item's event, so they are compared through `event` alone:
  `mail`'s `envelope` and `task`'s `notification`. A `tool-group`'s `entries` are compared element by element, by the
  same rule. `sameRowProps(a, b)` compares the item by `sameTranscriptItem` and every other prop by identity.
- `pwa/src/lib/highlightCache.ts` (L1, imports nothing): `createLru(maxEntries, maxWeight, weigh)`. It drops the least
  recently used entry first, never keeps an entry heavier than the weight bound, and has `clear()`. It records every
  cache it makes, and `clearEveryLru()` empties them all. That call is test isolation only (below).
- `ChatList.tsx`: `MeasuredItem` draws its row itself (`TranscriptRowView`) from the row's props, behind
  `memo(…, sameRowProps)`. This is the one row barrier. `computeItemKey` and `itemContent` are `useCallback`s.
- `MessageBubble` and `ChatMarkdown` are `memo`. Chat's remark plugins are one module constant.
- `markdown.tsx#boundedHighlight` takes its markup from a module-scope `createLru` (256 entries, 4,000,000 characters
  of markup), keyed by `lang` and `raw`. The cache is asked only after every bound has passed, so a refused block is
  never highlighted and never cached. The cache is shared by chat fences, T4a's tool wells (`ToolWellText`, which
  calls `boundedHighlight`) and the Docs reader's `CodeBlock`. T4a's routing is unchanged: the ANSI reader never
  highlights, and `ignoreIllegals` makes the markup a function of the pair.
- `SessionScreen.tsx`: `onRetry`, `onDiscard` and `onAnswer` are `useCallback`s. They are now at the screen's state
  block; the plan's ≈:621-625 had moved to ≈:644-657 by T1c and T3e.

### Fix round 1 (review 1128)

- **F3, the day key.** The row barrier froze a clock-derived label: a usage-limit pill drawn on the day of its reset
  ("resets 12:00") kept those words the next day while the tab stayed open. `lib/clock.ts#dayKey` gives the viewer's
  local day (`YYYY-MM-DD`). SessionScreen derives it from the clock it already ticks for the header's facts
  (`useNow(30_000)`), so no timer is added, and passes it to `ChatList` as `day`. `sameRowProps` compares `day` only
  for a row whose words read the clock (`sameRow.ts#readsClock`: a usage-limit pill with a reset time), so that row
  draws again within one tick of local midnight and no other row does. `MessageBubble` takes `day` as a prop it does
  not read, so its memo lets the pill draw again.
- **F4.** `HIGHLIGHT_CACHE_MAX_CHARS`'s sentence is corrected; the code is unchanged. The bound weighs the markup only.
  A key is at most its markup plus the language's name and one character, so the cache holds at most twice the bound
  plus that per entry. The old sentence said a key is never longer than its markup, which is false by the language's
  name and the separator.
- **F5.** `highlightCache.ts` says that under the dev server's hot reload a re-evaluated `markdown.tsx` makes a new
  cache and leaves the old one reachable from `MADE` until the page reloads; production evaluates each module once.
- **F1, F2 and F6** are pins, listed in the mutation table: the streaming flag and a non-item prop (`askBelow`) reach a
  row through the list; the module cache's two bounds are pinned by what it holds, not by the constants; a rebuilt
  task item is the same row.

## Departure (named for the coordinator to number)

`c7-reset-seam-for-call-counting-suites`. The cache outlives a test case, and two existing suites counted
`hljs.highlight` calls as a stand-in for "this block was highlighted":

- `markdown-bounds.test.tsx`'s `spyHighlight` answers `''`. The cache stored that answer for an 8,192-character ts
  block one case rendered, and the worker-path case on the same block then saw 0 calls.
- `docs-highlight-budget.test.tsx`'s `run()` asks whether hljs saw each block, and page G repeats page S's 48 fills.

Neither file is in C7's Files. The coordinator ruled on C7's two asks: one reset, in the shared harness.
`pwa/test/setup.ts`'s shared `afterEach` calls `clearEveryLru()`, which is test isolation only; production never
calls it. `setup.ts` imports `highlightCache.ts`, which imports nothing, so no file's own `vi.mock` of `lib/markdown`
meets an instance loaded first. With that reset, `markdown-bounds.test.tsx` passes with main's text unchanged.
`docs-highlight-budget.test.tsx` renders several pages in its one case, and page G repeats page S's blocks, so its
`run()` also empties the cache between pages: one call, and nothing else in the suite changes.
`markdown-highlight.test.tsx` needs no reset of its own for its counts. Each case in its cache block highlights text
that no other case in the file does. The file's earlier cases repeat bodies (`tsBody(1000)` and `pyBody(65 536)`, two
cases each), but they count no calls; they read the markup, which a held answer leaves unchanged. (The first round's
note said every case in the file used its own text, which was false.)

## Residuals

- `renderToolWell(use)` returns a new function on every call, so `ToolCard`'s `renderWell` is not identity-stable. It
  is built inside the row, so the row barrier covers it, and C7 leaves it alone.
- The row barrier compares a field added to an item later by identity. That is the safe direction: at worst the row
  renders again.
- A date divider's words (`chatItems.ts`'s `dividerLabel`, "today · 14:02") read the clock too, but they are an item
  field that `buildChatItems` computes, so they change only when the events do. That was so before C7, and the barrier
  lets a changed label through.
- Inside ONE test the cache persists, so a test that renders the same (language, block) twice and counts
  `hljs.highlight`'s calls sees one call. `docs-highlight-budget`'s `run()` is the one such case today, and it empties
  the cache between pages.
