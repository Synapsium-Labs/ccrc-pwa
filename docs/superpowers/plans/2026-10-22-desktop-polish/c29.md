# C29: the two macOS reds left in main's daily full suite (D-8354)

The task note for the programme ledger (Task C29 of `docs/superpowers/plans/2026-10-22-desktop-polish.md`, D-8354). The
coordinator folds it into the ledger. This task starts from `main` at `ab757c19a`.

The brief: the daily full run on `main`, 43147459620 at `80d5823be`, failed one job only, `test-macos 4/8` (job
130948672022), with two red tests. A promotion to stable needs a green `full-suite`, which includes that leg. Root cause
first, for each file separately: say whether the code under test or the test's measure is wrong on macOS, and fix the
cause. No skip on Darwin, no raised bound or timeout as the fix, no change to the gate, `full-suite` or `macos.yml`'s
role. `ccd/session-hook.sh` is under another programme's claim, so only test files change.

## In short

- **`session-hook-compact-carry.test.ts`: the test's measure was wrong, on every platform. Fixed.** Its grammar table
  read the clock once, when the file was collected. The red row was built 175 s old on purpose, a 5 s margin inside
  the 180 s lease, and the macOS shard reached it about 5.5 s after collection. `parseServerCaps` judged the row
  current. Then the Stop and the PreCompact ran, and the hook read its clock past the lease. The two "disagreed" about
  a file that the case itself had let age across the boundary between the two reads. The hook and the parser agree. Each row is now rendered at the moment its case runs, after the Stop,
  and the parser is asked at both ends of the hook's run.
- **`session-hook-prune-deny.test.ts`: the test's measure was wrong on macOS. Fixed.** Its CPU probe (`childCpu`) fed jq
  a 128 KB input through `spawnSyncGroup`, a detached `spawnSync`, with `input`. On a hosted macOS runner such a run now
  and then delivers every byte of the input and never the end of it. The child waits in `read(2)` for an end that never
  comes, until the timeout. The hang was measured with `cat` in jq's place. That the red, one jq run past the 120 s
  timeout with nothing on its stderr, was this hang is inferred from its matching symptoms. The hook's jq program is
  fine. The probe now hands the run its input as a regular file.

## compact-carry

### The red (measured)

`the skip engages only behind the server's word (D-5239, spec §6.1) > grammar row "at 1794456851\ncaps
dispatch-live-gate-v1\nend\n": the hook and parseServerCaps agree`, at `session-hook-compact-carry.test.ts:191`:
`parseServerCaps: {"ok":true,"at":1794456851,"words":["dispatch-live-gate-v1"]}: expected false to be true`. So the
parser answered "advertised", and the hook wrote the hookstate as if it was not.

- The run's plain rows carry `at 1794457026`, which is 04:17:06Z, the moment the file was collected (`n`). The red
  row's `at 1794456851` is exactly `n - 175`: the table's eleventh row, `n - SERVER_CAPS_LEASE_S + 5`, built 175 s old
  on purpose with a 5 s margin. It is the file's 25th case (14 cases come before the table), and the table's first row,
  the 15th case, was green.
- The 24 cases before it took 5 459 ms together, so the red row ran about 5.5 s after collection, and its 5 s margin was
  spent. The parser still answered "current", so it read its clock at most 180 s after the row's `at`.
- `SERVER_CAPS_LEASE_S` is 180, and the hook's copy of it is `now - at <= 180` (`_hook_server_cap`).
- The case asked `parseServerCaps(text, nowS())`, then ran the Stop (`doneAt`) and the PreCompact. The parser read the
  clock before two hook runs. The hook read it after them.

### The cause

`const n = nowS()` sat in the `describe` body, which vitest runs when it collects the file. Every row's `at` was
relative to that moment, not to the moment its case ran. The boundary rows are built with 5 s margins (`n - 175`,
`n - 185`, `n + 60`), so a case reached more than 5 s after collection may find its row at the very edge of the lease.
On the loaded macOS shard the row `n - 175` was reached about 5.5 s after collection, its parse fell inside the
lease, and the two hook runs carried it past. No grammar disagrees: the case compared two readings of a clock taken at
different times, and the file crossed the lease between them.

### Reproduced on Linux (measured)

In a scratch copy of the tree, `n` was aged to 179 s (`n = nowS() - (SERVER_CAPS_LEASE_S - 1)`) and `doneAt` given a
2.5 s pause after its Stop, as a slow runner's Stop. The table's first row went red with the daily run's own message:
`parseServerCaps: {"ok":true,"at":…,"words":["dispatch-live-gate-v1"]}: expected false to be true`. That is a different
row from the daily run's (the eleventh), reddened by the same mechanism: a row at the lease's edge, judged current
before two hook runs and stale after them. With a 1.5 s pause the row was still green, because the hook's `now - at`
was still 180 at whole seconds.

### The fix

| Where | Change |
|---|---|
| the grammar table | Each row is a function of the moment (`Row`, `atFrom`). Its label is rendered with `<now>`, `<now-175>` and so on, so the case names are stable across runs. |
| the grammar case | Runs the Stop first. Then it reads the clock (`t0`), renders and writes the row, runs the PreCompact, and reads the clock again (`t1`). The parser is asked at `t0` and at `t1`: the hook reads its clock between them, and a row's answer is one interval of that clock, so both ends agreeing fixes what the hook must answer. If they differ, the case says the runner was too slow for the row's margin instead of naming a disagreement. |
| the control "lease − 1 s" | Plants its file after the Stop, so its one second of lease covers the PreCompact's run alone, and checks that the file was still inside its lease when the hook had run. |

The other rows (`NOT_ADVERTISED`) are unchanged. All but one only move further from "advertised" as time passes. The
exception is "in the future" (`at` now + 60), which becomes current after 60 s: planted before the hook runs, it could
only misfire after a 60 s stall, and then the case reds, never passes.

## prune-deny

### The red (measured)

`the forbidden program's cost on quote-dense payloads naming worktree and prune > dqsub: deny linearity from 64 to 128 KB
stays within the inherited-cost bound`: `bash's times line, after "": Error: spawnSync bash ETIMEDOUT`, after 122 068 ms.

- The case runs eight jq invocations (the original and the current program, at 64 and 128 KB, twice). On macOS each
  normally takes 0.2 to 0.5 s of CPU: this case measured `cpu ms 201, 213, 401, 404` in C27's dispatch 43142855710 and
  `269, 310, 486, 508` in C26's 43124495612. So 122 s is one run hung to the 120 s timeout, plus the others.
- Nothing reached stderr, not even `times`' line, so the jq never finished.
- The case beside it, "dqsub: deny stays within the startup-adjusted 33e521e07 bound at 64 KB", took 1 188 ms, its
  usual time. The files beside it on the shard ran their usual case times. Same runner image (`macos-26-arm64`
  20261102.0473.1) and the same jq (Homebrew 1.8.2) as the green runs.

### What it was not (measured)

Run 43158822625 repeated the exact invocation, with the jq started by an asynchronous `spawn`: 400 runs alone and 400
beside the files that ran beside the red (`ccd-child-reclaim-pin`, `ccd-reclaim-tail-window`, `ccd-reclaim-tail-mounts`).
None hung: 128 KB took 0.42 s at the median and 0.87 s at the worst. The file's dqsub cases were green 5 of 5 alone and 3
of 3 under that load. So the jq program is not slow on macOS, and load alone does not explain the red.

### Reproduced on macOS (measured)

These runs used a throwaway workflow on this task's branch (`c29-darwin-probe.yml`), removed before the wave-done.
Run 43164250729 repeated what `childCpu` does, a detached `spawnSync` with a 128 KB `input`, with `cat` in jq's place, and
a watcher that dumped every child alive past 8 s (`ps`, `lsof`, `sample`). The runner's Unix-domain stream sockets have
8 KB buffers (`net.local.stream.sendspace` and `recvspace` 8192), and node hands a child its stdin as such a socket.

| What (run 43164250729) | Runs | Hung to the 20 s timeout |
|---|---|---|
| `cat`, detached, alone | 3000 | 2 |
| `cat`, attached, alone | 3000 | 0 |
| jq, detached, alone | 300 | 0 |
| `cat`, detached, beside the red's files | 3000 | 6 |
| jq, detached, beside the red's files | 600 | 0 |
| `cat`, attached, beside the red's files | 3000 | 0 |
| the whole file, beside the red's files and `ccd-ws-reap` | 2 | 0 (`dqsub/deny` cpu ms 177, 181, 337, 353 and 189, 198, 352, 359) |

Every one of the 8 hangs looked the same. `cat` had written 131 161 bytes to `/dev/null`, which is exactly the input's
length, and sat in `read(2)` on its stdin socket. Its `bash` waited for it. node sat in `kevent`, inside
`SyncProcessRunner::Run`. So every byte arrived and the end of input did not, and stdout and stderr were empty.

**Inferred, not measured:**
- That the daily run's jq red was this hang. No dump was taken in the daily run, and the detached jq runs here did not
  hang (0 of 900). The link rests on the matching symptoms: a timeout, an empty stderr, and 122 s beside a 1.2 s
  neighbour. A hang in roughly 1 in 750 detached `cat` runs is rare enough to stay green in most runs of the file, and
  to red one now and then.
- Whether node never shut down its end of the socket, or Darwin never woke the reader. The dumps cannot tell the two
  apart, and either way the input does not end.

### The fix

| Where | Change |
|---|---|
| `server/test/session-hook-prune-deny.test.ts#childCpu` | Writes the input to a file under a fresh temp directory, opens it, and passes the descriptor as the run's stdin (`stdio: [fd, 'pipe', 'pipe']`) instead of `input`. It closes the descriptor and removes the directory afterwards. Still `spawnSyncGroup`, still timed, still `times` for the CPU. A regular file ends where it ends. |
| a new case, "a run reads its input from a regular file, whole, never from a socket node writes (D-8354)" | Runs `test -f /dev/stdin`, then `wc -c`, on a 200 KB input. It is red if the input goes back through `input`. |

The bounds, the sizes, the timeouts, `spawnGroup.ts` and the hook are unchanged.
