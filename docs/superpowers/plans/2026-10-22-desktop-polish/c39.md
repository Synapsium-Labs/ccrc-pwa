# Task C39: a masked key can still move the terminal drawer's rows (D-8694)

Run 2288, wave 134. Base: `main` at b99bc6390 (C36 landed). Every claim below is labelled **measured** (a run whose
output is quoted or summarised here) or **inferred** (read from code or documented behaviour, not run). Every key used
was synthetic; no real key, revoked or not, was used anywhere.

## What C36 left open

C36 (#2912, D-8665) stopped the drawer drawing a PROVISIONAL mark while a run is withheld. The FINAL mark is still
`SECRET_MASK` (`‹secret masked›`, 15 columns), spliced by `spliceMasked` (`server/src/accounts/shapes.ts`) once per

client, so a mark wider than the text it replaces runs past where tmux believes the row ends.

### Correcting C36's departure note (review 2248, finding F1)

C36's note, departure `drawer-final-mask-columns`, is wrong in two sentences, as review 2248 F1 found. This note
carries the correction rather than editing `c36.md`:

- "Only the two rows holding the key differ from the raw screen, and nothing else moves (**measured**)": the
  measurement used a 44-character key on one row, so it says nothing about a key split across a row break. A key split
  by a hard row break is masked one row segment at a time (`fingerprintSpans`' joined candidate is two spans, and
  `shapeSpans` splits a span at each joined seam), and each segment becomes its own 15-column mark (**measured**,
  below; **inferred**, from the code).
- "Only a secret shorter than 15 columns, masked at a row's end, could reach the right edge (**inferred**)": the unit
  is the row SEGMENT, not the secret. A key of any length overruns when its head segment is narrower than 15 columns
  and starts in the row's last 14 columns, and a short tail segment pushes the text after it on its row past the edge
  (**measured**, below). A whole shape-only key can be shorter than 15 columns too: `genericSk` matches
  `sk-` and 8 more characters, 11 in all (**inferred**, from `CREDENTIAL_MASKS`).

The same on both maskers and at rows 20, 49 and 50 (**measured**). The rule the sweep shows, for a segment that fits
its row: a mark moves other rows exactly when it is wider than the text it replaces AND that excess reaches the row's
last column, either because the segment starts in the row's last 14 columns or because the text after it on the row is
pushed past the edge (**measured** for every shape above). Such a segment of 15 columns or more never does: its mark is
narrower than the text it replaces (**measured**: 0 of 156 one-row placements). A key drawn UNBROKEN past the right
edge is the exception, the terminal-wrap residual (review 2326 F2): tmux sends it as one run and leaves the wrap to the
terminal, in a paint and in a redraw (**measured** through a real tmux 3.6, desktop polish Task C41, `c41.md` §2), and
a mark of any width shorter than the key removes the wraps the raw stream took, so each later relative move lands a
row up: for a 500-character key at 220 columns, rows 49 and 51, the status row among them, differed from the raw
stream's screen (**measured**, C41, on `main` and after C41 alike). No mark shorter than the key can keep those wraps
without showing its length.

**The status row.** With tmux's scroll region set, an overrun near the bottom scrolls the pane's rows and leaves the
status row alone (**measured**, every sweep row above: status row unchanged). Without it, as tmux sends a client
between scrolls, a relative move down from the key's rows lands one row lower on the glass than tmux intends: a key
split at row 20, then `CR LF`, `CUD 28` and a write meant for the pane's last row, put `* Working... (11s)` over the
status row for heads starting at 207, 210 and 215 (5 rows differ), and left it intact for heads at 100 and 200 (2 rows,
the key's own) (**measured**). That is review 2248's shape (`row 50 raw: '[demo] 0:node*' / after: '* Working...'`).

**Later redraws.** Every move above lasts until tmux next addresses the moved rows absolutely; tmux keeps its own
picture and redraws only what it thinks changed, so a moved row stays wrong until something on it changes or the
client is re-attached (**inferred**, from tmux's redraw model and C36's measurement of the provisional mark's identical
failure).

**How often a row's width changes.** Every masked segment whose width is not exactly 15 columns changes its row's
width on the glass: a segment of 16 or more columns makes its row shorter (every fingerprinted key is 20 bytes or more),
one under 15 makes it wider (**inferred**, from `spliceMasked`; **measured**: the key's own rows differ in every
placement above). For a segment that fits its row, only a wider row can move other rows, and only from the last 14
columns or with the row's text reaching the edge (a key drawn unbroken past the edge is the terminal-wrap residual
above): about 14 in 220 of keys hard-wrapped at the right edge (review 2248's refuter C; **measured** above as
14 of 44 head placements across the last 44 columns).

## Options, and what each reveals

The drawer is the only egress where a row's width matters. Every option below changes the DRAWER only (a drawer-only
splice beside `spliceMasked`, chosen by `DrawerMask.out`); `spliceMasked` and every other egress (transcripts, pane
history, the fleet frames, mail, push) stay byte for byte as they are (**inferred**, from the call graph: `DrawerMask`
is built once, in `server.ts`'s `/ws/pty/:id`).

A width-keeping mark is one exactly as wide as the text it replaces, so the text after it on its row lands at the
column tmux drew it at. That is also what makes it reveal the length: the reader sees where the key's text ends.
**No option keeps every row's width without revealing each masked segment's width in columns**, and on one row a key's
width is its length (**inferred**: the end column of a width-keeping mark is the end column of the key, and the text
after it is drawn there; also readable in the stream itself as the mark's byte count). A cursor move in place of
cells (`CUF n`, `ECH n`) carries the same `n` in the stream.

Measured on the same frames as the sweep, replacing each masked segment with the option's mark (the geometry each option
draws; rows that move, of 44, 44, 150 and 1 placements of the four shapes: split at the edge with a relative move to
the last row, split 7 before the edge at row 49, one row with prose after it, a short tail followed by prose). This
second harness placed the one-row key at columns 6 to 155 only, so it counts 150 placements where the sweep above,
which placed it at every column it fits, counts 156 (fingerprinted) and 160 (shape); the plan's "316" is that sweep's
two maskers together at one row:

| Option | Rows that move | Keeps the key's row width | What it reveals about a key, beyond today | Label |
|---|---|---|---|---|
| Today: `SECRET_MASK`, 15 columns | 14, 7, 0, 1 | no (wider under 15, narrower over 15) | nothing (constant width) | **measured** |
| A. Exact width: the label cut to the segment's width, or padded with a filler to it | 0, 0, 0, 0 | **yes** | **the key's length**: every segment's width in columns, so a one-row key's exact length and a wrapped key's total | **measured** (geometry); reveal **inferred** |
| B. Never wider: the label cut to `min(15, width)` | 0, 0, 0, 0 | only under 15 | **the exact width of every segment under 15 columns**: a wrapped key's short tail (so its total length), and a whole short shape key's length | **measured**; **inferred** |
| C. One column: a constant one-column mark for every segment | 0, 0, 0, 0 | no (narrower, like today's mark over a long key) | **nothing**: constant width, as today | **measured**; **inferred** |
| G. The label when the segment is 15 columns or wider, else a one-column mark | 0, 0, 0, 0 | no | **one bit per segment**: whether it is under 15 columns, so for a wrapped key's tail whether the length past its last full row is under 15, and for a shape key whether it is under 15 characters | **measured**; **inferred** |

What changes for the other egresses: nothing, under every option (**inferred**: the drawer-only splice is the drawer's
alone). What C and G change in the drawer: a masked key is no longer always read as `‹secret masked›`. Under C every
masked key is one cell; under G only a short segment is. A one-column mark must be one column in xterm.js: the PWA loads
no Unicode-11 addon, so xterm.js's default width table applies, where an East Asian Ambiguous character such as `•`
or `▒` is one column (**inferred**, from `pwa/src`: no `unicode11` import). Narrower marks (C, G, and today's over a
long key) leave the text after the key on its row further left than tmux drew it, so tmux's next partial redraw of that
row can leave stale cells on it (**inferred**); while each segment fits its row they never move another row
(**measured**, 0 in every shape), and a key drawn unbroken past the edge is the terminal-wrap residual above.

Options considered and set aside:

- **Clamp to the room left on the row.** Needs the cursor's column, which the masker does not track (C36 measured why a
  saved cursor and `CUB` cannot recover a pending wrap); tracking it means a terminal emulator per drawer socket in the
  server, and the clamped width would still reveal a short segment's width. (**inferred**)
- **Exact width only for a key's head, the row it is broken on.** A key that simply ends its row, followed by an
  indented row, is read as a head too (rows mode masks the next row's leading run, failing closed), so the head's
  width is often the whole key's length. (**inferred**, from `shapeSpans` and `fingerprintSpans`' row joins)
- **Mask through the end of the row.** Hides text that is not a key, and the cursor's column still matters to tmux's
  relative moves after it. (**inferred**)

## The rule, and the ruling

The brief's rule: build an option that keeps every row's width AND reveals nothing a reader of the screen could not
already tell; if every option that keeps the rows in place reveals more about a key, such as its length or a bound on
it, stop and ask. The only option that keeps every row's width is A, and it reveals the key's length. So this task
stopped before building and mailed the options to the coordinator, recommending C.

**Ruled (the coordinator, 2026-11-16, mail delivery 21918): build C.** It is the only option that reveals nothing beyond today's
constant-width mark, and it removes every measured move of another row and every status-row overwrite. **A, B and G
were declined for that reason**, each revealing a length or a bound on it (measured reveals in the table above: A, every
segment's width, so a key's length; B, the exact width of every segment under 15 columns; G, one bit per segment, under
15 columns or not). The operator may ask for G later if the readable label matters more to them than that bit.

## What was built

`DRAWER_SECRET_MASK` (`server/src/accounts/mask.ts`) is the drawer's mark. `spliceMasked` takes the mark as a
parameter whose default is `SECRET_MASK`; `maskWithCarry` passes `MaskOpts.mark`, and only `DrawerMask.out` sets it, so
every other egress calls exactly what it called before. `DrawerMask`'s taint check (a run past what a drawer holds that
ended in a mark) reads the drawer's mark. Nothing else moved: no `ccd`, no tmux window size, no PWA file.

**One glyph per row a key touches.** `spliceMasked` draws one mark per run of touching spans, and a key broken across
rows is masked one row segment at a time (the row end between its segments is kept), so a key across a row break shows
one `⌧` on each row it touched (**measured**: `drawer-mask-screen.test.ts` pins the head's row as `…key: ⌧` and the tail's
as `  ⌧ done.`, and a sweep pins the count of marks to the rows a key touches for keys of 11 to 8,192 characters). How
many rows a key spans was already visible with the 15-column mark. One exception, as on `main`: a run longer than the
drawer holds (`DRAWER_HELD_MAX`) on one row draws two adjacent marks, the fail-closed chunk's and the next chunk's
taint mark (`x=⌧⌧`, where `main` drew `x=‹secret masked›‹secret masked›`; review 2307, measured there). No real key is
that long.

**The glyph** (the coordinator's conditions 1 to 3). U+2327 X IN A RECTANGLE BOX, the ISO 9995-7 symbol for a "clear"
key:
- East Asian Width **N** (Neutral) and general category So in the Unicode data (**measured**, Python's `unicodedata`),
  so no terminal that widens Ambiguous characters draws it in two columns; U+2022 BULLET, U+2592 and U+26BF SQUARED KEY
  are Ambiguous and were set aside. Not a combining or format character.
- One column in xterm's own width table (**measured**: `@xterm/headless` 6.0.0 advances the cursor one column for it and
  reports cell width 1, pinned in `drawer-mask-screen.test.ts`). That table (Unicode 6, xterm 6.0.0's only one) cannot
  tell Neutral from Ambiguous, since it gives U+2022, U+2592 and U+26BF one column too, so "never Ambiguous" is held by
  the test's literal pin of U+2327, whose East Asian Width class is N; a comment beside the assertion says so (review
  2307 M3).
- Not ASCII, not box drawing or a block element, and not a glyph Claude Code draws: absent from the installed Claude
  Code build (2.1.325, the newest on the fleet box) both as the character and as a `\u2327` escape (**measured**, a
  byte search of the build), and not among the glyphs its output uses (`⏺ ⎿ ● ○ ◯ · • ✻ ✶ ✳ ✢ ✽ ✓ ✔ ✗ ✘ ☐ ☒ ❯ › ※ ▪ ▫ ↓ ↑ → ← ⧉`, the block
  quadrants of its logo, `⏵ ⏸`), the list the test pins.
- No SGR around it: the mark is the one character, so the attributes of the text around it are untouched.
