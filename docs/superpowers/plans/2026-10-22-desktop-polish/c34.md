## 1. `chat-marks-negation.test.ts`, "the check scales linearly"

**The failure.** A merge-queue run on 2026-11-12 measured a ratio of 8.25 against the bound of 8 (`pwa 3/3`, the brief's
receipt; not re-read here). The shipped case timed the fastest of three runs at 50k characters, then the fastest of three at
200k, in wall time, and asserted `large / max(small, 1) < 8`.

**Reproduced (measured).** The case's own code, with a line that wrote its ratio to a scratch file, run as the whole test file
in a fresh `vitest run` each time, inside the fleet's test slice (a CPU quota of 4 s per second, like a 4-vCPU runner) with
six busy loops beside it: **12 of 40** runs red, ratios up to 15.8; a second batch of 40, **5** red. In the red runs the
fastest 50k run took 5.5 to 12.5 ms and the fastest 200k run 88 to 112 ms, against about 5 and 17 ms on an idle box. With the whole pwa suite looping
beside it (three workers) instead, 0 of 40 were red (ratio at most 4.3): that load is milder than the one that hit the queue
run, and the busy loops are the one that reproduces it.

**The cause (measured, with one inferred step).** The brief's reading, that the 50k run is mostly fixed overhead, is not what
inflates the ratio: overhead would make it smaller, not larger. The 200k run itself slows. Four candidate forms ran side by
side in one instrumented case, 40 runs under the six busy loops:

| Form | Ratio p50 | p90 | max | Red (≥ 8) |
|---|---|---|---|---|
| shipped: wall time, fastest of 3 at 50k then of 3 at 200k | 3.19 | 8.47 | 15.80 | 5 |
| wall time, 5 alternating turns | 4.12 | 5.03 | 17.85 | 3 |
| wall time, four 50k runs in one timed batch against one 200k run (equal work) | 3.90 | 5.94 | 16.79 | 4 |
| thread CPU time, fastest of 3 each | 4.11 | 4.83 | 5.26 | 0 |
| thread CPU time, 5 alternating turns | 4.24 | 4.62 | 4.87 | 0 |

Equal work in wall time did not help: four 50k runs in one batch took about 30 ms while one 200k run took about 90 ms, though
the 200k run's thread CPU time was 17 to 29 ms. So under load the 200k run spends about two thirds of its wall time off the
CPU, and runs of the same total work in smaller pieces do not. The likely mechanism is garbage collection: a 200k run holds
far more live data at once (its 200k-entry table, its runs and matches), and on a loaded box the main thread waits for GC
helper threads that are not scheduled (inferred, not traced). Whatever the waiting is, CPU time does not count it.

**The fix.** The case now measures CPU time with `process.cpuUsage()` (the worker process's user and system time; in vitest's
default `forks` pool that process runs this one test file). Each size runs once untimed first, then the two take five turns,
and the least CPU time of each is kept; the bound stays `< 8`. Every run, the warm-ups included, is still bounded at 400 ms of
wall time, so a quadratic check fails fast. The failure message lists every turn's CPU times. `process.threadCpuUsage()`
(this thread only) held as well in the table above; `process.cpuUsage()` is the older, everywhere-present call, and it reads
to well under a millisecond here (measured: a 1 ms busy loop read 1.00 ms five times of five). It counts the GC helper
threads' CPU time too (measured: under mutant M3 below a 200k run read about 500 ms of CPU inside a 400 ms wall bound), which
is work the check caused, so it belongs in the ratio.

**Measured after the fix:**

- Under the six busy loops, **100 of 100** runs green: ratio p50 4.02, p90 4.64, p99 5.76, max 6.10. The 200k run's CPU time
  had a median of 23.7 ms (at most 32.0 ms).
- With the whole pwa suite looping beside it, **40 of 40** green, ratio at most 5.37.
- Idle, ratios of 3.95 and 4.09.

**The test keeps its power (measured; each mutant applied to `pwa/src/lib/chatMarks.ts` from a saved copy, three runs each
unless stated):**

| Mutant of `LabelScan.withheld` | Shipped form | New form |
|---|---|---|
| M1: `this.questions ??=` becomes `=` (the sentence table rebuilt for every label) | red 3/3, wall bound (about 700 ms) | red 3/3, wall bound (about 720 ms) |
| M2: `restart()` on every call (the token scan starts again for every label) | red 3/3, wall bound (about 1590 ms) | red 3/3, wall bound (about 1650 ms) |
| M3 with 2048: the table rebuilt every 2048th label (quadratic, small constant) | red 3/3, ratio about 12.9 | red 3/3, ratio 14.8 to 19.7 |
| M3 with 8192: the table rebuilt every 8192nd label | red 2/3 (8.30, green, 8.51) | red 3/3, ratio 11.6 to 12.5 |

M3 passes the 400 ms wall bound at both sizes, so only the ratio catches it; the new form catches the milder one every time,
where the shipped form missed it once. Every mutant ran with the case's `-t` filter.

**Departure found, not fixed (`plugin-bound-under-load`).** In the 100 runs under the six busy loops, a different case in the
same file, "through the plugin, one clause split into many text nodes is one pass too", went red once: `expected
400.6598180000001 to be less than 400`, its wall bound on one `runSync` at 100k characters (6 to 21 ms on an idle box, by its
own comment). It is the same off-CPU waiting (inferred). It is not on the watch list and the brief does not name it, so it
is left as it is for the coordinator to rule on.

## 3. `platform-hazards.test.ts`, R14(i) on Linux

**The case.** D-3833 and D-3979 pin `LC_ALL=C` around the auth readers, because under a UTF-8 locale bash misses a NUL that
follows a lead byte in an unpinned `read -d ''` and merges a line ending in a lead byte with the next one in an unpinned
`read -r` loop. R14(i)'s Linux case asserted both misreads (`NUL_RC=1`, `LINES=1`) as the control that makes mutation rows
T4-M32, T4-M31 and T1-1 able to red.

**The cause (measured).** The misread belongs to bash before 5.3. The case's own probes (the same two files, `LC_ALL` set to
`C` and to `C.UTF-8`), run on 2026-11-16:

| bash | C library | where | `C.UTF-8`: `NUL_RC` / `LINES` | `C`: `NUL_RC` / `LINES` |
|---|---|---|---|---|
| 5.1.16 | musl | the official `bash:5.1` image | 1 / 1 (misreads) | 0 / 2 |
| 5.2.15 | glibc | the `node:24` image (Debian) | 1 / 1 (misreads) | 0 / 2 |
| 5.2.37 | musl | the official `bash:5.2` image | 1 / 1 (misreads) | 0 / 2 |
| 5.3.9 | glibc | the fleet box | 0 / 2 (reads bytes) | 0 / 2 |
| 5.3.20 | musl | the official `bash:5.3` image | 0 / 2 (reads bytes) | 0 / 2 |

The change is bash's, not the C library's: both libraries misread under 5.1 and 5.2 and neither does under 5.3. On 5.3.9 a
two- and a three-byte lead (`\xe2\x82`, `\xf0\x9f\x98`) and a lone `\xe2` read correctly too, and on 5.2.15 all three misread
(measured). CI's Linux runner has bash 5.2.21 (the brief's figure, not re-measured here), so the case is green there; it goes
red as soon as the runner image moves to bash 5.3 (inferred). A bash below 5.1 is inferred to misread, not measured.

**What changed.** The Linux case reads the bash version from the probe (`BASH_VERSION`). On a bash below 5.3 it asserts both
misreads exactly as before. On 5.3 and later it records, as the macOS case does: it prints which answer the probes gave and
whether a dropped pin can red T4-M32, T4-M31 and T1-1 on this bash, and asserts only that both probes ran and gave their
fields. A version it cannot read fails the case. The shipped locale pins in `ccd/ccrc` are unchanged.

**Measured, each mutant restored from a saved copy:**

| Run | bash 5.3.9 (the fleet box) | bash 5.2.15 (`node:24`, the worktree mounted) |
|---|---|---|
| R14(i), as changed | green (recorded) | green (asserted) |
| R14(i) with the probe pinned to `LC_ALL=C` (a bash that does not misread, faked) | green: records | **red**, both soft assertions (`NUL_RC=0`, `LINES=2`) |
| U4n, `_box_env_has_nul`'s own `LC_ALL=C` dropped (T4-M32) | green: the mutant survives | **red**: `LC_ALL=C.UTF-8: a lead byte right before the NUL: expected 1 to be +0` |
| U4u, `_box_unit_env`'s `local LC_ALL=C` dropped (T1-1) | green: the mutant survives | **red**: F2 `expected [ +0, 'on', …] to deeply equal [ +0, 'off', …]` and L1 |

So on a bash that misreads the case still asserts the hazard, and a removed pin still reds its row. On bash 5.3 the pins
guard nothing that these probes can show, and T4-M32 and T1-1 survive there; the case now says so in its output instead of
failing. T4-M31 was not run; it is the same shape (inferred).

**Departure found (`locale-pins-hollow-on-bash-5-3`).** On bash 5.3 the shipped pins guard nothing these probes can show, so
mutation rows T4-M32, T4-M31 and T1-1 cannot red there (two of them measured above). Once CI's runner image moves to bash
5.3, those rows lose their power in CI as well, and no other check that runs there would see a pin removed (inferred). The pins
stay, since a bash below 5.3 is still in use (CI's runner, and any box with an older bash). Left for the coordinator.
