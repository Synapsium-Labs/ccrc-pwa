# Task C35: the timeout helper's pure-bash arm passes the caller's stdin through (D-8658)

Run 2207, wave 129. Base: `main` at 649ac3f13. Every claim below is labelled **measured** (a run whose output is
quoted or summarised here) or **inferred** (read from code or documented behaviour, not run).

## The defect

On a box with neither `timeout` nor `gtimeout`, the shared timeout helper starts the command as `"$@" &` in a shell
without job control. Bash gives such a job /dev/null for stdin unless the job carries a stdin redirection of its own,
so the command read nothing, while the same call under the binary read the caller's stdin. C28's fix round 1 found it
on the sign-in mint, and ask 357 ruled the fix at that helper's call sites (the fd-5 trampoline), leaving the helper
unchanged.

**Measured** (bash 5.3.9, Linux), with `f0(){ "$@" & wait $!; }`: `f0 cat < file` and `f0 cat <<<HS` print nothing,
and so does `f0 cat` after `exec < file`. With `fA(){ "$@" <&0 & wait $!; }` all three print the bytes, and so they do
under `bash --posix`.

## The change

One line in each copy: `"$@" &` becomes `"$@" <&0 &`, with one comment block above it, identical in all four copies.
`<&0` is a stdin redirection of the job's own, and it names the caller's fd 0, so bash does not substitute /dev/null.

Why not a copy through a spare descriptor (`{ "$@" 0<&6 6<&- & } 6<&0`): **measured**, with fd 0 closed the `6<&0`
copy fails (`0: Bad file descriptor`) and the command never runs. With `<&0` and fd 0 closed the command runs with fd 0
closed (`cat` answers `Bad file descriptor`, rc 1), which is what `timeout 5 cat <&-` does too (**measured**).

Unchanged, and still pinned by the tests that pin them today: the expiry code 124 and the stamp file that decides it,
the single TERM and the absence of any pid escalation in this arm (D-2764), the watcher's discarded streams (D-2272),
the `|| exit 0` on its sleep, and the whole binary arm (`-k` probe, grace clamp, the 137-to-124 rule). The watcher
subshell keeps its /dev/null stdin; it reads nothing.

## Call-site census

85 call sites (**measured**, by a script over the seven files that call a copy; comments and definitions excluded):
40 in `ccd/ccd`, 17 in `ccd/ccrc`, 11 in `ccd/ccrc-doctor-checks`, 8 in `ccd/lib/disk-retention.sh`, 3 in
`ccd/lib/train-proof.sh`, 4 in the sign-in helper and 2 in `ccd/ccgpt-runtime`.

On every box with coreutils (every Linux box) the binary arm already passes stdin through at all 85, so the change
reaches only a box with neither binary, such as macOS without Homebrew's coreutils, and there it makes each site
behave as it already does on Linux (**inferred**, from the binary arm's code and the measured shapes above).

What changes per site, in four groups:

1. **The call binds the command's stdin itself: no change on either arm.** The redirect sits on the call or inside
   the bounded command, so the command reads what it names, as before. `ccd/ccd` `_ws_reclaim_idwalk` and
   `_ws_cwd_users` (`</dev/null`); `ccrc-doctor-checks` `_check_cert`, `_check_docs` (two), `_dr_pw_launch` and
   `_check_cap-floor` (`</dev/null`); `ccd/ccgpt-runtime` `_rt_build`'s probe (`< probe.py` inside a child shell); the
   sign-in helper's three mint spawns (C28's fd-5 trampoline puts its own stdin back on fd 0) and its drain read
   (`read -u 8`, never stdin). C28's handling is kept exactly; only its comments now say the arm passes stdin through
   (**inferred**, read; the C28 cases stay green, **measured**).
2. **The strict neighbour's sites: no change.** `_plat_timeout_strict` runs only on a `strong` capability, so its
   sites (ccrc's models lock, writer, hook and canary arms) never reach the pure-bash arm (**inferred**, read; pinned
   by `ccd-plat-timeout.test.ts`'s "answers none ... the strict call runs nothing" cases). The two `true` calls that
   prime the capability read nothing.
3. **The command never reads stdin: no change in effect.** stdin now reaches it and it reads none of it: tmux
   (`display-message`, `list-panes`, `list-sessions`), gh (`api`, `pr view|list|checks|create|merge`; `pr create` is
   given `--title` and `--body`), git (`fetch`, `ls-remote`, `status`, `ls-files`, `rev-parse`; a transport's ssh is
   fed by git's own pipe), find, du, df, rm, lsof, journalctl, systemctl, the python3 scans (argv only; the in-flight
   scan hands jq its own pipe), the node scripts (`models-op.mjs`, `models-canary.mjs`, history `status`: none reads
   fd 0), `deploy/notify.sh` (its curl reads its own pipe), pip (`--no-input`), the bash probes that read fd 3, and
   `claude auth status` and `auth logout` (**inferred**, read). Two of these sit lexically inside a read loop whose
   input is redirected, the case where an inherited stdin could be consumed: `ccd/ccd`
   `_ws_archive_unrecorded_empty`'s `git ls-remote` (`done <<< "$remotes"`) and `train-proof.sh`
   `_ws_train_record`'s `gh pr view` (`done < <(...)`). Neither command reads stdin, so neither loop loses a line
   (**inferred**; both already run this way on every Linux box).
4. **The command reads a non-terminal stdin: stdin matters.** ccrc's three account probes (`_acct_probe` and
   `_acct_token_probe`'s two calls) run `claude -p`, which reads stdin when it is not a terminal (**inferred**, Claude
   Code's documented print mode; not run, because each is a billed turn). None sits in a read loop: their callers are
   `ccrc account` verbs that run once per call (**inferred**, read). On a box with no deadline binary they used to
   get /dev/null; now they get the caller's stdin, as they already do on every box with coreutils: a terminal (not
   read), /dev/null, or a pipe the caller wrote. A caller that leaves an open pipe on stdin now waits on it on both
   arms, up to the deadline, as it already did on the binary arm. Not changed here: a `</dev/null` at those three
   calls would change Linux too, and is a decision of its own (named below).

## The tests (red first)

`server/test/ccd-plat-timeout.test.ts`, a new describe, on all four copies, each case on a PATH of links that holds no
deadline binary (its first field proves `type -P` finds neither):

- a command that reads stdin gets the caller's bytes: a redirect on the call, a here-string, the shell's own stdin;
- inside a read loop the command takes the rest of the loop's input (`<1>2,3,`), as under the binary, and the same
  loop under the binary answers the same (that case skips where no system `timeout` exists);
- a reader blocked on a stdin that never ends (a FIFO held open read-write) still answers 124 at its deadline;
- a closed stdin stays closed, and the command still runs (rc 1 from `cat`).

**Measured** on `main`'s helpers (commit afa659334, the test alone): 16 red (4 cases × 4 copies), with
`arm:|||`, `arm:|<1><2><3>`, `arm:|0` (the blocked reader read /dev/null and answered 0 at once) and `arm:|0` (the
closed stdin was /dev/null); the 4 binary-arm parity cases green.
