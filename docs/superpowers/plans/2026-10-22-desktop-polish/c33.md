## Why four entries wait for C33b: the moved-definition false positive

**Measured** at local tip 7ff3674b1 (all 112 converted, the four notes reworded), against `origin/main` 649ac3f13: every
whole-tree guard was green except one case of `deviation-refs.test.ts`, "no allocator-era D-<n> is defined in two plans
across this branch and its base". It reported `D-8344 (one each side): 2026-10-22-desktop-polish.md / c27.md`, and the
same for D-8345 (`c28.md`), D-8354 (`c29.md`) and D-8381 (`c30.md`).

`crossTreeCollisions` takes the union of the branch's plans and the base's. On the branch, the plan defines each of the
four numbers and the note does not. On the base, the note still defines it. The definition moved between files, which is
the first false positive the scan's own message names. **Inferred**: it stays red in the merge queue as well, because
the queue measures against `origin/main` as it was before the merge. So it clears only after the merge, and a PR in that
shape cannot land.

**The ruling (delivery 21116): option A, two steps, with no change to any guard.** This PR converts 108 entries and
rewords the four notes. The four plan lines keep the hyphen form and are listed in `UNREAD_BASELINE` under the
desktop-polish plan, with a comment that names C33b. **Measured** on a throwaway local commit with the four lines back
in the hyphen form: the cross-tree case passed (run with `--testTimeout=180000`, because the box was at load 12 and the
case timed out at the default 20 s twice). On the branch nothing defines those four numbers, and on the base only the
note does: one file each, so no collision. After the merge, the coordinator's run C33b converts the four and removes
them from the baseline under D-8656. The base then holds no note definition, so that step is green too (**inferred**).

**Until C33b merges, the sweep reads none of D-8344, D-8345, D-8354 and D-8381 in the plan.** **Inferred**: on `main`
the four notes' lines are the readable definitions. After this PR they are citations, so for that interval no tracked
line defines the four.

**Option B, declined and not implemented.** Teach `crossTreeCollisions` that a file present on both sides is read from
the branch only. That would remove this false positive for everyone, but it changes an L1 rule of a guard, beyond this
brief. It would also hide a definition that main added to that file after the fork. It is recorded here as an
observation.

## The guard

A new describe at the end of `server/test/deviation-refs.test.ts`, "every definition-shaped line is one the ledger reads
(Task C33)":

- **The shape** is `^- \*\*D-(\d+)\*\*`: a bullet whose bold closes right after the number, at column 0. It is narrower
  than the floor scan's `DEFINED` prefix, so bolded citations such as `- **D-149 sweep:**` and `- **D-1039..D-1045**`,
  which the corpus rows pin as citations, stay out.
- **Fence-aware without a second fence parser.** A candidate line is replaced by `- **D-N** — probe` with its own
  number, and the file is read again with `definitionsIn`. If that adds a definition of N, the line sits where the
  reader looks, and it is flagged. A line inside a fenced block adds nothing, so it is a quotation and is skipped.
- **`UNREAD_BASELINE`**, file to numbers, holds the lines other plans hold today. It is compared as a multiset in both
  directions: a line beyond it reds ("write the entry readable"), and a member that no longer stands unreadable reds
  ("delete it from the baseline"). So it may only shrink.

**Measured, red first.** With the guard committed and the plan not yet converted, the first case failed and listed the
112 numbers in `2026-10-22-desktop-polish.md`, and nothing else.

**Measured, with one entry put back** (at the first step, before the four were restored). On a throwaway local commit
that restored `- **D-7257** - `, the case failed with exactly `2026-10-22-desktop-polish.md: D-7257`. The commit was
then dropped (`git reset --keep` to the tip before it).
