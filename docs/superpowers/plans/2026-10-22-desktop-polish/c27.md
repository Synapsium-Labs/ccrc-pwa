# C27: the macOS FIFO-EOF probe measured its own reader, not the FIFO (D-2661)

The task note for the programme ledger (Task C27 of `docs/superpowers/plans/2026-10-22-desktop-polish.md`, D-8344). The
coordinator folds it into the ledger. This task starts from `main` at `abeae005c`.

The brief: close D-2661 on macOS, so that the last red file in the macOS test legs, `server/test/platform-hazards.test.ts`
(its darwin case "BSD: after the deadline fires, does the output FIFO reach EOF? — candidate (b)"), goes green and a
promotion to stable can pass its gate. Root cause first. If the deadline shim leaves a descendant holding the output, fix
the shim. If the probe itself is wrong on Darwin, fix the probe and show why.

## In short

The probe was wrong on Darwin. Its writer did close. No descendant held the FIFO's write end in any red. The probe read
the FIFO with `read -t 0.5` in a loop. On macOS a FIFO's end of file is one-shot for anything that waits for it, so that
loop could consume the EOF in a read that still answered "timeout" (142). After that, `select()` never reported the FIFO
readable again, and the probe reported "never" for 15 s while a fresh `read(2)` on the same descriptor returned 0 bytes at
once.

The probe now waits with one blocking reader in a subshell, which never asks `select()`, and polls a marker file. It records
the timeout's process group before the deadline, so a real leak would be named. A control on both platforms keeps the reader
able to say "never" while a writer holds the FIFO. The shim (`_auth_timeout`) is unchanged. D-2661's candidate (b) as stated,
a descendant holding the write end, was not seen once on macOS: in every red that was inspected the timeout's group was
empty, and the fixed reader saw EOF in 260 of 260 iterations.

The account sign-in helper's pump waits on the same `read -t` and very likely has the same defect. Booked as Task C28 by the
coordinator's ruling (ask 356): not changed here.

**The old diagnostics were blind on Darwin, and that is why the reds said nothing.** `writer pgid=` was empty because it
asked `ps -o pgid= -p $W` after the deadline, when `$W` (the subshell running the shim) had already exited. So it matched
nothing. `holding the write end:` was empty because `lsof -- <path>` matches no row for a FIFO on macOS. It did not even
list the probe's own read end, `8r`, which was open at that moment.

### Why it is one-shot (two readers on one FIFO)

Run 43136715351 put a second reader on the same FIFO in the same iteration: a blocking `read` loop in a subshell, which
never asks `select()`. Usually only ONE of the two saw the EOF:

| Condition | both saw EOF | only `read -t` | only the blocking reader | neither |
|---|---|---|---|---|
| 2 x ncpu `yes`, 60 iterations | 16 | 32 | 10 | 2 |
| a test shard, 40 iterations | 0 | 34 | 1 | 5 |

On Linux a FIFO with no writers stays readable, and every read returns 0. On macOS, EOF is delivered once to whatever is
waiting. The flag that `select()` and an already-blocked `read(2)` wait on is cleared by the first read that returns EOF.
A new `read(2)` still returns 0 while no writer is left, because it checks the writer count before it waits. In the
single-reader reds, the only reader was `read -t`. So its own read consumed the EOF and still answered 142: no rc 1 appears
in any red. **Inferred, not measured:** the exact bash path that turns that EOF into 142. The last writer to close is `$W`,
whose exit also sends SIGCHLD to the reading shell at that instant, and that coincidence may be what loses the EOF.

## What changed

| Where | Change |
|---|---|
| `server/test/platform-hazards.test.ts#eofWait` | New. Waits for EOF on fd 8 with one blocking `read` loop in a subshell that marks EOF in a file. The shell only polls that file and never reads fd 8, so there is one reader and no `select()`. Its comment carries the measurement above. |
| the darwin case "BSD: after the deadline fires, does the output FIFO reach EOF? — candidate (b)" | Reads through `eofWait(15)`, the same 15 s window. Records the timeout's process group at +1 s, while it exists. GNU `timeout` makes its own group, so the group id is the binary's pid. A "never" now lists what is still alive in that group. The `lsof` line, blind on macOS, is gone. The red message still names candidate (b) and the remedy to end the descendants, now for a reader that cannot mistake its own lost EOF for a held writer. |
| a new case, both platforms: "the select-free EOF reader still says never while a writer holds the FIFO (D-8344 control)" | A subshell holds the write end for the whole 3 s window. The only correct answer is "never". |

Not changed, by the brief's rulings: the shim (`_auth_timeout`, `_plat_timeout`), the 15 s window, `macos.yml`, the
gate and `full-suite`. C26's files were not touched.

### Tests, and what each is red without

- **The control** goes red if the reader is made to answer "eof" whatever happens. Measured: with `GOT=never` mutated to
  `GOT=eof` in `eofWait`, the control is red on Linux (`a held writer read as EOF`). Restored, it is green.
- **The darwin case** goes red without the fix on macOS only: 17 of 185 iterations of its scenario with the old reader,
  0 of 260 with the new one (runs above). Linux cannot show this red. On Linux the old reader saw EOF in every iteration
  tried, because a Linux FIFO's EOF is not one-shot. Run on Linux with `itDarwin` lifted, the fixed case is green. With
  the grandchild `setsid`'d out of the group, it is red and names the recorded group.

## For C28: the pump (inferred, not measured)

`ccd/ccd-account-auth#_auth_pump` is the account sign-in helper's one read loop. It reads the child's output FIFO
(`$AUTH_RUN/out`, fd 8) with `_auth_read -r -t "$CCRC_AUTH_TICK" -u 8 line`. It leaves the loop only on rc 1, EOF (its
`else` arm), or on D-2736's backstop once `CCRC_AUTH_TIMEOUT + CCRC_AUTH_PUMP_GRACE` has passed. A timeout, rc above 128,
loops. So on macOS, if a `read -t` consumes the FIFO's one-shot EOF and answers 142, every later tick times out. The pump
then loops until the backstop, which sets `AUTH_EXPIRED=1` and sends TERM to the child that already exited. A mint that
finished, even successfully, would then be stamped `expired` after the full deadline (600 s by default) instead of reaching
its own end. That matches D-2661's first symptom: a 6-second `CCRC_AUTH_TIMEOUT` measured running 60 046 ms, before D-2736's
backstop existed. **This is inferred from the code and from the probe's measurement.** No pump run was measured on macOS in
this task.

`_auth_forward_code`'s `_auth_read -t 0 -u 7` peek, on the code channel, waits on `select()` too, but fd 7 is not read for
EOF.
