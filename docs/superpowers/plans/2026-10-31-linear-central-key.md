**Which tasks may run in parallel.** LK4, LK5 and LK6 share no file with each other or with LK1 to LK3, and may be built and land in any order, in parallel with the LK1 → LK3 chain. LK7 may be built in parallel too, but it shares `server/src/deps.ts` and `server/src/index.ts` with LK2 and LK3 (and `deps.ts` with #2031): its hunks are kept line-disjoint and whichever lands later rebases. A later task's Step 0 may start on the previous task's branch tip, but it commits only after rebasing on `main` once the previous task has merged.

**Why this order.** The store comes first because everything reads it and it calls no one. The rate service comes second because every later caller of Linear asks it before it calls (spec §6.7: "nothing else holds a bucket"), so no later task has to retrofit a budget. Routing and titles come third because the refresher is the only thing allowed to call Linear for teams and names (spec §4.3, §4.4), and the proxy and the Settings routes both need it. The containment pieces are independent and come before the code they protect (D-7683). The proxy comes before the verbs it serves, the Settings routes before the card that calls them, and the skill last because it switches every session over.

1. **A key outside its file.** A key in a log line, an error string, a journal row, a record, a response header, a closure, the directory or the rate service. 3. **A passthrough.** Any route field that becomes part of a GraphQL document, or a document that is not one of `LINEAR_OPS`' own constants (spec §6.4). Row 4's census reads the table; the reviewer greps `proxyRoutes.ts` for string concatenation into a document.
