# The growth check exempts a PR the operator names

**Size:** S. **Deploy class:** `server/test/` only (one new data file, one new fixture, two edited test modules, one edited test and one edited data file); no production byte, no `agent/`, `pwa/`, `ccd/` or wire change. One task.

## Problem

The god-file growth check (D-5848) was armed on 2026-10-21 (OA-C2, D-6178). A PR that grows a listed file by more than `GROWTH_LIMIT` (40) net code lines against the merge-base now fails that file's row in `test (server)`, unless one of two waivers holds: the same diff adds a new file under `L1_L2_NEW_FILE_DIRS`, or it shrinks another listed file by at least as much. Spec §5.2 (rev 2) foresaw a third answer, a PR "named exempt" by the operator, but nothing implements it. Path-identity W3 grows `ccd/ccd` by several hundred code lines, and its hard boundary rules out both waivers. The operator ruled on 2026-10-21 that W3 is named exempt, for `ccd/ccd` only, through a narrow mechanism that lands on its own, before W3. This plan builds that mechanism. It names no PR: the list ships empty, and W3's entry is a later change of two files, landed just before W3 at W3's measured delta: the entry in `growth-exemptions.json` and its stamp in `exemption-age.data.ts` (size 1, `since` re-dated). It edits no test.

## Task 1: a named PR may grow one listed file up to a cap (D-6211)

**Files:** create `server/test/growth-exemptions.json` and `server/test/fixtures/growth-exemptions/two-entries.json`; modify `server/test/growthCheck.ts`, `server/test/growth-check.test.ts`, `server/test/rings/exemption-age.data.ts` and `server/test/rings/exemption-age.test.ts`.

**Design:**

- **The list** is `server/test/growth-exemptions.json`, `{"exemptions": [...]}`. Each entry is `{pr, file, cap, reason, ruling, since}`: `pr` a positive integer; `file` one of `GROWTH_FILES`; `cap` an integer above `GROWTH_LIMIT`; `reason` and `ruling` one non-empty line each (`ruling` names the operator's ruling the entry rests on); `since` a real `YYYY-MM-DD` day, not in the future. A key outside those six, a missing key, or two entries for the same `pr` and `file` is malformed. It is JSON rather than a `*.data.ts` module because the authority is a blob read with `git show`, and a JSON blob parses without running anything from that ref.
- **One helper reads and decides.** `armedGrowth(files, root, base, head, env)` is the armed rows' whole read and decision: each file's growth, the two waivers, `origin/main`'s list, the PR number, the growth check's own files the diff touches, and the verdict per file. The armed describe calls only it, and a fixture row drives it end to end in a sandbox repository. The decision inside it is the pure `growthVerdicts(rows, over, entries, pr, touched)`, with a table test.
- **Authority is `origin/main`'s copy.** `exemptionsOnMain(files, root)` takes no ref: it always reads `fileAt(GROWTH_EXEMPTIONS_FILE, 'origin/main', root)`, never HEAD or the working tree. A PR's own edit to the list therefore never exempts that PR, and a CI re-run after an entry lands on `main` picks it up, because each server shard's checkout (`actions/checkout@v4`, `fetch-depth: 0`) fetches every branch afresh on a fresh runner. A list absent on `origin/main` holds no entries. A malformed copy on `origin/main` exempts nothing: the whole list is ignored, with a printed notice.
- **The PR number comes from `GITHUB_REF`, paired with its event**, through the pure `prNumberFromEnv(env)`: `refs/pull/<n>/merge` only under `GITHUB_EVENT_NAME` `pull_request`, and `refs/heads/gh-readonly-queue/<base>/pr-<n>-<sha>` only under `merge_group`. Anything else (a push, a schedule, a `workflow_dispatch` on any branch, a ref under the other event, no env) answers `null`, and then no entry applies.
- **An entry waives only its own file, only for its own PR, and only while the measured delta is at or below its cap.** `matchExemptions(over, rows, entries, pr, touched)` answers, for each file in `GROWTH_OVER`, the entry naming it for this PR and whether it applies. A row fails when its file is over and no entry applies.
- **A PR that edits the growth check gets no exemption.** An entry applies only when the diff the run measures (merge-base(origin/main, HEAD)..HEAD, renames split into both sides) touches none of `GROWTH_MACHINERY`. Under today's merge queue (one entry per group) that diff is the PR's own. The list has seven files: `growthCheck.ts`, `growth-check.test.ts`, `growth-exemptions.json`, `rings/exemption-age.test.ts`, `rings/exemption-age.data.ts`, and the two modules `growthCheck.ts` imports, `rings/exemptions.ts` and `scan/parse.ts`. Its own entry is included. A row pins the list as a literal. The end-to-end row edits each member from a hand-written list. Another row reads `growthCheck.ts`'s relative imports from its source and requires each to be in the list, so a future import must join it. An entry's own PR touches the list and the stamp, but grows no listed file, so it needs no exemption.
- **The trust boundary has an in-tree half and an external half.** In the tree, the list is read from `origin/main` only, and the machinery rule withholds every exemption from a diff that touches the check's own files. The bodies of `growth-check.test.ts` and `growthCheck.ts` sit inside the boundary, and no row in the tree can guard them: an edit there can switch the rule itself off, just as `GROWTH_ARMED = false` was already a one-token off switch before this work (fix rounds 1 and 2). The external half is the coordinator's landing act. Before enqueueing a PR under an exemption, the coordinator compares its file list (`gh pr diff --name-only`) with `GROWTH_MACHINERY` as read from `origin/main`, plus any local import of `growthCheck.ts` on `main`. Any overlap means it does not land under the exemption. A ruleset or CODEOWNERS rule over these paths would be the operator's, and is not part of this plan. `GROWTH_LIMIT`, `growthOver` and today's two waivers are unchanged.
- **The HEAD copy is checked on every run**, in a row outside the CI-only describe: it must parse and be well formed. The list is stamped in `EXEMPTION_SET_STAMPS` as `server/test/growth-exemptions.json#exemptions` (size held exactly, the 60-day rule), so a forgotten entry turns red rather than living on. `exemption-age.test.ts`'s `sizeOf` gains a `.json` arm to measure it. Its CONTROL measures a committed two-entry fixture, so the arm's count is pinned for a non-empty list. The live list is held only by the stamp rule, so an entry plus its stamp is green and an entry without one is red.
- **The report stays honest.** `GROWTH_OVER` still lists every file that grew over the limit and is not waived. An exempted file is annotated there, in the job summary and in the console table, with the PR number, the cap and the ruling. A file over its cap is named in its row's failure message with the cap it passed, and a file whose measured diff edits the growth check is named with the files it edited.

**Steps:**

1. Red: rows for `prNumberFromEnv` (a table of refs under their events, with trailing suffixes and a queue-shaped dispatch), the list's well-formed check (one row per malformed shape), `matchExemptions` (own PR at the cap, one over the cap, another PR, another file, no PR number, the machinery touched), `growthVerdicts` (a table: not over; over with no entry; at the cap; past it; another file, another PR, no PR number; the machinery touched), `exemptionsOnMain` in a fixture repository (an entry on HEAD only is not read; an entry on the fixture's `origin/main` is), `armedGrowth` end to end in a fixture repository (an entry on HEAD only exempts nothing; one on `origin/main` does; an edit to each of the seven machinery files, from a hand-written list, withholds it, the list file's own entry included), `GROWTH_MACHINERY` as a literal, `growthCheck.ts`'s relative imports all in `GROWTH_MACHINERY`, the summary's annotation, the HEAD copy and its stamp, and `sizeOf`'s `.json` arm on the fixture. Each is red against `origin/main` (no export, no file, no stamp).
2. Green: the functions in `growthCheck.ts`, the empty list, the stamp, the `sizeOf` arm, and the armed rows reading `origin/main`'s list.
3. Mutation proofs in a sandbox (a `git archive` committed as the base, with the sandbox's `origin/main` pointed at it), each measured before and after and recorded in the PR body: an entry for this PR at or under its cap passes; one line over the cap is red; a different PR number is red; an entry on HEAD only is red; an entry naming another file leaves the over file red; no PR number leaves it red; each malformed shape is red; reading HEAD instead of `origin/main` is red in every form (the read's literal, the helper calling `fileAt` at HEAD, the helper reading the working tree); a PR that edits any one machinery file is red with its entry on `origin/main`; deleting any one member of `GROWTH_MACHINERY`, or emptying it, is red; a new relative import in `growthCheck.ts` that is not in the list is red; a patch to `rings/exemptions.ts` or `scan/parse.ts` that fakes `origin/main`'s list is red; the decision mutated to `over && m === undefined` is red; removing either ref regex's trailing `$` is red; and the entry change (one entry plus its stamp at size 1) is green on `exemption-age` and `growth-check`, while an entry with its stamp left at 0 is red.

**Verify:** from `server/`: `growth-check`, `exemption-age`, `deviation-refs`, `dtbd`, `single-definition`, `topology-clean`, `typecheck-tests`, and `docs-grammar` for this plan. `git diff --name-only origin/main...HEAD -- server/src agent/src shared pwa ui ccd deploy` prints nothing.

**Routing:** native. **Needs:** nothing. **Gates:** none. **Not in this task:** any entry (W3's lands just before W3), and any edit to `GROWTH_ARMED`, `GROWTH_LIMIT`, `GROWTH_FILES` or `L1_L2_NEW_FILE_DIRS`.

## Deviations found

### Issued for this work and defined here

- **D-6211** — `growth-check-exempts-a-named-pr`: the armed growth check (D-5848, D-6178) gains a third waiver, an operator-named PR. `server/test/growth-exemptions.json` lists entries of `{pr, file, cap, reason, ruling, since}`. The armed rows call one helper, `armedGrowth`, which reads that list from `origin/main`'s copy only (`exemptionsOnMain` takes no ref), so a PR cannot exempt itself and a re-run after the entry lands picks it up. The PR number comes from `GITHUB_REF` paired with its event (a `pull_request` merge ref or a `merge_group` queue branch); with neither, nothing is exempt. An entry waives one file for one PR while the measured delta stays at or below its cap, and only when the diff the run measures (merge-base(origin/main, HEAD)..HEAD) touches none of the check's seven files (`GROWTH_MACHINERY`: the check's code and its two imports, its rows, the list, and the list's stamp and its test), pinned as a literal and against `growthCheck.ts`'s imports. The decision is the pure `growthVerdicts`. The trust boundary has two halves. In the tree: the `origin/main` read and the machinery rule, with the bodies of `growth-check.test.ts` and `growthCheck.ts` inside the boundary, since an edit there can switch the rule off, as `GROWTH_ARMED = false` always could. Outside it: before enqueueing a PR under an exemption, the coordinator compares the PR's file list with `origin/main`'s `GROWTH_MACHINERY` and `growthCheck.ts`'s imports, and any overlap means it does not land under the exemption. The HEAD copy is checked for shape on every run, and the list is stamped under the 60-day rule (D-6045). The list ships empty, and an entry is two files: the entry and its stamp.
