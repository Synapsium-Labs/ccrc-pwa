## In short

- **F1, the drawer's lead.** The drawer reads the last 64 bytes of what it sent with each push (`lead`). When the
  escapes before a key row's first byte pass 64 bytes, that text starts inside an escape, and its tail reads as a run
  joined to the key's row. The walk then stopped a row late as if it had proven the chain's start, so each push sent the
  held text's first row, unjoined. On `main` the whole key shows in a styled listing in small chunks (**measured**).
  Here, a run that joins back past the first unsent byte is held from that byte, and so is a run that ends its row and
  reaches past it; nothing in any form measured shows (**measured**).
- **F2, the cap arm.** Pane history's lookahead grows up to its cap. When the cap stopped the read inside a row's indent
  or between whole escapes, the arm read no run there and answered "no cut", so the key's rows went out raw on both
  sides of the cut: the whole key at 15 of 16 placements, and 448 bytes at the other (placement 11), on `main` (**measured**). Here the arm reads from the row
  before, as the first read does, and a read that is all one row's indent grows as for a chain that crosses the cut
  (an indent wider than the read sent a key's rows raw on `main` too) (**measured**: 0 at every placement).
- **F3, one joined row.** A key coloured per character on a row with no break was cut by slices inside an escape, and
  the chain's rows were carried for one 256 KiB window only, so its tail went out raw (up to 7,538 of 8,192 characters
  on `main`). Here slices and windows end outside an escape, a chain cut at a cap is carried on through every later
  slice (read over that slice only), and it is counted in its own units (**measured**: 0).
- **F4, cost.** The most a drawer holds for a key's rows and pane history's lookahead (`WHOLE_HELD_MAX`) is 64 KiB here
  (256 KiB on `main`); past it a chain's rows are masked, never sent raw. On the review's hostile key-free forms the
  worst slice or push falls from 10.2 to 47.3 ms on `main` to 5.8 to 18.1 ms here at the same load, the 18.1 a first
  repetition (**measured**, §6).
- **F7, r19's arm.** It has a row now (masked in the push itself, the review's form). Writing that row found that the
  arm also took a run that ends its row at the window's first byte, which the fail-closed tail does not reach: 98 bytes
  of a 108-byte shape key on `main` (**measured**). The arm now takes the open tail only.
- **Found in the task and closed** (each red on its mutant, §5): a BEL-ended hyperlink whose tail joins the key's row with
  no escape between (F1's family); the rest of a row a push ended inside, read as an empty row that ended a chain past

## 3. The fixes, and why each fails closed

All in `server/src/accounts/mask.ts`; `shapes.ts` is unchanged.

- **F1: the floor.** `chainBack`'s `ok` predicate became `floor`, the first index of the view a hold may start at (the
  first byte not sent). A run joined back past it, at the walk's first run or at a row before, is held from it and the
  walk ends there, proven: nothing before the floor can be held, and the most that can be held is held. `rowTailAt` holds
  a run that ends its row and reaches past the floor from the floor; one sent whole before it is not held again, so an
  Enter's echo after a run that was sent is still drawn at once (**inferred** from the code; the echo rows in
  `secret-mask.test.ts` pass, **measured**). The brief offered `lead = ''`, which the review measured closing every probe.
  It was not taken: the lead is also what lets the drawer see that a run begun in sent text is still open, and with it
  empty `secret-mask.test.ts`'s fail-closed row "a compatible key typed slowly stays masked past its first 19 bytes"
  reds (**measured**, a mutant `x-lead-empty` at both sites, load 12). The floor keeps that row and closes every F1 form.
- **F2: the cap arm.** `lookaheadEnd`'s step back to the row before ran on the first read only; it runs at the cap too
  (`!grown || le >= cap`). Below the cap a grown read ends at a row break, so its last row is whole, and a row with no run
  ends every key's rows. A read that is all one row's indent and escapes (no row break) now grows as for a chain across
  the cut, and at the cap answers "cut", so the chain's rows fail closed (`chainRowsBack`, `chainRowsOn`).
- **F3: a chain on through every slice.** (1) A slice with no row break in its last 64 KiB ends outside an escape
  (`outsideEscape`: the start of an escape begun before the cut and not ended by it, read back 4 KiB), and so does each
  window `chainRowsOn` reads. (2) `chainRowsAcross` is gone: a cap's cut masks the chain's rows back from the cut at once
  (`chainRowsBack`), and leaves the chain open; every later slice masks its own share (`chainRowsOn` up to the slice's
  end), so the cost stays a slice's and the carry has no window limit. (3) A chain's rows are counted in their own
  units, never the NUL each escape inside a run reads as. (4) A text that ends inside a row hands the next text the rest
  of that row (`ChainLeft.cont`, `endsInRow`): read as a row of its own, its blanks and escapes ended the chain.
- **F4: the bound.** `WHOLE_HELD_MAX` is 64 KiB. It bounds three reads: what the drawer withholds for a key's rows, how
  far pane history's lookahead grows, and each window of `chainRowsOn`. Past it a chain is masked, never sent raw: the
  drawer's past arm and pane history's cap arm, with F2 and F3 closing the forms where those arms failed open. 64 KiB is
  the measured choice: at it the review's forms run at 5.8 to 18.1 ms a slice or push at load 8.8 to 9.5 (§6). At 128
  KiB each re-read would be twice as long, and the margin under 25 ms smaller (**inferred**, not measured).
- **F7: the arm takes the open tail only.** `hold === 0 && base > 0` sends the text with its open tail failing closed;
  that tail masks only the text's last run, so a hold that came from `rowTailAt` (a run that ends its row) is held from
  the window's first byte instead (`rowHold`).
- **The taint through escapes.** The drawer's "one mark per run" taint compared the raw output's first and last
  characters with the mark, so a mark that escapes followed (a key coloured per character) drew one mark a push. It reads
  the output with its escapes read away. Key bytes are unaffected; it masks a little more (a tainted leading run is masked
  where an escape followed the last mark), never less (**inferred** from the code).

### 12.1 F1: the carried-chain arms read row breaks as `ROW_BREAK` does

Lowering `WHOLE_HELD_MAX` to 64 KiB sent texts of 64 to 256 KiB, which `main` read whole, to the arms that carry a chain
past the hold: `chainRowSpans` (the drawer's later pushes and pane history's later slices) and `lookaheadEnd`'s step back
at the cap. Those read row breaks one byte at a time (`\n`, `\r`), not through `ROW_BREAK`, the shared grammar. Two forms
leaked:

- a move down then a CR (CUD+CR, IND+CR), which the view reads as LF, NUL, CR: the skip stopped at the NUL, read it as
  an empty row, and the chain ended there, so the key's later rows went out raw;
- a push or slice that ends inside a break (between CR and LF, or a move down and its CR): `endsInRow` answered "not
  inside a row", and the next text's leading break read as an empty row that ended the chain.

The change (`server/src/accounts/mask.ts` only, no new break reader):

- `chainRowSpans` steps past each row break, and any that follow it, with `BREAK_AT`, a sticky copy of `ROW_BREAK`
  (beside `LINE_BREAK` and `LEADING_BREAK`); a text that ends at a break the next may complete sets `cont`.
- `lookaheadEnd`'s step back to the row before reads the break back with `breakStartAt`, which reads back the way
  `ROW_BREAK` reads forward.
- `endsInRow`, and so `cont`, answers true for a text that ends inside a row break, or right after one a following byte
  may complete (`breakMayGoOn`: a CR, which a LF makes CR LF, or a LF no CR comes before, which blanks and a CR make one
  move down). Unread still answers true.

Reading the breaks this way closed three more forms, each found while measuring this one:

- **The same reader past `main`'s 256 KiB hold**, which review 2430's refuter 3 measured on `main` (a 290,320-byte
  CUD+CR form, 704 bytes).
- **CR LF at a grown read** (review 2430 F3, at `main` and before the fix alike): a grown lookahead ended at the LF of a
  CR LF, read the CR as an empty last row and answered "no cut". It now ends at the break's start (`breakStartAt`).
- **LF then CR at a slice cut** (found here, at `main` and before the fix alike): pane history cut a slice after the LF
  of a LF then CR (or a LF, blanks, then a CR), which `ROW_BREAK` reads as one move down, and the next slice began with
  the CR, an empty row. The cut now falls at the end of the break as `ROW_BREAK` reads it, read within 64 bytes of the
  LF (`BREAK_CUT_MAX`): an automated security review of the first version of this change found that blanks between a LF
  and a CR could stretch a slice without bound (300,000 blanks made a 360,024-byte slice); past 64 bytes the cut stays
  after the LF, as on `main`. The F4 row pins it.
