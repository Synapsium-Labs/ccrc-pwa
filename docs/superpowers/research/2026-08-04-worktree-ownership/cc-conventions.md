**Date**: 2026-08-04  
**Sources**: code.claude.com/docs/en/worktrees.md, sessions.md, hooks.md, superpowers plugin v6.2.0, local filesystem inspection

## C1: When does Claude Code create .claude/worktrees/<name>?

### Creation Triggers

**DOCUMENTED**: Claude Code creates worktrees under `.claude/worktrees/` in these scenarios:

1. **User runs `--worktree` flag**:
   - `claude --worktree feature-auth` creates `.claude/worktrees/feature-auth/`
   - Also accepts `-w` as short form
   - Can omit name; CC auto-generates names like `bright-running-fox`
   - With PR syntax: `claude --worktree "#1234"` creates `.claude/worktrees/pr-1234/`

2. **User asks Claude to create a worktree mid-session**:
   - Prompt: "work in a worktree" or "create a worktree for this task"
   - Claude uses `EnterWorktree` tool (documented native tool for worktree creation)

3. **Subagents configured with `isolation: worktree`**:
   - Subagent frontmatter field: `isolation: worktree`
   - Each subagent gets a temporary worktree under `.claude/worktrees/`
   - Example: `.claude/worktrees/agent-<hex>` for system-named subagent worktrees

4. **Background sessions (Agent view)**:
   - Background sessions automatically move into isolated git worktrees under `.claude/worktrees/` before editing files
   - Each session gets its own worktree; isolation prevents file conflicts between parallel sessions

### Naming Conventions

**DOCUMENTED**:

- **Subagent and background session worktrees**: `agent-<hex>` where `<hex>` is a 16-character hex identifier
  - Example: `agent-a060b944c2ef05931`, `agent-a0710a8f33ec9d36d`
  - Generated by Claude Code; no user control

- **Named user worktrees**: `worktree-<name>` or `<name>` (depends on how launched)
  - User specifies with `--worktree <name>`
  - Example: `worktree-feature-auth` or just `feature-auth`

- **Pull request worktrees**: `pr-<number>`
  - Created with `claude --worktree "#1234"`
  - Example: `pr-1234`

- **Auto-generated user worktree names**: machine-readable like `bright-running-fox`
  - Generated when `--worktree` omits name
  - Format: `<adjective>-<adjective>-<noun>`

### What Does NOT Create .claude/worktrees

**DOCUMENTED**:

- The superpowers `using-git-worktrees` skill creates worktrees under `.worktrees/` (no dot) or `worktrees/` at project root, NOT `.claude/worktrees/`
- User-run `git worktree add` creates worktrees wherever the user specifies (typically `../project-name` or custom paths)
- EnterWorktree tool can move to any existing worktree path, not just those under `.claude/worktrees/`

## C2: Lifecycle & Auto-Cleanup Behavior

### Interactive Session Cleanup

**DOCUMENTED**:

- **Unnamed interactive sessions**:
  - On exit, if worktree is clean (no changes, no untracked files, no new commits), Claude Code **removes** the worktree and its branch automatically
  - No prompt; cleanup is silent

- **Named interactive sessions**:
  - On exit, if worktree is clean, Claude Code **prompts** whether to keep or remove the worktree
  - User chooses preservation or deletion

- **Worktrees with changes**:
  - If worktree has uncommitted changes, untracked files, or new commits, Claude Code **prompts**:
    - "Would you like to keep this worktree?"
  - User chooses preservation or deletion
  - If kept, directory and branch remain on disk
  - If deleted, work is lost

### Non-Interactive Session Cleanup

**DOCUMENTED**:

- Non-interactive runs with `-p` do **NOT** clean up their worktrees on exit
- User must manually remove with `git worktree remove <path>` (add `--force` if worktree has uncommitted changes or untracked files)

### Subagent and Background Session Auto-Cleanup

**DOCUMENTED**:

- **Subagent worktrees**:
  - Temporary worktrees created for subagents are removed **automatically when the subagent finishes WITHOUT changes**
  - If subagent makes changes, worktree is preserved on disk

- **Background session worktrees**:
  - Subject to periodic cleanup sweep

- **Periodic sweep** (applies to subagent + background session worktrees):
  - Claude Code runs a periodic sweep that removes worktrees older than `cleanupPeriodDays` setting (configurable, default 30 days)
  - **Sweep skips**:
    - Any worktree with uncommitted changes or untracked files
    - Any worktree with unpushed commits
    - Any worktree created with `--worktree` (user-created worktrees are never auto-removed by sweep)
  - **Sweep skips locked worktrees**:
    - Claude Code sets `git worktree lock` while an agent is running
    - Lock is released when agent finishes
    - Sweep releases a lock if process has exited (handles killed background sessions)
    - Sweep NEVER releases user-set locks (via `git worktree lock` command)

### Is 26 GB of agent-* worktrees Expected?

**OBSERVED + DOCUMENTED**:

- Found 31-32 agent-<hex> worktrees in `/data/projects/expoAI-assistant/.claude/worktrees/`
- Total size: 20 GB (older data, likely smaller now)
- Individual worktrees: 1-1.3 GB each

**This is EXPECTED behavior IF**:
1. Worktrees contain changes (uncommitted or unpushed)
   - Cleanup sweep will NOT remove them
   - Will persist until changes are committed + pushed, or until user manually removes them

2. Worktrees are still being used by running agents
   - `git worktree lock` prevents auto-cleanup
   - Will persist until agent finishes + lock is released + sweep runs

3. cleanupPeriodDays setting is long, or sweep hasn't run recently
   - Sweep only runs periodically; recent subagent worktrees won't be cleaned up yet

**This is a cleanup BUG/GAP IF**:
- Worktrees are old, have no changes, have no locks, and sweep hasn't removed them
- Could indicate:
  - Sweep process isn't running or is broken
  - Worktrees were created by a different mechanism (not CC) and don't match expected cleanup conditions
  - Lock is stuck (killed agent didn't release lock cleanly — before v2.1.210 this was a known issue)

**Recommendation for ccd**:
- Query each worktree's state:
  - Check for dirty state: `git -C <worktree> status --porcelain`
  - Check for unpushed commits: `git -C <worktree> rev-list --count origin/HEAD..<worktree-branch>`
  - Check for locks: `git worktree list --porcelain | grep locked`
- Only remove worktrees that are old, clean, and unlocked
- Preserve worktrees with changes or locks

## C3: Worktree Root Configurable?

### Built-in Configuration

**DOCUMENTED**:

- No explicit `worktreeDir` or `CLAUDE_WORKTREE_DIR` setting found in `settings.md`
- Default is hardcoded: `.claude/worktrees/` at repository root

### Customization Options

**DOCUMENTED**:

1. **WorktreeCreate hook** — the recommended way to move worktree location:
   - Add a `WorktreeCreate` hook to `settings.json` (user, project, or local scope)
   - Hook receives worktree name as input (JSON on stdin)
   - Hook can create worktree anywhere and print the directory path
   - Example use: SVN or Perforce worktrees outside `.claude/worktrees/`
   - When a hook is configured, it replaces default `git worktree` logic entirely

   ```json
   {
     "hooks": {
       "WorktreeCreate": [
         {
           "hooks": [
             {
               "type": "command",
               "command": "bash -c 'NAME=$(jq -r .name); DIR=\"/custom/path/$NAME\"; git worktree add \"$DIR\" -b \"$BRANCH_NAME\" && echo \"$DIR\"'"
             }
           ]
         }
       ]
     }
   }
   ```

2. **Pair with WorktreeRemove hook** — for cleanup when session ends:
   - Receives the worktree path as input
   - Example: removes the worktree with `git worktree remove` or custom logic

**NOT SUPPORTED**:
- Environment variables for worktree root location
- settings.json fields like `worktreeDir` or `worktreeRoot` (no such fields documented)
- `.claude/worktrees/` location is not overridable via simple configuration

**Environment Variables Available** (for reference):
- `CLAUDE_CONFIG_DIR` — changes where `~/.claude/` storage lives (affects all Claude Code config, not just worktrees)
- No `CLAUDE_WORKTREE_DIR` documented

## C4: Ownership Metadata & Liveness Tracking

### Git Worktree Metadata

**OBSERVED**:

- Each worktree has a metadata directory in `.git/worktrees/<name>/`:
  - `HEAD` — current HEAD commit hash
  - `CLAUDE_BASE` — appears to track base branch or reference
  - `COMMIT_EDITMSG` — last commit message or editor state
  - `logs/` — reflog directory
  - `ORIG_HEAD` — previous HEAD

Example from local filesystem:
```
.git/worktrees/agent-a060b944c2ef05931/
├── CLAUDE_BASE         (40 bytes)
├── COMMIT_EDITMSG      (1.6 KB)
├── HEAD                (63 bytes)
├── ORIG_HEAD           (41 bytes)
├── commondir           (6 bytes)
├── gitdir              (98 bytes)
├── index               (~328 KB)
└── logs/
```

### Session/Agent Ownership

**NOT DOCUMENTED**:

- No standard field in `.git/worktrees/` metadata that records:
  - Which session/agent created the worktree
  - When it was created
  - Whether it's actively in use
  - What process owns it

**PARTIALLY AVAILABLE**:

- `git worktree list --porcelain` shows:
  - Worktree path
  - Branch
  - Commit hash
  - `locked` flag (if set by CC during agent execution)
  - `locked reason` (CC sets reason like "agent running")

Example output:
```
/srv/projects/expoAI-assistant
HEAD 54fac4cf440138d091ca11f980948e1f473a11f2
branch refs/heads/fix/canary-cards-nondeterminism

/srv/projects/expoAI-assistant/.claude/worktrees/agent-a060b944c2ef05931
HEAD b46e76293908895018d109decaf64a1e68164173
branch refs/heads/fix/cha-150-persona-greeting-thinking-disabled
```

### Worktree Liveness Inference

**DOCUMENTED**:

- While agent is running, CC sets: `git worktree lock <path>`
  - Lock includes a reason string (CC sets this to indicate agent is using it)
  - Lock remains until agent finishes + CC releases it

**Not Documented**:
- No persistent metadata linking worktree to session ID, agent ID, or start time
- No documented way to query "is this worktree actively in use by a running session"

**Inference Approach for ccd**:
1. Check `git worktree list --porcelain` for `locked` flag
   - If locked, assume in use (unless lock is stale from killed process)
2. Check filesystem timestamps (mtime of worktree directory or .git/worktrees/<name>/)
   - Old timestamp + clean state + no lock = safe to remove
3. Check for session files in `~/.claude/projects/` or `$CLAUDE_CONFIG_DIR/jobs/`
   - Background session metadata might indicate active sessions

## C5: Superpowers using-git-worktrees Skill

### Worktree Directory Placement

**DOCUMENTED**:

The superpowers `using-git-worktrees` skill (v6.2.0, `/home/you/.claude/plugins/cache/claude-plugins-official/superpowers/6.2.0/skills/using-git-worktrees/SKILL.md`):

1. **Step 1a: Native Worktree Tools** (preferred):
   - Check for a native tool like `EnterWorktree`, `WorktreeCreate`, `/worktree` command, or `--worktree` flag
   - If available, use it; skip manual git worktree setup
   - Never fight the harness

2. **Step 1b: Git Worktree Fallback** (manual):
   - Only if no native tool available
   - Placement priority order:
     1. Check user instructions for declared worktree directory preference
     2. Check for existing `.worktrees/` at project root (preferred, hidden)
     3. Check for existing `worktrees/` at project root (alternative)
     4. Default to `.worktrees/` at project root

   - **CRITICAL**: Verify directory is ignored before creating:
     ```bash
     git check-ignore -q .worktrees 2>/dev/null || git check-ignore -q worktrees 2>/dev/null
     ```
   - If NOT ignored, add to .gitignore and commit before creating worktree

   - Create worktree:
     ```bash
     git worktree add "$LOCATION/$BRANCH_NAME" -b "$BRANCH_NAME"
     cd "$LOCATION/$BRANCH_NAME"
     ```

### Ownership & Cleanup

**DOCUMENTED** (from superpowers design doc `2026-04-06-worktree-rototill-design.md`):

```
3. **Phantom state** — skill-created worktrees at `.worktrees/` are invisible to 
   the harness; harness-created worktrees at `.claude/worktrees/` are invisible 
   to the skill

Whoever creates the worktree owns its cleanup. If the harness created it, 
superpowers doesn't touch it. If superpowers created it (via git fallback), 
superpowers cleans it up. 

The heuristic: 
- If the worktree lives under `.worktrees/` or `worktrees/`, superpowers owns it.
- Anything else (`.claude/worktrees/`, `~/.codex/worktrees/`, `.gemini/worktrees/`, 
  or old user-global Superpowers paths) belongs to the harness or user and is 
  left alone.
```

### Cleanup Behavior

**DOCUMENTED**:

- Superpowers cleans up `.worktrees/` or `worktrees/` directories after feature work completes
- Superpowers does NOT touch `.claude/worktrees/` (belongs to Claude Code harness)
- Superpowers does NOT touch worktrees placed outside the project

## C6: External Tool Cleanup Guidance

### Safe Removal Prerequisites

**DOCUMENTED**:

Before a tool (ccd) removes a worktree, check:

1. **Dirty state check**:
   ```bash
   git -C /path/to/worktree status --porcelain
   ```
   - If output is non-empty, worktree has changes
   - Do NOT remove without user confirmation

2. **Unpushed commits check**:
   ```bash
   git -C /path/to/worktree rev-list --count origin/HEAD..<branch>
   ```
   - If count > 0, worktree has unpushed work
   - Do NOT remove without user confirmation (CC cleanup preserves these)

3. **Lock check**:
   ```bash
   git worktree list --porcelain | grep "^/path/to/worktree" | grep locked
   ```
   - If locked, worktree is in use by a running agent
   - Do NOT remove (CC will unlock after agent finishes)

4. **Age check** (optional):
   ```bash
   stat /path/to/worktree | grep Modify  # mtime
   ```
   - Compare to `cleanupPeriodDays` setting
   - Worktrees older than limit are candidates for cleanup

### Removal Process

**DOCUMENTED**:

```bash
# Safe removal (clean worktree)
git worktree remove /path/to/worktree

# Force removal (has uncommitted changes or untracked files)
git worktree remove --force /path/to/worktree
```

### What NOT to Do

**DOCUMENTED**:

- Do NOT remove a worktree that CC has locked (use `git worktree unlock` only if absolutely certain the lock is stale)
- Do NOT remove a worktree with unpushed commits without confirmation
- Do NOT remove a worktree that CC might be using (check for active sessions/agents first)
- Do NOT rely on removing `.claude/worktrees/` directory without using `git worktree remove` (leaves phantom .git/worktrees/ entries)

### Recommended Cleanup Strategy for ccd

**OBSERVED + DOCUMENTED**:

```
For each worktree under `.claude/worktrees/<name>/`:

1. Check lock:    git worktree list --porcelain | grep locked?
   → if locked, skip (agent is using it)

2. Check dirty:   git status --porcelain in worktree?
   → if dirty, log for review (don't remove automatically)

3. Check unpushed: git rev-list --count origin/HEAD..branch?
   → if > 0, log for review (don't remove automatically)

4. Check age:     mtime of .git/worktrees/<name>/ directory
   → if older than cleanupPeriodDays, safe to remove

5. If clean + unlocked + old:
   → run: git worktree remove --force /path/to/worktree
   → also runs: git branch -D <branch> (automatic)

6. Log results for audit trail
```

## Open Questions / Confidence Gaps

1. **Session ID → Worktree Mapping**:
   - Not documented which session/agent created a worktree
   - No field in .git/worktrees/ metadata links back to session ID
   - Inference: use branch name, mtime, and lock reason as heuristics

2. **cleanupPeriodDays Default Value**:
   - Documented as configurable setting
   - Default value not explicitly stated in fetched docs (assumed 30 days based on wording)
   - Affects when periodic sweep removes old subagent/background worktrees

3. **Periodic Sweep Frequency**:
   - Documented that sweep is periodic
   - Exact interval (hourly? daily?) not specified
   - Not documented when sweep runs relative to session start/end

4. **Agent Lock Reason String**:
   - Documented that CC sets lock with a reason
   - Exact reason string format not provided
   - Useful for ccd to distinguish "CC agent locked" from "user locked"

5. **Phantom State Cleanup**:
   - If `.git/worktrees/<name>/` exists but `.claude/worktrees/<name>/` directory deleted
   - How to detect and clean this state not documented
   - Recommend: `git worktree prune` as cleanup fallback
