Path identity design

Spec · 3 Nov 2026
In shortA document is named by its project, its ref and its path, never by where a checkout happens to sit.

This spec fixes how the reader names a document.

FleetRunsDocsMore

How it works with the reader frame

The reader is a separate document in a sandboxed iframe (sandbox="allow-scripts", so an opaque origin). The console cannot read the frame's scroll position, and the frame's bridge today carries only op, copy and changes messages to the host. So this design needs one small library change, and the library's release is held.

  1. Library: a top inset. A new mount option (for example chrome.insetTop, in px, updatable by the host) becomes extra top padding on the reader's root. The library's sticky bar sits after that space, so at open it shows below the console head and sticks to the frame's top once the inset has scrolled past. Its phone bar rule (HIDE_AFTER 300 px) counts from below the inset, so the bar does not hide while the head is still on screen.
  2. Library: a scroll signal. The frame posts {kind:'scroll', y} over the existing port, at most once per animation frame, only while y is within the inset (plus one final message when it passes it, and one when it comes back). Mid-document scrolling sends nothing, so the port stays quiet.
  3. Console: the head becomes an overlay. On a phone, when the page holds a reader, .docs-screen loses its padding, the frame fills the screen from the top, and the head block (crumbs, truth line, actions, banners) is absolutely positioned over the frame's top. A ResizeObserver measures it and sends its height as the inset, so a wrapping truth line or a banner simply makes the inset taller.
  4. Console: following the scroll. On each scroll message the head gets transform: translateY(-min(y, h)). Past h it also gets inert and visibility: hidden, so focus and screen readers cannot land on controls that are off screen.
  5. Older library (absence permits). If no inset option or scroll message exists, the console keeps today's pinned head. Nothing breaks; the design just does not engage.
  6. Also fixed on the way. The 'Formatting…' line moves into the reserved inset area instead of pushing the frame down, so the 28 px jump at load goes away. The frame body's inferred 8 px default margin should be reset in the same library change.

What it costs

  • A library change (inset option, scroll message, HIDE_AFTER offset, body margin), so it waits for the held library release, then a pin bump in the console.
  • Console work: overlay layout on phones, a ResizeObserver, the scroll listener, inert handling, and a fallback for older libraries. Tests for each guard.
  • Messages cross a port, so the head can trail the text by about one frame during a fast fling on a 120 Hz screen: a few px of visible lag at the head's lower edge.

What the user loses

  • At open, nothing is gained: about 341 px still sit above the title. This angle only helps once reading starts (0 to 48 px above the text, instead of 256 to 304).
  • Mid-document, back, Share, GitHub and Export are not one tap away. The user scrolls to the top (or uses the phone's back gesture for back). A scroll up returns only the library bar.
  • A swipe that starts on the head lands on the console page, not the frame, so dragging on the head does not scroll the document. The head is only on screen near the top, so this matters for the first swipe.
  • Can be combined with a compact head (another variant) to also fix the open state.
