## In short

- **One door, three providers.** The Accounts screen gets an **Add account** door. It opens one connect sheet that is reshaped by the provider, not a wizard: **Anthropic** (mint a long-lived token, the default by the operator's ruling; or sign in with a Claude subscription; or paste a token), **OpenAI** (sign in with a ChatGPT subscription, which creates a ccrc-owned Codex lane), and **OpenRouter** (three ways in, each validated with OpenRouter before anything is saved: **mint** a sub-key with its own credit limit from a management key kept on the fleet box, **connect** through OpenRouter's PKCE sign-in, or **paste** a key, which always works).
- **The long-lived token is the default (Q1).** The operator: "without long lived token we keep having to reauth IN the sessions and it's a major pain." Flow A opens on Mint. A signed-out sign-in lane's first fix, and an act on every sign-in lane, is **Switch to a long-lived token** (§4.2, §9).
- **OpenRouter connect and minting are designed now (Q4).** PKCE runs its exchange **on the fleet box**: the verifier never leaves it, and the key never reaches the server or the browser. Its default arm needs no redirect at all: the operator copies a code from openrouter.ai back into the sheet, the same shape as the Anthropic sign-in, so it works from an installed iPhone PWA (§8.2). The redirect arm is moved to Later. Minting reads a **management key** that lives only in a 0600 file on the box. It is installed and replaced only from a shell on the fleet host, never through the browser or the server. It is never sourced into any session's environment, and only the management-key and minting verbs read it. Every minted key carries a credit limit, normalised to a monthly figure, under a ceiling that only the CLI can raise, and ccrc deletes its own minted keys at OpenRouter when a lane is removed or rotated (§8.7, §8.8). The threat model says plainly what a compromised box costs.
- **macOS fleet nodes sign in and mint too (Q10).** A transient launchd job replaces `systemd-run`. The helper's measured BSD `script(1)` arm is reused, and its quirks are listed, including where Claude Code keeps a Mac's sign-in credential: the login keychain, not a file (§3.10). Testing has three layers: stubbed arms on Linux CI, a real macOS CI runner behind an explicit CI-only gate, and one operator-run check in a disposable macOS VM, so nothing is ever installed into the operator's real home (§16.1).
- **OpenRouter models are suggested and not editable in the first cut (Q6).** Editing arrives with Plan 3a's class-registry surfaces, and nothing here waits for it (§8.5).
- **The fleet box already does most of this.** `ccrc account add|check|enable|disable|credential|remove`, the sign-in helper with its status file and code FIFO, and `ccd caps account-v1` all exist. What is missing is the **path to them**: there is no server route, and no agent op (the agent can exec only `tmux` and `ccd`). Some box-side steps are also missing: onboarding and trust seeding, a verb that creates a Codex lane, a lane-state file the server can read, the controller roster reload, supervisors picking up a new lane, and locks and reconciliation for a verb that dies halfway. §13 lists every route and verb, existing or new; §14 lists the gaps.
- **Secrets have one path, and it is short.** A key or token is typed once into a field. It is sent once in an HTTPS POST under the operator's session. The server holds it for that one request and keeps no reference to it, then passes it as stdin on a typed agent op. The agent passes it as stdin to the fleet verb. The verb refuses control bytes, validates the secret, and only then writes a 0600 file. The secret is never echoed back, stored in coord.db, put in browser storage, logged, mailed, pushed, put in the feed or carried on a websocket. No child program's output reaches the browser, and every transcript, drawer and feed frame is masked for credential shapes before it reaches a websocket, because a session that runs `env` would otherwise write its lane's token into the transcript the PWA renders. The OAuth code follows the same rules: it is relayed once into the helper's FIFO and then forgotten (§3).
- **Only the operator's own browser, through the PWA, can do any of it.** Every account write needs three things: a verified session cookie (the gate's `session` verdict), an armed gate, and an https or loopback origin. A box token is refused. A dark gate and a plain-HTTP origin each refuse every write, and neither has an exception. Adding a credential, rotating it and removing a lane also need a step-up from the last five minutes, through dedicated step-up routes that mint no session. **This guards only the HTTP path.** Processes that run as the fleet user, sessions and coordinators included, are inside the trust boundary for secrets at rest. The CLI path has only an accident guard: deny rules on every fleet session, which a deliberate same-uid caller can evade (§3.1).
- **The list tells the truth in seven words.** Five are states: **Signed in**, **Expiring**, **Signed out** (expired), **Rate-limited** and **Off**. Two are the 09-05 spec's honest non-readings: **Not checked** and **Inconclusive**. Each word names its source file and its age, and every trouble state has its fix on the card (§4).
- **Layouts per skin.** Refined: lane cards at ≤760, with trouble cards on top; the door is the last row on a phone and a page action on desktop. Instrument: a lane table grouped by state word in the list column, with the selected lane in the detail pane; on a phone, a dense two-line list under the tab bar. The connect, re-auth and remove flows are shared sheet bodies that become centred dialogs at ≥900 (§12).

## 3. The security model

### 3.1 What is being protected, and from whom

| Asset | Where it lives at rest | Who can reach it there |
|---|---|---|
| Anthropic session credential (login lanes) | Linux: `~/<suffix>/.credentials.json`, 0600, written by Claude Code. **macOS: an item in the user's login keychain**, written by Claude Code (D-5442 measured that a fixture `HOME` loses it); how the item is named per config dir is measured at plan time (§3.10) | Claude Code on the fleet box, **and any process running as the fleet user**. On macOS the item's ACL is whatever Claude Code sets; while the login keychain is unlocked (the normal state of a signed-in Mac), a process of that user can read it through `security`, subject to that ACL. ccrc never reads it |
| Anthropic long-lived token (setup-token / paste lanes) | `~/.cc-secrets/<id>-oauth.env`, 0600. The wrapper sources it as `export CLAUDE_CODE_OAUTH_TOKEN=…`, so **at run time it is in the environment of every process of every session on the lane**: tool subprocesses, hooks, MCP servers and test runners | as above, plus anything any session on the lane runs. This is the cost of Q1's default, and §3.3's transcript row is what keeps it off the screen |
| OpenRouter key | `~/.cc-secrets/<id>-openrouter.env`, 0600, and in every session's environment on the lane, as above | as above |
| Codex (ChatGPT) OAuth | `auth.json` in `exec.authDir`, owned by the Codex runtime; ccrc passes the path and never reads the file | as above |
| The agent token | `~/.ccrc/agent.env` | as above. With it, a caller can drive the agent op directly and skip the gate, the step-up and the audit |
| The one-time OAuth code (Anthropic) | **nowhere**: it passes through, and is never at rest. While it is in the 0600 FIFO, any fleet-user process could race to read it | anyone who could replay it inside its lifetime |
| OpenRouter **management key** (minting, §8.7) | `~/.cc-secrets/openrouter-management.key`, 0600, one per box; installed only from a shell on the fleet host; never sourced into any environment | any fleet-user process. **This is the strongest credential on the box**: with it a caller can create, raise, disable and delete every API key in the OpenRouter account, not only ccrc's (§8.7's threat model) |
| The PKCE verifier (OpenRouter connect, §8.2) | `~/.ccrc/auth-scratch/<id>/pkce`, 0600 in a 0700 dir, for the attempt's lifetime only; outside the agent's read roots | any fleet-user process; with the matching one-time code it yields a key |
| The OpenRouter one-time code (§8.2) | **nowhere**: relayed once, like the Anthropic code | anyone who also holds the verifier, inside 10 minutes [OR] |

**The trust boundary, stated plainly.** Sessions and coordinators run as the fleet user and have a shell. So they can already read every file in the table above, open the FIFO, write the helper's status file, and run `ccrc account add|credential|remove` themselves. **Same-uid processes on the fleet host are inside the trust boundary for secrets at rest.** No HTTP rule changes that. In local fleet mode, the server shares that uid as well.

The adversaries, and what each door actually closes:

1. **A session or coordinator calling the server's HTTP surface** with the box token. **Closed** by D-5511: every account route needs the `session` verdict (§3.2). In local fleet mode this is an accident guard only, because the same uid could read the agent token and skip the server.
2. **A session or coordinator acting on the fleet host** through Bash, for example a prompt-injected session that runs `ccrc account remove --id lane-b`. This design cannot stop a deliberate same-uid attacker. **It has an accident guard, and it is deny-based** (N1 `account-cli-deny`):
   - **Why not a permission prompt.** Rev 2 promised that these commands would be default-escalate, so that "the permission prompt always reaches the operator". That cannot hold: every fleet session is spawned with `--dangerously-skip-permissions` (`ccd/ccd`, both spawn lines), and the coordinator-first rig measured that bypass mode raises only safety-check prompts. A plain Bash command in bypass mode raises no prompt at all, so there is nothing to escalate.
   - **What works in bypass mode is a deny rule.** A new list, `ACCOUNT_DENY_RULES` in `shared/api.ts`, sits beside `CHILD_DENY_RULES` and is written into the same managed deny file (`~/.cc-sessions/child-deny.settings.json`, `permissions.deny`). Unlike the child list, it is applied to **every fleet session**: coordinators, operator-driven sessions and children alike, through the `--settings` file that `ccd`'s spawn passes. It names: the mutating `ccrc account` subcommands (`add`, `auth-start`, `auth-code`, `auth-cancel`, `set`, `check`, `enable`, `disable`, `credential`, `remove`, `seed`) and the `openrouter-management` verb with every sub, `ceiling` named on its own; `ccd-account-auth`; `ccd account-pane`; Read and Bash access to `~/.cc-secrets/*`, `~/.ccrc/auth-scratch/*`, `~/.ccrc/codex/*/runtime.env` and `~/.ccrc/agent.env`; writes under `~/.cc-sessions/.auth/` and `~/.cc-sessions/.accounts/`; and, as best effort, bare `env` and `printenv` (§3.3).
   - **Path-qualified forms.** `CHILD_DENY_PATH_QUALIFIED` is off on main, so `~/.local/bin/ccrc account remove` would not match a bare-name rule. A **PreToolUse hook**, installed with the session hooks, denies a Bash command whose words name any of the programs or paths above in any form.
   - **What it is not.** It is an accident guard. `bash -c "$(echo …)"`, a Python one-liner or a script file evades both the rule and the hook, and the threat model says so. No approval can override a deny rule, so a coordinator can neither approve nor be asked; the operator runs these commands from their own shell.
   - **What it never blocks** (the operator's ruling of 2026-10-19, §19 Q8): a session moving to another account, and the auto-swap. The `ccd` supervisor's automatic swap, `ccd swap-self`, `ccd prefer`, `ccd swap`, `POST /api/sessions/:id/swap` and the Move sessions sheet are never refused, nor anything they run or read. So bare `env` and `printenv` are exact forms only (never a prefix rule, which would catch `env FOO=1 ccd swap-self …`), the `ccrc account` rules name each sub (never the bare `ccrc account`, whose `roster` read a refused swap tells its reader to run), and the path rules name the listed paths exactly. The plan's Task A9 records what each swap path runs and reads, and holds them with a must-allow corpus.
   - The ccrc-pwa `CLAUDE.md` SAFETY rules name the same commands and paths as forbidden to sessions.
   - The server never trusts the helper's status file for what the operator is asked to open (§3.8).
3. **Anyone on the network path** when the origin is plain HTTP and not loopback. **Closed** by refusing every account write there (§3.2).
4. **A stolen or left-open browser** that still holds a session cookie. **Narrowed** by step-up (§3.2).
5. **Accidental disclosure**: a secret in a log, an error sentence, a mail, a push, the feed, a websocket frame, the offline snapshot, the terminal drawer, tmux scrollback, `/proc/<pid>/cmdline`, a core dump or a screenshot. **Closed** by §3.3.
6. **A compromised fleet box**, or a deliberate same-uid attacker on it, or **a leaked or restored snapshot of its disk** (§3.3's backups row). **Not closed, and bounded instead.** Such an attacker holds every secret in the table: year-valid Anthropic tokens on every token lane (Q1), the sign-in credentials, the Codex OAuth, the gateway keys, the agent token, every OpenRouter key and the management key. What bounds it is set outside the box: each credential's own expiry, the OpenRouter account's balance and auto top-up, and revocation from another device. §3.11 lists what the operator does then, for every provider.

### 3.2 Who may act (D-5511, D-5512)

- **Every account write needs the gate's `session` verdict**, which is the only verdict that means a credential was presented and verified. None of the new routes is in `EXEMPT`, and none is exempt-but-authenticated. **A box token is never accepted**, so `ccrc-api` on the fleet box, any session and any coordinator get a 401 on the HTTP path. This follows the same reasoning as `POST /api/token/rotate` and `POST /api/coord/pause`.
- **A dark gate (`flag-off`) refuses every account route with `auth-off`, and there is no exception.** That covers every write, `GET /api/accounts/:id/auth`, and the identity fields of `GET /api/accounts`. Rev 0 had a loopback exception; it is deleted. Three facts make it unsafe:
  - The default bind is loopback (`CCRC_HOST` 127.0.0.1) and the default origin is `http://localhost:<port>`. Every real deployment puts `tailscale serve` or the Caddy that `ccrc expose` writes in front of that bind. So every dark box looks like loopback, whichever of the two values you read.
  - In local fleet mode (also the default), sessions share loopback with the server.
  - `installGate` skips the origin check while the gate is dark (`gate.ts:864`), so a cross-site page could drive the same writes.

  `GET /api/accounts` keeps answering while the gate is dark, with the usage and roster it carries today, but without `lanes` (§3.4). The dev lane and the tests arm the gate with a test passphrase.
- **An insecure origin refuses every account write with `insecure-origin`.** Writes need `cfg.origin` to be https, or http on a loopback host. This is derived only from `cfg.origin`, and only while the gate is armed, which is the only time `cfg.origin` is enforced on writes. It is never derived from `cfg.host`, `Host` or `X-Forwarded-*`. Over plain HTTP the session cookie and the JS bundle are both open to a man in the middle: injected script could run the step-up the moment a sheet opens, and swap a device URL or code. So there is no Codex exception either (rev 0 had one). The screen goes read-only and names the `ccrc expose` fix (§12.6).
- **Step-up for the acts that put, replace or delete a credential (D-5512):** `POST /api/accounts`, `/:id/auth/start` (the OpenRouter PKCE method included), `/:id/credential` (a mint rotation included), `/:id/set` when it changes a method or raises a minted key's monthly commitment (a higher limit or a shorter reset, §8.8), `/:id/remove` (including discard, §11), and `POST /api/providers/openrouter/management/remove` (§8.7). The management key itself is never installed or replaced through any route: that is CLI-only (§8.7). Each needs a step-up from the last **5 minutes** on the **same session**. Step-up gets its own routes, because the login doors mint a new session (§2). Re-using them would change the session's `idHash` mid-flow, which breaks §3.7's same-session check. It would also leave a live session row per step-up, and spend the login lockout budget.
  - `POST /api/auth/step-up/start` and `POST /api/auth/step-up/finish` (passkey), and `POST /api/auth/step-up/passphrase` (the fallback on a box with no passkey enrolled). Each is session-only, not in `EXEMPT`, and has **its own limiter**, separate from `LoginRateLimiter`.
  - **The passphrase arm is refused `passkey-enrolled` whenever any passkey is enrolled.** Otherwise a stolen session could step down to the weaker factor.
  - **An exhausted limiter locks step-up for that session** until the session ends or the operator signs in again, and writes a `step-up-locked` audit row (§3.6). Other sessions keep their own budget.
  - Challenges use their own `ChallengeStore` purpose, `step-up`, **bound to the requester's session `idHash`**. A challenge started by one session is refused when another session finishes it.
  - Success stamps `assertedAt` on **that session only**. It mints nothing, rotates nothing and keeps the session's `generation`. The new field `SessionRecord.assertedAt` is the only change to the record.
  - `GET /api/accounts` carries `connect.stepUpFreshUntil` for the current session. When freshness has lapsed, the sheet shows **Confirm it's you** as an explicit button step before Continue, Remove or Replace. The tap calls `navigator.credentials.get` directly, because iOS Safari needs a fresh user activation for that call, which it would not have after an async fetch returned. The sheet never retries a refused request on its own. If the stamp lapses between the button and the act, the route refuses `step-up-required` and the sheet shows the button again.
  - Check, enable and disable need no step-up: they are reversible and touch no secret. Enable still has a readiness precondition (§10).
- **Never a coordinator's act, and never an ask.** No account act is ever offered as an ask, a mail action or a command a session can request. The CLI path is covered by N1 (§3.1). #626's palette has **Go to Accounts** (chord `a`), which is navigation. It gets **no** "Add account" command, because the 09-05 ruling "the connect door lives on this screen and nowhere else" stands.

### 3.3 The one path a secret takes (D-5513)

```
field (type=password, autocomplete=off, spellcheck=false, no form autofill name)
  → POST over the authenticated session        (gate armed, https or loopback origin, else refused)
  → server: route checks charset and size       (key-charset; no reference kept after the request)
  → agent  {op:'account', sub, id, …typed fields, stdinB64}
  → agent: spawns ~/.local/bin/ccrc account <sub> with the agent-built argv, the secret on stdin
  → verb:  refuses C0/DEL bytes again → validates (OpenRouter §8.3, Anthropic paste §6.3)
           → writes 0600 tmp → rename        (or writes nothing)
```

**Keys born on the box take a shorter path.** A minted key (§8.8) and a PKCE key (§8.2) are created by OpenRouter in answer to a `curl` that the verb runs on the fleet box. The answer goes from curl's stdout through a pipe into `jq`, whose output is written straight to the umask-077 temp file. The key is never on an argv, never on the verb's own stdout, and never in an answer to the server. The browser and the server see only the key hint. **The management key never takes the long path at all.** It is installed from a shell on the fleet host, on the verb's stdin (§8.7), and after that it only ever goes from its file to curl's stdin.

**What can and cannot be promised about memory.** Fastify's JSON parser yields an immutable string, and `stdinB64` is an immutable string on both ends, so no buffer can be zeroed. The promise is that the secret is held for one request and that no reference to it is kept. The remote client's pending map drops the frame once it is sent, and no retry queue ever holds it. Both the server and agent units set `LimitCORE=0`, so a crash cannot dump a secret to disk (G22).

The rules that make it hold, each of which a test pins:

| Never | How it is kept out |
|---|---|
| **Bytes a consumer can misread** | Before any consumer sees a secret, the route **and** the verb refuse NUL, CR, LF, the other C0 bytes and DEL with `key-charset`, and anything over 8 KiB. An HTTP header can't carry those bytes anyway, so no real key or token has them. The verb repeats the check because the threat model includes a compromised server. The same check covers the OAuth code before `auth-code` writes it into the FIFO (§3.7). The existing writer's "a token is exactly its bytes" stays true for every byte a credential can hold. |
| **The PWA store or any browser storage** | The key lives in a component's local state in the sheet. It is cleared on submit, on close, on route change and on `visibilitychange` to hidden. It never enters a Zustand store, `localStorage`, `sessionStorage` or IndexedDB. `offline.ts` persists `RosterWire` only, and `RosterWire` gains no secret-bearing field. The identity and key-hint fields (§3.4) ride a separate `lanes` map that the offline snapshot does **not** persist; a test asserts the snapshot's keys. |
| **The answer** | No route ever returns a key, a token or a code. A failed validation answers with the code and an **empty** field, never the value. |
| **Error text** | Refusal sentences are built **only** from the verb's refusal code and its fixed text. No child program's output (claude, codex, curl) is ever sent to the browser, quoted in a sheet, or put in an audit row. As defence in depth, the route also masks the exact secret bytes it holds, and their base64, in any text it returns. |
| **Caches** | Every `/api/accounts*` and `/api/auth/step-up/*` answer carries `Cache-Control: no-store`. The service worker already treats `/api/` as `NetworkOnly`. |
| **Logs** | `Fastify({logger:false})` stays. The account routes never `console.*` a body. The agent logs the op name, the sub and the id, never `stdinB64`. |
| **Mail, push, the feed, websockets** | No account route writes a `feed_events` row, sends mail or a push, or emits on `/ws/fleet`. The audit is its own session-only table (§3.6). The one change the fleet sees is the roster changing. |
| **Session transcripts, the drawer and the feed** (new in rev 3) | A lane's token or key is in the environment of everything a session on it runs (§3.1). One `env`, `printenv` or `cat ~/.cc-secrets/…` writes it into the session's JSONL transcript, which the server tails to the PWA and the drawer. On main, `redactCommand` and `maskSecretAssigns` (`server/src/coord/redact.ts`) apply only to approval rows. So **the server masks credential shapes in every egress of session-derived text**: the transcript, ask and drawer websockets (the drawer at the one handler both its local and remote arms pass through), `GET /api/sessions/:id/pane/history`, `GET /api/feed`, `GET /api/runs/:id/items`, mail bodies shown in the PWA, and every web-push title and body. It masks the whole `sk-ant-` family (OAuth access and refresh tokens, API keys), `sk-or-v1-…`, the generic `sk-` and JWT shapes `redact.ts` already knows (a Codex `auth.json`'s tokens), the codex gateway key's shape, and the exact bytes of each lane secret the server can fingerprint, on decoded strings before serialization and across TUI row wraps (plan rev 2, from its security review). The fingerprint is a keyed hash of each secret file's value, computed on the box by the verbs and kept in a server-only, never-served table; the server never holds the secret. The mask is `‹secret masked›`. The deny rules for `env` and `printenv` (§3.1) are best effort on top. At plan time the plan measures whether Claude Code strips `CLAUDE_CODE_OAUTH_TOKEN` and `ANTHROPIC_AUTH_TOKEN` from Bash-tool subprocesses; if it does not, §3.1's row states it as the cost of Q1, as it does now. |
| **Backups and snapshots** (new in rev 3) | **macOS:** the verbs run `tmutil addexclusion` on `~/.cc-secrets` and `~/.ccrc/auth-scratch` whenever they create them, and `ccrc doctor` checks that both are excluded and that FileVault is on. The management key is **refused on a darwin node** (`management-key-darwin`): a laptop with Time Machine, iCloud and a lid that opens is the wrong home for the strongest credential, and minting runs from a Linux fleet host. **Linux:** whether the fleet box has Hetzner server backups, snapshots or volume snapshots is stated by `ccrc doctor`, from the operator's answer at install. **Any snapshot or backup image taken while a credential existed holds that credential**, and §3.11's compromise steps apply to a leaked or restored image exactly as to a compromised box. A test asserts that the verbs set the darwin exclusion. |
| **argv and `/proc`** | The agent builds argv from typed fields, with the bounds in §13.2. There is no free argv, so a compromised server cannot pass `--force` or a path. The secret is only ever stdin. For OpenRouter validation the verb runs `curl -H @-`, which reads one header per line from stdin and takes **no** directives. Rev 0's `curl --config -` is withdrawn: that is a config grammar, so a key holding a quote or a newline could add `output =` or `upload-file =` (G7). Every OpenRouter call the verbs make takes the same shape: the bearer header on `-H @-`, a fixed `https://openrouter.ai/api/v1/…` URL, `--proto =https --max-redirs 0 --max-time 10`, and only non-secret JSON on argv (a key's name and limit). The PKCE exchange, whose body is the secret, sends it with `--data-binary @-` (§8.2). |
| **The terminal, scrollback and the drawer** | `login` uses a pipe, not a pane. The pane methods move to a **private tmux socket** inside the attempt's own unit (§3.5), which neither `ptyOpen` nor the drawer can reach. The setup-token line is captured and blanked before it reaches the pty, as it is today (the canary test stays). |
| **Core dumps** | `LimitCORE=0` on both units. |
| **Screenshots and committed bytes** | The custody line shows placeholders in every fixture. At runtime it shows the lane's own path on the operator's own box, which is the 09-05 ruling. |

### 3.4 What the screen may show about a credential

- **Anthropic login lane:** "Signed in as `someone@example.invalid` · Max", read from `claude auth status --json` on the fleet box. Its keys, measured on Claude Code 2.1.302, are `loggedIn, authMethod, apiProvider, email, orgId, orgName, subscriptionType, …`. Every `check` re-reads it, so it is a measurement, not a declaration.
- **Anthropic token lane:** the identity **cannot** be read (`user:inference` gets a 403 from the profile endpoint). The operator states it at consent, in one field of the sheet, "Which account did you approve?" (1–120 characters, no control bytes). It shows as "Approved as `…` · stated by you", and the source word is the point. A **minted** token records its mint time. A **pasted** token has no mint time, so it reads "pasted 4 months ago · actual age unknown" and never raises Expiring.
- **OpenRouter:** the **key hint** `sk-or-v1-…a3f9` (the prefix plus the last four characters), the key's own label, and its limit or credit, read from OpenRouter's key endpoint by the validation (§8.3), each with its time. The card also names **how the key came**: "pasted", "connected with OpenRouter" or "minted by ccrc". A minted key also shows its limit reset ("$20 a month") and its expiry when it has one.
- **Codex:** "Signed in with ChatGPT" and the 7-day meter. ccrc never reads `auth.json`, so no identity is shown unless the operator states one.
- **Where these fields live (G16).** Every account verb, and `ccd-account-health`, writes a non-secret **lane-state file**, `~/.cc-sessions/.accounts/<id>.json` (mode 0600, never committed). Rev 0 put it under `~/.ccrc`, which is not an agent read root, so the 20 s poll could not have read it. `.cc-sessions` is a read root, and the `.auth/` dot-dir already sets the precedent. `GET /api/accounts` reads it in the same pass as `readLimits`, so it survives a server restart and shows what the box timers write. The plan measures that no existing reader of `.cc-sessions` descends into dot-dirs. The file holds `{check:{verdict,at}, identity?, identitySource, keyHint?, keySource?, keyHash?, keyLimit?, limitReset?, keyExpiresAt?, retiredKeyHash?, validatedAt?, credit?, mintedAt?, seedVerifiedAt?, lastRunAt?, fleetIdentity}`. `keyHash` is OpenRouter's identifier for a key ccrc minted. It is not a secret: it names a key and cannot call a model, and §8.8's rotate and remove need it to address the key. It is **not** written into `accounts.json`, so it never reaches the roster mirror or the offline snapshot.
- **Who sees them.** `GET /api/accounts` includes `lanes` **only when the verdict is `session`**. A box-token reader, and anyone at all while the gate is dark, gets today's answer with no identity, key hint or credit.
- **What they are worth.** Any fleet-user process can write the lane-state file (§3.1), so it is for display, and an accident guard for `enable` (§10). It is never authority for anything that touches a secret. Whether an email may appear at all is decision Q5.

### 3.5 Where a sign-in runs (D-5515)

- **As the fleet user, never inside an operator session.** No path types into a `claude-session@` pane, and no path asks a session to run `/login`.
- **Detached as a transient service, not a scope.** `systemd-run --user --scope` runs in the caller's scope and does not detach, so a 600 s helper would block the agent's sub, and the agent's timeout would kill it mid-flow. `ccrc account auth-start` instead launches `systemd-run --user --unit=ccrc-auth-<id>-<attempt8> --collect -p RuntimeMaxSec=660 -p MemoryMax=512M ccd-account-auth <id> <method> --attempt <attemptId>`. It returns as soon as the status file reads `starting` with that `attemptId` (under 5 s, which a test asserts), and the server polls from there. The unit sits in the fleet's capped user tree.
- **`login` (Anthropic)** runs on a **pipe** inside the unit: no pty, no tmux.
- **`setup-token` and the Codex device login** need a pty. The Codex need is measured: `_auth_openai_login_codex` runs under `script(1)` (rev 0's G9, now closed). Both keep their pane, but on a **private tmux socket**, `tmux -L ccrc-auth-<id>`, started **inside the attempt's unit**, so its server lives and dies in that cgroup. Today the pane is on the shared server that every session is a child of. The socket is per lane, so two attempts on two lanes never share a server. The agent's tmux grant takes subcommand prefixes only and cannot name `-L`, so `ptyOpen`, the drawer and `send-keys` cannot reach the auth server. The pane is killed on every terminal state, and the unit's end kills whatever is left.
- **macOS fleet nodes** have no `systemd-run`. There the same verb launches a transient launchd job instead, with the same contract: it returns on `starting`, it is bounded, it holds the private socket, and it leaves nothing behind (§3.10, D-5557).
- **The code goes in through the FIFO, not through `send-keys`.** The 09-05 spec's `tmux send-keys -l <code>` would put the code on tmux's argv and into pane history. The FIFO path already exists in the helper.

### 3.6 The audit trail (D-5516)

A new coord.db table, `account_events`: `{id, at, actor, act, laneId, provider, method?, outcome, code?, fleetIdentity}`.
- `actor` is the session's `label` (its device label) and the first 8 hex characters of its `idHash`. It is never an IP.
- `act` is one of `add|auth-start|auth-code|auth-cancel|auth-url-untrusted|set|check|enable|disable|credential|retire-key|remove|discard|reconcile|management-remove|ceiling-lower|revoke-acknowledged|step-up-locked`. Rev 1's `models` is dropped with editing (§8.5). Rev 2's `management-install` is dropped: install, replace and raising the ceiling run only on the fleet host's CLI, which cannot write coord.db, so they are recorded in the management state file instead (§8.7). `revoke-acknowledged` records that the operator ticked "I revoked the old token at claude.ai" (§9, §11); it carries no value. OpenRouter's key-plane outcomes ride `code`: `minted-deleted`, `minted-not-installed`, `pkce-minted-deleted`, `pkce-minted-not-installed`, `provider-delete-failed`. A minted key's row may carry its **name** (`ccrc lane-d 2026-10-18`), which is what the operator needs to find it at openrouter.ai. It never carries the key, its hint or its hash.
- `outcome` is `ok|refused|failed|unknown`, and `code` is the refusal code.
- **No secret, code, URL, key hint or email** ever goes in a row. A test writes a canary through every route and greps the table.
- **v1 writes the table and ships no screen to read it.** Rev 0's `GET /api/accounts/audit` and Settings › Security's "Recent account changes" are deferred. Nobody asked for a read UI, and the rows lose nothing by waiting. Rows are kept for 365 days. The box run in §16 reads them with `sqlite3`.
- **The OAuth code relay is audited as an event and never as a value:** `auth-code ok` or `auth-code refused bad-code`.

### 3.7 The OAuth code: relayed once, never stored (D-5514)

- `POST /api/accounts/:id/auth/code {attemptId, code}`: step-up is not repeated (it was taken at `auth/start`), but the route refuses unless the **same session** that started this attempt sends the code. Step-up no longer mints a session (§3.2), so the `idHash` stays the same throughout. The server keeps the attempt's `{attemptId, sessionIdHash, method, startedAt, expiresAt}` in memory.
- The code is checked for shape (`^[A-Za-z0-9._#-]{8,512}$`, to be measured at plan time against a real code) by the route, and checked for C0 and DEL bytes again by the verb. It is sent once over the `account` op's stdin to `ccrc account auth-code --id --attempt` (new), and written once into the FIFO. **The server holds it for the length of one request.** It is never in coord.db, the status file, a log or the audit row.
- **One code per attempt.** After a code is accepted, the attempt moves to `exchanging`, and a second POST is refused `code-already-sent`. A rejected code (the helper reports `failed`) ends the attempt, and the sheet offers "Start the sign-in again", which takes a new URL.
- **The deadline has one source.** `expiresAt` is the earlier of the provider's expiry and the helper's 600 s bound. Every countdown and expiry sentence reads it; the copy hard-codes no duration.

### 3.8 What the operator is asked to open (N2 `auth-url-allowlist`)

The URL and the device code the sheet shows come from `~/.cc-sessions/.auth/<id>.json`. Any fleet-user process can write that file, and the helper publishes the first `https://` run of any output line. A prompt-injected session could swap the URL for a phishing page while an attempt waits. Or it could swap in a device code it started itself, which would bind its own ChatGPT account to the lane and route the operator's session traffic through it. So `GET /api/accounts/:id/auth` validates before it answers:

- The file must echo the `attemptId` the server generated and passed in the helper's argv at `auth/start`.
- The URL's scheme is `https`, and its host is in an exact per-method allowlist that is measured at plan time. Anthropic `login` and `setup-token`: `claude.ai`, `claude.com`, `platform.claude.com`. Codex: the OpenAI auth host (`auth.openai.com`, to be confirmed).
- **OpenRouter PKCE (§8.2) never reads a URL from the status file.** Rev 2 compared the file's URL with "the challenge the verb recorded", but that record was only in `auth-scratch`, which is not a read root, so the only copy the server could read was the file being checked. Instead the `auth-start` op **answers the full authorisation URL** (it is not a secret: it carries only the S256 challenge). The server keeps it in the attempt's in-memory record (§3.7) and `GET …/auth` serves only that. Before keeping it, the server checks that it is exactly the verb's shape: `https://openrouter.ai/auth?code_challenge=<43 base64url characters>&code_challenge_method=S256&key_label=<the fixed label>`, those three parameters in that order and nothing else. No `callback_url`, no `plain`, no extra parameter. Anything else ends the attempt with `auth-url-untrusted`. The status file then carries only the attempt's state for this method.
- `userCode` matches a fixed shape, measured at plan time.
- Anything else ends the attempt with `auth-url-untrusted` and an audit row. The sheet shows a sentence and no link: "The sign-in link on the fleet host didn't look like claude.ai, so it isn't shown. Nothing was signed in. Start again, or check the fleet host."
- The mono host label next to the button is rendered from the URL **the server parsed**, never from the file's text and never hard-coded.

A test rewrites the status file to a foreign host mid-attempt and expects the refusal.

### 3.9 Locks, timeouts and a verb that dies halfway (D-5518)

- **One act per lane at a time.** Every mutating verb takes a per-lane `flock` and refuses `lane-busy`. A retry therefore cannot race an add that is still running.
- **Timeouts end cleanly.** On a sub's timeout the agent sends SIGTERM, then SIGKILL after a 5 s grace period. The verbs trap TERM and remove their own temp files. `add`, `credential` and `remove` also sweep any `.<id>-*.tmp.*` left in `~/.cc-secrets` by an earlier kill.
- **The server reconciles; it never guesses.** After any account op that errors or times out, the server runs the `roster` sub and reconciles by fingerprint (`reconcile` audit row). It does the same whenever `FleetHostBanner` sees a roster mismatch. The sheet's **outcome unknown** state (§6.2) rests on this.
- **Remove and sign-in don't overlap.** `remove` refuses `auth-in-progress`, and the sheet offers "Cancel the sign-in first". Every terminal attempt, and every remove, deletes `~/.ccrc/auth-scratch/<id>`.
- **The private tmux server is killed by name.** tmux daemonises its server (it forks and calls `setsid`), so on macOS it leaves the launchd job's process group, and `bootout` would not reach it. On every terminal state, in the reaper (§3.10) and in `remove`, the verb runs `tmux -L ccrc-auth-<id> kill-server`, on both platforms (on Linux the unit's cgroup would also catch it; the explicit kill costs nothing).

A test kills `add` mid-write, then asserts that no secret temp file remains and that the server shows the roster again.

### 3.10 macOS fleet nodes: the darwin arm (D-5557)

**When it applies.** The arm is chosen by the node that `AccountOps` reaches (§13.2), from the platform the verb itself detects (`CCD_OS`), never from anything the browser says. Today that node is a Mac in two cases: a ccrc install running in local fleet mode on a Mac, or a Mac running the agent. Reaching a second node is still out of scope (§13.2). Only the Anthropic sign-in and mint and the Codex sign-in use the helper, so only they need this arm. OpenRouter's three methods run as plain `curl` inside the verb (§8), and so do paste, check, enable, disable, set and remove. Those work on macOS as they do on Linux.

**One contract, two launchers.** Every promise of §3.5 holds on both platforms. Only the mechanism changes:

| Promise (§3.5, §3.9) | Linux arm (unchanged) | Darwin arm |
|---|---|---|

It then runs `launchctl bootstrap gui/<uid> <plist>`, only through `_svc_launchctl`, so the sandbox guard applies. The label is `app.ccrc.auth.<id>.<attempt8>`, with `RunAtLoad` true, `KeepAlive` false and `AbandonProcessGroup` false. The job is launchd's child, so it is outside the agent's process group |
| Returns on `starting`, in under 5 s | as today | the same poll of the status file for this `attemptId` |
| Bounded in time | `RuntimeMaxSec=660` | launchd has no runtime ceiling. Three things bound the job instead: the helper's own `_auth_timeout` (600 s), the pump's backstop (D-2736), and a **reaper**. Every `auth-start`, `auth-cancel` and `remove` on any lane first boots out every `app.ccrc.auth.*` job whose attempt is past `expiresAt` + 60 s. `ExitTimeOut` 5 gives bootout the same SIGTERM → SIGKILL grace as §3.9 |
| Bounded in memory | `MemoryMax=512M` | **none enforceable**: launchd's resource limits do not cap resident memory on current macOS. Stated as a gap; the time bound is the only bound |
| No core dump | `LimitCORE=0` | `SoftResourceLimits` and `HardResourceLimits` `{Core: 0}` in the plist |
| Leaves nothing behind | `--collect` | `launchctl bootout gui/<uid>/<label>` on every terminal state, and the plist goes when `auth-scratch/<id>` is deleted (§3.9). The macOS test asserts that no `app.ccrc.auth.*` job and no plist remains (§16.1) |
| The tools it needs | the unit inherits the user manager's PATH, plus the absolute `ccrc` path (§13.2) | launchd gives a job a minimal PATH (`/usr/bin:/bin:/usr/sbin:/sbin`), which lacks Homebrew's `tmux` and `jq` and the user's `claude`, and whose `bash` is macOS's 3.2. `ccd-account-auth` and `ccrc` are `#!/usr/bin/env bash`, and `ccrc` needs bash 4.4 or newer. So the verb resolves **a bash of 4.4 or newer** first, then `tmux`, `jq` and `claude`, each with `command -v` in its own environment. It puts the bash's directory **first** in the plist's `EnvironmentVariables` PATH, followed by the other tools' directories, and names that bash by absolute path as `ProgramArguments[0]`, with the helper as its first argument. `HOME` in `EnvironmentVariables` is pinned to **the user's real home** (`dscl . -read /Users/<user> NFSHomeDirectory`), never a value inherited from the caller, because a sign-in under any other `HOME` loses the login keychain (next row). A missing tool, or no bash of 4.4 or newer, refuses `auth-unsupported-here` and names it |
| Where the sign-in credential lands | `~/<suffix>/.credentials.json` (§3.1) | **the login keychain**, not a file (§3.1; D-5442). Rev 2 assumed file custody here, and that was wrong. At plan time, layer 3 (§16.1) measures the keychain item's service and account naming for two scratch lanes with two config dirs. **If the item is not per config dir**, signing in lane-b would overwrite lane-a's credential, a silent cross-lane account swap. Then `login` on darwin refuses `auth-unsupported-here` with the measured reason `keychain-shared` ("On a Mac, Claude Code keeps one sign-in for every lane. Mint a long-lived token instead."), and Mint, the default, is offered. **If it is per config dir**, `remove`, Sign this lane out and the switch to a token each delete that lane's item (`security delete-generic-password` with the measured service and account) and then verify that it is gone; a lingering item refuses `keychain-item-left` and the ledger names it. Identity still comes from `claude auth status --json` |
| The pty | util-linux `script -qfc … /dev/null`, the FIFO redirected | BSD `script -q /dev/null <cmd> <args…>`, fed through the measured pipe and copier (§2; D-2614, D-2673, D-2735). In both arms the status comes from `verb.rc`, never from `script`'s exit code |
| The private socket | `tmux -L ccrc-auth-<id>` inside the unit | the same `tmux -L` inside the job. The socket lives in tmux's per-user temp directory, and the agent's tmux grant can't name `-L` on either platform. The tmux server daemonises out of the job's process group, so it is killed by name on every terminal state (§3.9) |
| One act per lane | `flock(1)` | stock macOS has no `flock(1)`, and ccd refuses by name where it needs one. The darwin arm of the platform layer takes the per-lane lock with an atomic `mkdir` of `~/.ccrc/locks/<id>.lock` inside a 0700 per-user directory (`~/.ccrc/locks`, never a shared `/tmp`). It records the owner's pid **and that pid's start time** (`ps -o lstart= -p <pid>`), and reclaims the lock only when the pid is dead or its start time no longer matches, so a reused pid cannot hold a stale lock. The Linux arm stays `flock`, verbatim, as the platform layer's contract demands. If neither arm can lock, the verb refuses `lock-unavailable`. It never runs unlocked |
| No secret on argv | `/proc/<pid>/cmdline` is readable by everyone | `ps -o args` shows every user's argv on macOS too, so the rule and its tests are the same |

**What still refuses on a Mac**, each with its reason in the method radio (§12.6), never a blanket refusal:
- `no-launchd-session`: `launchctl bootstrap gui/<uid>` fails when nobody is logged in to the Mac's GUI (for example, a Mac reached only over ssh). The exact behaviour under ssh-only access is measured in the macOS wave's first PR (§16.1) and the sentence follows the measurement. The verb does not fall back to the `user/<uid>` domain, because ccrc's own services live in `gui/<uid>` and a second domain would be a second thing to clean up. Paste, and all three OpenRouter methods, still work.
- A missing tool, or no bash of 4.4 or newer (above).
- `keychain-shared`, for `login` only, if the measurement says so (above).
- `codex-runtime-absent` (§7.2), when `ccrc install` has not built the Codex runtime on that Mac. Whether the runtime builds on darwin at all is measured at plan time. If it doesn't, the OpenAI provider row on a Mac node reads "ChatGPT lanes need a Linux fleet host" and Anthropic and OpenRouter are unaffected.

**Nothing else moves.** The status file, the FIFO, the code relay, the URL allowlist, the audit and the screen are byte-for-byte the same on both platforms. The step ledger names the host that ran each step, as it does on Linux (§13.2).

### 3.11 If the fleet host is compromised: every provider (new in rev 3)

Rev 2 wrote compromise steps for OpenRouter only. With Q1, a compromised box (or a leaked or restored snapshot of it, §3.3) also holds a year-valid Anthropic token for every token lane. So one disclosure, **"If this fleet host is ever compromised"**, covers every provider. It is shown in **Settings › Security** (where the Settings spec moves Security) and in the token, Codex and OpenRouter sheets' result frames as a disclosure. Every step is done **from another device**, because the box is what is no longer trusted:

1. **Anthropic:** at claude.ai/settings/claude-code, revoke every long-lived token this fleet minted or was given (each lane's stated identity and mint date help find them); at the claude.ai account settings, sign out other sessions for every sign-in lane's account.
2. **OpenAI:** at chatgpt.com, end the sessions of every account a Codex lane signed in with.
3. **OpenRouter:** delete the management key; then at openrouter.ai/keys disable every key named `ccrc …` and any key you don't recognise; check the balance and activity, and turn off auto top-up until you're done (§8.7).
4. **On the rebuilt box:** rotate the agent token and every Codex lane's gateway key, then add each lane's credential again (Mint a new token, Sign in again, Mint a replacement).

The disclosure names the providers present in the roster, so a fleet with no OpenRouter lane does not show step 3.

### 4.5 Moving sessions off

"Move N sessions off" on a trouble card, beside the kill switch, and in remove's pre-check all open one **Move sessions** sheet. It is a client composition over `POST /api/sessions/:id/swap`, but it obeys that route's real rules. The route needs an explicit target wrapper, refuses a move across pools unless `crossPool` is set, refuses hibernated sessions, and asks for busy or interrupt consent (`SWAP_BUSY_CAP`).

- **The target** uses SwapSheet's own target choice. Its default is the projected least-loaded lane **in the same pool**. Moving across pools is a separate, explicit choice that sets `crossPool`.
- **One at a time.** The server serialises nothing, and firing N swaps at once would restart N Claude processes together, each running its SessionStart hooks. So the sheet awaits each move before starting the next, shows "Moving 2 of 4", and gives each session its own outcome word: moved, skipped busy, refused hibernated, refused other pool.
- **Busy sessions are skipped by default.** An explicit "Also interrupt busy ones" choice includes them, with the existing consent.
- Each refusal is named in the sheet, with the reason taken from its code.

- **Cancelled**: "Sign-in cancelled. Nothing was stored. The lane is still there, off." **Cancel** is always present: `POST /api/accounts/:id/auth/cancel` → `ccrc account auth-cancel`, which stops the attempt's unit (E for the pane; N for the pipe arm).

So on **any route's** load, when `GET /api/accounts` shows a `LaneWire.authAttempt` in `waiting-code` started by **this session** (same session only, §3.7), the app shows a global banner: "A sign-in for lane-x is waiting for its code · 7 min left · **Continue**". - **Discard this lane.** In every terminal state of a lane that was **never enabled and has no sessions** (live or archived), a one-tap **Discard this lane** removes it. It calls the same remove verb in `discard` mode, whose checks run on the server and on the box. It skips the typed-id confirm and needs only a fresh step-up. Without it, every abandoned sign-in would leave an off lane holding its id, and the only way out would be the full remove.
- **The lane already existed** (re-login, §9): steps 1 and 3 are skipped, and step 10's Turn it on is skipped if the lane was already on.

### 6.3 Mint (the default) and paste: the token methods

- **Mint (default, Q1):** the same as 6.2, but step 4 runs `--method setup-token`, which takes the **private-socket pane** (§3.5). Steps 5–7 are identical from the operator's side; the token line is captured into `~/.cc-secrets/<id>-oauth.env` and blanked. Step 8 cannot read the identity, so the sheet asks "Which account did you just approve?" (a free-text field, 1–120 characters, optional, as Q5 ruled) → `POST /api/accounts/:id/set {stated}` → lane state. The mint time is recorded for **Expiring** (§4.1).
- **Paste: validate first.** The secret field (§3.3) is part of the add POST (`method:'paste', credential`). The verb checks the bytes, then runs the check probe **with the candidate in the probe's environment**, before the token is renamed into the lane's sourced env file. A 401 writes **nothing**: the field re-presents itself **empty**, with "That token was refused (HTTP 401). Nothing was saved." The same holds for a wrong-service secret pasted by mistake. An unreachable provider refuses `token-unverified` ("Anthropic didn't answer: nothing was saved. Try again."). Rev 0 kept a refused token in the file; that is withdrawn.
- **Remote Control note** on both: "Inference only: Remote Control won't work on this lane."
- **macOS fleet nodes:** Mint and paste work; sign-in works if §3.10's keychain measurement shows a per-config-dir item. Mint and sign-in run through the darwin arm (§3.10, D-5557). The method radio shows a reason in place only for that arm's measured refusals (`no-launchd-session`, a missing tool, `keychain-shared`).
- **One account at a time.** Which account a mint approves is decided by the browser's claude.ai session, and a token can't tell you afterwards (inventory gap 5). The URL card on a phone therefore says "Paste it into a private tab to choose the account", and the stated-identity field follows the result.

### 8.2 Connect with OpenRouter: PKCE, exchanged on the fleet box (D-5552, D-5553)

**What OpenRouter offers [OR].** The authorisation page is `https://openrouter.ai/auth`, with `code_challenge`, `code_challenge_method` (`S256` or `plain`), an optional `callback_url`, an optional `key_label` ("Prefills the label of the API key that will be created") and an optional `state` (returned unchanged on the callback). Localhost callbacks are allowed on any port. **Omitting `callback_url` is a supported headless mode**: the user copies the code from the screen, and a `code_challenge` is then required. The exchange is `POST https://openrouter.ai/api/v1/auth/keys` with `{code, code_verifier, code_challenge_method}`, answering `{key}`. "The code is single-use and expires after 10 minutes." The flow cannot set a key's credit limit.

**Why rev 1 deferred it, and what changes.** Rev 1 assumed a redirect. On iOS a redirect lands in Safari, which does not share the home-screen PWA's cookie jar, so the callback could not prove the session. OpenRouter's headless mode removes the redirect. The default arm is therefore a **code arm**, the same shape as the Anthropic sign-in that already works from an installed iPhone PWA: open a link, approve, copy a code, come back, paste it. Rev 2 also designed a callback arm as a desktop convenience; rev 3 moves it to **Later** (below).

**Where each piece lives.** This is what changes from the 09-05 spec's §10 (verifier in `sessionStorage`) and from rev 0 (verifier in server memory):
- **The verifier is made and kept on the fleet box.** `auth-start` draws 32 bytes from `/dev/urandom` and writes the base64url verifier to `~/.ccrc/auth-scratch/<id>/pkce`, 0600 in a 0700 directory, outside the agent's read roots. Only the S256 challenge leaves the verb, inside the URL.
- **The exchange runs on the fleet box**, in `auth-code`, so the key is born there and never travels (§3.3).
- **The code is relayed once**, under D-5514's rules unchanged: the same session that started the attempt, a byte check, shape-checked at the route, never stored, logged or audited as a value.

**Step by step (the code arm):**

| # | What the operator sees | What runs | E/N |
|---|---|---|---|
| 1 | Provider **OpenRouter** → name → method **Connect with OpenRouter** → placement (§8.4) → **Confirm it's you** | as 6.2 steps 1–2 | N |
| 2 | `✓ lane created · off` | `POST /api/accounts {provider:'openrouter', method:'pkce', id, label, hue, placement}` → `ccrc account add --provider openrouter --method pkce`: the off marker, the roster entry (`telemetry: "openrouter"`), the lane state; **no key file yet** | **N** |
| 3 | `… preparing the OpenRouter link` | `POST /api/accounts/:id/auth/start {method:'openrouter-pkce'}` → `ccrc account auth-start --method openrouter-pkce`. **No helper and no unit**: the verb writes the verifier, then the status file `{state:'waiting-code', attemptId, expiresAt}`, and **answers the URL** (`{ok, attemptId, expiresAt, url}`). The URL is exactly `https://openrouter.ai/auth?code_challenge=<S256>&code_challenge_method=S256&key_label=ccrc%20<id>%20<date>`, with no `callback_url`. The server checks that exact shape and keeps the URL in the attempt's in-memory record (§3.8). `expiresAt` is start + 600 s, the same single source as §3.7 | **N** |

**The limit line.** OpenRouter's PKCE flow cannot set a limit [OR], so step 6 reads "no limit" and the result frame says: "This key has no credit limit. Set one at openrouter.ai/keys, or mint keys instead, which always carry one (§8.8)."

**Terminal states** mirror 6.2: expired, cancelled, outcome unknown, resume (the app-level banner carries the attempt across an iOS relaunch, §6.2), and discard. A server restart loses the in-memory URL; the attempt then reads expired, and the sheet offers Start again. Two are particular to this flow:
- **Code refused** (`exchange-refused`: OpenRouter answered 4xx to the exchange): "openrouter.ai didn't accept that code. Codes work once and expire after 10 minutes. Start again for a fresh link." Nothing was made, so nothing is left at OpenRouter.
- **Made, not installed.** The exchange answered a key, and then validation or the write failed. The key exists at OpenRouter, and ccrc has no way to address it except through a management key. When one is installed, the verb pages through **the whole** `GET /api/v1/keys` list (it is paginated by `offset` [OR]) and deletes the key only on an **exact** name match whose creation time falls inside the attempt's window; the audit row then reads `pkce-minted-deleted`. The operator can edit the prefilled `key_label` on openrouter.ai, so a renamed key, two matches or a match outside the window all count as ambiguous. When none is installed, or the match is ambiguous, the answer says "A key named `ccrc lane-d 2026-10-18` was made at OpenRouter but not saved here. Delete it at openrouter.ai/keys ↗", and the audit row reads `pkce-minted-not-installed`. The key itself is never printed or kept.

**The callback arm (D-5553): moved to Later.** Rev 2 offered a callback arm at desktop in a browser tab, carrying `callback_url=<cfg.origin>/connect/openrouter/done` and a `state` nonce, with a static callback page and a secret-bearing `POST /api/providers/openrouter/pkce/callback`. It saved one copy-paste on desktop, while the code arm already works everywhere. It also carried `code` and `state` in a GET query string, which the reverse proxy in front of the server (the Caddy that `ccrc expose` writes, or `tailscale serve`) can write to its access log before the page's `history.replaceState` runs; that contradicts "never in logs", though the code is single-use and useless without the verifier on the box. So it is not built. Its bounds are recorded here for the day it is revived, and it is revived only if the operator asks after using the code arm: it is offered only at ≥900 outside standalone display mode with an https `cfg.origin`; it installs only for the session that started the attempt, and otherwise shows the code to copy; and `ccrc expose`'s Caddy config skips access logging for `/connect/*`. With it gone, the code arm's URL never carries a `callback_url`, and §3.8 refuses one.

**What this closes, and what it does not.**
- A network attacker sees nothing: every leg is https, and the verifier never crosses a network.
- A same-uid process that rewrites the status file cannot change the link, because the server serves the URL from the op's answer (§3.8).
- A copied link is worthless without the verifier on the box.
- **Not closed: a code from someone else's account.** Someone who sees the link could approve the public challenge with their own OpenRouter account and persuade the operator to paste the resulting code. The lane would then bill, and be visible to, that account. This is the device-code swap of §3.8 by social engineering. The result frame bounds it by showing the key's label and its credit, read back from OpenRouter, with "Not the key you meant? **Discard this lane**".

### 8.3 Validate before saving (G7)

The add verb, not the browser and not the server, validates the key **on the fleet box**, before it writes anything:
1. **Bytes first.** The route and the verb refuse NUL, CR, LF, other C0 bytes, DEL and anything over 8 KiB with `key-charset` (§3.3).
2. `GET https://openrouter.ai/api/v1/key` with `curl -H @- --max-time 10`. Stdin carries exactly one line, `Authorization: Bearer <key>`, and curl reads it as a header file, not a config. The key never reaches curl's argv, and no directive can be injected. OpenRouter documents this path as "Get current API key" [OR], and the plan re-measures it.
3. 200 → keep `label`, `limit`, `limit_remaining`, `limit_reset`, `usage` and `is_free_tier` for the lane state. **A 200 whose `is_management_key` or `is_provisioning_key` is true is refused `wrong-key-kind`**, and nothing is written: "That's a management key, which can't run models and must never sit in a session's environment. Add it as the management key instead (§8.7)." Without this refusal, a management key pasted into a lane's field would be sourced into every session on that lane. 401 → refuse `key-rejected`; **nothing is written**. Anything else → refuse `key-unverified` ("OpenRouter didn't answer: nothing was saved. Try again."). There is no "save anyway" in v1.
4. Then the secret file (0600), the off marker, the roster entry (with `telemetry: "openrouter"`, §8.6), convergence, and the suggested models (§8.5). Then `check`, which is one probe turn through the chosen `sonnet` model and the lane's first run, followed inside the same verb by the seed and its verify (§6.2). It costs a fraction of a cent, and the sheet says so.

A hostile-key test pins step 2. The value `"\noutput = <tmp>/pwned` must produce no file, and a `key-charset` refusal.

The sheet shows the validation as its own ledger line: `✓ Key accepted by OpenRouter · "ccrc lane-d" · $20 limit, $18.40 left · 0.4 s`.

### 8.7 The OpenRouter management key: custody and threat model (D-5554)

**What it is [OR].** OpenRouter's documentation now calls it a *management key*. It used to be a *provisioning key*, and `GET /api/v1/key` still reports both an `is_management_key` and an `is_provisioning_key` flag. It is exclusively for administrative operations: "Management keys cannot be used to make API calls to OpenRouter's completion endpoints." Its expiry is chosen when it is created, and "cannot be changed afterwards". Inside an organisation, only an Organization Admin can create one. OpenRouter's own warning: "A leaked management key could create, edit and delete the API keys in your account." Its endpoints are `GET|POST /api/v1/keys` and `GET|PATCH|DELETE /api/v1/keys/{hash}`.

**Why it is the strongest credential on the box.** A lane key's blast radius is its own credit limit. The management key's blast radius is the whole OpenRouter account's key plane. It can mint keys without limit, raise any key's limit, and disable or delete every key, including keys that ccrc never made. The operator ruled for minting knowing this (Q4). Everything below exists to keep it narrow.

**Where it lives, and who reads it.**
- **One file per box:** `~/.cc-secrets/openrouter-management.key`, 0600 in the 0700 `~/.cc-secrets`. It deliberately does **not** end in `.env` and holds the bare key, not an assignment. On main the existing writer emits `export VAR=%q`, so the writer gains a **bare-value arm** (umask 077, a temp file in the same directory, chmod 600, rename) that writes exactly the key's bytes and never an assignment; a test pins that the file has no `=` and no `export`. No wrapper, no `accounts.sh` and no settings env block names it, so nothing can source it into a session's environment by pattern or by accident. A test asserts that no generated wrapper, `accounts.sh` or settings file mentions it.
- **One reader.** A single function in `ccd/ccrc` streams `Authorization: Bearer <key>` into curl's `-H @-` (§3.3). Only these call it: `add --method mint`, `credential --method mint` (rotate), `set --limit`, `remove` of a minted lane, the PKCE made-not-installed cleanup (§8.2), and `ccrc account openrouter-management check`. A test greps the tree and finds the file name in exactly that function and its writer.
- **One destination.** It is only ever sent to `https://openrouter.ai/api/v1/keys…` and `…/api/v1/key`, with `--proto =https --max-redirs 0`, so a redirect cannot carry it elsewhere.
- **Never** in the roster, a lane-state file, an agent read root (`~/.cc-secrets` is not one), coord.db, a log, an answer, **the browser or the server, ever**, the offline snapshot or a mail. The browser sees only `{present, hint, expiresAt?, expirySource, ceiling, committed, mintedCount}` on `GET /api/accounts`, under `connect.openrouterManagement`, and only for the session verdict (§3.4).
- **Where those fields come from.** A non-secret **management state file**, `~/.cc-sessions/.accounts/_openrouter-management.json` (0600), on a read root, named so that no lane id can produce it (`ID_RE` cannot start with `_`). It holds the hint, the expiry and its source, the ceiling, `mintedCount`, the last `committed` figure with its read time, and the **pending-deletes ledger** (§8.8). It is written only by `openrouter-management install|remove|ceiling` and by mint, rotate, retire and remove. Like the rest of the lane state it is same-uid writable, so the ceiling in it guards the browser path only (§3.1).
- **N1 covers reads, not only writes.** The deny rules name `openrouter-management.key` and `~/.cc-secrets/*` for Read and Bash on every fleet session, and the ccrc-pwa `CLAUDE.md` SAFETY rules name the file. A session's accidental `cat` is then refused. A deliberate same-uid attacker is not stopped by this (§3.1).
- **Not on a Mac.** Install refuses `management-key-darwin` on a darwin node (§3.3's backups row).

**Installing it: CLI-only.** Rev 2 installed it through `POST /api/providers/openrouter/management {credential, ceiling}`: typed into the PWA, held in server memory, sent on the agent's stdin, and on a phone carried through the clipboard, which Universal Clipboard syncs to other devices. That was the very exception the operator's ruling excludes ("never in the browser"), for the strongest credential on the box. So install and replace run **only on the fleet host**: `ccrc account openrouter-management install --ceiling-usd <n>` reads the key on stdin, from a shell on the host or over ssh (`ssh <fleet-host> ccrc account openrouter-management install --ceiling-usd 100 < key.txt`, or typed at a prompt with echo off). There is no route that carries it and no agent sub that installs it. The PWA's **Provider keys** row, and Mint's narrowed state, show the exact command with Copy, and then reflect the result.
- The PWA's install sheet (§12.3) is instructions only: it links "Create a management key at openrouter.ai ↗" and says "Give it an expiry. 90 days is plenty: when it lapses, your lanes keep working, and only new mints and rotations wait for a new one." That last clause is what makes a short expiry cheap, and the plan measures it: minted keys belong to the account and survive their management key's expiry and deletion.
- The CLI verb validates before it writes, exactly as §8.3 does: the byte check, then `GET /api/v1/key`. The key must answer 200 with `is_management_key` or `is_provisioning_key` true, or it is refused `not-a-management-key`.
- **Expiry is required.** If the answer reports `expires_at` and it is null, the key is refused `management-key-no-expiry`: "ccrc won't keep a management key that never expires. Make one with an expiry at openrouter.ai." If OpenRouter doesn't report the field for the key itself (measured at plan time), the verb requires `--expires <yyyy-mm-dd>`, the date is recorded with `expirySource: 'stated'`, and the row says "stated by you".
- **The ceiling** is a **monthly** dollar figure, required at install (`--ceiling-usd`). It caps the **sum of the monthly commitments** of every key ccrc has minted on this box and that still exists at OpenRouter (§8.8 defines the commitment and how it is counted). The browser may only **lower** it (`POST /api/providers/openrouter/management/ceiling`). **Only the CLI can raise it** (`ccrc account openrouter-management ceiling --usd <n>`, run on the fleet host). A browser session, even one with a fresh step-up, can therefore never mint past what the operator set from a shell.

**On the screen.** Below the lanes, a **Provider keys** block holds one row: "OpenRouter management key · not installed · **How to add**", or "installed · `sk-or-v1-…9b1d` · expires 18 Jan · 3 keys minted · $60 of $100 a month". How to add opens the instructions sheet with the install command (§12.3). Inside 14 days of its expiry the row reads Expiring, with **How to replace**, which shows the replace command. After expiry it reads "Expired: lanes keep working; minting is off until you replace it", and Mint narrows in place (§8.1). **Replace** is the same CLI command run again (`install --replace`), which swaps the file atomically and **keeps the existing ceiling as an upper bound**: a replace may lower the ceiling but never raise it; raising stays the separate `ceiling` command. **Remove** is a browser act with step-up (`POST /api/providers/openrouter/management/remove`); it deletes the file, and keys already minted keep working. **Lower the ceiling** is a browser act too, on its own route (`POST /api/providers/openrouter/management/ceiling`), with no step-up because it only narrows. Both end with "Delete the old one at openrouter.ai ↗ too", unless the plan measures that a management key can delete itself, in which case ccrc does it and says so.

**The threat model, plainly:**

| Who | What they can do with this design | What bounds it |
|---|---|---|
| Anyone on the network | nothing | https only, a fixed host, no redirects; the key never crosses ccrc's own network legs at all (CLI install) |
| A stolen or left-open browser, step-up lapsed | read the hint, expiry and ceiling | every mint, rotate, commitment raise and remove needs step-up (§3.2); install and replace are not in the browser at all |
| A stolen browser with a fresh step-up | mint keys whose summed monthly commitment stays under the ceiling, raise a minted key's commitment under it, delete ccrc-minted keys by removing lanes | the monthly ceiling (raised only on the CLI), counted from OpenRouter's own list plus the pending-deletes ledger (§8.8); the per-key limits; the audit rows; it can't read the management key or any minted key. **PKCE keys are outside the ceiling**: they carry no limit at all (§8.2), and only the operator's own approval at openrouter.ai creates one |
| A session or coordinator, by accident or prompt injection | run a `ccrc account` verb, or read the file | N1's deny rules and hook refuse the plain forms (§3.1); evadable on purpose, which puts it in the next row |
| **A compromised box, or a deliberate same-uid attacker** | **read the management key**: mint unlimited keys, raise any limit, disable or delete every key in the account (an outage for every OpenRouter lane, ccrc's or not), spend up to the account's balance and any auto top-up, and read every minted key on the box | **nothing on the box.** Outside it: the key's immutable expiry, a modest account balance with auto top-up off (the install sheet recommends both), and revocation from another device |

**If the box is compromised**, or a snapshot of it leaks, §3.11's disclosure applies; it is shown in Settings › Security and in the install sheet. Its OpenRouter steps, all done **from another device**:
1. Delete the management key at openrouter.ai. This ends all key-plane access at once.
2. At openrouter.ai/keys, disable every key named `ccrc …`, because the box held them all, and any key you don't recognise.
3. Check the account's balance and activity, and turn off auto top-up until you're done.
4. Once the box is rebuilt: install a new management key from its shell, then **Mint a replacement** on each lane.

### 8.8 Minting sub-keys (D-5555)

**What OpenRouter offers [OR].** `POST /api/v1/keys`, authenticated with a management key, takes `name`, `limit`, `limit_reset` (`daily`, `weekly`, `monthly` or null; resets at midnight UTC, and weeks run Monday to Sunday), `include_byok_in_limit` and `expires_at` (ISO 8601 UTC, with seconds; OpenRouter's management-key page does not document it as a create field, so the box run measures it, and if it is unsupported the Expires field is hidden rather than faked). "The plaintext key is returned only in this response and cannot be retrieved later." Keys are addressed by `hash`. `PATCH /api/v1/keys/{hash}` changes `name`, `limit`, `limit_reset` and `disabled`.

**The sheet (method Mint):**

| Field | Default | Rule |
|---|---|---|
| **Credit limit** | $20 | required; $1 up to what fits the ceiling's remainder once normalised (below); the line under it reads "$20 a month · $40 of your $100 a month is left" |
| **Resets** | Monthly | Never · Daily · Weekly · Monthly, with "Resets at midnight UTC; weeks run Monday to Sunday". The line under the limit shows the normalised figure: a $20 daily key reads "$20 a day, up to $620 a month" |
| **Expires** | In a year | in 90 days · in a year · Never. **In a year** matches a long-lived token's lifetime. Rev 2 defaulted to Never, citing Q1, but Q1 was about Anthropic re-auth inside sessions; a minted key needs no sign-in and is replaced with one tap from the Expiring card (§4.2), so that reason does not carry over. Never stays available as an explicit choice |

The name is fixed by the verb: `ccrc <lane-id> <yyyy-mm-dd>`. It is what the operator sees at openrouter.ai/keys, and what §8.7's compromise steps search for. `include_byok_in_limit` is not offered, and OpenRouter's default stands.

**Step by step.** Provider → name → method **Mint** → limit, resets and expires → placement → **Confirm it's you**. Then `POST /api/accounts {provider:'openrouter', method:'mint', id, label, hue, placement, limit, limitReset, expiresIn}` → `ccrc account add --provider openrouter --method mint`, which runs these steps under the per-lane lock **and** a box-wide `openrouter-management` lock, so two mints can't both pass the ceiling check:
1. The catalogue and the suggested models (§8.5). Nothing exists at OpenRouter yet, so a failure here costs nothing.
2. **The ceiling.** Rev 2 summed `keyLimit` regardless of `limit_reset`, so a $100 ceiling admitted a $100 **daily** key (about $3,100 a month), and it read `committed` from same-uid-writable lane-state files that forget keys still live at OpenRouter. Rev 3 counts it this way:
   - **Each key's monthly commitment** is its limit normalised by its reset: never (no reset) = limit, monthly = limit, weekly = limit × 5, daily = limit × 31.
   - **`committed`** is the sum of those commitments over the keys **OpenRouter itself lists** (`GET /api/v1/keys`, paged to the end) whose hash ccrc recorded, in any lane state, retired slot or the **pending-deletes ledger**. The ledger, in the management state file (§8.7), holds the hash of every key ccrc made and could not delete: a failed delete on remove (where the lane state is gone with the lane), a minted-not-installed key and a PKCE made-not-installed key it found. Each entry is retried on every use of the management key, is counted until OpenRouter no longer lists it, and survives the lane's removal.
   - If `committed + this key's commitment > ceiling`, the verb refuses `ceiling-exceeded`: "That would commit $120 a month of your $100 ceiling. Lower the limit or lengthen the reset, or raise the ceiling with `ccrc account openrouter-management ceiling` on the fleet host."
   - PKCE keys carry no limit and are **outside** the ceiling, which §8.7's threat model states.
3. **Mint.** The JSON body is built by `jq` on argv; it carries only the name, limit, reset and expiry, none of which is secret. The header goes on stdin (§3.3). The answer is piped through `jq`: the key goes to the umask-077 temp file, and `hash`, `limit`, `limit_reset` and `expires_at` go to the lane state.
4. **Validate the new key** with §8.3 step 2, then rename it into `<id>-openrouter.env`. The ledger line reads `✓ Key minted · "ccrc lane-d 2026-10-18" · $20 a month · 0.5 s`.
5. Then the off marker, the roster entry, convergence, check (with its seed and verify) and the result frame, as §8.3 step 4.

**A mint that fails after step 3.** The verb holds the new key's `hash`, so it **deletes the key at OpenRouter** before it answers. The audit row reads `minted-deleted`. Only if that delete also fails does the hash go to the pending-deletes ledger and the answer name the key ("A key named `ccrc lane-d 2026-10-18` was made at OpenRouter but not saved here. Delete it at openrouter.ai/keys ↗"), with `minted-not-installed`. The key itself is never printed.

**Rotate: "Mint a replacement".** This is `POST /api/accounts/:id/credential {method:'mint'}`, which carries no secret, with step-up:
- The verb mints a new key with the lane's current limit, reset and expiry, validates it, and swaps the env file atomically. The old key's hash moves to `retiredKeyHash`.
- Running sessions keep the key they started with (09-05 decision 10), so the old key is **not** deleted at once. The sheet lists live sessions with one-tap Restart, and offers **Retire the old key**. Once no listed session predates the swap, that is a plain button. Before then it is a danger confirm: "2 sessions still use the old key and will fail their next request." Retiring disables the old key, then deletes it.
- Each lane has **one** retired slot. A second rotation first retires the key already in the slot, under the same confirm. So a lane never holds more than two live keys, and the ceiling's count (step 2) includes the retired one until it is gone.

**Change the limit** (`POST /api/accounts/:id/set {limit?, limitReset?}`): `PATCH /api/v1/keys/{hash}`. Any change that **raises the key's normalised monthly commitment** is a raise: a higher limit, and also a shorter reset (monthly → daily turns $20 into $620). A raise needs step-up and must stay under the ceiling. A change that lowers or keeps the commitment needs no step-up. The card's credit meter re-reads at once.

**Remove and discard** delete a minted key **at OpenRouter**, its retired key too, as part of the verb. §11's ledger then reads "Deleted at OpenRouter" for minted keys, instead of "still valid". If the delete fails (OpenRouter unreachable), the lane is still removed. The key's hash moves to the pending-deletes ledger (step 2), which keeps retrying and keeps counting it against the ceiling. The remove ledger names the key to delete by hand, and the audit row carries `remove ok` with the code `provider-delete-failed`.

**Off is not revoke.** Switching a minted lane off touches nothing at OpenRouter, because it is a reversible ccrc act (§10).

**Without a management key**, none of this is offered. A pasted or PKCE key's limit is managed at openrouter.ai (§8.2's limit line).

## 10. On and off (the kill switch)

It mostly stays as 09-05 §12.10 has it: it flips directly with no confirm sheet, the knob moves only when the server acks, and enabling does not probe. The row reads "On: new sessions can land here" or "Off: no new sessions; the 3 running here keep running." Switching off keeps today's behaviour: placement and swap rotation skip the lane, and running sessions continue. The row says so, and offers "Move 3 sessions off" beside it (§4.5).

**Enable has a readiness precondition (G19).** Rev 0 would have let the kill switch, or a stale sheet's Turn it on, enable a lane whose sign-in expired, whose mint failed or whose seed never ran. Its sessions would then strand on the first-run wizard or on a 401, which is exactly the runbook's outage. `ccrc account enable` therefore refuses `not-ready` unless the lane state records all three of these:
- a credential present;
- the onboarding and trust seed verified after the last run (`seedVerifiedAt > lastRunAt`). This is G1's interactive smoke assertion, the flag read back, moved into a precondition;
- a last check of `ok`.

**Lanes that exist before this ships (backfill).** They have no lane-state file, so without a migration an operator who switches a healthy legacy lane off and on would get `not-ready` on day one. `ccrc install` and `ccrc update` therefore write a lane-state file for every existing lane that lacks one, with `check` absent and the onboarding flag seeded (G1). The not-ready reason for such a lane reads "Check it once to turn it on", and the knob's row offers **Check** beside it.

`--force` exists on the CLI only; no route sends it. In the UI the knob is disabled while the lane is not ready, with the reason beneath it ("Not ready: the last check didn't pass. Check it first."). The lane-state file is same-uid writable (§3.4), so this precondition guards against accidents, not attacks.

`last-enabled-home` is refused with the sentence "lane-a is the only lane that can take new sessions. Turn another on first."

## 11. Remove, and what happens to sessions

The mechanism is unchanged (09-05 §9, §12.9). It is restated here for the new screen, with the gaps the reviews found filled in:

1. **Pre-check, measured on the box at open:** `0 live sessions · not the upstream lane · 2 other lanes can take new sessions · no sign-in in progress · read just now`.
2. **Live sessions block removal, with a way through.** `live-sessions` lists them, and the sheet offers per-session **Move** and **Move all** through §4.5's sequential mover. 3. **The ledger**, built from the verb's answer and never guessed. **Removed:** the roster entry, wrapper, markers, limits file, managed settings and hooks, timer, lane-state file, `auth-scratch/<id>`, any stray secret temp files, and the credential (point 4). **Kept on the box:** the config dir and transcripts, and model files until `ccrc models <id> rm`. **Still valid at the provider until you revoke it**, with the revoke link for each kind:

   | Kind | At the provider | Link |

   | Sign-in | depends on what `claude auth logout` revokes on the server side, which is measured at plan time (G23). 4. **The credential row, by kind.** A lane id can be re-added, and anything left behind would be inherited silently (G20), so the UI's defaults delete:

   - codex lane: **Delete this lane's ChatGPT sign-in folder** (its fresh `authDir`), default on.

5. **Typed-id confirm**, then a `danger` button (`QuickConfirm` tone), with step-up. **Discard** (§6.2) is the same verb in `discard` mode. It is offered only for a never-enabled lane with no live or archived sessions, and the server and the verb both check that before they skip the typed confirm.
6. The answer reloads the roster on the server (§13), after checking `fleetIdentity`. The supervisors drop the lane on their next re-read (G3).

### 12.4 Accessibility and input

- The secret field: `type="password"` with a show/hide toggle (default hidden), `autocomplete="off"`, `autocapitalize="off"`, `spellcheck=false`, `inputmode="text"`, and no `name` a password manager would key on. - **Wrong account.** Which account approves is decided by the browser's claude.ai session. The sheet does not tell the operator to sign out of their own browser. ## 13. Every route, op and verb each flow needs

**E** = exists on `537b6a41`. **N** = new. **X** = exists, extended. "Step-up" = §3.2. Every route below has these properties:
- it is session-only (D-5511): not in `EXEMPT`, and never accepts a box token. Rev 2's one exception, the static PKCE callback page, moved to Later with its arm (§8.2);
- it answers `auth-off` while the gate is dark, and `insecure-origin` on a plain-HTTP non-loopback `cfg.origin`;
- it sends `Cache-Control: no-store`;
- it is gated on `capSupported('account-v2')` with the refusing no-evidence polarity (09-05 §7), answering `501 unsupported`;
- after an error or timeout it reconciles (§3.9).

### 13.2 Agent

| Item | E/N | What |
|---|---|---|
| `{t:'req', op:'account', sub, id, fields, stdinB64?}` | N | A closed `sub` union: `add · auth-start · auth-code · auth-cancel · set · check · enable · disable · credential · remove · roster · or-management-remove · or-management-lower`. There is deliberately **no** sub that installs or replaces the management key, and none that raises the ceiling (§8.7). There is no `seed` sub: `check` runs the seed in-verb (§6.2). The agent builds argv from typed fields, with **no free argv** (bounds below). It spawns `$HOME/.local/bin/ccrc account <sub> …` (an absolute path; the unit's PATH lacks `~/.local/bin`) with stdin from `stdinB64`, an 8 MiB output cap, and a per-sub timeout (`check` 90 s, `add` 180 s, the rest 120 s) that ends SIGTERM → 5 s → SIGKILL (§3.9). It logs op, sub and id only. Every answer carries `fleetIdentity`. An older agent answers `bad-request`, which maps to `unsupported`. This is a typed op, separate from Plan 3a's `ccrc` exec seam, because it carries a secret on stdin |
| **Input bounds** (checked by the agent and again by the verb) | N | `id`: `ID_RE`. `label`: 1–64 characters, refused by `LABEL_UNSAFE_RE`, passed as `--label=<v>`. `stated`: 1–120 characters, no C0 bytes or DEL. Model ids: `MODEL_ID_RE`. `hue`, `provider`, `method`, `placement`, `mode`, `limitReset`, `expiresIn` (`90d`, `365d` the default, `never`): closed enums. `limit` and `ceiling`: whole dollars from 1 to 100000, as digits only. `attemptId`: 32 hex characters. Secrets and codes: ≤ 8 KiB, no NUL, C0 or DEL (`key-charset`). Base URL: the URL validator (CLI-only `compatible`) |
| `read` op on `~/.cc-sessions/.auth/<id>.json` and `~/.cc-sessions/.accounts/<id>.json` | E | already on the agent's read roots |
| tmux grant | E, unchanged | subcommand prefixes on the default socket only, which keeps the per-lane auth sockets unreachable (§3.5) |
| Units | X | `LimitCORE=0` on the server and agent units (G22) |

**Which box (G13).** The `AccountOps` arm is chosen **only** by `cfg.fleetMode`: local mode gets the local spawner, and remote mode gets the agent client. The local arm is **never constructed** in remote mode, where the controller keeps only its own `~/.ccrc/accounts.json` mirror, and where `index.ts` already runs a local spawner for updates (`localUpdateSpawnFor`). Wiring `AccountOps` that way would run `ccrc account add` on the controller. `reloadRoster` refuses a roster whose `fleetIdentity` differs from `fleet.identity`. An attempt's later calls are refused if the answer comes from a node other than the one the attempt started on. The step ledger names the host that ran each step. **v1 targets only the agent's node.** The server has exactly one agent connection (`index.ts:137`), and there is no path to a second node.

## 16. Verification

- **Canary secret** (extends the shipped setup-token canary). One test drives `POST /api/accounts` (paste), `/credential` and `/auth/code` with canary values, through a local `AccountOps` and the real agent. It includes a **stub child program that echoes the canary on stderr**. The test then greps every one of these: every answer body and refusal sentence; coord.db (every table); `feed_events`; the mail and push outboxes; the captured stdout and stderr of server and agent; the offline snapshot (jsdom localStorage); `sessionStorage`; the Zustand store dump; the tmux scrollback of every socket; the status file and the lane-state file. The canary must be found **only** in the 0600 secret file (or, for the code, nowhere). **Transcripts too (G31):** the test also plants the canary, and a real-shaped `sk-ant-oat…` and `sk-or-v1-…` value, in a session's JSONL transcript (as an `env` dump would), and asserts that every transcript, drawer and feed frame the browser receives carries only the mask.
- **The deny guard (N1, G21).** On a session spawned exactly as `ccd` spawns one (`--dangerously-skip-permissions`, the managed deny file), each listed command is refused without a prompt: `ccrc account remove --id lane-x`, `ccrc account openrouter-management ceiling --usd 100000`, `cat ~/.cc-secrets/x-oauth.env`, a read of `~/.ccrc/auth-scratch/x/pkce`, `printenv`, and the path-qualified `~/.local/bin/ccrc account add …` (the hook). Coordinators and operator-driven sessions are tested, not only children. A further test documents the evasion (`bash -c` with an assembled command runs) so nobody mistakes the guard for a boundary.
- **Gate tests.** Every new route is refused with a box token, refused while the gate is dark, and refused without a recent assertion where step-up applies. A named test covers the default deployment: dark gate, default host and origin, `POST /api/accounts` → `auth-off`. Another covers gate armed with an `http://` non-loopback `cfg.origin` → `insecure-origin`. `auth-gate.test.ts`'s sweep picks the routes up because they are registered in `server.ts`. `GET /api/accounts` carries no `lanes` without the session verdict.
- **Step-up binding.** `/finish` with a cookie stamps `assertedAt` on that session only, mints no session, sets no cookie, and keeps `generation`. A challenge started by session A is refused when session B finishes it. The passphrase arm keeps the session too, and is refused `passkey-enrolled` once any passkey exists. An exhausted step-up limiter locks that session's step-up and writes `step-up-locked`, while another session still steps up. Failed step-ups do not touch `LoginRateLimiter`.
- **Untrusted URL.** A test rewrites the status file mid-attempt to a foreign host, or to a different `attemptId`, and expects `auth-url-untrusted` with no URL in the answer.
- **Hostile key and code.** A key of `"\noutput = <tmp>/pwned` produces no file and `key-charset`, at the route and, with the route bypassed, at the verb. The same goes for a code with a newline.
- **Kill mid-write.** Killing `add` between the temp-file create and the rename leaves no secret temp file after the next verb. The server reconciles and shows the roster again. Two concurrent `add`s on one id: one gets `lane-busy`.
- **Detach.** `auth-start` returns in under 5 s while the helper keeps running in its unit, and it survives the agent sub's timeout.
- **Enable readiness.** `enable` refuses `not-ready` for a lane with no credential, an unverified seed, a seed older than the last run, or a failing last check. After `ccrc update`'s backfill, a legacy lane reads "Check it once to turn it on", and enables after one passing check.
- **Method switches.** Cancelling a token → sign-in switch mid-sign-in (and letting one expire, and feeding it a refused code) leaves the token file and the roster `method` byte-identical. A sign-in → token switch writes the token and the method under the lane lock only after the token's probe passes, and leaves `.credentials.json` in place until **Sign the old sign-in out**.
- **Re-add.** Removing a lane and re-adding the same id refuses `config-dir-exists`; a codex re-add gets a new `authDir`.
- **PKCE.** The verifier exists only in `auth-scratch/<id>/pkce` (0600, dir 0700) and is gone after the exchange, whatever its outcome. With a stub OpenRouter, the exchange's body arrives on curl's stdin, and neither the code nor the verifier appears in any process's argv during the run, sampled by `ps`. A status file rewritten mid-attempt to another URL changes nothing the browser sees: `GET …/auth` keeps serving the op's URL. An op answer whose URL adds `callback_url`, uses `plain`, carries an extra parameter or another host refuses `auth-url-untrusted`. A second code on a spent attempt refuses `code-already-sent`. The made-not-installed cleanup, against a stub whose key list spans three pages and holds a renamed key and a same-named key from before the attempt, deletes only the exact in-window match and otherwise reports ambiguous.
- **Management key.** Its file name, `openrouter-management.key`, appears in exactly one reader and its writer (a tree grep), and nowhere as `.env`. The file holds the bare key: no `=`, no `export`. No generated wrapper, `accounts.sh` or settings env block names it. No server route and no agent sub accepts it: the route table and the sub union are enumerated, and neither has an install member. Install refuses a lane key (`not-a-management-key`), a key with a null expiry, and any key on a darwin node (`management-key-darwin`). `--replace` with a higher `--ceiling-usd` keeps the old ceiling. A management key pasted into a lane's field refuses `wrong-key-kind` and writes nothing. A crafted `or-management-lower` with a higher figure is refused. The management state file's name can't be produced by `ID_RE`.
- **Mint.** With a stub OpenRouter: two concurrent mints that each fit the ceiling only alone get one `ceiling-exceeded`. A $100 daily key against a $100 ceiling is refused (it commits $3,100 a month). `set {limitReset:'daily'}` on a monthly key needs step-up and is refused over the ceiling. A key whose delete failed on remove is still counted, from the pending-deletes ledger, until the stub stops listing it, and is retried on the next use of the management key. A failure after the create deletes the key by hash (`minted-deleted`). Rotation leaves exactly one retired hash, and a second rotation retires the first. Remove deletes both at the stub. The plaintext key never reaches the verb's stdout. The Expires field defaults to a year.
- **Backups.** On a darwin sandbox (stubbed `tmutil` on PATH) the verbs that create `~/.cc-secrets` and `~/.ccrc/auth-scratch` call `tmutil addexclusion` on each.
- **Resume.** With an attempt in `waiting-code` for this session, loading `/` (not `/accounts`) shows the banner, and Continue opens the sheet at the code field. Another session's attempt shows no banner.
- **argv test:** the agent's argv builder is fed hostile fields (`--force`, `../`, a newline, a 65-character label, a 10 kB label, a bad model id) and must refuse each before spawning.
- **Visual matrix** (two-skins §9): the list (all seven states, Instrument's groups), the door's narrowed states, each provider's sheet at every frame (§12.3) with each of OpenRouter's three methods and Mint narrowed, the Provider keys block and the management-key instructions sheet, Move sessions, remove with live sessions, discard, outcome unknown, resume (including the app-level banner after a relaunch at `/`), the revoke checklist, and offline. Run at 360, 390, 1280 and 1920 × Refined/Instrument × Phosphor & Ink/Daylight, with fixture lanes `lane-a`…`lane-f` and the email `someone@example.invalid`. The matrix asserts **no overflow in the 340 px list column and the 360 px phone row**, no horizontal scroll, and the 44px floor on coarse pointers.
- **On a box, before W2b ships** (operator-run, never by a session; again before W3a–W3c for the OpenRouter measurements): one real Anthropic mint and one sign-in, one Codex sign-in, and OpenRouter by all three methods (with a scratch management key whose ceiling is $5 and which expires within a week) on scratch lanes, then remove them all and check at openrouter.ai/keys that every minted key is gone. This run also measures OpenRouter's headless code display, whether `POST /api/v1/keys` accepts `expires_at`, whether `GET /api/v1/key` reports a management key's `expires_at`, whether a management key can delete itself, and whether minted keys survive their management key's deletion. ### 16.1 macOS: how the darwin arm is tested, safely (D-5558)

A macOS fleet node does not exist today. The operator's Mac is where sessions run, but it has **no ccrc install** (no `~/.ccrc`, no `~/.local/bin/ccrc`, no `~/.cc-secrets`, no `app.ccrc.*` LaunchAgents), so "the operator's Mac as a fleet node" would mean a full install into the operator's real home: launchd services in its gui domain, wrappers in `~/.local/bin`, a roster and an armed gate.
