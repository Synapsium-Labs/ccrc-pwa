Box token lifecycle

How ccrc mints, hands out, rotates and checks its box token with no human after install, and how the first rotation retires the value that leaked into transcripts.

In short

  • The box token is hand-made, placed by deploy.sh over ssh, read once at server boot and accepted as exactly one value. Its live value sits in 35 transcript files and, through the server's public name, it admits every box-token lane from the internet. The operator ruled: build the automated feature instead of a hand rotation.
  • The server becomes the authority. It mints the token at boot when none exists, keeps the current value in ~/.ccrc/mail.token (still one value, so an older build still boots), and stages each new value in its own 0600 file.
  • One check accepts a small set. checkMailToken accepts the current value, a staged or handed-out next value, and for a few minutes the previous one, all compared in constant time. The 27 lanes change in one place and the verdict words stay.
  • The handout never uses the box token. The server sends a new agent op, token-sync, carrying only a one-time code. The fleet box runs ccrc token sync, trades the code for the value at a new door (POST /api/token/claim) over HTTPS, writes the file atomically, proves it with one call and reports back. A holder of the leaked value can neither mint a code nor reach the agent. The handout's trust root is the network position of the server-to-agent connection, which on plain ws:// is weaker than it sounds (§7).
  • The claim door cannot be jammed. It compares the code before it charges any budget, always serves a live code, and never burns a code on misses, so nobody on the internet can keep the leaked value current by flooding it.
  • A value becomes current only when the fleet box confirms it over the agent link, and a handed-out value is dropped only when a later value is confirmed or the fleet itself reports the code used. A fleet box that is behind gets a new generation, never the current value again. Retired values are remembered as digests, so an old deploy.sh cannot bring the leaked value back.
  • Wave 1 is the smallest change that retires the leak (two PRs). Wave 2 adds the schedule and rotates the agent link token; wave 3 gives each box its own token, stored as hashes.
  • The operator ruled on the open questions at 12:40. Automatic rotations hold only on an explicit window marker, $REG/token-rotation-held, a file with no writer in the tree (the mail-disabled precedent), and while an update is in flight. auto=off never holds a rotation, and "Rotate now" never holds on the marker or on auto. So the leaked value retires once wave 1 has landed and the gate (§9.2) opens. A plain-http install rotates and shows its transport. A server-written mail.token found unusable at boot is recovered from a sibling the server wrote (4.2.1); a hand-made one still refuses. Wave 2's schedule is weekly.
  • Check: the failure table (§6), the security analysis (§7), the first-rotation gate (§9) and the "Waiting on you" box, which now holds only wave 2's agent link token and two small operator acts.

4.2 The server is the authority, and its files

Boot handles the token in this order. The mint itself is agreed; the order, the recovery arms and the retired-value rule are judgement.

  1. Finish a recorded promotion. If box-token.json records a promotion in progress, it is completed from the files before anything below reads mail.token. §5 orders the steps so each one can safely run again.
  2. Read mail.token. A hand-made file that is present but unusable, or that holds the placeholder, still refuses boot exactly as today (server/src/coord/token.ts:109-157). If the file carries no usable value but box-token.json proves the server wrote it, and a sibling the server also wrote can be recovered, the server recovers from that sibling and warns (4.2.1). agreed (R3, 12:40)
  3. Refuse a retired value. If the value's sha256 matches a digest in box-token-retired.json, the server never adopts it. Something wrote it back: for example, a checkout from before this feature whose deploy.sh still runs ship_secret over both boxes and then restarts the server (deploy/deploy.sh:407-415, 619, 1226, 1264). The server mints a fresh current value, keeps the retired value refused, records that a rotation is owed, and warns; doctor FAILs once its FAIL arms are on. The fleet is resynced through the code path, which needs no box token.
  4. Mint if absent. If mail.token is absent and box-token.json records no history, the server mints 32 random bytes as 64 lowercase hex, one bare value line with no comment. It writes the file as below, records origin minted and warns once. If the state does record an earlier generation, the file was lost on a box that is not fresh. The server recovers it from the recorded pending file of the promoted generation, or else from mail-previous.token, with the same sibling proof and order as 4.2.1, and mints only when neither qualifies. It warns, and a forward rotation is owed.
  5. Mint failed (disk full, or ~/.ccrc not writable): the server boots with no current value, so every lane answers unconfigured (401). It warns, naming the path; doctor FAILs; the driver retries the mint on each tick. Refusing to boot would need a human to clear a full disk.
  6. Adopt, and record the origin. A present, usable value with no state file is the hand-made one. The server records origin adopted and rotationOwed: true before it does anything else. That flag is the first-rotation trigger. It survives restarts, and only a confirmed promotion clears it.
  7. Auxiliary files. Pending and previous files go through the same measured reads. If value files are found with no state file (a plain uninstall of an earlier build, or lost state), they stay accepted as unverifiable, the server warns, and a forward rotation is owed; its confirmation discards them. A present but unusable auxiliary file cannot be compared with anything, so its slot is empty. The server warns and owes a forward rotation at once; §6 states the 401s this can cost.

Every write, on this adapter and the both-box writer alike: create a temp file in the same directory with O_EXCL at mode 0600, write it, fsync it, rename it over the target, then fsync the directory. Without the two fsyncs, a power loss after the rename can leave a zero-length mail.token, which is a MailTokenFileUnusable (server/src/coord/token.ts:139-143). 4.2.1 recovers it when a qualifying sibling exists; the two fsyncs keep it from happening at all, and a first-ever write has no sibling and would still refuse. judgement Generation ids are 64 random bits written as 16 lowercase hex, never a counter. A fleet file left over from lost server state therefore cannot falsely confirm a new generation that happens to reuse its number. Every value file ends in .token, so the ccrc-history value layer, which loads ~/.ccrc/*.token (docs/superpowers/specs/2026-10-05-ccrc-history-lossless-dag-design.md:1483-1486), sees pending and previous values without a change. The server's value files hold one bare line each, which matters because that layer reads a *.token file as its whole trimmed content (:1496); for the fleet file, see §9.3. State lives in files rather than a coord.db table, so no schema migration is needed and a rollback reads nothing new.

The holder replaces the string in deps.mailToken with an object that the driver mutates in place. Every call site keeps reading deps.mailToken ?? null at request time, so no route changes (server/src/index.ts:130, 186). The field's type widens to string | BoxTokenHolder | null, so the many tests that inject a literal string keep working (server/test/auth-gate.test.ts:164-167).

The hold rule (R1, 12:40, "Explicit window marker"): the automatic triggers, the first and the third, hold only while (a) the window marker $REG/token-rotation-held stands, or (b) an update is in flight on either box. $REG is the fleet registry, ~/.cc-sessions (cfg.registryDir, server/src/config.ts:474). Agreed

  • No hand rotation; build the feature (10:44, 11:06).
  • No human after install; the server is the authority and mints at boot.
  • Retire the leak first: wave 1 is the smallest safe change, likely two PRs.
  • One-time code over the agent link, then a fetch over HTTPS.
  • mail.token stays one value holding the current one.
  • One check accepts current, next and, for a few minutes, previous; the verdict words stay.
  • One new op, token-sync, by the update op's recipe; the agent touches no secret.
  • One new door with its own census set; "Rotate now" session-only.
  • Doctor check on each box, never the value or its hash.
  • deploy.sh stops shipping the token; a both box writes both files.
  • New doctor checks PASS/SKIP only while lane gates are open.
  • Own programme, coordinated by the centralised-update coordinator.
  • Hold rule, "Explicit window marker" (about 12:40, R1). Automatic rotations (first rotation, schedule) hold only on $REG/token-rotation-held, a marker with no writer in the tree, read the way mail-disabled is read (listed, fail-shut), plus the update-in-flight check. auto=off never holds a rotation; "Rotate now" never holds on the marker or on auto (§5 step 1, 9.2).
  • Plain HTTP, "Rotate, show the transport" (about 12:40, R2). Never refuse; doctor and the console show transport http (4.5, 4.7, 4.8).
  • Boot recovery, "Recover, for server files" (about 12:40, R3). A server-written mail.token with no usable value is recovered from a sibling the server wrote, with a warning; a hand-made one still refuses boot (4.2.1).
  • Interval (about 12:40, R4). Wave 2's automatic schedule is weekly, 7 days.
  • Update setting (recorded fact). Auto-install was restored to "Every release on my channel" (dev) at about 11:21 UTC, after the GPT-lane window's Step 20; the fleet box is on v0.0.118 (9.2).
