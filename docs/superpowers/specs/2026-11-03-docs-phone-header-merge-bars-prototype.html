The reader shows a document at one ref. Today a phone spends a third of its height saying where the document came from before it shows the document.

This spec separates the document's identity from the checkout that serves it, so a link means the same thing on every box and every branch.

Section 1 sets the vocabulary. Section 2 lists the three resolutions a host may offer, and section 3 records which one this host chose and why.

Each resolution is drawn as a figure and followed by a table of the decisions it implies.

What moves where

  • Crumbs (≈70 px) → the one bar: ‹ keeps "up one level"; the file-name crumb is replaced by the document's title on one line with an ellipsis; the full path goes to the details sheet.
  • Truth line (≈106 px) → a green, amber or red freshness dot beside the title, plus the details sheet opened by tapping the title (ref, how it was chosen, commit with Copy, source, size, freshness with Re-list). A draft or branch view adds an amber dot and a one-word chip ("draft", "branch") to the title, not a line.
  • Actions row (44 to 92 px) → the ⋯ menu: View on GitHub (with "may differ" as its second line), Share, Export (with its state words), Document details. "Updating to <short>…" shows as a spinner on ⋯ and as the menu items' second line, so it never wraps a row.
  • The reader's own bar (48 + 29 px) → off, through the library's existing host option features.chrome.bar = false. Its quick jump, Aa and Contents buttons move into the console bar; its running head is unneeded, because the console bar always shows the title; its 2 px progress line is drawn by the console under the bar.
  • Banners stay under the bar, unchanged; they are rare and they matter.
  • "Formatting…" becomes a thin indeterminate line in the progress line's place, so the frame no longer jumps 28 px when it is ready.

What the library needs, and whether its host adapters allow it today

NeedAllowed today (library 1.0.0)?Cost
Hide the reader's barYes. The host mount accepts features with chrome: {bar, rail, settings}, each defaulting to true; the library's own comment says "a host may build its own bar".ccrc's bridge passes features for the first time: its adapter set is pinned at fourteen keys by a test, so it becomes fifteen, and its header comment changes.
Open quick jump, Aa and Contents from the host's buttonsNo. Those tools live in the bar's tray, and no host-to-frame command opens them. With chrome.bar = false, quick jump is reachable only by keyboard, which a phone lacks.A library change: host commands such as open('jump' | 'settings' | 'contents') over the frame protocol, plus a "tools available" report so the host shows only the buttons that exist (Outline on plans, the changes stepper). The library's release is held, so this waits for the next batched release.
Progress for the console's lineNo. No scroll or progress signal crosses the bridge.The same library change: a throttled progress report. Without it, the console drops the progress line.
Facts inside the reader (alternative to the sheet)No. The reader has a facts panel built from the document's byline, but its seam (facts.take/summary/block) is for in-frame plugins, and the frame runs only library code.Not proposed. The console sheet is cheaper and keeps the facts that ccrc measures in ccrc.
Trim the top inset (8 px body margin, 28 px phone padding)No. No host option controls it.A small library CSS change: about 81 → 61 px.

Shipping in two steps

  • Step 1, ccrc only (no library change). One 44 px console bar with ‹, title, dot and ⋯, plus the details sheet. The reader's bar stays on, because hiding it now would strand quick jump. Above the title: 44 + 1 + 8 + 48 + 29 ≈ 130 px (from 341), and the reader's 48 px still slides away on scroll down. That makes two bars, but the console bar is thin.
  • Step 2, after the library's host commands land. Pass chrome.bar = false, move ⌕, Aa and ☰ into the console bar, and draw progress: 81 px (61 with the inset trim). One bar.

What it costs, and what the user loses

  • Loses: the bar hiding on scroll. Today the reader's 48 px bar slides away while you read. The console bar stays at 44 px, because ccrc gets no scroll signal. While reading, the net is still about 44 px against today's 256 + 0, a large gain, but it is not zero.
  • Loses: provenance at a glance. Ref, commit and size are one tap away instead of always visible. The dot and the draft or branch chip keep the "is this current, is this a draft" signal on screen.
  • Loses: one-tap GitHub, Share and Export. Each is now two taps (⋯, then the item).
  • Loses: the crumb trail. "specs" as a tappable crumb is gone; ‹ goes up one level, and the full path is in the sheet. Jumping two levels up is now ‹ twice.
  • Width: ‹ (44) + ⌕ Aa ☰ ⋯ (4 × 40) leave about 200 px for the title, about 22 characters at 15 px. A long title ends in an ellipsis. The full title is the h1 directly below, and the sheet repeats it.
  • Cost: step 1 is a ccrc-only change (head, menu, sheet, CSS) with tests for the moved controls' accessible names. Step 2 needs a library change and a new release, which the operator is holding for a batch, plus the bridge's pinned adapter count going from fourteen to fifteen.
  • Desktop is unchanged: at 900 px and wider, the full truth line and the actions row stay as they are.
