# ccrc: rollout readiness

## 1. The honest verdict

The distance is not "a few hardcoded IPs away." It is also not "a rewrite." The single structural obstacle is this: **ccrc is not a program that gets installed — it is a running machine that was grown in place, and the repo is a partial description of it.** The repo cannot rebuild the author's own box, let alone anyone else's.

That is provable, not rhetorical. `deploy/ccrc.service` (verified) carries `Environment=CCRC_HOST=203.0.113.7` and **no `EnvironmentFile=` at all**, so the `~/.ccrc/ccrc.env` that `deploy.sh:144` faithfully ships is read by nothing. Yet the README says remote mode is what is deployed and `/api/fleet/health` answers `{"mode":"remote"}`. The live configuration therefore exists only as an unversioned hand-edit on server-box. The same pattern repeats down the stack: the wrapper binaries `ccd` hard-requires are all five present in `~/.local/bin` on this box (confirmed: `claude`, `claude2`, `claude-corp`, `claude-dev0`, `gpt`) and zero of them are in git; `claude-session@.service` and `statusline-command.sh` and `tmux.conf` are in the repo and installed by nothing; the systemd drop-ins whose own comments call them "the guardrail that actually contains a runaway" (`protect.conf`, `limits.conf`, `ccd-cap-scopes.service/.timer`) exist only on the running host; `tailscale serve` — without which the PWA is not installable at all — appears exactly once, as prose.

Everything else follows from that. There is no version anywhere (verified: zero git tags, no `version` key in server/agent/shared, `/health` returns a bare `{ok:true}`), so "update" is not a distinct operation from "install" — both are `rsync` of whatever is on someone's disk. There is no `LICENSE` (verified absent) and the repo is private. There is no installer, no prerequisites section, no bootstrap, and no local-install path: every line of `deploy.sh` goes through `"${SSH[@]}" "$BOX"`, so a developer sitting at the machine they want ccrc on has no supported command.

Given that framing, the work is smaller than it looks *if* the answer to Fork A below is "each person gets their own fleet." Most of the blockers are one-line seams that were never cut because one operator never needed them. The honest estimate: a focused week or two to get one teammate genuinely running on their own box, plus a hardening pass. If the answer is "shared fleet," add a quarter, because that is a re-spec.

## 2. The forks

**Fork A — one fleet per person, or one shared fleet?** This is the decision that determines everything else, and it is not primarily a security question. The account layer is where it bites. `ACCOUNTS` is not a roster of people; it is a roster of Claude *subscriptions living under one `$HOME`* — `configDirFor` joins a suffix to one home, `~/.cc-limits/*.json` is one pool of rate-limit telemetry, `_ws_least_loaded` places sessions by scoring lanes in that one pool, and session ids are `<wrapper>-<project>`, exactly one per pair for the whole box. A second human does not get a second lane; they get *the same lanes*, consuming the same 5h/7d headroom and triggering auto-swaps on the other person's live sessions. Per-person fleets make that a non-problem by construction and give quota isolation for free — the account model is already honest about being per-`$HOME`. The cost is N boxes, N tailnet nodes, and N sets of Claude subscriptions per teammate (note: the whole telemetry layer requires a claude.ai subscription — an API-key or Bedrock user gets no `.cc-limits` file, which downstream reads as "assume free" rather than "no data"). Shared fleet costs you `SessionRecord` (17 fields, none a person), `run_events.causedBy` (where `'operator'` is one undifferentiated role), the id scheme, the 144-name slug namespace, global presence suppression, broadcast push, and the box-wide kill switches — all at once. The v1 spec put multi-user out of scope and everything downstream honoured that. There is a tempting middle — shared box, separate unix users — which buys `$HOME` and quota isolation cheaply but requires N servers, N agents, N ports and N serve paths, against fixed 7788/7789/8443 baked into the committed unit. Name it, but know it is "N of everything on one box" rather than sharing.

**Fork B — is the tailnet ACL the security boundary you are willing to bet on?** Today, adding a teammate to the tailnet *is* granting them root-equivalent control of your fleet: `buildServer` registers ~40 routes with zero auth hooks (the only `addHook` is `onClose`), `/ws/pty/:id` is a raw shell as the box's unix user, and `POST /api/sessions` will spawn a session in any directory that exists. The box token authenticates a machine, not a human, and its own comment says so. If you accept the ACL as the boundary, the work is to *document the ACL as a deploy artifact* and keep the bind narrow — zero code. If you don't, one Fastify `onRequest` hook plus `tailscale serve`'s identity headers is roughly a day and is worth it even under per-person fleets, because it converts "a teammate joined the tailnet" from a security event into a non-event. Note these are separable: auth (can you call this API) is a day; *ownership* (whose session is this) is Fork A's re-spec.

**Fork C — internal-only or open source?** Internal-only means `gh release download` against a private repo works fine, you never need a public URL, and the operator's defaults can live in a gitignored `deploy/target.env`. Open source means a LICENSE, and it means the shipped bundle stops containing one person's account labels (`team·max`, `alt·max` are literals in `shared/api.ts`), and it means `--dangerously-skip-permissions` — which every session launches with, and whose safety dialog `ccd` actively clicks through — becomes a documented, overridable posture rather than a silent default. It also buys you a support surface for Claude Code version skew you do not currently have the version identity to reason about. There is a narrow version of this fork worth separating: `ccd` alone is a single self-contained 442 KB bash file with no build step and the only piece with an audience beyond this fleet. Releasing *it* is nearly free once it has a `--version` and a doctor. That is a product decision, not a rollout decision.

## 3. What is needed regardless of the forks

Ranked by whether it is broken *today* and by what everything else depends on.

**1. Atomic `ccd` install, plus a supervisor restart sweep.** This is not a rollout issue; it is a live correctness bug on the current box. `deploy.sh:91` does a plain in-place `scp` over a script bash is actively executing, and bash resumes at a saved byte offset — reproduced by the critic as a verb printing its correct result and then exiting 2 on a syntax error, which `lifecycle.ts:15` maps to `ok: false` and the routes turn into a 409 for a destructive verb that already completed. Fix is `scp` to a temp name then `mv -f` (same for `notify.sh`, `session-hook.sh`, `install-session-hooks.sh`). Separately, no deploy ever restarts `claude-session@*`, so every live session keeps executing the pre-deploy ccd for days, and the agent's `ccd caps` cache — the one surface claiming to say what ccd is deployed — stats the file on disk and is structurally blind to it.

**2. Build identity.** A git sha plus run timestamp, stamped at deploy, returned by `/health`, carried on the agent ready frame, printed by `ccd version`, rendered in the PWA. Without it, "easy to update" has no *from* and no *to*: a teammate cannot say what they are running, you cannot ask, and the deploy's final `curl` proves only that something answers on a URL that by default is your box, not theirs. Note the temperament collision — the deploy goes to real trouble to prove the PWA bundle is fresh locally (`stat` against `RUN_START`, refuses a stale one) and then proves nothing whatsoever about the far side.

**3. Make the repo able to reproduce one box.** `EnvironmentFile=-%h/.ccrc/ccrc.env` on `ccrc.service` and delete the baked `CCRC_HOST`; ship the artifacts already in the repo that nothing installs (`claude-session@.service`, `statusline-command.sh`, `tmux.conf`); commit the live drop-ins and the `ccd-cap-scopes` unit/timer; commit the `tailscale serve` invocation; cut the agent's projects-root env seam (`agent/src/server.ts:59` is a literal Hetzner volume id with no override, verified) and reconcile the three disagreeing roots — `$HOME/projects`, `/data/projects`, `/srv/projects` — onto `$HOME/projects` by construction.

**4. A preflight that fails loudly — `ccd doctor`.** Node ≥22.13.0, tmux/git/gh/jq/python3/flock, `gh auth status` with repo scope, `git ls-remote` against one project's origin, `git config user.email`, linger, wrapper presence, `origin/HEAD`, tailnet HTTPS. This is the temperament argument in its purest form: the project treats "an instruction standing in for a mechanism" as an anti-pattern, and the entire prerequisite set today is instructions that were never even written.

**5. The wrapper and roster seam.** `ccd start` cannot launch anything on a fresh machine — it dies `wrapper missing`. Generate the wrappers from a declared list; move `ACCOUNTS` to `~/.ccrc/accounts.json` with today's five as the shipped default, and let the cross-language fixture test guard the loader rather than five literals in two languages. Make "no telemetry on this account type" visible instead of scoring as 0% used.

**6. The three failures that point *outward*.** An unmodified `notify.sh` POSTs a teammate's swap notices — with their box token — to your box, and swallows the error. `ccclip` scps their clipboard to your box. `HEALTH_URL` defaults independently of `CCRC_BOX`, so on a shared tailnet a teammate's deploy is greenlit by *your* server answering `{"ok":true}`. These are cheap to fix and they are what makes a teammate's first week actively harmful rather than merely frustrating.

**7. First-run spawn correctness.** `_accept_first_run_prompts` has no terminal return, so on exhaustion it exits with `sleep`'s status 0; `_spawn` then injects `/effort ultracode` into whatever dialog is on screen and `cmd_start` prints `started <id>`. In remote mode the 90s exec budget kills ccd mid-spawn first, and because `started 1` is written *after* `_spawn` returns, the uuid is consumed while the registry says the session never started — so the next `ensure` re-spawns `new` against a uuid Claude Code already owns. This is the teammate's literal first command.

**8. A local-install path and a documented permissions posture.** `deploy.sh` has no local branch, and the units require the tree at exactly `%h/ccrc/`. Separately: every session runs with permissions bypassed and ccd answers the dialog for you. Whatever you decide, that must be stated before another human onboards a repo — a system that gates its own destructive verbs on human confirmation should not silently click through Claude Code's.

**9. Reversibility.** `coord.db` is the one artifact whose loss is not free and the one file `deploy.sh` never backs up (the code says so twice, in its own error text) — one `.backup` line fixes it. `~/ccrc-backups/` grows unbounded and sits outside the only disk guard, which measures `WORKTREES_ROOT` alone. And `install-session-hooks.sh` rewrites `settings.json` in four Claude config homes on every deploy with no inverse, so a teammate who trials ccrc and declines is left with every Claude Code session shelling out to a script that no longer exists. An uninstall is what makes a *second* install safe to attempt.

## 4. Re-architect vs merely package

Almost everything above is packaging: a seam that was never cut, a file that was never shipped, a default that was never parameterised. Three things are not.

**The account model** is the deepest. Making the roster a JSON file is packaging; making it multi-human is a redesign that moves session ids, registry shape, swap placement and the limits reader simultaneously. Per-person fleets sidestep it entirely, and that is the strongest single argument for that branch of Fork A.

**Ownership** — as distinct from authentication — is a re-spec, not a hook. Nothing in the system has a person: not `SessionRecord`, not the coord DB, not presence (any viewer suppresses everyone's push), not the push store (one flat list, broadcast to all), not the seen-marks (per-device localStorage, with a comment saying "ccrc has no user accounts"). Every store keyed "per box" or "per device" would need re-keying.

**ccrc assumes it owns the box and owns `/`.** The service worker's navigation denylist has this box's co-tenants compiled into the shipped bundle (`/docs` for the docserver, `/fleet` for rp-llm); the manifest is scope `/`, and fastify-static sits at the bare root with a catch-all. Ports are fixed and baked into the unit. Two instances cannot coexist on one host without editing committed files. This is also why Docker is not a plausible shape: the server's entire job is reading `$HOME/.cc-sessions`, shelling to `ccd`/`tmux` on the host, and driving `systemctl --user`.

One thing per-person fleets do **not** sidestep, and it deserves a decision: the branch namespace. The slug pool is 12×12, `_ws_slug_free` consults only the local registry, `ccd` never deletes a remote branch (zero `push --delete`), and the only acknowledgement that remote branches vanish is a comment assuming GitHub's auto-delete-on-merge — an unchecked per-repo setting. Two teammates on the same repo draw from independent registries into one shared `origin/ws/*` namespace, and the collision surfaces at `pr-open`'s non-fast-forward push, after all the work is done. The fix is small (have `_ws_slug_free` consult git refs after the fetch it already does; widen the pool), but it is a genuine design question, not a config gap.

## 5. Staged sequence

**Stage 0 — stop the bleeding on the box you have.** Atomic install for all four shipped scripts; the `claude-session@*` restart sweep; `coord.db` into the backup set; a retention sweep on `~/ccrc-backups`. *Proof:* deploy twice in a row while a session is live and a ccd verb is mid-flight; no non-zero exit, and every `claude-session@` unit active afterwards. This has nothing to do with teammates — it is a live bug you are currently carrying.

**Stage 1 — the repo can rebuild *this* box.** The `EnvironmentFile` cutover, the unshipped artifacts, the committed drop-ins, the agent projects-root seam, the three roots reconciled, VAPID and `CCRC_PROJECTS_ROOT` into `ccrc.env.example` — and the build stamp, because Stage 1's proof needs it. *Proof:* provision a scratch VM, run the deploy, and get a green `/health` **whose build id equals what you just shipped**. Today that assertion cannot even be phrased.

**Stage 2 — one teammate, their own fleet.** `bootstrap.sh` and `ccd doctor`; the wrapper generator; the roster file; `CCRC_BOX` required rather than defaulted; `HEALTH_URL` derived from the target; `notify.sh` and `ccclip` de-hardcoded; the two first-run spawn fixes; the PWA empty state rendering the `roots` the API already returns and discards; a local-install target. *Proof:* on a box you never touch, the teammate runs bootstrap, gets a green doctor, deploys, installs the PWA to their phone, runs `ccd start` on a real repo, watches the first spawn complete without hanging, and receives a push notification. Every single one of those steps is broken today.

**Stage 3 — generalise.** Auth if Fork B says yes; the uninstall path; tags, a CHANGELOG and CI-built artifacts so an update ships a *ref* rather than someone's disk (plus a dirty-tree refusal); the slug-namespace fix; the VAPID key-rotation fix, where a stale subscription is reused without comparing keys and the resulting 403 is silently swallowed so the toggle reads ON forever. *Proof:* a teammate updates from tag N to N+1 with one command and `/health` reports N+1; a second teammate joins without either being able to drive the other's sessions.

**Stage 4 — only if Fork A goes shared.** The ownership re-spec. Do not begin it before Stage 3 proves the per-person shape holds.

## 6. What to explicitly not build

No Docker or OCI image — the server's job is host manipulation, so a container needs host PID/IPC plus `$HOME` bind-mounted and buys nothing. No npm publishing — `file:../agent`, three lockfiles, no workspace root, and node-pty ships no Linux prebuilds so every install compiles anyway; a GitHub release tarball plus the already-prebuilt 1.4 MB `dist-pwa` does everything npm would. No real multi-tenant auth (SSO, roles, per-route grants) — one bearer token per person behind `tailscale serve` identity headers covers a team under ten. No build-out of the PWA↔server protocol kill-switch: `FLEET_PROTO`/`MIN` are both pinned at 1 and `BlockScreen` is untested, and adding version *negotiation* before you have version *identity* is backwards — exercise it once in staging the first time you raise MIN, as a checklist item, not a project. No subpath hosting or base-path config; name it a known limitation. No config UI, no account-management UI, no ccd self-update — a release asset plus `ccd version` is the whole story for a bash script. No provider abstraction over the Hetzner reboot route; it already fails closed with 501. No migration framework for `~/.cc-sessions`; additive-only works — document the contract next to `_reg_set`. And no `coord.db` retention tuning yet: back it up now (one line), and only add retention when a real box shows growth, rather than tuning against an imagined curve.

## Where the findings are thin or wrong

I checked the load-bearing disagreements. **Two surveys claimed `ccrc-agent.service` already uses the optional `EnvironmentFile=-` pattern and recommended copying it into `ccrc.service`. It does not** — line 6 is `EnvironmentFile=%h/.ccrc/agent.env` with no dash, verified. The critic is right: the first agent deploy from a clean clone hard-fails at `systemctl --user enable --now` with a message about environment files rather than about the token nobody told you to mint. So `ccrc.service` should get the dash *and* `deploy.sh` should preflight the agent env file — copying the agent's current pattern would propagate the bug.

One survey listed `~/.local/bin` as holding `claude, claude2, claude-corp, ccgpt`, implying the `gpt` wrapper is absent even here; all five (`claude`, `claude2`, `claude-corp`, `claude-dev0`, `gpt`) are present, and none is in git. Line numbers drift by one or two across surveys for the same symbols (`WRAPPER_DIR`, `VALID_WRAPPERS` — actually line 14, `PROJECTS_ROOT`); do not take any single citation as gospel when writing the patch.

Two claims are reasoned rather than measured and should not be quoted as observations. The "15-minute first-run hang" is derived from the loop's 450×2s bounds — a worst case, not a timing anyone took; the structural conflict with the 90s remote budget stands on its own and does not depend on the number. And the coord.db migration framework's higher-`user_version` read path and its 0→N chain have never been exercised — the surveys say so honestly, and that gap is a reason to back the file up before Stage 1, not a reason to distrust the framework.
